## Background

PyTorch's [deterministic cumulative sum](https://github.com/pytorch/pytorch/blob/main/aten/src/ATen/cuda/cub.cuh#L457) (used when `torch.use_deterministic_algorithms(True)` is set) runs a custom CUDA kernel in two passes: the first pass adds up each block, the second pass reads the input again and scans each block starting from the sum of the blocks before it. Doing it this way keeps the add order fixed, so the result is the same every run, but it reads the input twice. Scan speed is limited by memory, so that extra read means this approach can only reach about 66% (2 of 3 memory passes) of the speed a single-pass scan can hit.

CCCL now makes `cub::DeviceScan` reproducible on its own through a `run_to_run` env knob ([CCCL PR #9098](https://github.com/NVIDIA/cccl/pull/9098)), will be available in the upcoming CCCL 3.5 release. (Check here for the related blogpost  [Controlling Floating Point Determinism in NVIDIA CCCL](https://developer.nvidia.com/blog/controlling-floating-point-determinism-in-nvidia-cccl/), and [docs] (https://nvidia.github.io/cccl/unstable/cccl/determinism.html)).

Building against the latest CCCL, instead of the copy that ships with the CUDA toolkit, lets us delete the custom kernel and call `DeviceScan` instead.

## Build change: fetch CCCL from GitHub

Today PyTorch uses CCCL from the headers bundled inside the CUDA toolkit (CTK). The `run_to_run` deterministic scan arrives in CCCL 3.5 (upcoming release), which is newer than the CCCL any released CTK ships with, so adopting it means building PyTorch against CCCL 3.5 instead of the toolkit's copy. There are a few ways to make this possible, one we tried locally is to do CMake fetch that pulls latest CCCL (master) from GitHub and prepends it to the include path, ahead of the toolkit's copy.

This is safe because of CCCL's [compatibility policy](https://github.com/NVIDIA/cccl#cuda-toolkit-ctk-compatibility): the latest CCCL stays backward compatible with the current and previous CTK major versions (two major versions), and CCCL can be upgraded on its own, independently of the toolkit. So PyTorch keeps building against the CUDA version it already uses, with only the CCCL headers moved forward.

## Determinism usage

The whole deterministic path becomes a single `DeviceScan` call with a `run_to_run` env:

```cpp
auto env = ::cuda::std::execution::env{
    stream,
    ::cuda::execution::require(::cuda::execution::determinism::run_to_run),
    caching_allocator_resource{}};
cub::DeviceScan::InclusiveSum(input, output, num_items, env);
```

## Takeaway

Building against the latest CCCL, instead of the version bundled with the CUDA toolkit (CTK), is what makes this work and it is seamless. We remove 105 lines of hand-written scan code and get a faster, reproducible `DeviceScan` in return. As CCCL adds more features, staying on the latest version lets PyTorch use them right away instead of waiting for a toolkit release.
