# FP-C02 aclnn 接口检视（fpc02-dtype-perf-review）

对用户指定的 aclnn 接口（如 aclnnIndexAdd）做 FP-C02 专项性能源码检视：先定位算子实现，再按清单逐项核查，每个结论给出**文件 + 行号 + 推导链**证据，命中即出 Bug 卡，输出检视报告。**本模式特殊纪律：① 结果对、只是 fp16 慢——静态检视只能产出「嫌疑点」，任何「劣化 N 倍」的量化结论必须以基线差分实测为准；② 判据是「同 shape、同硬件、同版本下 fp16 vs bf16 的耗时比值异常」，缺 dtype 对比轴即不成立；③ 缺陷形态是「dtype 派发到未优化路径」——fp16 分支指向了不同的算子实现 / 不同的 DAG 拓扑，而非同一实现内的数据类型差异。**

## 0. 与相邻模式的边界

| 相邻模式 | 分工 |
|---|---|
| FP-C03（bf16 与 fp16 性能差异大） | **同一现象的对称面**：C02 是「**fp16 慢于 bf16**」（fp16 侧走了降级/旧实现路径）；C03 是「**两种 dtype 差异异常**」且残缺在 **bf16 侧特化**（硬件/API 缺口、冗余 Cast DAG）。两条共用「fp16/bf16 双 dtype 性能对比基线」，常合并执行；判定时先定向「哪一侧路径残缺」再归条 |
| FP-C01（端到端耗时占比高） | C01 看绝对耗时与跨版本回归，**无 dtype 轴**；C02 必须给出「同 shape 同硬件下 fp16/bf16 比值」才成立 |
| FP-B01（派发/白名单过拦） | **同源**：dtype 派发白名单 / 条件硬编码写错，功能面表现为过拦或漏拦（B01），性能面表现为某 dtype 被派到未优化路径（C02）——同一处 dtype 分支代码的两个后果面，须同核 |
| FP-G01（挂死/超时） | C02 是「**慢但能完成**」（日志持续推进）；G01 是「**根本没完成**」（日志完全无进展） |
| FP-C05 / FP-C06（确定性/代际特化型） | 同属**同版本内跨维度对比**家族，但维度不同（开关 / 代际）；C02 的维度是 **dtype**，勿合并 |

**症状反查定位**：同 shape、同硬件、同版本下 **fp16 明显慢于 bf16** 且精度全对 → C02（fp16 走降级/旧实现）；若 **bf16 侧本身不达标**（如无原生 BF16 算术指令需手写 VCONV 往返）→ C03；与 dtype 无关的绝对耗时高或跨版本回归 → C01。派发侧出现 `dtype 白名单 / 条件硬编码` 可疑处时，同步按 B01 核功能面。

## 1. FP-C02 模式卡摘要（检视依据，源自本库 `patterns/FP-C/FP-C02.md`，v3.1）

- **编号 / 名称**：FP-C02 A2 上 fp16 Vector 算子性能不如 bf16 ｜ **类别**：性能 ｜ **风险**：高（S2×O3=6）｜ **状态**：活跃
- **适用声明头**（照抄卡片）：仓 All ｜ 侧别 Kernel ｜ 载体 Kernel源码 ｜ 触发 half|float16 ｜ 默认启用 true
- **skill 核查面**：侧别 Kernel——skill 落地为 op_kernel 的 dtype 派发点与各模板变体（fp16 / bf16 / fp32 分支、arch 子目录变体）；延伸至 op_host tiling 的 dtype 分流与 tilingkey 派发（决定 fp16 落到哪个 kernel 实现）、op_host/op_api 中 dtype 决定的实现选择点
- **故障机理**：**dtype 分支走了非优化路径**——fp16 与 bf16 被派发到不同的算子实现 / 不同的 DAG 拓扑，而非同一实现内的数据类型差异。典型形态：① fp16 走**旧算子路径**（先 Cast 到 FP32 再 Cast 回），bf16 走带排序的新算子；② fp16/bf16 分支复用带**冗余外层 Cast** 的 DAG，而 fp32 直接走精简 DAG。
- **触发条件**：fp16 Vector 类算子；同算子同时支持 fp16 与 bf16，且二者派发路径不对称（一优一降级）。
- **典型表现**：**同算子 fp16 慢于 bf16**；精度全对、功能全对、无报错、无 coredump，仅耗时变长；单看 fp16 绝对值可能仍「合格」，只有双 dtype 对比才暴露。
- **源码审查映射点**：dtype 分支实现差异，fp16 是否走降级路径。
- **检测签名**（命中即候选缺陷点位）：`half|float16` 与 dtype 分支（`switch (dtype)` / `if (dtype == ...)` / tilingkey 分支）同现；`bfloat16|bf16` 与同一分支组同现；`Cast` 与 dtype 分支同现（降级路径嫌疑）；同族双实现命名（`Xxx` vs `XxxWithSorted` 类新旧算子对）；`*CastDag` 类「外层两次 Cast」的 DAG 命名。
- **审查关键词**（命中只表示值得人工审）：`Cast`——**须人工确认是否为降级路径所必需**：部分手写 Cast 是为还原中间舍入语义，属语义必须而非冗余（同族判定见 FP-C03 #2535）；`InplaceIndexAdd|WithSorted` 类新旧双实现并存；`static_cast` 类型收窄点。
- **测试拦截建议**：fp16/bf16 双 dtype 性能对比基线（与 FP-C03 合并执行）；同 shape 同硬件下记录 fp16/bf16 耗时比值；「精度 pass + 双 dtype 耗时对比」双判据必须成对出现。
- **实证案例**：ops-nn **#2930** 【aclnnIndexAdd】在 Atlas A2（910B/910_93）上 **FP16 走旧 `InplaceIndexAdd` 路径**（先 Cast 到 FP32 再 Cast 回），而 BF16 走带排序的新算子 `InplaceIndexAddWithSorted`，导致相同 shape 下 FP16 性能明显差于 BF16（`index/inplace_scatter_add/op_host/op_api/aclnn_index_add.cpp`）；ops-nn **#5303** leaky_relu 在 arch35 上 FP16/BF16 路径使用 `LeakyReluCastDag`（外层两次冗余 Cast）而 FP32 直接走 `LeakyReluDag`，带来冗余寄存器搬运与类型转换开销。**共性特征：dtype 分支指向了不同的算子实现 / 不同的 DAG 拓扑，而非同一实现内的数据类型差异——即「dtype 派发到未优化路径」。**
- **关联**：FP-C03（同一现象的对称面）、FP-C01（性能总类）、FP-B01（派发白名单/条件硬编码同源，功能面）。

## 2. 检视输入与算子定位

**输入**：aclnn 接口名（必填，如 `aclnnIndexAdd`）；可选 ref（默认 master）、指定仓（默认自动定位）；可选现象描述（fp16/bf16 耗时对比数据——用于反查优先清单点）；可选复现条件（SOC/板型 + shape + dtype——性能结论的可比性要素）。

**接口名 → 算子目录换算**：去 `aclnn` 前缀 + 驼峰转下划线小写：
`aclnnIndexAdd → index_add`、`aclnnLeakyRelu → leaky_relu`、`aclnnSwiGlu → swi_glu`。

**仓定位顺序**（GitCode `cann` 组织，逐仓用目录列表确认）：`ops-nn`（norm/loss/activation/matmul/index 类）→ `ops-math`（math/conversion 类）→ `ops-cv`（image/vision 类）→ `ops-transformer`（attention/moe 类）。**类目名不总与直觉一致**（如 `index_add` 的实现在 `index/inplace_scatter_add/` 而非 `index/index_add/`），以目录列表为准。FP-C02 高发面：同算子同时声明 fp16/bf16 双 dtype 的 Vector 类算子、带新旧双实现命名的算子族（`Xxx` / `XxxWithSorted`）、DAG 化（图模式）算子的 Cast 节点拓扑、tilingkey 按 dtype 分流的模板族。

**算子目录结构约定**（已验证示例 `cann/ops-nn` → `index/inplace_scatter_add/`）：

```text
{类别}/{op_name}/
├── op_host/
│   └── op_api/            # aclnn_*.cpp——dtype 决定实现选择的首检视面（实证 #2930 在此）
├── op_host/*_tiling*.cpp  # tiling 的 dtype 分流与 tilingkey 派发
│   └── config/<soc>/      # *_binary.json（按 dtype / soc 的派发配置）
├── op_kernel/             # kernel 模板（fp16/bf16/fp32 变体、arch35 等子目录——冗余 Cast 检视面）
├── op_graph/  tests/  docs/  examples/
└── CMakeLists.txt
```

**aclnn 出口位置提示**：多数算子的 aclnn 出口在 `op_host/op_api/` 或顶层 `op_api/`（`aclnn_*.cpp`），以目录列表与 `docs/aclnn*.md` 确认。

## 4. dtype 派发检视清单（每点：查什么 → 何处 → 命中判据）

对算子的 op_kernel（dtype 模板变体）/ op_host tiling（dtype 分流）/ op_host op_api（实现选择）全部相关文件逐点核查，**每点先查命中面、再做反证排除**，防护面（已对称的派发、语义必须的 Cast）也要记录。

### ① dtype 派发分支枚举与对称性
- 查什么：把算子所有 **dtype → 实现** 的派发点列全（`switch (dtype)` / `if (dtype == ...)` / tilingkey / binary.json 分派 / op_api 的实现选择），逐 dtype 填「落到哪个实现 / 哪个 DAG 拓扑」——找出 fp16 与 bf16 **指向不同实现**的不对称项。
- 何处：op_api 的 dtype 判定与实现调用点（实证 #2930 在 `op_host/op_api/aclnn_index_add.cpp`）、tiling 的 tilingkey 计算、op_kernel 模板实例化清单。
- 命中判据：能写出「同算子 fp16 → 实现 A、bf16 → 实现 B，A 为旧/降级路径」的对表 ⇒ 命中（给出派发点与两实现入口的行号对表）。

### ② fp16 降级路径识别（Cast 往返 / 旧算子）
- 查什么：fp16 分支是否**先 Cast 到 FP32 再 Cast 回**（降级到 fp32 计算路径），或调用**旧算子实现**（如 `InplaceIndexAdd` 对 `InplaceIndexAddWithSorted`）；对照 bf16 分支的新路径做同族比较。
- 何处：fp16 分支的实现调用点与其内部 Cast 链。
- 命中判据：fp16 分支存在「Cast 到更宽 dtype → 计算 → Cast 回」的完整往返，且同算子 bf16 分支无此往返 ⇒ 命中（实证 #2930）。

### ③ DAG 冗余 Cast 节点（图模式算子）
- 查什么：fp16/bf16 路径的 DAG 是否存在**外层两次冗余 Cast**（`LeakyReluCastDag` 类命名），而 fp32 走精简 DAG（`LeakyReluDag` 类）；冗余 Cast 是否可由硬件指令（`LoadAlign` / `StoreAlign` 类，见 FP-C03 #2993）直接完成类型转换。
- 何处：op_kernel 的 DAG 定义 / 图节点注册、arch35 等子目录变体。
- 命中判据：DAG 中可指认「结果与省略等价」的 Cast 节点，且同算子另一 dtype 路径已省略 ⇒ 命中（实证 #5303）。

### ④ 派发条件硬编码与白名单（与 FP-B01 同源）
- 查什么：dtype 判定是否为**硬编码白名单 / 条件表达式**（如仅枚举部分 dtype、用错比较对象、soc 与 dtype 交叉条件写错），使 fp16 落进 fallback 分支。
- 何处：op_api / tiling 的 dtype 条件表达式、`config/<soc>/*_binary.json` 的 dtype 派发项。
- 命中判据：条件表达式可给出「fp16 输入被判到 fallback / 通用路径」的静态推导 ⇒ 命中；同步按 FP-B01 核是否兼有过拦/漏拦（功能面）。

### ⑤ 语义必须的反证排除（防误报）
- 查什么：fp16 路径的 Cast 是否**为还原中间舍入语义所必需**（手写 Cast 还原 TBE 舍入语义的形态，见 FP-C03 #2535），而非可省略的冗余；fp16 与 bf16 是否本就共用同一实现（此时 dtype 差异属硬件能力差异，不归本条）。
- 何处：Cast 的语义注释、与参考实现（TBE/golden）的舍入对齐说明、同族已优化样板。
- 命中判据：Cast 可被证明为语义必须 / 两 dtype 共用实现 ⇒ 反证排除（写出防护面与语义依据）。

### ⑥ 测试拦截面（双 dtype 基线）
- 查什么：tests / 评测脚本是否具备 **fp16/bf16 双 dtype 性能对比基线**；是否只跑单 dtype 致不对称长期漏检。
- 何处：tests/ut、examples、评测配置。
- 命中判据：无双 dtype 对比项可静态确认 ⇒ 记录为拦截缺口（与 FP-C03 合并执行）。

## 5. 检视流程

1. **定界**：换算 op 目录、确认所在仓与 ref/HEAD；确认用户是否提供 fp16/bf16 耗时对比数据（无对比数据时结论降级为嫌疑点）；记录 SOC/板型与 shape（可比性要素）。
2. **枚举**：目录列表列出 op_api / op_host（tiling + config）/ op_kernel（含 arch 子目录）全部相关文件，产出文件清单。
3. **触发词扫描**：按 `half|float16`、`bfloat16|bf16`、dtype 分支（`switch`/`if (dtype`）、`Cast`、`*CastDag`、`WithSorted` 定位风险面（本地仓用 grep；API 模式逐文件拉取后检查）。
4. **派发表构建**：以第 4 节 ① 建立「dtype → 实现 → 关键路径」对表——后续所有清单点都在此表上比对。
5. **清单逐项核查**：每点记录命中面与防护面证据（文件:行号）；Cast 逐个确认是否语义必须（第 4 节 ⑤）。
6. **反证排除**：fp16/bf16 共用实现、Cast 语义必须、派发条件无误、DAG 已精简 → 明确写出反证理由。
7. **判定**：按第 7 节标准给出 命中 / 观察项 / 反证排除。
8. **GitCode 查重**（仅命中项）：issues API 按接口名 + `fp16|bf16|性能|劣化|Cast` 检索，逐条比对是否同机理；无同机理才立卡。
9. **业务可达性核查**（仅命中项）：判 B 等级、定业务影响类型、给处置建议；默认保守（无法证明不可达即记 B3），降档须附证据；B 不改 S×O 档位。
10. **出报告**：按第 8 节模板落盘；静态推演结论一律标注「需基线差分实测确认」，并附双 dtype 对比方案。

## 6. 风险定级（S×O）与业务影响评估（B 轴）

- **S**：S2（性能不达标 / 交付受限——同 shape 下 fp16 明显慢于 bf16）；S1（轻度资源浪费——冗余 Cast 带来的局部开销）。性能类缺陷不涉 S3/S4（结果仍正确）。
- **O**：O3 = ≥2 条独立实证；O2 = 1 条独立实证；O1 = 仅静态扫描命中或团队笔记（实证 = 确认对应的 issue / PR，或经跨仓、跨分支核验确认的缺陷记录，同权计入）。静态推演命中且无实证默认 **O1**；升档须在报告中给出实证依据。
- **风险 = S×O**：≥6 高；3/4 中；1/2 低。FP-C02 基准：模式卡整体 S2×O3=6（高）；纯静态命中 **S2×O1=2（低，暂定，量化劣化待基线差分实测后复评）**。

### B 轴：业务影响评估（与 S×O 正交；报告层新增，不改卡片定级）

S×O 回答"多严重、多常见"，**不回答"真实业务能不能碰到"**。B 轴补这一问，只决定**修复优先级建议**，**不参与 S/O 取值、不改 S×O 档位与卡片元数据**。

**业务可达性（B）**——触发条件在真实负载中的可达程度：

| 等级 | 判据 | 证据要求 |
|---|---|---|
| B3 现实可达 | 主流框架/公开模型默认路径即可命中（如 PTA/torch_npu、vLLM、MindIE 常规调用） | 调用方或公开负载来源 |
| B2 条件可达 | 需特定 attr/dtype/shape 组合，业务中存在但非默认 | 该组合的业务来源 |
| B1 边界/不可达 | 需极端、超规格或非法参数（超出接口合理上限的 shape、退化/非法输入） | "为何不可达"的说明 |

- **默认保守**：无法证明不可达 → 记 **B3**；降为 B1/B2 必须附证据，**不得仅凭"业务应该不会这么用"**。
- 超规格参数是否算 B1 取决于**接口契约**：契约允许但业务不用 → B1；契约不允许（本应报错）→ 属校验缺失（FP-B04/B05 类），另行归属。

**业务影响类型**（命中后对用户可见结果的后果，用业务语言表述）：静默精度损失（模型效果下降 / loss 不收敛 / 偶发 NaN）｜ 任务失败中断（报错 / 崩溃 / 挂死）｜ 性能退化 ｜ 仅可观测性（日志 / 错误码 / 文档，不影响结果）。

**处置建议**（由两轴推导的报告结论，非新档位）：

| S×O \ B | B3 现实可达 | B2 条件可达 | B1 边界/不可达 |
|---|---|---|---|
| 高（≥6） | 尽快修 | 尽快修 | 排期修 |
| 中（3/4） | 尽快修 | 排期修 | 记录（业务难以触达） |
| 低（1/2） | 排期修 | 记录 | 记录 |

## 7. 判定标准与反误报原则

- **性能类特殊纪律（务必贯彻）**：静态检视只能立「嫌疑点 / 优化项」——「dtype 派发到未优化路径」可静态证；但任何「劣化 N 倍 / 慢 X%」的量化结论**必须以基线差分实测为准**（同 shape、同硬件、同版本、fp16 vs bf16 双 dtype 对照），不可用代码审查替代性能基线看护。
- **三种判定**：
  - **命中**（可静态证不对称）：派发表显示 fp16 与 bf16 指向不同实现 / 不同 DAG 拓扑，且 fp16 侧为可指认的降级路径（Cast 往返、旧算子、冗余 Cast 节点）→ 立 Bug 卡；
  - **观察项**：派发不对称存在但静态无法确证降级代价（如新旧实现差异需实测）→ 记录并附双 dtype 基线方案，按 S2×O1 暂定；
  - **反证排除**：两 dtype 共用实现、Cast 为语义必须、派发条件无误、DAG 已精简 → 明确写出反证理由与防护面证据。
- **「精度全对」不是排除理由**：本型典型表现正是精度/功能全对、仅耗时变长——双 dtype 耗时对比才是唯一暴露途径。
- **Cast 命中 ≠ 冗余**：手写 Cast 可能为还原中间舍入语义（FP-C03 #2535 同族）；判定前必须过第 4 节 ⑤ 的语义必要性反证。
- **与 C03 的定向**：以「哪一侧路径残缺」定向——fp16 侧残缺（降级/旧路径）归 C02；bf16 侧残缺（API 缺口/冗余 Cast DAG）归 C03；两条常合并执行同一份双 dtype 基线。
- **不臆造行号**：每条证据必须是实际读到的 文件:行号；引用实证样板时同样给出路径与行号，issue 时点行号与本仓 HEAD 漂移时注明。

### 判定纪律补充（v3.6）：非对称增减、证据等级与误判记录

**增减不对称**：允许追加候选（有据即可，错了可由用户排除）；**撤销或否决候选必须附 `[文件]:[行号] [代码行]` 负向证据**。无证据的「看起来没问题」一律记为「未核查」，不得计入反证排除，也不得据此下调等级——否决造成的漏报用户不可见、不可恢复。

- **证据等级**（Bug 卡必填）：`静态可证` = 推导链完整且触发输入可静态构造；`需实测确认` = 依赖运行时输入规模、设备行为或环境差异。标 `需实测确认` 的条目**不得以「命中」名义出卡**，按观察项记录并附实测用例。
- **Agent 误判记录**（Bug 卡必填）：本次被推翻的假设、推翻它的证据（`[文件]:[行号] [代码行]` 或实测输出）、判定标准是否随之修订；无推翻写「无」。
- **误判回流**：同类误判在 3 次检视中重复出现，登记至 `cases/misjudgments.jsonl`（字段见 `cases/README.md`），并在本模式判定标准中新增对应防线；守门 C19d 校验台账字段合法。

## 9. 示例速览：aclnnIndexAdd

- **定位**：`cann/ops-nn` → `index/inplace_scatter_add/`（op_host/op_api/aclnn_index_add.cpp——本算子 aclnn 出口在 `op_host/op_api/` 之下；op_kernel 含 fp16/bf16 模板变体与 arch 子目录；docs/aclnnIndexAdd.md）。
- **检视面提示**（引导，不预设结论，仍须逐点核查；行号以本地 HEAD 为准）：
  - 清单点 ①：在 `aclnn_index_add.cpp` 内定位 dtype 派发点，建立「dtype → 实现」对表——核查 fp16 与 bf16 是否指向**不同实现**（实证 #2930：FP16 → `InplaceIndexAdd`（先 Cast 到 FP32 再 Cast 回），BF16 → `InplaceIndexAddWithSorted`）；本地代码若已对称，记录为防护面证据。
  - 清单点 ②：fp16 分支的 Cast 往返链逐个确认——是否存在「Cast 到 FP32 → 计算 → Cast 回」的完整降级路径；对照 bf16 分支做同族反证。
  - 清单点 ③：对照实证 #5303 leaky_relu 的 `LeakyReluCastDag`（外层两次冗余 Cast，FP32 走 `LeakyReluDag`）——若本算子 fp16/bf16 路径出现「外层 Cast 包裹」的 DAG 形态，记录为嫌疑点。
  - 清单点 ⑤：反证面——若 Cast 为还原中间舍入语义所必需（FP-C03 #2535 同族）或两 dtype 已共用实现，写出反证理由。
- 任何一点的最终判定以第 4/5/7 节口径为准，禁止凭算子类型直接下结论。

## 10. 能力边界与自检（v3.8）

### 能力边界

- **静态可证**：清单里能在源码内给出「`文件:行号` + 推导链」的部分，按第 7 节判据出卡。
- **需实测确认**：依赖运行时输入规模、设备行为或环境差异的结论，只能记观察项并附实测用例（证据等级见第 7 节）。
- **不覆盖**：本模式以外的机理（边界见第 0 节）与仓外框架侧行为；`TRIAGE.md` 只负责收敛候选，不构成判定依据。
- **找不到 ≠ 没有**：按清单未命中只说明「本轮未发现」，不得表述为「该算子无此缺陷」；抽样核查须在报告写明抽样口径。

### 自检

```bash
python3 scripts/gen_triage.py --check                          # 分诊表与映射一致

```
