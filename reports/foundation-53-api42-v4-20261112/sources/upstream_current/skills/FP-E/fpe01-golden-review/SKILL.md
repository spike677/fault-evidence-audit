# FP-E01 golden/UT 资产检视（fpe01-golden-review）

对用户指定的算子（如 aclnnDiagV2 → DiagV2）做 FP-E01 专项检视：先定位算子的测试资产（golden 生成脚本、st 用例集、ut 用例），再按三类核查面逐项核查，每个结论给出**文件 + 行号 + 推导链**证据，命中即出 Bug 卡，输出检视报告。**本模式特殊纪律：golden 通过 ≠ 精度达标——golden 是「期望值」资产，它自己错了 UT 会永远绿；本 skill 检视的是验证链的有效性，不是实现的对错。修复类 diff 中 golden 与实现同步修改，是历史 golden 按错误实现编写的强信号。**

## 0. 与相邻模式的边界

| 相邻模式 | 分工 |
|---|---|
| FP-E02（判据/标杆口径设计缺陷） | **最易混淆项**：E01 是 **golden 期望值本身错**（数据/约定错）；E02 是 **判据/标杆口径设计错**（容差、比对方式、标杆选择错）。判据换一套口径能救的归 E02，期望值数据本身错的归本条；二者常叠加放大，命中时双向互查 |
| FP-A04 / A13 / A18（实现侧精度类） | A 系是「**实现算错**」——检视对象是 op_kernel / op_host；本条是「**期望值错了导致算错测不出来**」——检视对象是 tests/。二者互补：修复实现类缺陷时，若 golden 同步改动即落回本条 |
| FP-G01（挂死/超时） | 挂死类用例**根本走不到数值比较**，golden 再正确也拦不住——「断言不返回」属 G01 的测试拦截面，本条的 golden 修复救不了它 |
| FP-B06（空/0 元素输入防御缺失） | golden 对空张量的口径（崩溃 / no-op / 报错）须与算子契约一致——口径不一致归本条参照失真，防御缺失归 B06 |

**症状反查定位**：用例**永远通过**（含明知应失败的输入）→ 核查面 A（失配致静默失效）；修复 PR 的 diff 中 golden 与实现**双改** → 核查面 B；精度结论与三方标杆矛盾但 UT 全绿、或假红与 NPU 无关 → 核查面 C（参照失真）。

## 1. FP-E01 模式卡摘要（检视依据，源自本库 `patterns/FP-E/FP-E01.md`，v3.1）

- **编号 / 名称**：FP-E01 golden/UT 期望值失配或按错误实现编写 ｜ **类别**：测试有效性 ｜ **风险**：高（S3×O3=9）｜ **状态**：活跃
- **适用声明头**（照抄卡片）：仓 All ｜ 侧别 All ｜ 载体 UT与golden资产 ｜ 触发 golden ｜ 默认启用 true
- **skill 核查面**：载体为 UT 与 golden 资产——skill 落地为算子 `tests/` 全树（`assets/golden*.py` 生成脚本、`st/**/*.csv` 用例集、`ut/**` 用例）**加**修复类 PR/commit 的 diff；产品源码（op_host / op_kernel）仅在判定 golden 参照是否与待测实现**同源**时读取
- **故障机理**：① golden 生成脚本与用例命名/约定失配，精度验证**静默失效**（用例永远通过）；② golden 按（曾经的错误）实现逆向编写，缺陷被 UT「**合法化**」——修复 PR 中 golden 与实现同步修改即是强信号。
- **触发条件**：测试基础设施代码（golden.py、st csv）与用例演进不同步；缺陷修复未审视 golden 正确性。
- **典型表现**：精度验证静默失效；修复 PR 的 diff 中 golden 与实现同时修改。
- **实证案例**：ops-math **#3048** DiagV2 kernel 模式 golden 命名与用例命名失配，精度验证静默失效（golden.py + st csv 整改）；ops-nn **#5562** golden.py 随修复同步修改，证明 UT 期望值曾按错误实现编写；ops-nn **#5635** 11 个 foreach/scatter/lamb 算子 TTK golden 四类缺陷致精度结论失真（①空张量崩溃与算子 no-op 口径不一致；②整型入参强转 fp32 静默丢位，`2^30+100`→`2^30+128`，整型精度结论从未被验证；③golden 与三方标杆逐位相等致双标杆塌陷、RMSE 比值分母失效产生与 NPU 无关的假红；④三方 compose 与被测内核中间量精度/运算序列不对等，竞品凭空更准把内核判成缺陷）；ops-nn **#4483** 23 个算子 golden.py 为 numpy 纯公式（与被测 kernel 同类有损，把精度短板伪装成达标），另有整型走 fp32 尾数不足、Python min/max 静默丢 NaN、除法未做 Subnormal FTZ 等参照失真。
- **关联**：FP-A04、FP-A13、FP-A18、FP-E02（E01 是 golden 本身错，E02 是判据/标杆口径设计错——二者常叠加放大）。

## 2. 检视输入与算子定位

**输入**：算子名或 aclnn 接口名（必填，如 `aclnnDiagV2` 或 `DiagV2`）；可选 ref（默认 master）、指定仓（默认自动定位）；可选**修复类 PR / commit 区间**（用于核查面 B 的双改信号，缺省时该面只做存量核查）；可选存疑用例名/现象描述。

**接口名 → 算子目录换算**：去 `aclnn` 前缀 + 驼峰转下划线小写：
`aclnnDiagV2 → diag_v2`、`aclnnMoeInitRoutingV4 → moe_init_routing_v4`、`aclnnSwiGlu → swi_glu`。

**仓定位顺序**（GitCode `cann` 组织，逐仓用目录列表确认）：`ops-nn`（norm/loss/activation/matmul 类）→ `ops-math`（math/conversion 类）→ `ops-cv`（image/vision 类）→ `ops-transformer`（attention/moe 类）。**类目名不总与直觉一致**（如 diag_v2 在 `conversion/` 而非 math 类目），以目录列表为准。

**tests 目录结构约定**（已验证示例 `cann/ops-math` → `conversion/diag_v2/`）：

```text
{类别}/{op_name}/
├── tests/
│   ├── assets/            # golden 生成脚本（golden.py 等）——核查面 A/B/C 主对象
│   ├── st/                 # st 用例集（csv，引用 golden 键）——核查面 A 的约定匹配面
│   │   └── arch35/*.csv
│   ├── ut/                 # ut 用例（op_host / op_api 拆分）——断言链与用例覆盖面
│   └── CMakeLists.txt
├── op_host/ op_kernel/ op_api/   # 产品源码——仅判「golden 是否与实现同源」时读取
└── docs/                  # 接口文档（口径约定的旁证）
```

| 单文件内容 | `GET https://api.gitcode.com/api/v5/repos/cann/{repo}/raw/{path}?ref={ref}` |

## 4. 三类核查面（每点：查什么 → 何处 → 命中判据）

对算子 tests/ 全部资产逐点核查，**每点先查命中面、再做反证排除**；golden 正确的部分也要记录（作为反证依据）。

### 核查面 A：golden 与用例的命名/约定失配（成因①）
- 查什么：用例（st csv / ut cpp）引用的 **golden 键名/文件名/约定名**，与 golden 生成脚本**实际产出**的键名是否一致；失配后果是**断言取不到期望值或取到恒真路径**（如空期望集、跳过比较、恒 0 对 0），精度验证静默失效——用例永远通过。
- 何处：`tests/assets/golden*.py` 的键生成逻辑 × `tests/st/**/*.csv` 的用例行 × `tests/ut/**` 的数据加载函数；跨 arch 子目录（st/arch35 等）与 kernel 模式分支的键名拼接规则。
- 命中判据：能写出「用例引用键 X → 生成脚本中不存在 X（或 X 恒空/恒默认）→ 比较步被跳过或恒真」的完整推导链；修复 PR 若整改了 golden.py + st csv 双侧，即为历史失配的强旁证（实证 #3048 同族）。

### 核查面 B：golden 与待测实现同源（成因② + 双改信号）
- 查什么：golden 是否**按待测实现逆向/回放**编写（同源参照）——与 kernel 同一套有损运算序列时，实现的精度短板被「合法化」；修复类 PR 的 diff 中 **golden 与实现是否同步修改**——实现修复 + golden 跟着改，说明改动前的 golden 是按错误实现写的。
- 何处：`tests/assets/golden*.py` 的期望值来源（待测 kernel 回放 / 同仓工具复算 = 同源；独立参考实现 numpy、torch CPU 前向 = 合规）；修复类 commit 区间内 `tests/` 与 `op_kernel/`、`op_host/` 的**双文件 diff**。
- 命中判据：diff 可指认「实现行为变更 + golden 期望值同 commit 跟随变更」且实现变更属**纠错**（而非口径/接口变更）；或 golden 脚本中存在直接调用/复刻待测 kernel 逻辑的代码段。注意反证：接口语义变更（新增参数、口径切换）时 golden 合理同步改动，不算命中。

### 核查面 C：golden 参照失真（实证 #5635 / #4483 细类）
- 查什么（六点，均为「期望值口径与算子契约/真实参考不一致」）：
  ① **空张量口径不一致**——golden 对空输入的期望（崩溃 / no-op / 全零）与算子实际契约不符；
  ② **整型入参强转 fp32 丢位**——golden 生成路径把整型入参经 fp32 承载（`2^30+100` 被存成 `2^30+128`），整型精度结论从未被真实验证；
  ③ **双标杆塌陷**——golden 与三方标杆逐位相等，RMSE 比值分母为 0/失效，产生与 NPU 无关的假红；
  ④ **compose 不对等**——三方 compose 与被测内核的中间量精度/运算序列不对等，竞品「凭空更准」把内核判成缺陷；
  ⑤ **参考实现同类有损**——numpy 纯公式 golden 与被测 kernel 用同类有损路径，精度短板被伪装成达标；
  ⑥ **数值边界静默失真**——Python `min`/`max` 静默丢 NaN、除法未做 Subnormal FTZ、整型走 fp32 尾数不足。
- 何处：golden 生成脚本的数值构造段（dtype 选择、比较方式、特殊值处理）、空输入用例行、标杆比对与 RMSE 计算段。
- 命中判据：能构造**静态反例**推导「golden 口径 ≠ 算子契约/真实参考」的输入（如 `2^30+100` 的整型入参、含 NaN 的输入、空 tensor）；③④ 类需标注「需数值实验确认」转观察项。

## 5. 检视流程

1. **定界**：换算 op 目录、确认所在仓与 ref；确认修复 PR/commit 区间是否提供（决定核查面 B 的双改分析是否执行）。
2. **枚举**：列出 `tests/` 全树文件清单（assets / st / ut），记录 golden 脚本与用例集的对应关系。
3. **失配扫描**（核查面 A）：逐用例抽Trace 引用键 × golden 生成键，正反两个方向比对（引用了不存在的键 / 生成了无人引用的键）。
4. **双改审视**（核查面 B）：有修复区间时逐 commit 检查 tests/ 与实现的双文件 diff；无区间时对 golden 脚本做同源判定（期望值来源审计）。
5. **参照质量核查**（核查面 C）：按六点逐项核对 golden 的数值构造与口径；读产品源码中对应契约（空输入行为、dtype 约定）作旁证。
6. **判定**：按第 7 节标准给出 命中 / 观察项 / 反证排除。
7. **GitCode 查重**（仅命中项）：issues API 按算子名 + golden 关键词检索，逐条比对是否同机理；无同机理才立卡。
8. **业务可达性核查**（仅命中项）：判 B 等级、定业务影响类型、给处置建议；默认保守（无法证明不可达即记 B3），降档须附证据；B 不改 S×O 档位。
9. **出报告**：按第 8 节模板落盘。

## 6. 风险定级（S×O）与业务影响评估（B 轴）

- **S**：S3（验证体系失效——缺陷被 UT 合法化、精度结论失真/假红假绿）；S2（单用例失配但同族其他用例仍可拦截——降级）。
- **O**：O3 = ≥2 条独立实证；O2 = 1 条独立实证；O1 = 仅静态扫描命中或团队笔记（实证 = 确认对应的 issue / PR，或经跨仓、跨分支核验确认的缺陷记录，同权计入）。静态推演命中且无实证默认 **O1**；升档须在报告中给出实证依据。
- **风险 = S×O**：≥6 高；3/4 中；1/2 低。FP-E01 基准：模式卡整体 S3×O3=9（高，4 条实证）；纯静态命中 S3×O1=3（中，暂定）。

### B 轴：业务影响评估（与 S×O 正交；报告层新增，不改卡片定级）

S×O 回答"多严重、多常见"，**不回答"真实业务能不能碰到"**。B 轴补这一问，只决定**修复优先级建议**，**不参与 S/O 取值、不改 S×O 档位与卡片元数据**。

**业务可达性（B）**——触发条件在真实负载中的可达程度：

| 等级 | 判据 | 证据要求 |
|---|---|---|
| B3 现实可达 | 主流框架/公开模型默认路径即可命中（如 PTA/torch_npu、vLLM、MindIE 常规调用） | 调用方或公开负载来源 |
| B2 条件可达 | 需特定 attr/dtype/shape 组合，业务中存在但非默认 | 该组合的业务来源 |
| B1 边界/不可达 | 需极端、超规格或非法参数（超出接口合理上限的 shape、退化/非法输入） | "为何不可达"的说明 |

- **默认保守**：无法证明不可达 → 记 **B3**；降为 B1/B2 必须附证据，**不得仅凭"业务应该不会这么用"**。
- 超规格参数是否算 B1 取决于**接口契约**：契约允许但业务不用 → B1；契约不允许（本应报错）→ 属校验缺失（FP-B04/B05 类），另行归属。

**业务影响类型**（命中后对用户可见结果的后果，用业务语言表述）：静默精度损失（模型效果下降 / loss 不收敛 / 偶发 NaN）｜ 任务失败中断（报错 / 崩溃 / 挂死）｜ 性能退化 ｜ 仅可观测性（日志 / 错误码 / 文档，不影响结果）。

**处置建议**（由两轴推导的报告结论，非新档位）：

| S×O \ B | B3 现实可达 | B2 条件可达 | B1 边界/不可达 |
|---|---|---|---|
| 高（≥6） | 尽快修 | 尽快修 | 排期修 |
| 中（3/4） | 尽快修 | 排期修 | 记录（业务难以触达） |
| 低（1/2） | 排期修 | 记录 | 记录 |

## 7. 判定标准与反误报原则

- **「永远通过」优先于「写得好不好」**：golden 质量问题的第一后果是失配静默失效——一个写得粗糙但约定一致的 golden 不构成命中；一个写得精良但键名断裂的 golden 是高危命中。
- **三种判定**：
  - **命中**（可静态证失效/同源/失真）：引用链断裂、双改信号成立、失真反例可静态构造，三者任一推导链完整 + 反证排除失败 → 立 Bug 卡；
  - **观察项**：③④ 类需数值实验、或双改信号无法区分「纠错」与「口径变更」→ 记录并附验证方案，不定级或按 S3×O1 暂定；
  - **反证排除**：数值差异在判据容差内、空张量行为与算子契约一致、golden 属另一套合法命名约定、接口语义变更导致的合理同步 → 明确写出反证理由。
- **不臆造键名与行号**：每条证据必须是实际读到的 文件:行号/键名；golden 键的推导必须引用脚本中的实际拼接代码。
- **同族放大检查**：命中后向同仓同模板族（如同一套 TTK golden 框架生成的算子）横向扫描——#5635/#4483 均为批量化缺陷，单点命中常预示族性命中。

### 判定纪律补充（v3.6）：非对称增减、证据等级与误判记录

**增减不对称**：允许追加候选（有据即可，错了可由用户排除）；**撤销或否决候选必须附 `[文件]:[行号] [代码行]` 负向证据**。无证据的「看起来没问题」一律记为「未核查」，不得计入反证排除，也不得据此下调等级——否决造成的漏报用户不可见、不可恢复。

- **证据等级**（Bug 卡必填）：`静态可证` = 推导链完整且触发输入可静态构造；`需实测确认` = 依赖运行时输入规模、设备行为或环境差异。标 `需实测确认` 的条目**不得以「命中」名义出卡**，按观察项记录并附实测用例。
- **Agent 误判记录**（Bug 卡必填）：本次被推翻的假设、推翻它的证据（`[文件]:[行号] [代码行]` 或实测输出）、判定标准是否随之修订；无推翻写「无」。
- **误判回流**：同类误判在 3 次检视中重复出现，登记至 `cases/misjudgments.jsonl`（字段见 `cases/README.md`），并在本模式判定标准中新增对应防线；守门 C19d 校验台账字段合法。

## 10. 能力边界与自检（v3.8）

### 能力边界

- **静态可证**：清单里能在源码内给出「`文件:行号` + 推导链」的部分，按第 7 节判据出卡。
- **需实测确认**：依赖运行时输入规模、设备行为或环境差异的结论，只能记观察项并附实测用例（证据等级见第 7 节）。
- **不覆盖**：本模式以外的机理（边界见第 0 节）与仓外框架侧行为；`TRIAGE.md` 只负责收敛候选，不构成判定依据。
- **找不到 ≠ 没有**：按清单未命中只说明「本轮未发现」，不得表述为「该算子无此缺陷」；抽样核查须在报告写明抽样口径。

### 自检

```bash
python3 scripts/gen_triage.py --check                          # 分诊表与映射一致
python3 scripts/scan_fp.py --only FP-E01 --format json <目标文件>  # 签名候选（非结论）
python3 scripts/verify_lines.py <报告.md> --root <被检仓>        # 行号校验
python3 check_fault_patterns.py                                # 全库守门
```

### 工作量与抽样（v4.0）

- **深度档：宽浅**（索引 `depth` 字段）——只跑签名定位 + 每类抽 3 例；报告必须写「抽样，非全量」，不得表述为全量检视。
- **报告必填**：抽样口径（全量 / 每点前 N 处 / 每类 N 例）+ 停止点记录；未写口径视为未完成。
