### What this PR does
Fixes issue #16674 
`split_qkv_rmsnorm_rope` produced wrong, run-to-run non-deterministic Q and K above a shape-dependent `num_tokens` threshold — `max|err|` up to **9.4** against the op's own `atol=5e-2`, failing on **6/6** consecutive calls with identical inputs. V was always correct.

### Root cause

The RoPE position was staged into UB as a tile, then read back one element at a time as a scalar:

```python
x = tl.load(positions_gm_ptr + pos_indices + pos_offset, mask=...)
...
pos = get_element(x, (i,))
```

`get_element` reads the scalar from the UB buffer that the same iteration's `tl.load` is still filling, with nothing ordering the MTE transfer first. From the second outer iteration onward the scalar unit can still observe the previous
iteration's position, so `cos`/`sin` are fetched for the wrong position and the whole row — every Q head and every K head — is rotated by the wrong angle. V skips RoPE, which is why only Q/K were affected.

Because `x` is reloaded once per outer iteration, the race requires `iter_num_per_vec > 1`. `batch_size_per_iter_per_vec` is sized from the UB budget, so a larger `q_hidden_size + kv_hidden_size` yields more iterations and failure at a smaller `num_tokens` — `(12, 1)` first fails at 1024, `(64, 4)` at 257. `num_tokens` 1 and 16 pass only because the single iteration reads a freshly-zeroed buffer.

### The fix

Read the position straight from global memory as a scalar. The UB round-trip, and with it the race, is gone.

Three hunks total; `get_element` becomes unused in this file and is dropped from the import.

**On the clamp.** `last_row = input_batch_offset_end - 1` is always `>= 0`: for a core with no work, `input_batch_offset_end == batch_size >= 1`. Rows past the end read the last valid position instead of going out of bounds, and their outputs are discarded by `mmask` further down. This preserves the previous behaviour,
where the masked `tl.load` yielded `0` and those rows harmlessly read `cos_sin_cache[0]`.

**Why not a vectorized gather.** Replacing the inner loop with `tl.load(cos_sin_cache_gm_ptr + x[:, None] * ROPE_DIM + sin_cos_range[None, :])` would also fix it and be tidier, but limited vector-indexed gather support on
this backend is the likely reason the scalar loop exists at all. This patch keeps the existing structure and changes only the racy read.

### Validation

Ascend NPU, bf16, `head_dim=128`, full RoPE. Shapes and tolerance are taken from the op's own nightly test (`NUM_QKV_HEADS`, `NUM_TOKENS`, `DEFAULT_ATOL = 5e-2`), plus `num_tokens=257` from the PR gate.

**1. Non-determinism is gone.** Bitwise comparison of 24 repeated calls with identical inputs:

| num_tokens | (12,1) before | (12,1) after | (64,4) before | (64,4) after |
|---:|:---:|:---:|:---:|:---:|
| 1 | stable | stable | stable | stable |
| 16 | stable | stable | stable | stable |
| 257 | stable | stable | **UNSTABLE** | stable |
| 1024 | **UNSTABLE** | stable | **UNSTABLE** | stable |
| 10240 | **UNSTABLE** | stable | **UNSTABLE** | stable |

**2. Results are correct, not merely stable.** Per-row comparison against a fp32 reference at `atol=5e-2`, plus a count of rows matching the *preceding* token's position (the original failure mode):

`(12, 1)`:

| num_tokens | before max\|err\| Q / K | after max\|err\| Q / K | off-by-one rows after |
|---:|---:|---:|:---:|
| 1 | 0.0119 / 0.0077 | 0.0119 / 0.0077 | 0 |
| 16 | 0.0156 / 0.0143 | 0.0156 / 0.0143 | 0 |
| 257 | 0.0300 / 0.0283 | 0.0300 / 0.0283 | 0 |
| 1024 | **7.8431 / 7.6423** | **0.0310 / 0.0309** | 0 |

`(64, 4)`:

| num_tokens | before max\|err\| Q / K | after max\|err\| Q / K | off-by-one rows after |
|---:|---:|---:|:---:|
| 1 | 0.0148 / 0.0077 | 0.0148 / 0.0077 | 0 |
| 16 | 0.0306 / 0.0146 | 0.0306 / 0.0146 | 0 |
| 257 | **8.0298 / 6.8400** | **0.0311 / 0.0156** | 0 |
| 1024 | **9.3595 / 6.4640** | **0.0293 / 0.0306** | 0 |

Two things to note: on shapes that already passed, before and after are **identical**, so the patch does not perturb correct results; and residual error on the fixed shapes is ordinary bf16 rounding, comfortably inside `atol=5e-2`.

**3. No performance regression.** Measured over 2 repeats × 300 iterations (200 warmup) per cell, all 8 shape/config cells came out at or below baseline. I am deliberately not quoting a speedup: in this eager micro-benchmark
`num_tokens=1` and `num_tokens=1024` both land around 47 us, so it is dominated by dispatch overhead rather than kernel time, and run-to-run spread (~10%) is comparable to the effect. The patch removes one UB transfer per outer iteration, so a regression would be surprising, but a proper device-side kernel-time measurement would be needed to quantify any gain.
