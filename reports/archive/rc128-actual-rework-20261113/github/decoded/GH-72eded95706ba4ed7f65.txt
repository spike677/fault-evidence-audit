[Feature][Performance] Support InternLM2-20B-Chat and dispatch scaled RoPE variants to the NPU kernel
### What this PR does / why we need it?

`InternLM2ForCausalLM` runs on the existing upstream vLLM path, but its checkpoint sets `rope_scaling = {"type": "dynamic", "factor": 2.0}`, which resolves to `DynamicNTKScalingRotaryEmbedding`. That class was missing from `REGISTERED_ASCEND_OPS`, so every decoder layer silently fell back to `forward_native` — no log line, no error, just slower.

The same gap affects three other scaled RoPE types. They all share a property: the only thing they change is how the cos/sin cache is computed at init; the forward itself is inherited from `RotaryEmbedding`. So a single mixin (`_AscendScaledRopeMixin`) can route them all to the fused NPU kernel safely:

| `rope_scaling.type` | upstream class | models | before | after |
| --- | --- | --- | --- | --- |
| `dynamic` + `factor` | `DynamicNTKScalingRotaryEmbedding` | InternLM2, InternLM2.5 | `forward_native` | NPU kernel |
| `dynamic` + `alpha` | `DynamicNTKAlphaRotaryEmbedding` | Hunyuan | `forward_native` | NPU kernel |
| `ntk` | `NTKScalingRotaryEmbedding` | — | `forward_native` | NPU kernel |
| `llama3` | `Llama3RotaryEmbedding` | Llama 3.1+ | `forward_native` | NPU kernel |

Three variants are intentionally left out:

- `longrope` / `fope`: they override the forward, not just the cache.
- `linear`: indexes into the cache via the `offsets` arg, which `rope_forward_oot` rejects. Registering it would break multi-LoRA serving.

Dispatch verified on Atlas A2 — each config built through `get_rope`, class printed, excluded types confirmed still on `forward_native`.

**Throughput** (2 × Atlas A2, TP=2, 1024/128, 64 prompts, concurrency 8):

| --- | --- | --- |
| req/s | 1.70 | **1.96 (+15.4%)** |
| output tok/s | 216.97 | **250.42** |
| mean TPOT | 33.62 ms | **28.94 ms (−13.9%)** |

### Does this PR introduce _any_ user-facing change?

Yes. Checkpoints with `rope_scaling.type` = `dynamic`, `ntk`, or `llama3` now hit the NPU kernel instead of the reference path. InternLM2-20B-Chat is added to the docs and nightly accuracy suite. Release note fragment included.

### How was this patch tested?

**Environment:** 2 × Atlas A2 (Ascend910_9382, 64 GB), CANN 9.2.1, torch 2.10.0, torch_npu 2.10.0.post7, vLLM `24420b7a`, real BF16 weights (21 shards).

**Unit tests** — 76 passed (`tests/ut/ops/test_rotary_embedding.py`). Parameterized over all four variants: checks that `CustomOp.__new__` resolves to the Ascend class, that the cache comes from the parent, that `use_mtp` is wired up, that every forward arg gets passed through, and that a signature change in the upstream `__init__` will break the build.

**Serving checks** — 13/13 on TP=2 with real weights:

| check | result |
| --- | --- |
| models endpoint | 200 |
| completions, EN + ZH | 200, non-empty |
| greedy reproducible, EN + ZH | token-identical across runs |
| seeded sampling reproducible | identical |
| different seeds diverge | yes |
| 3-turn chat, recall from turn 1 | recalled |
| turn 3 in Chinese | correct |
| retrieval, short prompt (73 tok) | found |
| retrieval, long prompt (5749 tok) | found |

`tests/e2e/pull_request/two_card/test_internlm2_20b_chat.py` encodes these as two pytest cases (one `VllmRunner`, one `RemoteOpenAIServer`) — two model loads total.

**Accuracy** — C-Eval validation (52 subjects, 1346 questions, 5-shot), TP=2, ACL Graph:

```
ceval-valid | acc,none: ground_truth=0.6293 | measured=0.6337 | success=✅
1 passed in 603.84s (0:10:03)
```

Two runs: 0.6293 and 0.6337 (±0.0124 stderr). Baseline set to 0.6293.

**Performance** — numbers in the first section, `vllm bench serve`, same build with/without the registry entries.

**Lint** — `ruff check` + `ruff format --check` clean on the full tree; `codespell` + `markdownlint` clean on new files.
