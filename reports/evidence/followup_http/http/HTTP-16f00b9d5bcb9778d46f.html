Describe the current behavior / 问题描述 (Mandatory / 必填)

DequantSwigluQuant / aclnnDequantSwigluQuantV2 在 groupIndexOptional（DSK 高性能路径）+ quantMode=dynamic + int32 输入多分组 场景下，scaleOut 输出垃圾值，yOut 大量元素不一致。本 issue 是 #5063 的后续：#5063 已修复 srcRepStride 整除截断（官方已合入 9176e2d85），但仍有两个独立 bug 在 H=64（UbFactorDimy=32）与小 token 数场景暴露：

Bug 1：WholeReduceMax mask 写死 64（quant/dequant_swiglu_quant/op_kernel/dequant_swiglu_quant.h DynamicQuant）
当 UbFactorDimy < 64（如 H=64 → 32）时，第二阶段归约每个 repeat 跨 2 行读取并越界：

  • kernel printf 实测（x[15,64]，9 组，尾块 proDimsx=1）：行 max 读出 INT_MAX 级垃圾值，最终 scale 为 3e10 级错误值
  • proDimsx=2 时相邻两行 max 被合并（NPU[2i]=NPU[2i+1]=max(g[2i],g[2i+1])）

Bug 2：Brcb 广播覆写 scaleOut 自身
行 scale 广播链路 Brcb(outLocal, scaleOut, blockCount) + Copy 借道 outLocal 中转，而 scaleOut = outLocal[UbSingleOutSize_/4]。当 UbSingleOutSize_/4 < blockCount*64（如 UbFactorDimx=1, outDimy=160 → 偏移 40 < 64）时，Brcb 写 outLocal[0,64) 直接覆盖 scaleOut 本身：

  • kernel printf 实测（x[1,320]，9 组）：归约正确（行 max=254.069）、scaleOut 计算正确（2.0005）、广播后 Div 除数全部正确，但 CopyOut 写出的 scale 仍为垃圾（-3.7462），y 55/160 元素不一致

Environment / 环境信息 (Mandatory / 必填)

  • SoC：Atlas A2（ascend910b）
  • CANN 9.1.0
  • 算子路径：quant/dequant_swiglu_quant（DSK Tiling 路径，groupIndexOptional 非空，quantMode=dynamic）

Steps to reproduce the issue / 重现步骤 (Mandatory / 必填)

  1. case A：x=int32[15,64]，weight_scale/quant_scale 为 [9,64]/[9,32]，group_index=[2]*6+[1]*3（和=15），dynamic，swiglu_mode=3
  2. case B：x=int32[1,320]，weight_scale/quant_scale 为 [9,320]/[9,160]，group_index 9 组（和=1，仅组 0 有效），dynamic，swiglu_mode=3
  3. 调用 aclnnDequantSwigluQuantV2 并与 golden 比对

Describe the expected behavior / 预期结果 (Mandatory / 必填)

  1. WholeReduceMax 的 mask 取 min(UbFactorDimy, 64)：每行首元素经 ComputeReduceMax 后已是行 max，UbFactorDimy<64 时按实际行宽读取即可，≥64 时与原实现一致
  2. 广播改用单条 BroadCast<float, 2, 1>(tmpUbF32Gate, scaleOut, dstShape, srcShape)（与官方 dynamic_quant 实现一致），不再借道 outLocal，彻底避免 Brcb 覆写 scaleOut

Related log / screenshot / 日志 / 截图 (Mandatory / 必填)
