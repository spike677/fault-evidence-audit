问题
tests/framework/python/CsvOpsTestTool/atb_csv_ops_test.py
的
get_device_properties()
用一条 if/elif 链把
torch.npu.get_device_name()
映射到
soc_version
。同一个条件
re.search("Ascend950", device_name, re.I)
在这条链里出现了
3 次
（L1041、L1045、L1053），三处分支体都只有
soc_version = "Ascend950"
：
elif
re.search(
"Ascend910_93"
, device_name, re.I):
# L1038
...
elif
re.search(
"Ascend950"
, device_name, re.I):
# L1041  真正生效
soc_version =
"Ascend950"
elif
re.search(
"Ascend310P"
, device_name, re.I):
# L1043
soc_version =
"Ascend310P"
elif
re.search(
"Ascend950"
, device_name, re.I):
# L1045  ← 永不执行
soc_version =
"Ascend950"
...
elif
re.search(
"Ascend310B"
, device_name, re.I):
# L1051
soc_version =
"Ascend310B"
elif
re.search(
"Ascend950"
, device_name, re.I):
# L1053  ← 永不执行
soc_version =
"Ascend950"
elif 自上而下取第一个成立分支，
device_name
在 L1035 赋值后到该链结束前没有任何重新绑定，
re.search
是确定性的，所以 L1045、L1053 两处条件命中时必然已经在 L1041 被取走 —— 是彻底不可达的死分支。风险在于：后来的人给 Ascend950 加处理逻辑时，很容易改到 L1045/L1053 那两份上而完全无效。
判据：可运行的分支选择模拟（不依赖 torch/NPU）
用 AST 取出这条链的 8 个条件（按源码顺序），然后对一批设备名分别模拟"原样"与"删掉两个死分支"两种情况下的分支选择：
'Ascend950PR_958b'  改前 -> L1041 (soc_version='Ascend950')   改后 -> L1041   一致
'Ascend950'         改前 -> L1041                              改后 -> L1041   一致
'ascend950dt_9999'  改前 -> L1041                              改后 -> L1041   一致
'Ascend910B284'     改前 -> L1036 (soc_version='Ascend910B')   改后 -> L1036   一致
'Ascend910_9380E'   改前 -> L1038 (allow_internal_format=True)  改后 -> L1038   一致
'Ascend310P3'       改前 -> L1043                              改后 -> L1043   一致
'Ascend910ProB'     改前 -> L1047 (soc_version='Ascend910A')   改后 -> L1047   一致
'Ascend310B'        改前 -> L1051                              改后 -> L1051   一致
'Huawei Ascend910'  改前 -> else (quit(1) 未支持)               改后 -> else    一致
...
14 个设备名，删除死分支后分支选择不一致数 = 0
并且三个重复分支的分支体逐字相同（
ast.unparse
比对结果为单一值），所以删除它们不会丢掉任何"本来想做但写错位置"的处理逻辑 —— 这也是我敢直接删而不是改成别的条件的原因。
修改
删掉 L1045-1046、L1053-1054 这两个死分支（各 2 行），保留 L1041 那个生效的；其余分支、顺序、
else: quit(1)
