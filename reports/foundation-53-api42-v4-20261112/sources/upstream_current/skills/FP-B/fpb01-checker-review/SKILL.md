# FP-B01 aclnn 接口检视（fpb01-checker-review）

对用户指定的 aclnn 接口（如 aclnnQuantFlashAttention）做 FP-B01 专项源码检视：先定位算子实现，再按清单逐项核查，每个结论给出**文件 + 行号 + 推导链**证据，命中即出 Bug 卡，输出检视报告。**本模式特殊纪律：① 判定方向只有「过拦」一种——本卡不承载「该拦不拦」，漏拦一律按机理转 FP-B03/B04/B05/B06；② 「合法」是判定的前提，必须先用接口签名 + `docs/aclnn*.md` + 算子声明支持面（`*_def.cpp` / 配置）确认该 dtype/format/quant_mode/布局**确实被支持**，再谈白名单是否拦错；③ 报错关键词 `Not supported` / `Unsupported` 既是触发词也是噪声——真缺陷是「白名单未登记已支持项」，不是「凡是报不支持都算缺陷」；④ 白名单的权威来源是**算子声明支持面与放行提交**，不是 checker 自身，二者不一致才是缺陷。**

## 0. 与相邻模式的边界

| 相邻模式 | 分工 |
|---|---|
| FP-B03（跨仓迁移丢失防御/拦截） | **漏拦方向之一**：迁移时防御分支被删除或被 `skipCheck` 类开关显式跳过；本条只承载**过拦**（合法输入被拒），方向相反 |
| FP-B04（aclnn 必选入参空指针校验缺失） | **漏拦方向之二**：指针面（`nullptr` 未拦）；本条与指针无关 |
| FP-B05（入参校验覆盖度参差） | **漏拦方向之三**：同仓文件级校验范式参差不齐；本条是**单点过严**，不涉及范差 |
| FP-B06（空 tensor 分支缺失） | **漏拦方向之四**：`numel==0` 语义分支；本条的输入是正常非空输入，只是 dtype/模式未被白名单收录 |
| FP-A04（静默错误） | 方向相反：A04 是不报错地算错；本条是**明确报错**（`Not supported`）却把合法输入拒之门外 |

**症状反查定位**：新支持项（dtype / quant_mode / 布局）合入后仍报 `Not supported` → 首查该模式在 checker 白名单中的登记行；同一接口部分 dtype/模式通过、部分报不支持 → 白名单硬编码不全；量化模式（`quant_mode` / `quantmode`）特定取值（如 6）被拒 → 白名单漏登记该取值；报错信息里出现「Unsupported」「not support」但用例在参考框架（PyTorch/ONNX）可跑 → 过拦嫌疑；放开校验后**资料未同步**（`docs/aclnn*.md` 仍写不支持）→ 同族伴生缺陷。判定「漏拦 / 该拦不拦」时**先问是哪一种机理（迁移丢失 / 指针 / 覆盖度 / 空输入），再打对应标签**，不要挂到本条。

## 1. FP-B01 模式卡摘要（检视依据，源自本库 `patterns/FP-B/FP-B01.md`，v3.1）

- **编号 / 名称**：FP-B01 支持面校验过严误拦截合法输入 ｜ **类别**：功能/兼容 ｜ **风险**：中（S2×O2=4）｜ **状态**：活跃
- **适用声明头**（照抄卡片）：仓 All ｜ 侧别 All ｜ 载体 Tiling源码,IR与图配置 ｜ 触发 Not supported|Unsupported|OP_CHECK ｜ 默认启用 true
- **skill 核查面**：与卡片载体一致——主检视面为 op_host 的 tiling / infershape 与 `*_def.cpp` 中的 dtype/format/shape/quant_mode 校验分支（`OP_CHECK*` / `CHECK_RET` / 白名单表），延伸至 `config/<soc>/*_binary.json` 的支持面声明与 `docs/aclnn*.md` 的资料一致性；kernel 侧一般不承载本型（除非模板特化清单漏登记）
- **故障机理**：checker 的 dtype/format/shape/quant_mode **白名单硬编码不全或漏登记新支持项**，合法输入被错误拒绝。典型形态：白名单为静态数组 / `switch` 枚举，新增支持项时只改了 kernel 与文档、漏改 checker；或校验按「旧支持面」写死，新量化模式（如 `quant_mode=6`）未收录。
- **触发条件**：新增 dtype / quant_mode / 布局支持后 checker 未同步；量化模式取值扩展；跨芯片形态引入新 format；白名单由硬编码清单而非单一事实源推导。
- **典型表现**：合法输入报 `Not supported` / `Unsupported`；同一接口部分 dtype/模式通过、部分被拒；参考框架可跑而 NPU 侧第一段接口直接拒绝；放开校验后资料（`docs`）未同步。
- **源码审查映射点**：dtype/format/shape 白名单、硬编码校验清单与实际支持面的一致性；新支持项合入时 checker 是否同步放开。
- **检测签名**：`Not supported|Unsupported|not support`（报错点，**须人工确认被拒输入是否合法**）；dtype/format/quant_mode 白名单容器（`std::set` / `std::vector` / `switch`）与 `*_def.cpp` 的 `DataType` / `Format` / `Attr` 声明集合做**差集扫描**（差集非空即漏登记嫌疑）；`quant_?mode` 枚举常量与校验分支取值集合差集。
- **测试拦截建议**：每次放开新支持项后，二级冒烟必跑该 dtype/模式**全矩阵（正反向）**；正向矩阵（已声明支持的 dtype/format/quant_mode 组合应全部通过）与反向矩阵（确实不支持的组合应报 `Not supported`）成对建设；资料同步检查（`docs` 与实现一致）纳入合入门禁。
- **实证案例**：ops-transformer **#4934 / PR !11201** `quant_flash_attention` 的 `quantmode=6` 被 checker 硬编码白名单错误拦截（报错含 `Not supported`/`Unsupported` 关键词误判），修复为放开校验 + 资料同步 + 二级冒烟验证。
- **关联**：**「不该拦却拦」与「该拦不拦」的完整分工**——本卡只承载**过拦**方向；**漏拦方向按机理拆到四条**：FP-B03（跨仓迁移丢失防御/拦截逻辑，含「校验被显式跳过」）、FP-B04（aclnn 必选入参空指针校验缺失）、FP-B05（入参校验覆盖度参差，同仓文件级）、FP-B06（空 tensor（numel==0）输入分支处理缺失）。判定「漏拦 / 该拦不拦」类问题时，**先问是哪一种机理（迁移丢失 / 指针 / 覆盖度 / 空输入），再打对应标签**。

## 2. 检视输入与算子定位

**输入**：aclnn 接口名（必填，如 `aclnnQuantFlashAttention`）；可选 ref（默认 master）、指定仓（默认自动定位）；可选现象描述（报错原文 / 被拒的 dtype 或 quant_mode 取值——用于症状反查）；可选「声明的支持面」（接口签名 / `docs` / `*_def.cpp` 中声明的 dtype/format/模式——判定的前提）。

**接口名 → 算子目录换算**：去 `aclnn` 前缀 + 驼峰转下划线小写：
`aclnnQuantFlashAttention → quant_flash_attention`、`aclnnRmsNorm → rms_norm`、`aclnnQuantMatmulV5 → quant_matmul_v5`。**目录名以目录列表为准**：仓内可能存在简写/别名目录（如 quant flash attention 系列存在 `quant_flash_attn` 等命名），换算结果需用目录列表确认后再进入。

**仓定位顺序**（GitCode `cann` 组织，逐仓用目录列表确认）：`ops-transformer`（attention/moe 类，量化注意力高发）→ `ops-nn`（norm/loss/activation/matmul 类）→ `ops-math`（math/conversion 类）→ `ops-cv`（image/vision 类）。**类目名不总与直觉一致**，以目录列表为准。FP-B01 高发面：带 quant_mode / 量化 dtype 枚举的 checker、dtype/format 白名单静态表、刚放开新支持项的算子、checker 与 `*_def.cpp` 声明支持面各写一份的算子。

**算子目录结构约定**（已验证示例 `cann/ops-transformer` → `attention/quant_flash_attention/`；`cann/ops-nn` → `norm/rms_norm/`）：

```text
{类别}/{op_name}/
├── op_host/                  # *_def.cpp（原型/支持面声明）、*_infershape.cpp、*_tiling*.cpp——白名单与校验分支主检视面
│   └── config/<soc>/         # *_binary.json（各 SOC 的支持面与模板声明）
├── op_api/（或 op_host/op_api/）  # aclnn_*.cpp（入口校验：报错点定位）
├── op_kernel/                # 模板特化清单（支持面的实际实现面，用于与白名单对差集）
├── docs/                     # aclnn*.md（声明支持面与报错行为——判定「合法」的依据，资料同步面）
└── tests/ examples/ CMakeLists.txt
```

## 4. 过拦检视清单（每点：查什么 → 何处 → 命中判据）

对算子的 op_host（tiling + infershape + def）/ op_api / config / docs 逐点核查，**每点先查命中面、再做反证排除**，已有的白名单与放行逻辑也要记录（防护面证据）。

### ① 白名单与声明支持面的一致性（差集扫描）
- 查什么：dtype / format / shape / quant_mode 白名单容器（静态数组、`std::set`、`switch` 枚举）所允许的取值集合，与 `*_def.cpp` 的 `DataType`/`Format` 声明、`config/<soc>/*_binary.json` 的支持面、`docs/aclnn*.md` 的支持矩阵做**双向差集**——「声明支持但白名单未收录」即过拦命中。
- 何处：op_host 的 checker / 校验函数、`*_def.cpp` 的数据类型与属性声明、config 各 SOC 声明、docs 支持矩阵。
- 命中判据：存在某 dtype/format/quant_mode 取值 ∈ 声明支持面 ∉ 白名单（且该取值有 kernel 模板可承载）⇒ 命中（给出「取值 → 声明支持处行号 → 白名单未收录处行号」对表）。

### ② 新支持项合入时 checker 同步放开
- 查什么：新增 dtype/quant_mode/布局的合入提交是否**同步改 checker**——只改 kernel/文档而未改白名单，是 #4934 的根因形态；量化模式枚举扩展（如新增取值 6）后校验分支取值集合是否随之扩展。
- 何处：checker 的 `quant_?mode` 校验分支、dtype/format 允许列表；同族算子的放行样板。
- 命中判据：能写出「某新支持项 → 已在 kernel/def/docs 声明 → checker 校验仍按旧集合拒绝」的推导链 ⇒ 命中（实证样板 #4934 `quantmode=6`）。

### ③ 硬编码校验清单与实际支持面脱节
- 查什么：白名单是否**硬编码**（而非由单一事实源推导）——硬编码清单更易在支持面扩展时漂移；`OP_CHECK*` / `CHECK_RET` 的拒绝分支是否引用硬编码集合；是否存在「同一支持面在 def、config、checker 各写一份」的多副本。
- 何处：checker 内的静态表 / `switch` / 条件链；def 与 config 的重复声明点。
- 命中判据：白名单为硬编码且与声明支持面存在副本不一致 ⇒ 命中（至少立「支持面多副本」观察项并给出漂移点）。

### ④ 报错点与关键词误判
- 查什么：`Not supported` / `Unsupported` 报错点**归属的判定条件**——是否把「未登记」与「确实不支持」混为一谈（前者是过拦，后者是正确行为）；报错信息是否可区分二者（便于用户/CI 定位）。
- 何处：全部含 `Not supported|Unsupported|not support` 的拒绝分支。
- 命中判据：拒绝分支的条件集合 > 声明支持面的补集（即把合法项一并拒掉）⇒ 命中；报错不可区分时记观察项（可观测性）。

### ⑤ 资料与报错行为同步（伴生面）
- 查什么：放开校验后 `docs/aclnn*.md` 是否同步更新支持矩阵（#4934 修复含「资料同步」）；文档写不支持而代码已支持，或反之。
- 何处：`docs/aclnn*.md` 的支持矩阵与限制说明；`*_def.cpp` 声明。
- 命中判据：文档与实现/checker 不一致 ⇒ 记观察项（资料面），与命中项一并上报。

### ⑥ 正反向冒烟覆盖（测试建设面）
- 查什么：每次放开新支持项后，是否跑该 dtype/模式**全矩阵（正反向）**；存量用例是否只覆盖旧支持面（缺口现存证据）。
- 何处：`tests/` 用例的 dtype/format/quant_mode 取值清单；二级冒烟配置。
- 命中判据：新支持项无正向用例（或旧白名单被误拒的组合无用例）⇒ 记观察项（测试建设项）。

## 5. 检视流程

1. **定界**：换算 op 目录并用目录列表确认实际目录名、确认所在仓与 ref；按用户报错原文反查优先清单点；先确立**声明支持面集合**（接口签名 + `*_def.cpp` + `config` + `docs`）。
2. **枚举**：目录列表列出 op_host（tiling + infershape + def）/ op_api / config / docs / tests 全部相关文件，产出文件清单。
3. **触发词扫描**：按 `Not supported|Unsupported|not support`、dtype/format 白名单容器、`quant_?mode`、`OP_CHECK`、`CHECK_RET` 定位风险面（本地仓用 grep；API 模式逐文件拉取后检查）。
4. **清单逐项核查**：按第 4 节 ①~⑥ 逐点记录命中面与防护面证据（文件:行号）；对 ① 做**双向差集对表**（声明支持面 vs 白名单取值集合）。
5. **反证排除**：白名单 == 声明支持面（差集为空）、新支持项已同步放开、报错条件集合 == 支持面补集、文档一致 → 明确写出反证理由（防护面证据）。
6. **判定**：按第 7 节标准给出 命中 / 观察项 / 反证排除。
7. **GitCode 查重**（仅命中项）：issues API 按接口名 + `Not supported|Unsupported|不支持|误拦截|白名单` 检索，逐条比对是否同机理；无同机理才立卡。
8. **业务可达性核查**（仅命中项）：判 B 等级、定业务影响类型、给处置建议；默认保守（无法证明不可达即记 B3），降档须附证据；B 不改 S×O 档位。
9. **出报告**：按第 8 节模板落盘；静态结论一律附**正反向冒烟矩阵**方案（声明支持的组合应全通过，未声明组合应明确报不支持）。

## 6. 风险定级（S×O）与业务影响评估（B 轴）

- **S**：S2（合法输入被误拦——功能不可用，但不崩溃、不损坏数据）；S1（仅报错信息不可区分 / 文档不一致等可观测性、资料面问题）。
- **O**：O3 = ≥2 条独立实证；O2 = 1 条独立实证；O1 = 仅静态扫描命中或团队笔记（实证 = 确认对应的 issue / PR，或经跨仓、跨分支核验确认的缺陷记录，同权计入）。静态推演命中且无实证默认 **O1**；升档须在报告中给出实证依据。
- **风险 = S×O**：≥6 高；3/4 中；1/2 低。FP-B01 基准：模式卡整体 S2×O2=4（中）；纯静态命中 S2×O1=2（低，暂定，放行提交或实测确证后复评）。

### B 轴：业务影响评估（与 S×O 正交；报告层新增，不改卡片定级）

S×O 回答"多严重、多常见"，**不回答"真实业务能不能碰到"**。B 轴补这一问，只决定**修复优先级建议**，**不参与 S/O 取值、不改 S×O 档位与卡片元数据**。

**业务可达性（B）**——触发条件在真实负载中的可达程度：

| 等级 | 判据 | 证据要求 |
|---|---|---|
| B3 现实可达 | 主流框架/公开模型默认路径即可命中（如 PTA/torch_npu、vLLM、MindIE 常规调用） | 调用方或公开负载来源 |
| B2 条件可达 | 需特定 attr/dtype/shape 组合，业务中存在但非默认 | 该组合的业务来源 |
| B1 边界/不可达 | 需极端、超规格或非法参数（超出接口合理上限的 shape、退化/非法输入） | "为何不可达"的说明 |

- **默认保守**：无法证明不可达 → 记 **B3**；降为 B1/B2 必须附证据，**不得仅凭"业务应该不会这么用"**。
- 超规格参数是否算 B1 取决于**接口契约**：契约允许但业务不用 → B1；契约不允许（本应报错）→ 属校验缺失（FP-B04/B05 类），另行归属。

**业务影响类型**（命中后对用户可见结果的后果，用业务语言表述）：静默精度损失（模型效果下降 / loss 不收敛 / 偶发 NaN）｜ 任务失败中断（报错 / 崩溃 / 挂死）｜ 性能退化 ｜ 仅可观测性（日志 / 错误码 / 文档，不影响结果）。

**处置建议**（由两轴推导的报告结论，非新档位）：

| S×O \ B | B3 现实可达 | B2 条件可达 | B1 边界/不可达 |
|---|---|---|---|
| 高（≥6） | 尽快修 | 尽快修 | 排期修 |
| 中（3/4） | 尽快修 | 排期修 | 记录（业务难以触达） |
| 低（1/2） | 排期修 | 记录 | 记录 |

## 7. 判定标准与反误报原则

- **报错 ≠ 缺陷**：报 `Not supported` 只表示「被拒」，是否为缺陷取决于该输入是否**合法**——必须先立声明支持面集合，`拒绝集合 ⊇ 支持面` 才是过拦。**不做差集对表就不下过拦结论。**
- **三种判定**：
  - **命中**（可静态证缺陷路径）：「声明支持 ∉ 白名单」「新支持项未同步放开」「拒绝条件集合超出支持面补集」的完整推导链 → 立 Bug 卡；
  - **观察项**：白名单硬编码但差集暂为空、报错不可区分、文档不一致、正反向用例缺口 → 记录并附复核方案，不定为命中；
  - **反证排除**：白名单与声明支持面差集为空、新支持项已放开、拒绝集合恰为补集 → 写出防护面证据。
- **漏拦方向转卡**：判定「该拦不拦」时按机理分流（迁移丢失 → B03；指针 → B04；覆盖度 → B05；空输入 → B06），不在本条立卡。
- **支持面多副本须给漂移点**：def / config / checker 各写一份支持面时，须给出各副本的具体位置与不一致项，而非泛泛「存在硬编码」。
- **不臆造行号**：每条证据必须是实际读到的 文件:行号；引用实证样板（#4934 / PR !11201）时给出其在卡片中的位置，issue 时点行号与本仓 HEAD 漂移时注明。

### 判定纪律补充（v3.6）：非对称增减、证据等级与误判记录

**增减不对称**：允许追加候选（有据即可，错了可由用户排除）；**撤销或否决候选必须附 `[文件]:[行号] [代码行]` 负向证据**。无证据的「看起来没问题」一律记为「未核查」，不得计入反证排除，也不得据此下调等级——否决造成的漏报用户不可见、不可恢复。

- **证据等级**（Bug 卡必填）：`静态可证` = 推导链完整且触发输入可静态构造；`需实测确认` = 依赖运行时输入规模、设备行为或环境差异。标 `需实测确认` 的条目**不得以「命中」名义出卡**，按观察项记录并附实测用例。
- **Agent 误判记录**（Bug 卡必填）：本次被推翻的假设、推翻它的证据（`[文件]:[行号] [代码行]` 或实测输出）、判定标准是否随之修订；无推翻写「无」。
- **误判回流**：同类误判在 3 次检视中重复出现，登记至 `cases/misjudgments.jsonl`（字段见 `cases/README.md`），并在本模式判定标准中新增对应防线；守门 C19d 校验台账字段合法。

## 9. 示例速览：quant_flash_attention

- **定位**：`cann/ops-transformer` → `attention/` 下的 quant flash attention 系列（卡片记为 `quant_flash_attention`；仓内目录名以目录列表为准，如同族 `quant_flash_attn` / `quant_flash_attn_grad` / `quant_flash_attn_metadata`）。关键文件：op_host 的 `*_tiling*.cpp`（checker / 校验分支）、`*_def.cpp`（dtype 与属性声明）、`config/<soc>/*_binary.json`、`docs/aclnn*.md`。
- **检视面提示**（引导，不预设结论，仍须逐点核查；行号以本地 HEAD 为准）：
  - 清单点①：把 checker 中 dtype / format / `quant_?mode` 白名单的取值集合，与 `*_def.cpp` 声明、config 支持面、docs 支持矩阵做**双向差集**——实证 #4934 即 `quantmode=6` 属已支持但未被白名单收录，被报 `Not supported`/`Unsupported` 误拦截；
  - 清单点②：核对「放开新支持项」的提交（PR !11201 形态）是否同步改了 checker 与 docs，还是只改了 kernel；
  - 清单点③：白名单若为硬编码集合，给出其与 def/config 支持面的副本漂移点；
  - 清单点④：检查报错点是否把「未登记」与「确实不支持」混判，报错信息可否区分；
  - 清单点⑤：docs 的支持矩阵是否与放开后的实现一致（#4934 修复含「资料同步」）；
  - 清单点⑥：二级冒烟是否覆盖该 quant_mode 的正向与反向矩阵。
- 任何一点的最终判定以第 4/5/7 节口径为准，禁止凭算子类型直接下结论。

## 10. 能力边界与自检（v3.8）

### 能力边界

- **静态可证**：清单里能在源码内给出「`文件:行号` + 推导链」的部分，按第 7 节判据出卡。
- **需实测确认**：依赖运行时输入规模、设备行为或环境差异的结论，只能记观察项并附实测用例（证据等级见第 7 节）。
- **不覆盖**：本模式以外的机理（边界见第 0 节）与仓外框架侧行为；`TRIAGE.md` 只负责收敛候选，不构成判定依据。
- **找不到 ≠ 没有**：按清单未命中只说明「本轮未发现」，不得表述为「该算子无此缺陷」；抽样核查须在报告写明抽样口径。

### 自检

```bash
python3 scripts/gen_triage.py --check                          # 分诊表与映射一致
python3 scripts/scan_fp.py --only FP-B01 --format json <目标文件>  # 签名候选（非结论）
python3 scripts/verify_lines.py <报告.md> --root <被检仓>        # 行号校验
python3 check_fault_patterns.py                                # 全库守门
```

### 工作量与抽样（v4.0）

- **深度档：标准**（索引 `depth` 字段）——每映射点取前 20 处命中；同一映射点连续 20 处反证排除即停止该点并记录。报告须写「抽样口径：每点前 20 处」。
- **报告必填**：抽样口径（全量 / 每点前 N 处 / 每类 N 例）+ 停止点记录；未写口径视为未完成。
