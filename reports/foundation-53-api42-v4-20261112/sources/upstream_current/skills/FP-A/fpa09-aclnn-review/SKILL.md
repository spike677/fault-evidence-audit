# FP-A09 aclnn 接口检视（fpa09-aclnn-review）

对用户指定的 aclnn 接口做 FP-A09 专项源码检视：先定位算子实现，再按清单逐项核查，每个结论给出**文件 + 行号 + 推导链**证据，命中即出 Bug 卡，输出检视报告。**本模式特殊纪律：① 缺陷是「对标框架选错」——算子以 TF 语义实现，而 torch_npu（PTA）API 的 attr 默认值、clip/epsilon/nan 处理与 TF 存在差异，表现为「精度不过」而非报错；② 触发签名 `epsilon|clip` 只是**检索起点**（卡片实证为「待补充」，无确认实证算子），命中只表示「值得人工核」，判定必须落到「torch_npu 参考语义 vs 本实现语义」的差异推导；③ 语义差异需与 torch 参考实现逐项对表——单靠本仓源码无法确证「选错对标」，须交叉核对 torch_npu 文档/参考实现；④ 与 A15（inf/nan 特殊值）交界：nan 处理差异若源于对标选错归本条，若为数值传播本身归 A15。**

## 0. 与相邻模式的边界

| 相邻模式 | 分工 |
|---|---|
| FP-A15（inf/nan 特殊值行为差异） | **最易混淆项**：A15 管 inf/nan **数值传播与处理语义本身**；A09 管「**选错对标框架**」导致语义面（attr 默认值、clip/epsilon/nan 处理）与 torch 参考不一致——nan 处理差异可两者共因，按「是否源于对标选错」归属，报告双向关联 |
| FP-A10（原型 Attr 不支持 Double） | A10 是 double **类型承载/降级**（精度丢失）；A09 是**语义与默认值**对标面（类型相同但语义不同）——按「类型 vs 语义」分 |
| FP-A11（AiCore 不支持 double 类型） | A11 是 double **dtype 底层不支持**；A09 是语义对标——dtype 支持面归 A11 |
| FP-B01（支持面校验过严误拦截合法输入） | B01 是**该放却拦**（校验面）；A09 是**放行了但算得不对**（语义面）——按「拦不拦 vs 算得对不对」分 |
| FP-B02（阈值依赖平台参数跨平台不一致） | B02 是**平台常量来源**差异（同一语义、不同常量）；A09 是**对标框架语义**差异（同一平台、不同框架语义） |
| FP-E01（golden/UT 期望值失配） | UT golden 若以**同一错误对标**生成则天然漏检本型——须与 torch_npu 官方参考语义交叉核对，不能只与本仓 golden 比 |

**症状反查定位**：epsilon 类参数在小值域（如 1e-8 级）下精度异常 → epsilon 语义/默认值面（清单③）；clip 边界行为与 torch 参考不一致 → clip 语义面（清单②）；attr 缺省传入时结果与 torch 默认行为不符 → attr 默认值面（清单①）；输入含 nan/inf 时输出与 torch 参考不同 → nan/inf 处理语义面（清单④，与 A15 交界）；多框架对标算子（同时对齐 TF 与 torch_npu）精度不过 → 对标框架选择面（清单⑤）。

## 1. FP-A09 模式卡摘要（检视依据，源自本库 `patterns/FP-A/FP-A09.md`，v3.1）

- **编号 / 名称**：FP-A09 对标 TF 语义与 PTA（torch_npu）不一致 ｜ **类别**：精度 ｜ **风险**：中（S3×O1=3）｜ **状态**：活跃
- **适用声明头**（照抄卡片）：仓 All ｜ 侧别 All ｜ 载体 aclnn源码 ｜ 触发 epsilon|clip ｜ 默认启用 true
- **skill 核查面**：侧别 All——skill 落地为 `op_api/aclnn_*.cpp`（attr 默认值、clip/epsilon/nan 处理的实现与校验）；延伸至 `op_host` 的 `*_def.cpp`（attr 默认值定义）与 `docs/` 的语义说明；kernel 侧仅核对语义落地与 aclnn 层是否一致
- **故障机理**：算子实现以 TF 为参考，而 torch_npu API 语义（attr 默认值、clip/epsilon/nan 处理）与 TF 存在差异，实现选错对标。
- **触发条件**：多框架对标算子、含默认参数与特殊值处理。
- **典型表现**：精度不过。
- **源码审查映射点**：语义对齐：attr 默认值、clip/epsilon/nan 处理与 torch 参考差异。
- **检测签名**（命中即候选缺陷点位）：`epsilon|clip`（语义对齐检索起点——卡片实证为「待补充」，命中仅作定位提示）。
- **测试拦截建议**：attr 全枚举 + 默认值专项用例；nan/inf 特殊值专项。
- **实证案例**：待补充（卡片明确记录本模式暂无确认实证算子——判定须从严，不得凭触发词命中直接立卡）。
- **关联**：FP-A15。注：PTA 指 PyTorch Ascend 适配（torch_npu）。

## 2. 检视输入与算子定位

**输入**：aclnn 接口名（必填）；可选 ref（默认 master）、指定仓（默认自动定位）；可选现象描述（epsilon 值域 / clip 边界行为 / 是否缺省 attr / 是否含 nan/inf——用于直接定位语义面）；可选 torch_npu 参考语义（对应 torch API 与版本）。

**接口名 → 算子目录换算**：去 `aclnn` 前缀 + 驼峰转下划线小写：
`aclnnLayerNorm → layer_norm`、`aclnnBatchNorm → batch_norm`、`aclnnClipByValue → clip_by_value`（目录名以目录列表为准）。

**仓定位顺序**（GitCode `cann` 组织，逐仓用目录列表确认）：`ops-nn`（norm/activation 类——含 epsilon/clip 类 attr 高发）→ `ops-math`（math/clip 类）→ `ops-transformer` → `ops-cv`。**类目名不总与直觉一致**，以目录列表为准。FP-A09 高发面：norm 类（epsilon）、clip/阈值类、多框架对标算子、含缺省 attr 的接口、nan/inf 特殊值处理算子。

**算子目录结构约定**（具体布局以目录列表为准）：

```text

├── op_api/（或 op_host/op_api/）  # aclnn_*.cpp——attr 默认值与语义处理：主检视面

├── op_kernel/                # 语义落地核对面

```

## 4. 检视清单（每点：查什么 → 何处 → 命中判据）

对算子的 `op_api` / `op_host`（def / infershape / tiling）/ kernel 语义落地逐点核查，`docs/` 同步核对，**每点先查命中面、再做反证排除**；与 torch 参考语义一致的实现要记录为防护面证据。

### ① attr 默认值与 torch_npu 对齐
- 查什么：接口**缺省 attr**（未传时）的取值是否与 torch_npu（torch 参考）默认值一致；`op_host/*_def.cpp` 中 attr 默认值定义与 `op_api` 入口兜底默认值是否一致（两处不一致即高风险）；`docs/aclnn*.md` 中记录的默认值是否与实现一致。
- 何处：`op_api` 的 attr 取值与默认兜底、`*_def.cpp` 的 attr 默认值定义、`docs/`。
- 命中判据：能写出「缺省场景下本实现默认值 ≠ torch 参考默认值 → 结果差异」的推导 ⇒ 命中候选（须附 torch 参考对照）。

### ② clip 语义对齐
- 查什么：`clip` / 裁剪类参数的**语义与执行顺序**——裁剪范围端点包含性、裁剪与其余计算的先后、`min > max` 等退化情形的处理是否与 torch 参考一致；是否存在 TF 风格的裁剪语义被套用到 torch_npu 接口。
- 何处：`op_api` 的 clip 处理、kernel 的裁剪实现。
- 命中判据：裁剪语义/顺序与 torch 参考不一致 ⇒ 命中候选。

### ③ epsilon 语义对齐
- 查什么：`epsilon` 的**默认值、作用位置、加法/开方下的插入点**是否与 torch 参考一致（如 norm 中 `sqrt(var + eps)` vs `sqrt(var) + eps`）；epsilon 小值域（1e-8 级）下的处理是否丢失（与 A10/A11 的 double 降级交界，须区分「语义位置错」与「精度承载不足」）。
- 何处：`op_api` / kernel 的 epsilon 使用点、`*_def.cpp` 默认值。
- 命中判据：epsilon 作用位置或默认值与 torch 参考不一致 ⇒ 命中候选。

### ④ nan / inf 处理语义（与 A15 交界）
- 查什么：输入/中间含 nan、inf 时的处理（是否传播、是否被 clip 吞掉、是否置 0）是否与 torch 参考一致；是否源于「按 TF 语义实现」。
- 何处：`op_api` / kernel 的特殊值处理段。
- 命中判据：nan/inf 行为与 torch 参考不同**且源于对标选错** ⇒ 归本条；若为数值传播本身 ⇒ 转 A15。

### ⑤ 对标框架选择与文档依据
- 查什么：算子/接口在 `docs/` 与注释中标注的对标对象是 TF 还是 torch_npu；多框架对标算子是否存在「以 TF 语义实现、却暴露给 torch_npu 接口」的错配；接口命名/attr 命名是否暗示 torch 语义而实现按 TF。
- 何处：`docs/`、代码注释、`op_api` 入口。
- 命中判据：存在「对标对象与接口目标框架不一致」的证据 ⇒ 命中候选。

### ⑥ attr 全枚举与特殊值用例覆盖
- 查什么：`tests/` 是否有 attr **全枚举 + 默认值**专项用例、nan/inf 特殊值专项用例；用例的 golden 是否来自 torch_npu 官方参考（而非同源错误实现）。
- 何处：`tests/` 的精度用例与 golden 来源。
- 命中判据：缺默认值/nan/inf 用例、或 golden 与实现同源 ⇒ 记观察项（测试面缺口）。

## 5. 检视流程

1. **定界**：换算 op 目录、确认所在仓与 ref；记录用户现象（epsilon 值域 / clip 行为 / 缺省 attr / nan-inf）。
2. **枚举**：目录列表列出 `op_api` / `op_host` / kernel 相关文件与 `docs/`、`tests/`，产出文件清单。
3. **触发词扫描**：按 `epsilon|clip`、`nan|inf|isnan|isinf`、attr 默认值定义定位风险面（本地仓用 grep；API 模式逐文件拉取后检查）。**触发为检索起点：卡片实证待补充、签名零命中时清单仍须逐项核查完毕**。
4. **逐点核查**：按第 4 节 ①~⑥ 记录命中面与防护面证据（文件:行号）；对每个语义点给出「本实现 vs torch 参考」对表。
5. **反证排除**：attr 默认值/epsilon 作用位置/clip 语义/nan-inf 处理均与 torch 参考一致、对标对象标注正确 → 明确写出反证理由。
6. **判定**：按第 7 节标准给出 命中 / 观察项 / 反证排除（**无实证纪律：一律按观察项暂定，不直接立卡**）。
7. **GitCode 查重**（仅命中项）：issues API 按接口名 + `精度|语义|默认值|epsilon|clip|对标` 检索，逐条比对是否同机理；无同机理才立卡。
8. **业务可达性核查**（仅命中项）：判 B 等级、定业务影响类型、给处置建议；默认保守（无法证明不可达即记 B3），降档须附证据；B 不改 S×O 档位。
9. **出报告**：按第 8 节模板落盘；所有结论标注「静态推演，需与 torch_npu 参考语义对表 + 专项用例实测确认」并附对表方案。

## 6. 风险定级（S×O）与业务影响评估（B 轴）

- **S**：S3（语义不一致致精度不过——结果错但可运行）；S2（仅缺省/特殊值场景可见的语义差异）；S1（语义差异不影响结果）。
- **O**：O3 = ≥2 条独立实证；O2 = 1 条独立实证；O1 = 仅静态扫描命中或团队笔记（实证 = 确认对应的 issue / PR，或经跨仓、跨分支核验确认的缺陷记录，同权计入）。静态推演命中且无实证默认 **O1**；升档须在报告中给出实证依据。本模式卡实证为「待补充」：当前一律 O1；torch 参考对表完整 + 专项用例实测复现并确认缺陷后方计独立实证。
- **风险 = S×O**：≥6 高；3/4 中；1/2 低。FP-A09 基准：模式卡整体 S3×O1=3（中）；纯静态命中 S3×O1=3（中，暂定，对表实测后复评）。

### B 轴：业务影响评估（与 S×O 正交；报告层新增，不改卡片定级）

S×O 回答"多严重、多常见"，**不回答"真实业务能不能碰到"**。B 轴补这一问，只决定**修复优先级建议**，**不参与 S/O 取值、不改 S×O 档位与卡片元数据**。

**业务可达性（B）**——触发条件在真实负载中的可达程度：

| 等级 | 判据 | 证据要求 |
|---|---|---|
| B3 现实可达 | 主流框架/公开模型默认路径即可命中（如 PTA/torch_npu、vLLM、MindIE 常规调用） | 调用方或公开负载来源 |
| B2 条件可达 | 需特定 attr/dtype/shape 组合，业务中存在但非默认 | 该组合的业务来源 |
| B1 边界/不可达 | 需极端、超规格或非法参数（超出接口合理上限的 shape、退化/非法输入） | "为何不可达"的说明 |

- **默认保守**：无法证明不可达 → 记 **B3**；降为 B1/B2 必须附证据，**不得仅凭"业务应该不会这么用"**。
- 超规格参数是否算 B1 取决于**接口契约**：契约允许但业务不用 → B1；契约不允许（本应报错）→ 属校验缺失（FP-B04/B05 类），另行归属。

**业务影响类型**（命中后对用户可见结果的后果，用业务语言表述）：静默精度损失（模型效果下降 / loss 不收敛 / 偶发 NaN）｜ 任务失败中断（报错 / 崩溃 / 挂死）｜ 性能退化 ｜ 仅可观测性（日志 / 错误码 / 文档，不影响结果）。

**处置建议**（由两轴推导的报告结论，非新档位）：

| S×O \ B | B3 现实可达 | B2 条件可达 | B1 边界/不可达 |
|---|---|---|---|
| 高（≥6） | 尽快修 | 尽快修 | 排期修 |
| 中（3/4） | 尽快修 | 排期修 | 记录（业务难以触达） |
| 低（1/2） | 排期修 | 记录 | 记录 |

## 7. 判定标准与反误报原则

- **签名 / 触发词命中 ≠ 成立**：`epsilon`/`clip` 在 norm/clip 类算子中普遍存在且多数与 torch 一致——命中只是检索起点，必须给出「本实现语义 vs torch 参考语义」的差异推导并交叉核对 torch_npu 文档/参考实现。
- **三种判定**：
  - **命中**（可静态证缺陷路径）：「attr 默认值 / epsilon 作用位置 / clip 语义 / nan-inf 处理与 torch 参考不一致且源于对标选错」的推导链完整 + torch 参考对照可复现 → 立 Bug 卡；
  - **观察项**：语义疑似不一致但需 torch 参考对表或实测确认（**本模式无实证，默认按观察项暂定**）→ 记录并附对表方案；
  - **反证排除**：语义与 torch 参考逐项一致、对标对象标注正确 → 明确写出反证理由（防护面证据）。
- **无实证纪律**：卡片「实证案例：待补充」——本模式**不得凭触发词命中直接立卡**，须有 torch 参考语义对表 + 专项用例实测支撑才升级。
- **「精度不过」先排除他因**：epsilon 精度问题须先区分「语义位置错」（本条）与「double 降级」（A10/A11）、「nan/inf 传播」（A15）。
- **「与 golden 一致」不是反证**：golden 若与实现同源（同样选错对标）则一致无意义，须与 torch_npu 官方参考语义交叉核对。
- **不臆造行号**：每条证据必须是实际读到的 文件:行号；引用 torch 参考时注明来源与版本。

### 判定纪律补充（v3.6）：非对称增减、证据等级与误判记录

**增减不对称**：允许追加候选（有据即可，错了可由用户排除）；**撤销或否决候选必须附 `[文件]:[行号] [代码行]` 负向证据**。无证据的「看起来没问题」一律记为「未核查」，不得计入反证排除，也不得据此下调等级——否决造成的漏报用户不可见、不可恢复。

- **证据等级**（Bug 卡必填）：`静态可证` = 推导链完整且触发输入可静态构造；`需实测确认` = 依赖运行时输入规模、设备行为或环境差异。标 `需实测确认` 的条目**不得以「命中」名义出卡**，按观察项记录并附实测用例。
- **Agent 误判记录**（Bug 卡必填）：本次被推翻的假设、推翻它的证据（`[文件]:[行号] [代码行]` 或实测输出）、判定标准是否随之修订；无推翻写「无」。
- **误判回流**：同类误判在 3 次检视中重复出现，登记至 `cases/misjudgments.jsonl`（字段见 `cases/README.md`），并在本模式判定标准中新增对应防线；守门 C19d 校验台账字段合法。

## 9. 示例速览：本模式暂无确认实证算子（签名/触发词起点）

## 10. 能力边界与自检（v3.8）

### 能力边界

- **静态可证**：清单里能在源码内给出「`文件:行号` + 推导链」的部分，按第 7 节判据出卡。
- **需实测确认**：依赖运行时输入规模、设备行为或环境差异的结论，只能记观察项并附实测用例（证据等级见第 7 节）。
- **不覆盖**：本模式以外的机理（边界见第 0 节）与仓外框架侧行为；`TRIAGE.md` 只负责收敛候选，不构成判定依据。
- **找不到 ≠ 没有**：按清单未命中只说明「本轮未发现」，不得表述为「该算子无此缺陷」；抽样核查须在报告写明抽样口径。

### 自检

```bash
python3 scripts/gen_triage.py --check                          # 分诊表与映射一致

python3 scripts/verify_lines.py <报告.md> --root <被检仓>        # 行号校验
python3 check_fault_patterns.py                                # 全库守门
```

### 工作量与抽样（v4.0）

- **深度档：宽浅**（索引 `depth` 字段）——只跑签名定位 + 每类抽 3 例；报告必须写「抽样，非全量」，不得表述为全量检视。
- **报告必填**：抽样口径（全量 / 每点前 N 处 / 每类 N 例）+ 停止点记录；未写口径视为未完成。
