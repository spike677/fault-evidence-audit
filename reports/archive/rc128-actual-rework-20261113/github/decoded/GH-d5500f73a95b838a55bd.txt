[BugFix][Attention] Keep SFA q up-projection batch-invariant past 65536 packed tokens
### What this PR does / why we need it?

`AscendSFAImpl._q_proj_and_k_up_proj` projected `q_nope` with
`npu_transpose_batchmatmul` while `q_nope.shape[0] < TRANSPOSE_BMM_MAX_SUPPORTED_DIM`
(65536), and fell back to `transpose -> torch.bmm -> transpose` otherwise.

`q_nope.shape[0]` is the token count of the *current launch*, i.e. the packed
prefill batch, not the length of a single request. Since the two paths do not
round identically, the same prompt got a different projection as soon as one
prefill step packed 65536 tokens or more. With `VLLM_BATCH_INVARIANT=1` that is a
batch-invariance violation: BS=1 and BS=N produce different logits for the same
request, and the first sampled token already diverges.

This PR always uses the fused operator, but launches it on a fixed token grid of
`TRANSPOSE_BMM_CHUNK` = `TRANSPOSE_BMM_MAX_SUPPORTED_DIM - 1` tokens. The split is
sound because the fused op is row independent; the grid size is deliberately the
largest launch the old guard already allowed, so **any token count that already
took a single launch keeps exactly one launch with unchanged arguments** -- the
only shapes whose behaviour changes are the ones that used to fall back to
`torch.bmm`. The `torch.bmm` path is kept only for unsupported dtypes and for
`torch_npu` builds without the fused op.

Measurements on Ascend 910 (A3, build platform `ascend910_93`), torch_npu
2.10.0.post4, GLM-5.x DSA models:

- The two paths disagree on identical input at identical T: 7622 / 167,772,160
  bf16 elements differ, max_abs = 2^-11 (one bf16 ulp). Both paths are
  self-consistent across repeats, so this is a real rounding difference, not
  noise.
- The fused op is bitwise row independent: a fixed set of rows gives identical
  output for T = 8192, 32768, 61440, 65000, 65640 and 66048. `_v_up_proj`, which
  has no such guard, has always used it at large T.
- The grid split is bitwise identical to a single launch: 537,722,880 elements
  compared, 0 differences.
- End-to-end with an equivalent runtime patch (same fixed-grid split), TP=4,
  BS=8, prompt 20480 / max_tokens 2048, `max_num_batched_tokens=131072`:
  without the change 6/8 prompts fail, with it all 8 pass; likewise for the
  authoritative TP=4 / BS=64 shape (whole harness passes) and for the
  65072-vs-65712 packed-token knee.

`_v_up_proj` is intentionally left untouched: it has no T guard today and was
measured to work at large T. Chunking it as well would be a behaviour-neutral
cleanup, better done separately.

### Does this PR introduce _any_ user-facing change?

No API or interface change. The only behaviour change is the corrected numerics
for packed prefills that previously switched to the `torch.bmm` fallback, which is
the bug being fixed.

### How was this patch tested?

New unit test `tests/ut/attention/test_sfa_batch_invariant_up_proj.py`:

- `test_method_uses_the_fused_grid_not_the_bmm_fallback` drives
  `_q_proj_and_k_up_proj` itself with a bf16 input and makes `torch.bmm` raise, so
  the test fails if the projection ever takes the fallback again;
- `test_every_launch_uses_the_fixed_grid` asserts the number of launches is
  `ceil(T / chunk)` and every launch is `<= chunk`, for T = chunk-1, chunk,
  chunk+1, 65712;
- `test_a_row_is_unaffected_by_the_packed_batch` asserts a row's output is
  unchanged when the same rows are packed into a batch 3x larger;
- `test_chunk_stays_under_the_operand_limit` asserts
  `0 < TRANSPOSE_BMM_CHUNK <= TRANSPOSE_BMM_MAX_SUPPORTED_DIM`.

The helper is exercised with a recording stand-in for
`npu_transpose_batchmatmul`, so the tests run on CPU. End-to-end validation was
done on A3 with GLM-5.2 / GLM-5.1 as described above.
