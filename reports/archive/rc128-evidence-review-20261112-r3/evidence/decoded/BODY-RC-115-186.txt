### Environment

- Hardware: Atlas 950DT (Ascend 950DT, 8x96GB HBM)
- torch_npu: 2.10.0.post7, CANN 9.2.1 (docker image quay.nju.edu.cn/ascend/vllm-ascend:v0.30.0-a5), Python 3.12, aarch64
- Mode: eager, single NPU

### Steps to reproduce

The script below runs the same fp32 attention-like computation (einsum -> masked_fill(-inf) -> softmax -> nan_to_num -> einsum) 10 times on identical inputs. Outputs are not deterministic: repeats fall into 2-3 distinct result variants.

```python
import logging

import torch
import torch_npu


def keep_set(selected_key_ids, query_start, query_count, key_count, window, sink, device):
    query_positions = query_start + torch.arange(query_count, device=device)
    key_positions = torch.arange(key_count, device=device)
    read_mask = torch.zeros(query_count, key_count, dtype=torch.bool, device=device)
    read_mask.scatter_(
        1,
        selected_key_ids.clamp_min(0).long(),
        selected_key_ids != -1,
    )
    read_mask |= (query_positions[:, None] - key_positions[None, :] < window) | (
        key_positions[None, :] < sink
    )
    read_mask &= query_positions[:, None] >= key_positions[None, :]
    return read_mask


def topk_attention(q, k, v, selected_key_ids, window, sink, scale, query_start=0, query_block_size=128):
    batch_size, query_count, query_head_count, head_dim = q.shape
    key_count = k.shape[1]
    kv_head_count = k.shape[2]
    query_to_kv_head = torch.arange(query_head_count, device=q.device) // (query_head_count // kv_head_count)
    output = torch.empty_like(q)
    for batch_index in range(batch_size):
        keys_by_query_head = k[batch_index].float()[:, query_to_kv_head, :]
        values_by_query_head = v[batch_index].float()[:, query_to_kv_head, :]
        for query_block_start in range(0, query_count, query_block_size):
            query_block_end = min(query_block_start + query_block_size, query_count)
            read_mask = keep_set(
                selected_key_ids[batch_index, query_block_start:query_block_end],
                query_start + query_block_start,
                query_block_end - query_block_start,
                key_count,
                window,
                sink,
                q.device,
            )
            attention_logits = (
                torch.einsum(
                    "qhd,shd->qhs",
                    q[batch_index, query_block_start:query_block_end].float(),
                    keys_by_query_head,
                )
                * scale
            )
            attention_probabilities = torch.softmax(
                attention_logits.masked_fill(~read_mask[:, None, :], float("-inf")),
                dim=-1,
            )
            output[batch_index, query_block_start:query_block_end] = torch.einsum(
                "qhs,shd->qhd",
                torch.nan_to_num(attention_probabilities),
                values_by_query_head,
            ).to(q.dtype)
    return output


logging.basicConfig(level=logging.INFO, format="%(asctime)s %(message)s")
torch.manual_seed(101)
DEV = "npu"
B, TQ, HQ, HKV, D = 2, 64, 8, 2, 64
TK, WINDOW, SINK, BUDGET = 4096, 128, 0, 64
SCALE = D ** -0.5

q = torch.randn(B, TQ, HQ, D).to(DEV, torch.bfloat16)
k = torch.randn(B, TK, HKV, D).to(DEV, torch.bfloat16)
v = torch.randn(B, TK, HKV, D).to(DEV, torch.bfloat16)
sel = torch.randint(0, TK - TQ, (B, TQ, BUDGET), dtype=torch.int32).to(DEV)
sel[:, :, : BUDGET // 8] = -1

outs = []
for i in range(10):
    outs.append(topk_attention(q, k, v, sel, WINDOW, SINK, SCALE, query_start=TK - TQ))
    torch.npu.synchronize()

mx = max((outs[0].float() - outs[i].float()).abs().max().item() for i in range(1, 10))
logging.info("max diff across 10 repeats: %.5f", mx)
```

### Observed behavior

- Repeats produce distinct outputs: most runs land on one of two stable variants. Typical per-repeat max diff vs the first call: 0.0155 (21 of 128 query rows differ), occasionally 0.0259 (34 rows). Max diff across 10 repeats: **0.0259** (bf16 outputs, values order ~0.7).
- Deviations appear on a small subset of query rows only and look like single softmax keys losing their weight (error magnitude ~ one key's contribution).
- Not a seeding issue: inputs are created once and reused; only the op sequence is repeated.
- A near-identical inline reimplementation of the same math (same shapes, same dtype flow, same masking) is fully deterministic across 10 repeats (max diff 0.0000) — the nondeterminism appears sensitive to how the mask / intermediate tensors are constructed (e.g. the extra `| (key_positions < sink)` term or tensor lifetime/layout), which suggests a varying kernel selection or a race rather than a mathematical property.

### Expected behavior

Repeated evaluation of the same deterministic fp32 computation on identical inputs should return identical results (up to fixed reduction order). The variation seen here (1e-2 absolute on ~0.7-magnitude outputs) breaks use as a reference/oracle implementation for parity testing.
