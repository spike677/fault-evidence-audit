Describe the current behavior / 问题描述 (Mandatory / 必填)

attention/kv_compress_epilog/tests/st/arch35/ttk_kernel_kv_compress_epilog_st.csv 中 20 条 ST 用例（quant_mode 0/1/2）在 Ascend950DT 真机上执行时， 14 条与 golden 逐字节比对失败，且结果非确定 ：同一份输入数据（runner 输入种子为固定值）连续运行 3 次，同一用例的差异字节数逐次不同。

关键证据 ：

  1. 非确定性 ：固定输入种子（np.random.default_rng(20261104) ）下连跑 3 次，同一用例差异字节数逐次变化，例如wb_mode1_default_d128 ：179 → 359 → 352 字节；wb_mode2_g32_d192 ：36 → 129 → 261 字节。详见"日志"一节。
  2. 决定性对照 ：保持 shape/属性不变，仅将 slot_mapping 改为唯一映射（np.arange(bs) ）后，mode 0/1/2 全部逐字节等于 golden（diff=0），多次运行稳定。
  3. 失败分布与并发写冲突强相关 ：6 条稳定 PASS 的用例（eps_tiny /allzero ×2/bs1 /tight_head /wide ）均为全零输入、bs=1 或 slot 恰好无实际冲突的场景；14 条 FAIL 用例的 slot 抽样均存在大量重复值（如 16 token 中 slot=0 出现 7 次、slot=1 出现 7 次）。
    该问题在 master（dd0c5026b）原始代码上即可复现，与近期任何功能修改无关。

根因分析 ：20 条用例的input_data_ranges 第 3 项（slot_mapping）均给定为(-1, 1) ，即 bs=16/32/64 个 token 的 slot 值只能在 {-1, 0, 1} 三个值中随机取值。该算子是 scatter 语义（按 slot_mapping 将各 token 的量化结果写入 kvCache 对应行），slot 空间仅 3 个值必然导致 大量 token 映射到同一 kvCache 行 ；kernel 多核并行写入同一行无顺序保证，而 golden（numpy 实现）按 token 顺序依次覆盖的确定性语义计算期望值，二者在"重复 slot"场景下必然不一致，且 kernel 多次执行结果互不相同。

Environment Information / 环境信息 (Mandatory / 必填)

  • 昇腾硬件型号：Ascend950DT（V120，device 2 实测）
  • CANN 版本：9.2.0（Ascend-cann-toolkit_9.2.0_linux-aarch64 + Ascend-cann-950-ops_9.2.0_linux-aarch64）
  • Python 版本：3.11.6
  • 操作系统：openEuler 24.03 aarch64
  • 代码版本：ops-transformer master dd0c5026b
  • 算子包：build.sh --pkg --soc=ascend950 --ops=kv_compress_epilog 构建安装

Describe the expected behavior / 预期结果 (Mandatory / 必填)

ST 用例应当稳定通过，至少结果应当确定。具体修复建议（二选一或组合）：

  1. 修用例（推荐） ：将 20 条用例input_data_ranges 中 slot_mapping 的范围从(-1, 1) 放宽到与 bs 匹配的唯一区间（如 bs=16 取(0, 15) ，bs=32/64 相应扩大且不超过 cache 行数），保证任意随机抽样下 slot 无重复；
  2. 明确契约 ：若"重复 slot_mapping"本身是合法输入，则需在算子接口文档中明确"多 token 映射同一 kvCache 行时写入顺序未定义"，并将 golden 调整为对应的容忍比对方式（如按行集合比对而非逐字节）。

感谢您提供详细的复现信息。我们沿着重复 slot 的线索补做了标准 TTK 入口与输入构造的对照，供参考。

本次环境为 Ascend950PR_9579 / CANN 9.2.0 / TTK 3.0.0，使用仓库原始 20 条 CSV 用例和修改前的 golden，运行 CANN 9.2.0 包内算子。结果如下：

输入方式 逐字节精度比对 同一输入连续 3 次执行的一致性
标准 TTK 入口，加载完整 TestSpec（含 customize_inputs） 20/20 PASS 20/20 MD5 一致
对照：保留同一 golden，跳过 customize_inputs，直接使用 CSV 随机 slot 7/20 PASS，13/20 FAIL 13/20 出现 MD5 不一致

已核对两组的 cache、x 输入完全相同，区别仅在 slot_mapping。例如 wb_mode1_default_d128，标准流程实际下发的 slot 为 [0,1,2,3,4,5,6,7,-1,9,10,11,12,13,14,-1]，有效值互不重复。

tests/assets/golden.py 已通过 KvCompressEpilogTestSpec.customize_inputs 生成唯一有效 slot，并加入 -1 跳过场景。标准 TTK 加载该插件后会调用此钩子，因此 CSV 中的 (-1, 1) 是定制前的初始随机范围，并非最终下发范围。README 约束说明 也已要求有效 slot 不重复，重复时不保证结果正确性。

建议先按原始 kernel CSV 和完整插件对照运行（从 ops-transformer 仓库根目录执行，--devices 可替换为可用卡号）：

python3 -m ttk kernel \
  -i attention/kv_compress_epilog/tests/st/arch35/ttk_kernel_kv_compress_epilog_st.csv \
  --plugin attention/kv_compress_epilog/tests/assets/golden.py \
  --devices 0 --pc 1 --seed 20261104 \
  --compare binary --run 3 --dl 1 --task-prof false

若继续使用转换后的 ACLNN CSV 和自定义 runner，建议核对是否在生成 golden 和下发设备之前，复用了 customize_inputs，且两侧消费的是同一组定制后的输入。仅扩大随机范围仍无法保证 slot 唯一。

从这组对照看，更倾向于输入构造链路的差异。由于本次使用的是 950PR 和包内算子，与您报告的 950DT、自行构建算子包存在环境差异，且尚未取得自定义 runner 的实现，暂不据此排除所有实现问题；若按上述标准入口仍有差异，欢迎补充 runner 实现和实际 slot 数据，便于继续定位。
