- **故障机理**：缺陷不是「算错了」，而是**「没按序」**——同一块 buffer / 地址上的生产者与消费者之间，缺少一条**以等待方为视角**的同步边，导致「读先于写」或「写覆盖了尚未被读的数据」。它属于**遗漏型缺陷**：出错的代码行本身语法正确、单看无异常，只有把「生产者—消费者」当成一对一起看才暴露，因此常规逐行审查与静态扫描（扫「错误行」）天然漏检。五种独立成因（编号与五子型一一对应）：① **同步原语配对失衡/不完整**——`SetFlag`/`WaitFlag` 次数不配平（只 set 不 wait、wait 个数多于 set、发起侧与等待侧计数不一致），或同步对被放在错误语句之后（先搬运后置同步），导致某方**永久等待**或搬运先于计算执行；② **跨流水同步遗漏或用错同步边**——`PipeBarrier<PIPE_X>` 只保证**同一管线内部**顺序，跨管线（V→MTE2 / V→MTE3 / MTE3→S / S→MTE3 / MTE2→V 等）必须用 `SetFlag/WaitFlag<HardEvent::…>` 显式事件同步；只写同管线 barrier、或用错方向的事件（如用 `SToMTE3Sync` 去护 V→MTE3），覆盖不到真实依赖；③ **事件 ID / flagId 冲突、越界、泄漏**——两个不同事件常量共用同一 ID（如 `FIX_MTE2_EVENT` 与 `S_MTE3_EVENT` 同为 `6`）、`id % N` 取模而 buffer 数 > N 致 ID 重复、循环内 `AllocEventID` 申请后从不 `ReleaseEventID` 致事件池（`MTE2_V` 仅 8 个）耗尽、缺失同步引发行为回退；④ **跨核同步覆盖不全**——`CrossCoreSetFlag/CrossCoreWaitFlag` 的 mode+flagId 映射只让等待方感知到**部分**核（如双 AIV 只覆盖 AIV0），另一核的写未被等待方感知，构成核间 RAW/WAW；⑤ **同步与调度约束缺失**——kernel 用 `SyncAll` 合并各核结果，但 host 侧未 `SetScheduleMode(1)`，无法保证所有参与核**同时驻留**，`SyncAll` 语义失效致卡死。**共性：单看每一行都「没错」，错在两条指令之间的**依赖顺序**；且这类缺陷**时隐时现**——双 AIV 冗余写结果逐字节一致时 `VerifyResult` 照样通过、新进程首次调用才触发、批跑轮换复现，使「偶现精度失败/偶发卡死」长期无解。**
- **触发条件**：手写同步的 kernel（`SetFlag` / `WaitFlag` / `PipeBarrier` / `CrossCore*` 出现在源码中）；双缓冲 / 流水复用**固定 UB / L1 / GM buffer**；同一物理核的**双 AIV 并行**（Ascend950 / arch35，`__NPU_ARCH__ == 3510`）；多核共享同一 workspace 或同一 GM 地址；事件 ID 池有限（`AllocEventID<HardEvent::MTE2_V>` 仅 8 个）且循环内反复申请；同步对落在**条件分支**（如 `!pseInfo.pseEndogenous`）内致另一分支缺失；host 侧 `SyncAll` 依赖核同时驻留却未设 `schedule_mode`；同一 pipe 对同一地址的两次访问之间只放了**产出方** flag（如 `MTE2→V`）而无**等待方**反向同步；开启确定性计算（dw 切 k）后 cube 空转而 set 过快。
- **典型表现**：`racecheck`（MindStudio Sanitizer / mssanitizer）报 `Potential WAW hazard` / `Potential RAW hazard`（GM 或 UB），且**典型输出含 `Write: xxx.h:56 (PIPE_MTE2)` / `Read: xxx.h:61 (PIPE_MTE2)` 成对地址与行号**；精度**偶现**失败（批跑通过率轮换、新进程**首次**调用易触发、后续调用因残留正确数据掩盖竞态）；输出**整段为 0**或错值；`WaitFlag` **永久等待 / 同步卡死 / 超时 `aic error`**；`VerifyResult` 通过但存在隐患（两 AIV 冗余写同址、结果逐字节一致掩盖 WAW）；同一输入多次运行结果不同。**关键识别特征：缺陷「复现性差」，越并发越不稳定，但一旦命中 racecheck 一行地址级报告即可直接定位。**
- **源码审查映射点**：每个 `SetFlag<HardEvent::X>(id)` 是否在**同一路径**有匹配 `WaitFlag<HardEvent::X>(id)`（次数与分支都配平）；`WaitFlag` 所在分支是否可能**没有**对应的 `SetFlag`（注意条件分支包裹）；`AllocEventID<…>` 是否与 `ReleaseEventID<…>` 成对，且**申请不在循环体内**（每迭代申请=泄漏）；事件 ID 常量定义是否**两两互异**、是否 `id % N` 而 N 小于实际 buffer 数；同一 buffer / 地址上的两次访问之间，是否放了**以该 pipe 为等待方**的 set/wait 或 `PipeBarrier<PIPE_该pipe>`（只有产出方 flag 不构成保护）；`CrossCoreSetFlag/CrossCoreWaitFlag` 的 mode 与 flagId 是否让等待方感知**全部**参与核（双 AIV 的 AIV0/AIV1 都要覆盖）；`SyncAll` 出现处 host 侧是否有 `SetScheduleMode(1)`；反向同步是否缺失（循环复用固定 UB buffer 时，MTE2 覆盖前是否等到 V 读完）。
- **检测签名（判别性指纹，命中即候选缺陷点位）**：`SetFlag<\s*(AscendC::)?HardEvent::`；`WaitFlag<\s*(AscendC::)?HardEvent::`；`CrossCoreSetFlag`；`CrossCoreWaitFlag`；`AllocEventID`；`ReleaseEventID`；`PipeBarrier<\s*PIPE_(V|MTE2|MTE3|S|MTE1|FIX)>`；`HardEvent::\s*(V_MTE2|V_MTE3|MTE2_V|MTE3_V|S_V|V_S|MTE3_S|S_MTE3)`；`SyncAll\s*<`；`SetScheduleMode\s*\(\s*1\s*\)`。**配对完整性检查（本模式核心方法）**：本模式的判别性**不在单条指纹**，而在「原语配对」——应把每个 `SetFlag`/`WaitFlag`/`CrossCore*`/`AllocEventID` 视为**只能成对出现**的原语，扫描**孤儿原语**（无配对的 set、无来源的 wait、只申请不释放的 event）而非扫错误行，详见 `scripts/scan_sync.py` 与本模式 skill 第 3 节。
- **审查关键词（`keywords` 字段；命中只表示该处值得人工审，不是缺陷候选）**：`双缓冲|double\s*buffer`（切换处是否有切换同步）；`核间同步|核内同步`；`同步缺失|同步不完整|漏同步|漏插`；`事件 ?ID|event ?id|flagId|flag_id`（常量定义是否重复/越界）；`buffer\s*复用|复用.*UB|固定.*buffer`（复用点是否有反向同步）；`racing|race\s*condition|竞态|竞争`；`WAW|RAW|hazard`；`SetScheduleMode|schedule_mode`；`workspace.*清零|清零.*workspace`（双核同址写）。
- **控制变量（v6.30）**：**必须固定**——kernel 源码版本、编译选项、核数三项固定；只改**一处** SetFlag/WaitFlag 的配对（删一个 wait、或把 set 移到分支外）；事件 token 必须归一（去 `AscendC::` 命名空间）后配对计数 ｜ **允许变动**——单个同步点 ｜ **多变量同变的典型误判**——`WaitFlag<AscendC::HardEvent::MTE1_MTE3>` 与 `SetFlag<MTE1_MTE3>` 被算成两个事件 → 误报 18 格 found(4.5%)；同名前缀函数（`SetFlagToFFN()`）被当同步原语 → 凭空多 8 格假阳
- **测试拦截建议**：① **racecheck 常态化（最高优先级）**——用 mssanitizer `racecheck` 对新增/改动 kernel 做 WAW/RAW 检测并**以零告警为门禁**；本模式绝大多数实证都是 racecheck 一行地址级报告直接暴露的，这是「最深一类 bug」目前唯一有效的自动化抓手；**⚠️ 生效前提（v6.49）**：racecheck / synccheck **只对以 `--cce-enable-sanitizer` 重编译过的内核生效**；未重编译时日志逐 kernel 打印 `No active sanitizer tool on kernel ...` + `racecheck|synccheck is not supported on the kernel that without '--cce-enable-sanitizer' compiler option, thus it's temporarily ignored`，紧接着仍打印 `Sanitizer finished on kernel .... No error detected.`——这是**假绿**，不得作为「零告警门禁」证据（A2 910B2 + CANN 9.3.0 实测：官方 example 二进制直接跑 racecheck/synccheck 全部未激活）。`memcheck` 不受此限（二进制级可用），所以「memcheck 有结论」不能推出「racecheck 有结论」，二者必须分别看激活状态；② **同步原语配平断言**——静态统计每个事件域的 `SetFlag`/`WaitFlag` 次数与分支路径，set≠wait 即告警；③ **事件 ID 池审计**——`AllocEventID` 是否成对 `ReleaseEventID`、申请是否在循环体内、常量是否两两互异，池容量（如 8）内不得越界；④ **跨核覆盖用例**——双 AIV / 多核共享 workspace 场景必须单独成类，不能只跑单核；⑤ **批跑轮换 + 新进程首调**——竞态在「单跑首次」与「批跑轮换」下暴露最充分，单次随机通过不代表无缺陷；⑥ **自动同步勿随意关闭**——确认性能优化（如关闭自动同步）不引入未补齐的手写同步。

- **子型⑥ 专项判据（v6.15 新增，作用域而非计数）**：前五子型都在问「配不配平 / 方向对不对 / ID 冲不冲突」，全部是**计数与方向**问题；子型⑥ 问的是「**这对同步定义了哪条路径归它管**」，是**作用域**问题。判别三步：① 取同步四件套（`AllocEventID` / `SetFlag` / `WaitFlag` / `ReleaseEventID`），求其**共同最内层块**；② 若该块是 `if/else` 分支，则该边只覆盖此分支；③ 检查**作用域外**是否还有对同一 buffer 的访问——有则成立。**关键在于：四件套配平、ID 不冲突、方向也对，单纯"计数配对"检查会全部放行。**#5836 即为典型：`eventIdPseDropVToMte2B` 的申请/Set/Wait/Release 各一次、ID 相同、完全配平，但因全部包在 `!this->pseInfo.pseEndogenous` 内，内源 PSE 路径（走 `PseSlopeCopyIn`）完全丢失该 V→MTE2 边。机检脚本见 `scripts/scan_sync_scope.py`（作用域审计，与 `scan_sync.py` 的配对审计互补）。
- **⚠️ 同管线同址也必须显式串行（v6.15 补正）**：本条正文强调「`PipeBarrier<PIPE_X>` 只保证**同一管线内部**顺序，跨管线须用事件同步」，这句话容易被反向误读为「**同管线天然安全**」——**不成立**。同一 `PIPE_V` 上对**同一 UB 地址**的两次访问，若在指令队列中可能乱序执行（尤其是 `Duplicate` / `Muls` / `PSE` 这类写与 `SoftmaxFlashV2` 这类读交替出现时），仍需显式 `PipeBarrier<PIPE_V>()` 建立顺序；`stage1PingBuf` 一类固定复用 buffer 是重灾区（实证 #12772 / #12555 / #13398：`ProcessVec1()` 的前序 PSE / Muls / AttenMask 写与 `SoftMaxCompute()` 内 `Duplicate()`、`SoftmaxFlashV2()` 重叠，补 `PipeBarrier<PIPE_V>()` 修复）。**判据：同一 pipe、同一地址、两条访问之间没有 barrier 也没有事件 → 候选 WAW/RAW，不可用「同管线」当豁免理由。**
- **⚠️ racecheck 假阳性四分类（v6.63 新增，判「报出来的 hazard 到底是不是缺陷」）**：本模式把 racecheck 当作「最深一类 bug 的唯一自动化抓手」，
  但实测（2026-11-09，Ascend950PR + CANN 9.2.0-beta.2，27 个探针 / 273 个 kernel）表明：**报出的 hazard 绝大多数不是缺陷**——
  5 类 kernel 共 7000+ 处告警，逐条查源码后**可提交缺陷 0 个**。落本模式前必须先按下表把告警归档，否则会把「自己的造数问题」和「工具的识别盲区」
  当成算子缺陷提上去。
  | 形态 | 大概率是 | 验证动作 | 本次实例 |
  |---|---|---|---|
  | WAW，写地址相同，写方**不同 block** | ①原子累加（设计）②输入索引重复（自造） | 查源码有无 `SetAtomicAdd` / `GetTensorC(..., enAtomic=1)`；把索引类输入改成互不相同的值重跑 | `Conv3DBackpropFilterV2` 28 处 = 原子累加；`QkvRmsNormRopeCacheWithKScale` 6734→61、`UndGenQkvRmsNormRopeCache` 56→**0**、`MoeFinalizeRoutingV2Grad` 6→**0** = 索引重复 |
  | WAR，同 block，serialNo **相邻**，地址相同 | 屏障未被 sanitizer 识别 | 回源码搜 `SetFlag/WaitFlag<HardEvent::S_MTE2\|MTE3_S\|V_S\|S_V>` 或 `PipeBarrier<PIPE_X>`，确认屏障覆盖该依赖 | `LayerNormQuant` 1 处，源码 `layer_norm_quant_regbase_normal.h:280-281` 有 `S_MTE2` 正好阻断 |
  | RAW/WAW，**单一方块内**两个 pipe（如 `PIPE_FIX Write` → `PIPE_MTE2 Read`） | 需读 kernel 源码才能定性 | 源码在仓内则查同步对；**框架闭源（如 blaze）且二进制无法反汇编时记「未定」，不得提缺陷** | `FlatQuant` 194 处 RAW，A5 走 blaze 框架（不在四仓内）、装包 `.o` 无 A5 指令表 ⇒ 记未定 |
  | 相邻 block（如 26/27）间的 RAW/WAR | AIV/AIC 协作对（`AIV_PER_AIC=2`），可能已有 CrossCore 同步 | 查 `CrossCoreSetFlag/WaitFlag` 是否用 `AIV1_FLAG_OFFSET` 做了双 AIV 隔离 | `QkvRmsNormRopeCacheWithKScale` 余下 61 处 |
  **三条硬纪律**：① **数量不是严重性**——6734 处里 6733 处可由同一个错误输入解释；1 处也可能是真缺陷，先看形态再看数量。
  ② **稳定性 ≠ 真实性**——三连跑都报同一处只能证明「确定性复现」，不能证明「确定性缺陷」（本例 61 处三跑一致，仍全是假阳性）。
  ③ **报 hazard 的 kernel 未必是探针调用的接口**——`Conv3DBackpropFilterV2` 是 `aclnnConvolution` 内部下沉的 kernel，
  归因要用「探针实际调了哪个 aclnn 接口」，不能拿 kernel 名当接口名。
