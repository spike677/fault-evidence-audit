# FP-A13 aclnn 接口检视（fpa13-input-rounding-review）

对用户指定的 aclnn 接口做 FP-A13 专项源码检视：先定位算子实现与其测试资产（golden / UT 输入生成），再按清单逐项核查，每个结论给出**文件 + 行号 + 推导链**证据，命中即出 Bug 卡，输出检视报告。**本模式特殊纪律：① 检视对象是「**测试资产把实现缺陷掩盖了**」——被检实现可能确实精度不足，但根因在测试侧（输入被 round / 截断后偏差落进容差），修复方向是「去掉预处理 + 修实现」而非只改测试；② 卡片触发为关键词（`Round|round|Truncate`）——`round` 在数值库中大量出现且多数是**业务语义本身**（如取整算子、索引换算），命中只作定位提示，须区分「输入预处理的 round」与「算子语义的 round」；③ 本模式卡片**无确认 issue 级实证**（检索命中均为异机理条目）——静态命中一律按 O1 定档，禁止把「发现 round 逻辑」直接表述为「精度标准被绕过」；④ 判定须给出「去掉预处理即失败」的可复现构造，仅有 round 代码不成立。**

## 0. 与相邻模式的边界

| 相邻模式 | 分工 |
|---|---|
| FP-E01（golden/UT 期望值失配或按错误实现编写） | **最易混淆项（卡片关联直指）**：E01 管**期望值错了**（按错误实现编写 / 命名失配）；A13 管**输入被预处理过**（round / 截断把实现精度不足掩盖过去）。输入生成与 golden 生成同源脚本时两侧同时被污染，两卡连打 |
| FP-A03（竞品高精度中间计算，NPU 直接低精度） | 卡片关联项：A03 是**精度档位**设计低于竞品（实现面）；A13 是**测试输入**被截断使档位问题不被暴露（测试面）——同一「精度标准被绕过」现象的两个面 |
| FP-E02（精度测试判据与标杆口径设计缺陷） | E02 管**判据 / 容差口径本身**设计缺陷；A13 管**输入分布**被改变使口径看似达标——先核 E02 口径，再核 A13 输入 |
| FP-A12 / FP-A18（转换精度） | 若 round / 截断发生在输入生成端的浮点转换处，数值机理按 A12（计算损失）/ A18（比较语义）核；A13 只对「该预处理是否掩盖实现不足」下判 |
| FP-A04（功能问题演变为精度静默故障） | 被掩盖的实现缺陷常以静默数值偏差存在——A13 定位「掩盖手段」，A04 定位「被掩盖的错误分支」 |
| FP-A07（tiling 条件判断错误走入错误分支） | 若去掉截断后失败形态是「特定 shape 走错分支」，归 A07；A13 只负责证明「测试输入被改过」 |

**症状反查定位**：仅截断 / 取整后的输入能过测试，原始精度输入失败 → 首查输入生成脚本的预处理；UT 全绿而 ST / 线上精度失败 → UT 与 ST 输入分布不一致；容差看似宽松却从不失败 → 输入域被压缩；测试脚本注释含「精度」「对齐标杆」「临时」字样 → 精度调试遗留的 round；golden 与输入同一脚本且同时做 round → 期望值与输入双污染（连打 E01）。

## 1. FP-A13 模式卡摘要（检视依据，源自本库 `patterns/FP-A/FP-A13.md`，v3.1）

- **编号 / 名称**：FP-A13 输入尾数截断才能通过精度标准 ｜ **类别**：精度 ｜ **风险**：中（S3×O1=3）｜ **状态**：活跃 ｜ **来源**：团队笔记
- **适用声明头**（照抄卡片）：仓 All ｜ 侧别 All ｜ 载体 UT与golden资产 ｜ 触发 Round|round|Truncate ｜ 默认启用 true
- **skill 核查面**：侧别 All——skill 落地为 `tests/`（UT 用例输入构造、`tests/assets/` 的 golden 与输入生成脚本）、`examples/`（样例输入），并回溯到 `op_host` / `op_kernel` 以界定「被掩盖的实现精度不足」具体在哪个环节
- **故障机理**：输入预处理存在 round / 截断逻辑，**掩盖实现精度不足**——测试以截断后的输入通过，真实场景未截断输入失败。
- **触发条件**：精度调试历史遗留的对输入做 round 的逻辑。
- **典型表现**：仅截断输入可过测试。
- **源码审查映射点**：输入预处理是否存在 round / 截断逻辑掩盖精度不足。
- **检测签名**：卡片未给独立 grep 签名，触发词为 `Round|round|Truncate`（关键词定位提示）；核查面须区分「输入预处理的 round」与「算子语义的 round」。
- **测试拦截建议**：golden 生成端禁止预处理输入；UT 输入与 ST 输入分布一致性抽查。
- **实证案例**：**待补充**——2026-09-16 对 GitCode CANN 组织 12 仓约 1.4 万条 issue 全量关键词检索，命中多为「尾块元素未参与计算」「fp32→fp16 截断舍入模式」等**异机理**条目，无本型「输入预处理 round 掩盖精度不足」的确认对应实证。即本模式暂无确认实证算子，检视结论一律按静态口径定档（详见第 9 节）。
- **关联**：FP-A03、FP-E01。

## 2. 检视输入与算子定位

**输入**：aclnn 接口名（必填）；可选 ref（默认 master）、指定仓（默认自动定位）；可选现象描述（「仅截断输入可过」「UT 过 ST 失败」——用于症状反查）；可选测试资产路径（用户提供的 golden / 输入生成脚本）；可选历史版本 ref（追溯 round 逻辑的引入原因）。

**接口名 → 算子目录换算**：去 `aclnn` 前缀 + 驼峰转下划线小写：
`aclnnRmsNorm → rms_norm`、`aclnnAdd → add`、`aclnnGridSampler2DBackward → grid_sampler2d_backward`。

**仓定位顺序**（GitCode `cann` 组织，逐仓用目录列表确认）：`ops-nn` → `ops-math` → `ops-cv` → `ops-transformer`。**类目名不总与直觉一致**，以目录列表为准。FP-A13 高发面：`tests/assets/` 下的输入生成脚本（`golden.py` / `gen_data.py` / `*_case.py` 类命名）、UT 输入构造段、`examples/` 样例数据、含 `round` / 取整 / dtype 转换（`astype(np.float16)`）的预处理函数。

**算子目录结构约定**（已验证示例 `cann/ops-math` → `math/add/`）：

```text
{类别}/{op_name}/
├── tests/             # 主检视面：
│   ├── assets/        #   golden.py / 输入生成脚本——输入预处理与期望值生成的同源风险点
│   ├── ut/            #   UT 输入构造与比对脚本
│   └── st/            #   ST 用例与数据集资产——输入分布一致性对照面
├── examples/          # 样例输入（可能含截断示例）
├── op_host/  op_kernel/  op_api/   # 回溯面：界定被掩盖的实现精度不足在哪个环节
└── docs/
```

## 4. 输入预处理检视清单（每点：查什么 → 何处 → 命中判据）

对 `tests/`（assets + ut + st）、`examples/` 逐点核查，并回溯 `op_host` / `op_kernel` 界定被掩盖的实现问题；**每点先查命中面、再做反证排除**，正当的 dtype 契约转换 / 业务语义取整也要记录为反证证据。

### ① 输入生成端的 round / 截断逻辑
- 查什么：输入生成脚本对**输入**是否存在 `round` / `Truncate` / `trunc` / `floor` / 取整 / 降 dtype（`astype(np.float16)`、`.half()`）等预处理；该预处理是**业务契约要求**（如整型输入算子、索引类算子）还是**精度调试遗留**（无契约依据、注释含「精度」「临时」「对齐」字样）。
- 何处：`tests/assets/` 的输入生成函数、UT 用例的输入构造段、`examples/` 样例数据。
- 命中判据：存在无契约依据的输入预处理，且能说明其使偏差落进容差 ⇒ 命中候选；属算子契约要求的取整 / dtype（如 indices 必须为整型）⇒ 反证排除并写明契约依据。

### ② UT 与 ST / 线上输入的分布一致性
- 查什么：卡片拦截建议的「UT 输入与 ST 输入分布一致性抽查」——UT 输入域是否 ⊂ 截断后域，ST / 线上输入域是否更大；同一算子两组输入的 dtype、量级、尾数位数差异。
- 何处：UT 用例输入构造 vs ST 用例与数据集资产。
- 命中判据：UT 输入域被预处理压缩而 ST / 线上未压缩 ⇒ 命中候选（须给出两组输入域的差异对比）。

### ③ 精度标准的掩盖链量化
- 查什么：容差 / 比对口径与输入预处理的关系——同一实现在**未截断输入**下的偏差量级是否超容差；round / 截断对偏差的抑制幅度（可做代数估算）。
- 何处：比对脚本与容差配置、golden 资产。
- 命中判据：给出「未截断偏差 > 容差、截断后偏差 ≤ 容差」的量化推导 ⇒ 命中候选（强证据）；两组都在容差内 ⇒ 反证排除。

### ④ golden 生成端纪律（禁止预处理输入）
- 查什么：卡片拦截建议「golden 生成端禁止预处理输入」是否被遵守——输入生成与期望值生成是否**同一脚本 / 同一函数**（同源则期望值也被污染，连打 FP-E01）；golden 是否用原始输入独立计算。
- 何处：`tests/assets/` 的 golden 生成函数与输入生成函数的调用关系。
- 命中判据：输入与 golden 同源且同时预处理 ⇒ 命中候选并连打 E01；golden 用原始输入独立计算 ⇒ 记录为防护面。

### ⑤ 引入原因追溯（版本轴 / 注释线索）
- 查什么：该 round / 截断逻辑的引入提交与原因（卡片触发条件即「精度调试历史遗留」）；引入后是否伴随实现侧的精度修复（若无，则遗留目的更可能是「让用例过」）。
- 何处：`git blame` / `git log -L`（本地克隆）、版本 diff、脚本注释。
- 命中判据：提交信息 / 注释表明为通过测试而加、且无对应实现修复 ⇒ 命中候选（强证据）；有实现修复且预处理为独立契约 ⇒ 反证排除。

### 横切面：被掩盖的实现精度不足定位
- 查什么：去掉预处理后会暴露的**实现侧**问题落点（回溯 `op_host` tiling / `op_kernel`）——按 FP-A12 / A18 / A03 / A08 分流定位，避免只改测试不改实现。
- 何处：`op_host` / `op_kernel` 相关计算段。
- 命中判据：能指出具体环节 ⇒ 在 Bug 卡的修复建议中同时给出实现侧修复方向；无法定位 ⇒ 记观察项并附实测方案。

## 5. 检视流程

1. **定界**：换算 op 目录、确认所在仓与 ref；按用户现象（仅截断输入可过 / UT 过 ST 失败）反查优先清单点；收集测试资产路径与历史 ref。
2. **枚举**：目录列表列出 `tests/assets`、`tests/ut`、`tests/st`、`examples` 全部相关脚本，产出文件清单。
3. **触发词扫描**：按 `Round|round|Truncate|trunc|floor|ceil|astype|half\(\)` 定位输入预处理面（本地仓用 grep；API 模式逐文件拉取后检查），**并逐个区分「输入预处理的 round」与「算子语义的 round」**。签名零命中时清单仍须逐项核查（隐式 dtype 降级、`int()` 截断同样命中面）。
4. **逐点核查**：每点记录命中面与防护面证据（文件:行号）；对每处预处理写出「预处理对象（输入 / 期望值 / 中间量）→ 契约依据 → 抑制的偏差 → 去掉后是否失败」四项对表。
5. **反证排除**：契约要求的取整 / dtype、golden 用原始输入独立计算、两组输入域一致、预处理与实现修复同期引入 → 明确写出反证理由。
6. **判定**：按第 7 节标准给出 命中 / 观察项 / 反证排除。
7. **GitCode 查重**（仅命中项）：issues API 按接口名 + `精度|round|截断|测试` 检索，逐条比对是否同机理；无同机理才立卡（本模式历史查重命中均为异机理，属预期）。
8. **业务可达性核查**（仅命中项）：判 B 等级、定业务影响类型、给处置建议；默认保守（无法证明不可达即记 B3），降档须附证据；B 不改 S×O 档位。
9. **出报告**：按第 8 节模板落盘；静态结论一律附「截断 / 未截断两组输入对照实测」方案。

## 6. 风险定级（S×O）与业务影响评估（B 轴）

- **S**：S3（精度标准被绕过——实现缺陷长期潜伏，线上以精度失败暴露）；S2（仅测试资产问题、线上未触发该输入域）；S1（预处理有契约依据、仅文档说明不足）。
- **O**：O3 = ≥2 条独立实证；O2 = 1 条独立实证；O1 = 仅静态扫描命中或团队笔记（实证 = 确认对应的 issue / PR，或经跨仓、跨分支核验确认的缺陷记录，同权计入）。静态推演命中且无实证默认 **O1**；升档须在报告中给出实证依据。
- **风险 = S×O**：≥6 高；3/4 中；1/2 低。FP-A13 基准：模式卡整体 **S3×O1=3（中）**；纯静态命中一律 S3×O1=3（中，暂定），两组输入实测后复评。

### B 轴：业务影响评估（与 S×O 正交；报告层新增，不改卡片定级）

S×O 回答"多严重、多常见"，**不回答"真实业务能不能碰到"**。B 轴补这一问，只决定**修复优先级建议**，**不参与 S/O 取值、不改 S×O 档位与卡片元数据**。

**业务可达性（B）**——触发条件在真实负载中的可达程度：

| 等级 | 判据 | 证据要求 |
|---|---|---|
| B3 现实可达 | 主流框架/公开模型默认路径即可命中（如 PTA/torch_npu、vLLM、MindIE 常规调用） | 调用方或公开负载来源 |
| B2 条件可达 | 需特定 attr/dtype/shape 组合，业务中存在但非默认 | 该组合的业务来源 |
| B1 边界/不可达 | 需极端、超规格或非法参数（超出接口合理上限的 shape、退化/非法输入） | "为何不可达"的说明 |

- **默认保守**：无法证明不可达 → 记 **B3**；降为 B1/B2 必须附证据，**不得仅凭"业务应该不会这么用"**。
- 超规格参数是否算 B1 取决于**接口契约**：契约允许但业务不用 → B1；契约不允许（本应报错）→ 属校验缺失（FP-B04/B05 类），另行归属。

**业务影响类型**（命中后对用户可见结果的后果，用业务语言表述）：静默精度损失（模型效果下降 / loss 不收敛 / 偶发 NaN）｜ 任务失败中断（报错 / 崩溃 / 挂死）｜ 性能退化 ｜ 仅可观测性（日志 / 错误码 / 文档，不影响结果）。

**处置建议**（由两轴推导的报告结论，非新档位）：

| S×O \ B | B3 现实可达 | B2 条件可达 | B1 边界/不可达 |
|---|---|---|---|
| 高（≥6） | 尽快修 | 尽快修 | 排期修 |
| 中（3/4） | 尽快修 | 排期修 | 记录（业务难以触达） |
| 低（1/2） | 排期修 | 记录 | 记录 |

## 7. 判定标准与反误报原则

- **签名 / 触发词命中 ≠ 成立**：`round` 在数值库中大量出现且多为业务语义（取整算子、索引换算、量化契约）——必须过「契约依据 + 分布差异 + 掩盖链量化」三关；仅存在 round 代码不成立。
- **三种判定**：
  - **命中**（可静态证掩盖链）：无契约依据的输入预处理 + UT 输入域被压缩 + 「未截断偏差 > 容差」量化推导（或注释 / 提交明确为通过测试而加）⇒ 立 Bug 卡；
  - **观察项**：预处理存在但掩盖链需实测确认、或引入原因不可考 ⇒ 记录并附两组输入对照方案，按 S3×O1 暂定；
  - **反证排除**：属算子契约要求的取整 / dtype、golden 用原始输入独立计算、UT 与 ST 输入域一致、预处理与实现修复同期引入 → 写出防护面证据与反证理由。
- **「测试全绿」不是反证**：本型的识别特征正是「测试以被改造的输入全绿」——UT green 只说明该输入域通过，不排除实现缺陷。
- **修复方向不得只改测试**：命中的修复建议必须同时给出**实现侧**修复方向（回溯 A12 / A18 / A03 / A08 定位）与「去掉预处理」两项；只改测试属掩盖加重。
- **不臆造行号**：每条证据必须是实际读到的 文件:行号；无实证算子时不写算子名与行号（见第 9 节）。
- **静态推演声明**：无 NPU 环境时，所有运行时行为结论必须标注「静态推演，需 NPU 实测确认」。

### 判定纪律补充（v3.6）：非对称增减、证据等级与误判记录

**增减不对称**：允许追加候选（有据即可，错了可由用户排除）；**撤销或否决候选必须附 `[文件]:[行号] [代码行]` 负向证据**。无证据的「看起来没问题」一律记为「未核查」，不得计入反证排除，也不得据此下调等级——否决造成的漏报用户不可见、不可恢复。

- **证据等级**（Bug 卡必填）：`静态可证` = 推导链完整且触发输入可静态构造；`需实测确认` = 依赖运行时输入规模、设备行为或环境差异。标 `需实测确认` 的条目**不得以「命中」名义出卡**，按观察项记录并附实测用例。
- **Agent 误判记录**（Bug 卡必填）：本次被推翻的假设、推翻它的证据（`[文件]:[行号] [代码行]` 或实测输出）、判定标准是否随之修订；无推翻写「无」。
- **误判回流**：同类误判在 3 次检视中重复出现，登记至 `cases/misjudgments.jsonl`（字段见 `cases/README.md`），并在本模式判定标准中新增对应防线；守门 C19d 校验台账字段合法。

## 9. 示例速览：本模式暂无确认实证算子

卡片「实证案例」为 **待补充**——2026-09-16 对 GitCode CANN 组织 12 仓约 1.4 万条 issue 全量关键词检索，命中多为「尾块元素未参与计算」「fp32→fp16 截断舍入模式」等**异机理**条目（前者归 FP-A08，后者属 dtype 转换契约面），**无本型确认对应实证**。故本节不给具体算子与行号，改为给**触发词 / 检索起点速览**（**严禁虚构算子名或行号**）：

- **检索起点**（按第 2 节换算 op 目录后，在 `tests/assets` + `tests/ut` + `tests/st` + `examples` 全量 grep）：
  - `round` / `Round` / `Truncate` / `trunc` / `floor` / `ceil` 出现在**输入生成函数**内（而非算子语义段）；
  - `astype(np.float16)` / `.half()` / `int(` / `//` 等对输入降精度 / 取整的调用；
  - 同一脚本内「输入生成」与「golden 生成」共用同一预处理函数（同源污染，连打 FP-E01）；

## 10. 能力边界与自检（v3.8）

### 能力边界

- **静态可证**：清单里能在源码内给出「`文件:行号` + 推导链」的部分，按第 7 节判据出卡。
- **需实测确认**：依赖运行时输入规模、设备行为或环境差异的结论，只能记观察项并附实测用例（证据等级见第 7 节）。

- **找不到 ≠ 没有**：按清单未命中只说明「本轮未发现」，不得表述为「该算子无此缺陷」；抽样核查须在报告写明抽样口径。
