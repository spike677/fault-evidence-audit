# FP-B15 定长容器容量无校验（入参索引 + 越界写 + 静默截断）

> [← 库索引](../../README.md) ｜ [变更记录](../../CHANGELOG.md) ｜ 类别：功能/兼容 ｜ 风险：高（S3×O3=9） ｜ 状态：活跃

- **元数据**：类别 功能/兼容 ｜ 风险 高（S3×O3=9）｜ 状态 活跃 ｜ 来源 ops-nn/ops-math/ops-transformer 三仓语料静态扫描（2026-11-06，CANN 五仓 25 案 x 1370 aclnn 接口一轮，定长容器族命中 **foreach 7 处以上**）+ 实证 ops-nn#8254
- **适用**：仓 All ｜ 侧别 Host,Tiling ｜ 载体 Tiling源码,Host源码 ｜ 触发 \[256\]|MAX_TENSOR_NUM|tensorElements|listSize|groupNum ｜ 默认启用 true
- **故障机理**：host/tiling 侧用**定长数组**承载「由入参决定的变长集合」——tiling data 结构体里写死 `int64_t tensorElements[256]`，填充与消费各用一次循环下标 `for (i = 0; i < tensorNum; i++)`，而 `tensorNum`（`GetInstanceNum()` / `listSize` / `groupNum` / `tensorCount`）**来自调用方，全程无上界校验**。三条后果**同时**存在且互相遮蔽：① **host 结构体越界写**（`n=512` 时约 2048 字节）；② **kernel 侧用同一个未截断的 `tensorCount` 索引同一数组**，越界读后 fault（`sync 507035`）；③ **超出容量的尾部张量被静默丢弃**——接口两段都返回 0，前 256 个张量算对、后面全错。与 [FP-B07](FP-B07.md) 的区别：B07 错在**索引算式本身**（下标算错），本条**下标表达式没错**，错在**容器容量与入参上界之间没有约束**；与 [FP-B11](FP-B11.md) 的区别：B11 是「单个参数自身合法性」未校验（rank/长度/值域），本条特指**容器容量**这一类，且其静态形态（`Type name[N]` + 入参索引）可被机器一次扫清。
- **触发条件**：① 存在 `Type name[N]` 或 `constexpr int MAX_... = N` 的定长数组/常量；② 其索引来自入参（`tensorNum` / `listSize` / `groupNum` / `tensorCount`）；③ **同族兄弟实现有 `OP_CHECK_IF(x > N)` 而本算子没有**——第 ③ 条是零成本强证据，不需要论证 N 的合理性即可定缺陷。
- **典型表现**：**小规模输入全对、大规模输入静默错**；`n` 恰好越过容量时接口返回 `ACLNN_SUCCESS`（两段都 0）但尾部数据缺失或错值；`n` 再大一些则出现 `507035 Aicore kernel fault` 或进程 coredump；错误现场与 shape/dtype 无关，**只与「集合元素个数」有关**，因此常规用例矩阵（按 shape/dtype 铺）几乎不可能覆盖到。特征信号：把同一接口的列表长度从 `N-1` 逐级加到 `N+1`、`2N`，返回码仍为 0 而结果开始不一致。
- **源码审查映射点**：`op_kernel/**/*_tiling_data.h` 里所有 `T name[N] = {0}`（N ≥ 32 的一律可疑）；`op_host/**/*tiling*.cpp` 里对该数组的填充循环，其上界变量来自哪里（`GetInstanceNum()` / `GetDynamicInputShape` 的 count / attr `groupNum`）；同一文件内是否已定义 `MAX_*` 常量却**未用于校验**（定义了不用 = 作者知道有上限但漏了拦截）；kernel 侧消费同一数组时用的是 `tensorCount` 还是 `min(tensorCount, N)`；`op_api/aclnn_*.cpp` 的 `aclCreateTensorList` 长度与 tiling 侧读到的 instance num 是否可能不一致。
- **检测签名**：静态扫描三件套——① `[A-Za-z_][\w:<>]*\s+\w+\[\s*(\d{2,})\s*\]\s*(?:=|;)` 命中定长数组（记录 N）；② 同目录/同目录族内 `for\s*\([^;]*<\s*(\w+)` 中该变量出现在数组下标位置；③ `grep -c "OP_CHECK_IF|ACLNN_CHECK" <op>/op_host` 与 ① 的 N 比对——数组存在而**整个 op_host 无任何「> MAX」形态校验** ⇒ 候选。**兄弟对拍**（最强）：同族目录逐个统计「有 256 数组 / 有 MAX 校验」，只有少数接口缺校验时，缺的那批即高置信候选。实测命令与结果见 [cases/false-upper-bounds.md](../../cases/false-upper-bounds.md) 第三节。ops-nn foreach 族基线：`foreach_atan` 等有 `MAX_TENSOR_NUM=256` 校验，`foreach_expm1`、`foreach_neg` **无**。
- **测试拦截建议**：新增「**容量/上限线**」——对每个含 `TensorList` / 变长列表入参的接口，按 `1 / N-1 / N / N+1 / 2N`（N = 实现内部容量）扫描列表长度，断言两件事：① 超上限**必须**明确报错（161002 或等价错误码）；② 未超上限时**每个元素**的结果都与单元素调用一致（对 `foreach` 族可用 `torch._foreach_*` 逐元素对照）。**禁止只断言返回码**——本型的核心特征正是「返回 0 但尾部静默错」。同时把上述三件套静态扫描纳入 CI，新增定长数组而未加校验即告警。
- **实证案例**：**ops-nn #8254**（2026-11-06，P1，可论证 P0）`aclnnForeachExpm1`：tiling 在 `foreach_expm1/op_host/arch35/foreach_expm1_tiling_arch35.cpp:79` 执行 `tiling->tensorElements[i] = numel;`，数组定义在 `foreach_expm1/op_kernel/arch35/foreach_expm1_tiling_data.h:25` 的 `int64_t tensorElements[256] = {0};`，而整份 `op_host/` 中**不存在任何 `256` / `MAX_TENSOR` 字样的校验**（`grep -rn "256\|MAX_TENSOR" foreach_expm1/op_host/` 零命中）。实测后果三条：n=257 时 `rc=0` 但 `sync=507035` + kernel fault；n=258/300/512 分别有 2/86/510 处静默错误；910C 独立复现为**静默不写**（跨平台表现不同，但都不是报错）。host 侧结构体越界写约 2048 字节。**对照组**：同族 `foreach_atan/op_host/arch35/foreach_atan_tiling.cpp:32` 定义 `constexpr int32_t MAX_TENSOR_NUM = 256;` 并在 `:74` 有 `OP_CHECK_IF(tensorNum > MAX_TENSOR_NUM, OP_LOGE(context, "tensorNum should be less than or equal to 256"), return ge::GRAPH_FAILED);`——**同族已有护栏而本算子没有**，是本型最干净的判据形态。**族内交叉核对（2026-11-06，`ops-nn` @ `b27fda2`）**：`foreach/` 下**有 `tensorElements[256]` 的接口共 19 个**，逐个比对 `op_host` 是否含 `MAX_TENSOR_NUM` 校验 ⇒ **18 个有、仅 `foreach_expm1` 没有**（含 `foreach_neg`，它在 `op_host/arch35/foreach_neg_tiling.cpp:32` 定义 `MAX_TENSOR_NUM_FOREACH_NEG`、`:60` 拦截）。**这是一次自我更正**：本轮早期基于 `9.3.0-beta.1` 快照曾把 `foreach_neg` 列为同型新候选，在正式检出 `b27fda2` 上复核后**该结论不成立**（快照间已修）——`not-found ≠ 没有`，跨快照下结论前必须回到正式检出重核（同库 K1358 的教训）。
