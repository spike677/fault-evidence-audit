### 🐛 Describe the bug

## 1. Issue summary

For a **DeepSeek-V2** architecture model (custom fine-tuned 32B MoE), chat-completions generation is **corrupted (garbled Chinese, `�` replacement chars, repetition loop, `finish_reason=length`)** whenever the user prompt is **longer than roughly 5k–8k characters** (~2k–8k tokens). Short prompts (<5k chars) generate normally. The corruption is **independent of configuration** (verified below) and **does NOT reproduce on SGLang with the same weights** → it points to a vLLM-Ascend implementation/long-context issue for this model family.

- vLLM-Ascend log maps the `DeepseekV2ForCausalLM` model to `vllm_ascend.models.deepseek_v4:AscendDeepseekV4ForCausalLM` (see log line below). The model's own config says `model_type: deepseek_v2`, `architectures: ["DeepseekV2ForCausalLM"]`.

## 2. Model

- Path: a local `DeepseekV2ForCausalLM` 32B MoE (021-32b fine-tune).
- `config.json`: `model_type` = `deepseek_v2`, `architectures` = `["DeepseekV2ForCausalLM"]`,
  `max_position_embeddings=32768`, `rope_theta=1e6`,
  `rope_scaling={"type":"yarn","factor":1.0,"original_max_position_embeddings":32768,"beta_fast":32,"beta_slow":1,"mscale":1,"mscale_all_dim":1}`.
- Tokenizer: `trust_remote_code` with a custom `MixedTokenizer` (per-base DNA tokens `<d_>_X`, byte-level). Chinese/English encode correctly after tokenizer fixes (prompt token counts are correct: 15.5k chars → 11116 tokens).

## 3. Reproduction

### 3.1 Startup command

```bash
python -m vllm.entrypoints.openai.api_server \
  --model /path/to/model \
  --served-model-name 021-32b-best --port 30001 \
  --tensor-parallel-size 2 --enable-expert-parallel \
  --distributed_executor_backend mp --trust-remote-code \
  --reasoning-parser deepseek_r1 \
  --block-size 128 --gpu-memory-utilization 0.9 --async-scheduling \
  --max-num-seqs 64 --max-num-batched-tokens 2048 \
  --compilation_config '{"cudagraph_mode":"FULL_DECODE_ONLY","cudagraph_capture_sizes":[1,2,4,8,16,24,32]}' \
  --hf-overrides '{"max_position_embeddings":131072,"rope_parameters":{"rope_type":"yarn","factor":1.0,"original_max_position_embeddings":131072,"beta_fast":32.0,"beta_slow":1.0,"mscale":1.0,"mscale_all_dim":1.0}}'
```

Startup log shows the architecture mapping:

```
WARNING registry.py:945 Model architecture DeepseekV4ForCausalLM is already registered,
and will be overwritten by the new model class vllm_ascend.models.deepseek_v4:AscendDeepseekV4ForCausalLM.
```

### 3.2 Request

```bash
curl http://127.0.0.1:30001/v1/chat/completions \
  -H "Content-Type: application/json" -d '{
    "model": "021-32b-best",
    "messages": [{"role": "user", "content": "<long Chinese prompt ~14k–20k chars; e.g. a structured clinical-analysis instruction with patient data>"}],
    "max_tokens": 8192, "temperature": 0.0
  }'
```

> The full prompt is a Chinese-language structured task (~14k chars). 

### 3.3 Actual (broken)

```text
finish_reason = length
content       = null (empty)
reasoning     = ~13k chars, from the very first token it is garbled Chinese/ASCII mix
                with many U+FFFD replacement chars and repeated fragments, e.g.:
  '###（HAG-PS：.\n（A-1”。\n-    1，"（Hun-1”（B- 该（S-    1”：\n" ... � ... \n###\n###\n###...'
No usable JSON/answer is produced.
```

> **Byte-level clarification:** this is genuine garbage **produced by the model's byte stream**, not a display/decoder issue.
> The `U+FFFD` replacement chars can only arise from invalid UTF-8 byte sequences reaching the detokenizer; short Chinese outputs on the same server decode cleanly (0 `U+FFFD`), so the ByteLevel decoder itself is fine — the corruption is specifically in the long-context generated token/byte stream.

### 3.4 Expected

```text
Model should produce a coherent Chinese chain-of-thought and a final answer (JSON).
Same weights + same prompt on SGLang 0.5.17.dev386 (deepseek-r1 parser) → works: coherent Chinese reasoning, JSON answer, finish_reason=stop.
```

## 4. Length threshold (the key signal)

Same prompt truncated to different lengths (`max_tokens=4096–8192`, temp=0):

| Input length (chars) | Output |
| --- | --- |
| ~2,000 | OK (finish=stop, no U+FFFD) |
| ~5,000 | OK (finish=stop, no U+FFFD) |
| ~8,000 | **BROKEN** (finish=length, reasoning ~9.8k chars, U+FFFD, repetition) |
| ~14,000+ | **BROKEN** (finish=length, reasoning ~13k chars, U+FFFD from first token) |

Short tasks on the same server are fine (e.g., Chinese arithmetic answers correctly), so it is specifically a **long-context** problem, not a general/Chinese/tokenizer problem.

## 5. A/B already tested (all still reproduce ⇒ config-independent)

| Attempt | Result |
| --- | --- |
| `--max-num-batched-tokens 8192` (chunked prefill) | still BROKEN |
| MC2 off (`VLLM_ASCEND_ENABLE_FUSED_MC2=0`) + no `--enable-expert-parallel` | still BROKEN |
| `--enforce-eager` (no OOT compile / no CUDAGraph) | still BROKEN |
| RoPE `--hf-overrides factor=4.0` vs `1.0` | both BROKEN |
| `/no_think` (system msg) or `enable_thinking=false` | still BROKEN (long); helps only short tasks |
| `repetition_penalty=1.05 / 1.1` | still BROKEN (so not a plain repetition that sampling can fix) |
| SGLang (same weights, `--reasoning-parser deepseek-r1`) | **works** (coherent, JSON, stop) |

## 6. Supporting observations

- The corrupted output starts garbled at the **first generated token** for long prompts → the encoded context itself appears corrupted before/at prefill-decode transition, not a mid-roll divergence.
- `enable_chunked_prefill=True`, `compile_ranges_endpoints=[2048]` (from log).
- Possible related upstream issues (same family, DeepSeek + long-context/repeat on vLLM-Ascend):
  - #13661 `dsv4f0731 will repeat and repeat hungup`
  - #14118 `Prompt corruption/leak under high concurrency with prefix caching enabled for DeepSeek-...`
  - #9983 `Disable fused MC2 ... to prevent logit corruption`
  - #5823 (closed) `mla_v1.py ... strongly bound to deepseek_yarn rope_type` — DeepSeek MLA rope is custom on Ascend
  - #12723 / #12820 — examples of Ascend rope silently corrupting positions / QK

2. Any fix/workaround for long-context (>8k chars) correctness on vLLM-Ascend for DeepSeek-V2 models?
