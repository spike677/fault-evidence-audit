# FP-A11 aclnn 接口检视（fpa11-aclnn-review）

对用户指定的 aclnn 接口（如 aclnnTopk）做 FP-A11 专项源码检视：先定位算子实现，再按清单逐项核查，每个结论给出**文件 + 行号 + 推导链**证据，命中即出 Bug 卡，输出检视报告。**本模式特殊纪律：① 缺陷是「原型/资料声明支持某 dtype，底层 kernel 未实现该分支」——行为既非正确计算也非明确拦截，常表现为编译报错或运行期异常；② 触发签名 `DT_DOUBLE|double` 普遍存在，命中只表示「值得人工核」——必须给出「声明支持（proto/资料）vs 实现缺失（kernel 分派）」的不一致推导链；③ 判定须双向：正向（声明支持则应正确计算/拆分模拟）与反向（不应支持则应明确拦截报错）——「底层报错」不等于「已正确拦截」；④ 与 A10（double 标量 attr）同源但对象不同，按「张量 dtype vs 标量 attr」分。**

## 0. 与相邻模式的边界

| 相邻模式 | 分工 |
|---|---|
| FP-A10（原型 Attr 不支持 Double） | **张量 vs 标量**二分：A11 是**张量 dtype**（输入/输出 double）底层不支持；A10 是**标量 Attr** 的 double 承载/解析降级。两者同源于「高精度值在低精度链路上被静默降级」，按承载对象归属并双向关联 |
| FP-B01（支持面校验过严误拦截合法输入） | **同属「支持面声明 vs 实际行为」家族**：B01 是**校验过严、拦了合法输入**；A11 是**声明支持却未实现**（实际被底层报错拦截）——方向相反，报告双向关联 |
| FP-A13（输入尾数截断才能通过精度标准） | A13 是输入预处理阶段的**尾数截断**；A11 是**dtype 整体不支持**——按「精度截断 vs 类型缺失」分 |
| FP-A09（对标 TF 语义与 PTA 不一致） | A09 是**语义/默认值**对标差异；A11 是**dtype 支持面**缺失——语义面归 A09，类型支持面归 A11 |
| FP-E01（golden/UT 期望值失配） | double 用例缺失时 UT **天然漏检**——须专门构造 double 正向/反向用例 |
| FP-F04（交付面缺失） | 同属「声明与交付不一致」家族：F04 是**不报错地失败**（交付面）；A11 是**声明支持但实现缺失**（支持面）——按面归属 |

**症状反查定位**：原型/资料声明支持 double 但**编译期报错** → 「声明支持但未实现」面（清单①）；double 输入运行期功能/精度异常 → float64 拆分模拟缺失面（清单②）；接口层放行 double、底层 kernel 报错 → 分派与拦截缺失面（清单③④）；同型异 dtype（如 int16）也出现「声明支持但底层不支持」 → 横向参照面（清单⑤）。

## 1. FP-A11 模式卡摘要（检视依据，源自本库 `patterns/FP-A/FP-A11.md`，v3.1）

- **编号 / 名称**：FP-A11 AiCore 不支持 double 类型 ｜ **类别**：精度 ｜ **风险**：高（S3×O3=9）｜ **状态**：活跃
- **适用声明头**（照抄卡片）：仓 All ｜ 侧别 All ｜ 载体 Kernel源码,IR与图配置 ｜ 触发 DT_DOUBLE|double ｜ 默认启用 true
- **skill 核查面**：侧别 All——skill 落地为 `op_kernel/` 的 dtype 分派与 float64 分支实现（含 arch35 / regbase / SIMT 等架构变体）与 `op_host` 的 `*_def.cpp`（proto 声明的支持 dtype 列表，即「IR与图配置」的落地处）；延伸至 `op_api` 的 dtype 校验/拦截与 `docs/` 的 dtype 支持说明
- **故障机理**：AiCore 硬件无 float64 单元，double 路径既未正确拆分模拟也未明确拦截，行为未定义。
- **触发条件**：用户显式请求 double dtype 输入/输出。
- **典型表现**：double 输入精度/功能异常。
- **源码审查映射点**：float64 分支处理：是否正确拆分模拟或明确拦截报错。
- **检测签名**（命中即候选缺陷点位）：`DT_DOUBLE|double`（double 分派与实现定位点）。
- **测试拦截建议**：double dtype 正向（拆分模拟结果比对）与反向（应拦截场景必须报错）用例。
- **实证案例**：ops-nn **#2121** sort **不支持 double 类型数据处理**，导致 aclnnTopk 在部分场景下（先调 sort 再取前 k）出错（ascend950）——**典型「原型声明支持但实现不支持」**；ops-math **#2808** space_to_batch_nd「配置支持 double，实际编译过程不支持 double，会导致编译出错」；ops-math **#2842** batch_to_space 编译 double 输入报错；ops-nn **#2758** aclnnIndexCopy 对 int16 同样出现「原型/接口层支持但底层算子不支持」的报错（同型异 dtype，可作横向参照）。**共性特征：算子原型/资料声明支持某 dtype，底层 kernel 未实现该分支，行为既非正确计算也非明确拦截。**
- **关联**：FP-A10、FP-B01（B01 是该拦不拦的反面：此处是声明支持却未实现，实际被底层报错拦截）。

## 2. 检视输入与算子定位

**输入**：aclnn 接口名（必填，如 `aclnnTopk`）；可选 ref（默认 master）、指定仓（默认自动定位）；可选现象描述（是否编译报错 / 运行期异常 / 声明支持的 dtype 清单——用于直接定位支持面）；可选目标 dtype（double / int16 等同型异 dtype）。

**接口名 → 算子目录换算**：去 `aclnn` 前缀 + 驼峰转下划线小写：
`aclnnTopk → topk`、`aclnnSpaceToBatchNd → space_to_batch_nd`、`aclnnBatchToSpace → batch_to_space`。

**仓定位顺序**（GitCode `cann` 组织，逐仓用目录列表确认）：`ops-nn`（index/sort 类——实证集中地）→ `ops-math`（conversion/math 类）→ `ops-transformer` → `ops-cv`。**类目名不总与直觉一致**，以目录列表为准。FP-A11 高发面：排序/索引类算子（sort/topk）、shape 变换类（space_to_batch 系列）、原型声明 dtype 列表宽而 kernel 分派窄的算子、含 int16 等同型异 dtype 问题的算子。

**算子目录结构约定**（以实证算子为例，具体布局以目录列表为准）：

```text
{类别}/{op_name}/
├── op_host/                  # *_def.cpp（proto 支持 dtype 列表）——主检视面之一
│   └── op_api/               # aclnn_*.cpp（dtype 校验/拦截）——主检视面之一
├── op_kernel/                # dtype 分派与 float64 分支实现——主检视面之一
│   └── arch35/ regbase/ ...  # 架构变体
├── docs/                     # aclnn*.md——dtype 支持说明依据
└── tests/  examples/
```

## 4. 检视清单（每点：查什么 → 何处 → 命中判据）

对算子的 `op_host`（proto 支持 dtype 列表）/ `op_kernel`（dtype 分派与 float64 分支）/ `op_api`（dtype 校验拦截）逐点核查，`docs/` 同步核对，**每点先查命中面、再做反证排除**；已正确拆分模拟或已明确拦截的实现要记录为防护面证据。

### ① 原型声明与底层实现一致性
- 查什么：`*_def.cpp` proto 声明的**支持 dtype 列表**（含 `DT_DOUBLE`）与 `docs/aclnn*.md` 资料声明，是否与 `op_kernel` 实际实现的分派分支**一一对应**——声明支持但 kernel 无该 dtype 分支即「声明支持但未实现」（实证 #2121：sort 不支持 double 导致 aclnnTopk 出错；#2808 space_to_batch_nd 配置支持 double 但编译不支持）。
- 何处：`op_host/*_def.cpp` 的 dtype 列表、`op_kernel` 的模板实例化/分派、`docs/`。
- 命中判据：声明支持某 dtype 但 kernel 无对应实现/模板实例 ⇒ 命中候选。

### ② float64 拆分模拟是否正确
- 查什么：double 路径若走**拆分模拟**（用两个 float / 高低位组合模拟 float64），拆分与重组是否正确、是否覆盖全部运算（加减乘除、比较、归约）；精度是否满足 double 语义预期；若未模拟，是否走低精度近似（属静默降级）。
- 何处：`op_kernel` 的 float64 拆分实现、dtype 分派分支。
- 命中判据：存在「声明支持 double 但无拆分模拟、直接低精度计算」的路径 ⇒ 命中候选。

### ③ 明确拦截报错（该拦则拦）
- 查什么：**不支持**的 dtype 是否在 `op_api` 校验层**明确拦截并返回正确错误码**（而非透传到 kernel 后才报错/编译期才报错）——实证 #2808/#2842 的「编译出错」「编译报错」即拦截缺失/位置错误；「底层报错」不等于「已正确拦截」。
- 何处：`op_api` 的 dtype 校验、`op_host` 的 dtype 推导。
- 命中判据：不支持的 dtype 未被接口层拦截、错误码不正确、或报错时机晚于入口校验 ⇒ 命中候选。

### ④ dtype 分派与校验层一致性
- 查什么：`op_api` 校验放行的 dtype 集合与 kernel 实际支持集合是否**一致**（接口层放行 vs 底层报错的错配）；模板实例化是否覆盖校验放行的全部 dtype；多架构（arch35/regbase）分派的 dtype 支持是否一致。
- 何处：`op_api` 校验分支、kernel 模板实例化、架构变体。
- 命中判据：校验放行集合 ⊃ kernel 支持集合 ⇒ 命中候选。

### ⑤ 同型异 dtype 横向参照
- 查什么：同一算子在**其他 dtype**（如 int16，实证 #2758 aclnnIndexCopy）上是否也出现「原型/接口层支持但底层不支持」——同型异 dtype 问题常同源，修复一个 dtype 后须复核全部 dtype 的支持面。
- 何处：proto dtype 列表 × kernel 分派矩阵。
- 命中判据：存在多个 dtype 的声明/实现不一致 ⇒ 命中候选（横向扩展检查）。

### ⑥ double 正向/反向用例覆盖
- 查什么：`tests/` 是否有 double dtype **正向用例**（拆分模拟结果与高精度参考比对）与**反向用例**（应拦截场景必须报错且错误码正确）；是否覆盖全部声明支持的 dtype。
- 何处：`tests/` 的 dtype 用例矩阵。
- 命中判据：无 double 正向/反向用例 / dtype 矩阵缺档 ⇒ 记观察项（测试面缺口）。

## 5. 检视流程

1. **定界**：换算 op 目录、确认所在仓与 ref；记录用户现象（编译报错 / 运行期异常 / 声明支持的 dtype 清单）。
2. **枚举**：目录列表列出 `op_host/*_def.cpp`、`op_api`、`op_kernel`（含架构子目录）、`docs/`、`tests/`，产出文件清单。
3. **触发词扫描**：按 `DT_DOUBLE|double`、`DT_FLOAT|DT_INT16`、`dtype|DataType`、模板实例化列表定位风险面（本地仓用 grep；API 模式逐文件拉取后检查）。**触发为关键词：签名零命中时清单仍须逐项核查完毕**。
4. **逐点核查**：按第 4 节 ①~⑥ 记录命中面与防护面证据（文件:行号）；构建「声明支持 dtype 集合 vs kernel 实现集合」对照矩阵。
5. **反证排除**：声明与实现一一对应、double 有正确拆分模拟、不支持的 dtype 已在接口层明确拦截且错误码正确 → 明确写出反证理由。
6. **判定**：按第 7 节标准给出 命中 / 观察项 / 反证排除。
7. **GitCode 查重**（仅命中项）：issues API 按接口名 + `double|dtype|不支持|编译报错` 检索，逐条比对是否同机理；无同机理才立卡。
8. **业务可达性核查**（仅命中项）：判 B 等级、定业务影响类型、给处置建议；默认保守（无法证明不可达即记 B3），降档须附证据；B 不改 S×O 档位。
9. **出报告**：按第 8 节模板落盘；所有结论标注「静态推演，需 double 正向/反向用例实测确认」并附实测方案。

## 6. 风险定级（S×O）与业务影响评估（B 轴）

- **S**：S3（double 输入精度/功能异常或编译失败——任务无法按声明语义完成）；S2（仅部分 dtype/部分场景异常）；S1（不影响结果的支持面文档偏差）。
- **O**：O3 = ≥2 条独立实证；O2 = 1 条独立实证；O1 = 仅静态扫描命中或团队笔记（实证 = 确认对应的 issue / PR，或经跨仓、跨分支核验确认的缺陷记录，同权计入）。静态推演命中且无实证默认 **O1**；升档须在报告中给出实证依据。
- **风险 = S×O**：≥6 高；3/4 中；1/2 低。FP-A11 基准：模式卡整体 S3×O3=9（高）；纯静态命中 S3×O1=3（中，暂定，实测后复评）。

### B 轴：业务影响评估（与 S×O 正交；报告层新增，不改卡片定级）

S×O 回答"多严重、多常见"，**不回答"真实业务能不能碰到"**。B 轴补这一问，只决定**修复优先级建议**，**不参与 S/O 取值、不改 S×O 档位与卡片元数据**。

**业务可达性（B）**——触发条件在真实负载中的可达程度：

| 等级 | 判据 | 证据要求 |
|---|---|---|
| B3 现实可达 | 主流框架/公开模型默认路径即可命中（如 PTA/torch_npu、vLLM、MindIE 常规调用） | 调用方或公开负载来源 |
| B2 条件可达 | 需特定 attr/dtype/shape 组合，业务中存在但非默认 | 该组合的业务来源 |
| B1 边界/不可达 | 需极端、超规格或非法参数（超出接口合理上限的 shape、退化/非法输入） | "为何不可达"的说明 |

- **默认保守**：无法证明不可达 → 记 **B3**；降为 B1/B2 必须附证据，**不得仅凭"业务应该不会这么用"**。
- 超规格参数是否算 B1 取决于**接口契约**：契约允许但业务不用 → B1；契约不允许（本应报错）→ 属校验缺失（FP-B04/B05 类），另行归属。

**业务影响类型**（命中后对用户可见结果的后果，用业务语言表述）：静默精度损失（模型效果下降 / loss 不收敛 / 偶发 NaN）｜ 任务失败中断（报错 / 崩溃 / 挂死）｜ 性能退化 ｜ 仅可观测性（日志 / 错误码 / 文档，不影响结果）。

**处置建议**（由两轴推导的报告结论，非新档位）：

| S×O \ B | B3 现实可达 | B2 条件可达 | B1 边界/不可达 |
|---|---|---|---|
| 高（≥6） | 尽快修 | 尽快修 | 排期修 |
| 中（3/4） | 尽快修 | 排期修 | 记录（业务难以触达） |
| 低（1/2） | 排期修 | 记录 | 记录 |

## 7. 判定标准与反误报原则

- **签名 / 触发词命中 ≠ 成立**：`double`/`DT_DOUBLE` 在算子中普遍存在且多数正确——命中只是定位提示，必须给出「声明支持集合 ⊃ kernel 实现集合」的不一致推导。
- **三种判定**：
  - **命中**（可静态证缺陷路径）：「声明支持某 dtype 但无对应实现 / 无拆分模拟 / 未明确拦截」的推导链完整 + 触发 dtype 可构造 → 立 Bug 卡（档级按实测证据定）；
  - **观察项**：不一致存疑但报错与否依赖实测、或仅测试面覆盖缺口 → 记录并附实测方案，按 S3×O1 暂定；
  - **反证排除**：声明与实现一一对应、double 拆分模拟正确、不支持 dtype 已明确拦截且错误码正确 → 明确写出反证理由（防护面证据）。
- **「底层报错」不是「已正确拦截」**：编译期/运行期底层报错属拦截缺失或位置错误；正确做法是接口层明确拦截并返回约定错误码。
- **双向判定**：正向核「声明支持则须正确计算/拆分模拟」，反向核「不应支持则须明确拦截报错」——只核一侧即漏判。
- **同型异 dtype 需横向复核**：修复一个 dtype 后须复核 proto 列表中的**全部** dtype 支持面。
- **不臆造行号**：每条证据必须是实际读到的 文件:行号；引用实证样板时同样给出路径与行号，issue 时点行号与本仓 HEAD 漂移时注明。

### 判定纪律补充（v3.6）：非对称增减、证据等级与误判记录

**增减不对称**：允许追加候选（有据即可，错了可由用户排除）；**撤销或否决候选必须附 `[文件]:[行号] [代码行]` 负向证据**。无证据的「看起来没问题」一律记为「未核查」，不得计入反证排除，也不得据此下调等级——否决造成的漏报用户不可见、不可恢复。

- **证据等级**（Bug 卡必填）：`静态可证` = 推导链完整且触发输入可静态构造；`需实测确认` = 依赖运行时输入规模、设备行为或环境差异。标 `需实测确认` 的条目**不得以「命中」名义出卡**，按观察项记录并附实测用例。
- **Agent 误判记录**（Bug 卡必填）：本次被推翻的假设、推翻它的证据（`[文件]:[行号] [代码行]` 或实测输出）、判定标准是否随之修订；无推翻写「无」。
- **误判回流**：同类误判在 3 次检视中重复出现，登记至 `cases/misjudgments.jsonl`（字段见 `cases/README.md`），并在本模式判定标准中新增对应防线；守门 C19d 校验台账字段合法。

## 10. 能力边界与自检（v3.8）

### 能力边界

- **静态可证**：清单里能在源码内给出「`文件:行号` + 推导链」的部分，按第 7 节判据出卡。
- **需实测确认**：依赖运行时输入规模、设备行为或环境差异的结论，只能记观察项并附实测用例（证据等级见第 7 节）。
- **不覆盖**：本模式以外的机理（边界见第 0 节）与仓外框架侧行为；`TRIAGE.md` 只负责收敛候选，不构成判定依据。
- **找不到 ≠ 没有**：按清单未命中只说明「本轮未发现」，不得表述为「该算子无此缺陷」；抽样核查须在报告写明抽样口径。

