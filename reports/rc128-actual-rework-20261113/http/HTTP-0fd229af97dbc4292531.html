保序AllReduce在单轮元素数不能被rankSize整除且接近CCL buffer容量上限时，ReduceScatter尾块写入可能越界。大数据量多轮执行时，最后一轮也可能触发。

复现条件：实际CCL buffer为200MiB，8个rank，FP32，每rank输入26,214,399个元素。前后半区各100MiB，末rank的尾块为3,276,806个元素，接收8份尾块需要104,857,792字节，比后半区容量多192字节。仿真在SendSingleRankSlice调用HcommWriteOnThread时返回HCCL_E_MEMORY。实际buffer改为400MiB后，对应边界仍存在相同问题。

原因是OrchestrateLoop只限制每轮总数据量，没有计入余数全部追加到末rank分片后，rankSize份尾块占用的临时空间。

拟在OrchestrateLoop中按实际后半区容量限制尾块大小，将放不下的余数留到下一轮；保留原有每轮总量上限和RS/AG模板。整除及原本安全的轮次保持原有分块。

📋 问题摘要

保序AllReduce在元素数非整除rankSize且接近buffer上限时，OrchestrateLoop未计入尾块追加空间导致ReduceScatter尾块写入越界

🔍 根因分析

Issue 描述了保序 AllReduce 中一个内存越界缺陷。在 OrchestrateLoop 函数中，每轮数据量上限仅按总数据量限制，未考虑非整除余数全部追加到末 rank 分片后，rankSize 份尾块占用的临时空间。具体场景验证：8 rank、FP32（4字节）、每 rank 输入 26,214,399 个元素，CCL buffer 200MiB（前后半区各 100MiB = 104,857,600 字节）。26,214,399 = 8 × 3,276,799 + 7，末 rank 尾块为 3,276,806 个元素，接收 8 份尾块需 3,276,806 × 4 × 8 = 104,857,792 字节，超出后半区容量 192 字节。仿真在 SendSingleRankSlice 调用 HcommWriteOnThread 时返回 HCCL_E_MEMORY。实际运行中此越界可能导致内存污染或崩溃。提供的代码文件为文档和测试工具，未包含 OrchestrateLoop、SendSingleRankSlice、HcommWriteOnThread 的实际实现源码，无法直接在代码中验证，但 Issue 的数学推导自洽、函数名具体、复现条件明确，问题可信度高。需查看包含 OrchestrateLoop 实现的源文件（可能在 src/ 目录下的保序 AllReduce 算法实现中）以最终确认。

✅ Issue 已解决

关联 PR

  • PR #3914：[fix] 修复保序AllReduce非整除尾块CCL buffer越界

修改方案

问题根因：保序 AllReduce 的 OrchestrateLoop 函数在编排多轮通信时，仅以 maxCountPerLoop（每轮总数据量上限）来约束每轮处理规模，未考虑非整除场景下余数全部追加到末 rank 分片后，末 rank 需要暂存 rankSize 份尾块的临时空间需求。当数据量接近 CCL buffer 后半区容量上限时，尾块暂存空间超出后半区容量，导致 ReduceScatter 阶段 HcommWriteOnThread 写入越界，返回 HCCL_E_MEMORY。

修复要点（仅修改 src/ops/all_reduce/algorithm/executor/ins_v2_all_reduce_order_preserved_executor.cc 中的 OrchestrateLoop）：

  1. 尾块容量上限计算：保留原有 maxCountPerLoop 不变，新增根据 CCL buffer 后半区实际容量反算每份尾块的元素数上限。末 rank 需接收 rankSize 份尾块，因此单份尾块上限 = 后半区容量 / (rankSize × dtypeSize)。

  2. 余数分摊到多轮：每轮只保留尾块容量能容纳的余数部分，超出部分留到下一轮处理。通过按实际已处理元素数判断循环结束条件，确保所有数据都被正确处理。

  3. 兼容性保证：整除场景及原本安全的轮次保持原有分块逻辑不变，RS/AG 模板、归约顺序和对外接口均无改动。修正了 buffer 用途和容量计算的相关注释。

经验沉淀

  • 问题模式：临时空间放大效应被忽略。这类问题的典型特征是：算法编排时只关注了"单轮总数据量"是否在 buffer 限制内，却忽略了通信模式本身会导致某个 rank 需要暂存多份数据（如末 rank 暂存 rankSize 份尾块），实际临时空间是单份数据的 rankSize 倍。触发条件是：非整除 + 数据量接近 buffer 上限 + 多轮执行的最后一轮。

  • 排查思路：从报错点反推容量计算链路。当遇到 HCCL_E_MEMORY 这类 buffer 越界错误时，应从报错调用栈（如 SendSingleRankSlice → HcommWriteOnThread）定位到具体写入的 rank 和分片，再反推该分片的大小是如何计算出来的。关键在于区分"每轮总量上限"和"单个 rank 的临时空间上限"是否一致——如果不一致，说明编排逻辑存在容量计算盲区。

  • 修复策略：按最受限维度约束，而非按总量约束。修复的核心思路是将约束维度从"每轮总数据量"细化为"单个 rank 的最大临时空间"。对于尾块追加到末 rank 的场景，应以 后半区容量 / rankSize 作为单份尾块上限，将超出部分滚动到下一轮。这样既不改变通信模板和归约语义，又能精确控制内存使用。

  • 预防措施：容量计算需考虑通信拓扑的放大系数。在设计集合通信算法的轮次编排时，应始终问一个问题：每个 rank 在某一轮中实际需要暂存多少份数据？ 这个份数可能等于 rankSize（如 ReduceScatter 末 rank 收集所有尾块）、2（如双 buffer 乒乓）或其他系数。容量上限应按 buffer容量 / 放大系数 计算，而非直接用 buffer容量。建议在编排函数中加入断言或预检查，验证每轮每个 rank 的临时空间需求不超过 buffer 容量。
