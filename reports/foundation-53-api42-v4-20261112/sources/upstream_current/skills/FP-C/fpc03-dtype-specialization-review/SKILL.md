# FP-C03 aclnn 接口检视（fpc03-dtype-specialization-review）

对用户指定的 aclnn 接口（如 aclnnSquaredDifference、aclnnTanh）做 FP-C03 专项性能源码检视：先定位算子实现，再按清单逐项核查，每个结论给出**文件 + 行号 + 推导链**证据，命中即出 Bug 卡，输出检视报告。**本模式特殊纪律：① 结果对、只是 dtype 间差异异常——静态检视只能产出「嫌疑点」，任何「劣化 N 倍」的量化结论必须以基线差分实测为准；② 判据是「同 shape、同硬件、同版本下两种 dtype 的耗时差异异常」，缺双 dtype 对比轴即不成立；③ 缺陷形态是「dtype 特化路径残缺」——bf16（或 fp16）侧存在硬件/API 能力缺口需软件补救，或 DAG 中残留可由硬件指令替代的冗余 Cast 节点。**

## 0. 与相邻模式的边界

| 相邻模式 | 分工 |
|---|---|
| FP-C02（A2 上 fp16 性能不如 bf16） | **同一现象的对称面**：C02 残缺在 **fp16 侧**（fp16 被派发到旧/降级实现）；C03 残缺在 **bf16 侧特化**（无原生 BF16 算术指令 / 公开 API 缺口 / 冗余 Cast DAG）。两条共用「fp16/bf16 双 dtype 性能对比基线」，常合并执行；判定时先定向「哪一侧路径残缺」再归条 |
| FP-C01（端到端耗时占比高） | C01 看绝对耗时与跨版本回归，**无 dtype 轴**；C03 必须给出「同 shape 同硬件下双 dtype 差异」才成立 |
| FP-C06（A5 性能劣于 A2） | 维度不同：C06 的轴是 **SOC 代际**；C03 的轴是 **dtype**。同一份「性能不达标」现象先确认对比轴（#2535 的 BF16 API 缺口按 dtype 轴归本条，不按代际归 C06） |
| FP-A17（A1/A2 代际精度差异） | 硬件能力缺口若表现为**精度不一致**则归 A17；若表现为**性能不达标**（如为还原舍入语义多写转换）则归本条——同一 API 缺口两个后果面 |
| FP-G01（挂死/超时） | C03 是「**慢但能完成**」；G01 是「**根本没完成**」（日志无进展） |

**症状反查定位**：同 shape、同硬件、同版本下**两种 dtype 性能差异异常**、精度全对 → C03；若差异方向是「**fp16 慢于 bf16**」且 fp16 走了旧/降级实现 → C02；若 bf16 侧不达标源于**硬件无原生 BF16 指令、公开 Ascend C API 亦无对应算子**（需手写转换往返）→ C03 的 API 缺口形态；与 dtype 无关的绝对耗时高或跨版本回归 → C01。

## 1. FP-C03 模式卡摘要（检视依据，源自本库 `patterns/FP-C/FP-C03.md`，v3.1）

- **编号 / 名称**：FP-C03 bf16 与 fp16 性能差异大 ｜ **类别**：性能 ｜ **风险**：高（S2×O3=6）｜ **状态**：活跃
- **适用声明头**（照抄卡片）：仓 All ｜ 侧别 Kernel ｜ 载体 Kernel源码 ｜ 触发 bfloat16|bf16|half ｜ 默认启用 true
- **skill 核查面**：侧别 Kernel——skill 落地为 op_kernel 的 dtype 模板变体（bf16/fp16 特化分支、arch 子目录变体）与 DAG 节点拓扑（Cast 节点链）；延伸至 op_host tiling 的 dtype 分流与 tilingkey 派发
- **故障机理**：**实现中 dtype 特化不完整**——bf16 / fp16 侧缺少完整的优化路径：① 硬件无该 dtype 的原生算术指令、公开 Ascend C API 亦无对应算子，须**手写多次转换往返**（VCONV 等）补救，而参考实现（TBE）由编译器自动 lowering 只需更少次数；② DAG 中存在**可由硬件指令（`LoadAlign` / `StoreAlign` 类）直接完成类型转换**的冗余软件 Cast 节点（`OpCopyIn0Cast` / `OpResultCast` 类）。
- **触发条件**：双 dtype（bf16 + fp16）支持的算子；尤以需要 bf16 算术/广播的算子、DAG 化（图模式）算子的 dtype 特化路径为高发面。
- **典型表现**：**两种 dtype 性能差异异常**（同算子 bf16 与 fp16 耗时差异远超合理区间）；bf16 用例性能不达标；精度全对、功能全对、无报错，仅耗时变长；多 dtype 用例横向对比才暴露。
- **源码审查映射点**：dtype 特化分支完整性。
- **检测签名**（命中即候选缺陷点位）：`bfloat16|bf16` 与 `half|float16` 在同一 dtype 分支组同现；`Cast` 与 dtype 特化分支同现；`OpCopyIn0Cast|OpResultCast` 类**成对出现的软件 Cast 节点**；`VCONV` 类转换指令重复出现（次数与参考实现不匹配）；`LoadAlign|StoreAlign` 与 Cast 同现（硬件指令本可完成转换的旁证）。
- **审查关键词**（命中只表示值得人工审）：`Cast`——**须人工确认是否语义必须**：为还原参考实现（TBE）的中间舍入语义而手写的转换属「语义必须」（#2535），不可简单判为冗余；`VCONV` / 转换指令计数与参考实现比对；`OpCopyIn` / `OpResult` 前缀的 DAG 节点命名。
- **测试拦截建议**：双 dtype 性能对比基线（与 FP-C02 合并执行）；同 shape 同硬件记录 bf16/fp16 耗时比值；对 bf16 广播 / 多维广播用例单独成类（#2535 即广播用例不达标）；「精度 pass + 双 dtype 耗时对比」双判据。
- **实证案例**：ops-math **#2535** SquaredDifference（910B/DAV2201）**硬件无 BF16 原生算术指令**，公开 Ascend C API 亦无 BF16 Sub/Mul，为还原 TBE 的中间舍入语义须**手写 5 次 VCONV 往返**（TBE 编译器自动 lowering 仅 3 次），BF16 广播用例性能不达标（`[11,41,53,89]→[..,1]` bf16：TBE 17.77us vs AscendC 37.74us；多维广播 273.33→698.66us），issue 明示「影响所有需要 BF16 计算的算子」；ops-math **#2993** tanh（arch35）FP16/BF16 路径 DAG 存在 `OpCopyIn0Cast` / `OpResultCast` 两个冗余软件 Cast 节点（`LoadAlign` / `StoreAlign` 硬件指令本可完成类型转换），额外寄存器搬运与转换指令开销致性能低于最优，**PR #5250 移除冗余节点**；同族现象另见 ops-nn **#5303** leaky_relu 冗余 Cast DAG（收录于 FP-C02）。**共性特征：FP16/BF16 特化路径残缺（API 缺口 / 冗余 Cast DAG），致 dtype 间性能差异异常。**
- **关联**：FP-C02（同一现象的对称面）、FP-C01（性能总类）。

## 2. 检视输入与算子定位

**输入**：aclnn 接口名（必填，如 `aclnnSquaredDifference`）；可选 ref（默认 master）、指定仓（默认自动定位）；可选现象描述（双 dtype 耗时数据——用于反查优先清单点）；可选复现条件（SOC/arch + shape + dtype + 是否广播——#2535 类 API 缺口对广播形态敏感）。

**接口名 → 算子目录换算**：去 `aclnn` 前缀 + 驼峰转下划线小写：
`aclnnSquaredDifference → squared_difference`、`aclnnTanh → tanh`、`aclnnLeakyRelu → leaky_relu`。

**仓定位顺序**（GitCode `cann` 组织，逐仓用目录列表确认）：`ops-math`（math/conversion 类）→ `ops-nn`（norm/loss/activation/matmul 类）→ `ops-cv`（image/vision 类）→ `ops-transformer`（attention/moe 类）。**类目名不总与直觉一致**（如 tanh 可能在 `activation/` 或 `math/`），以目录列表为准。FP-C03 高发面：需要 bf16 算术/广播的逐元素算子、DAG 化（图模式）算子的 dtype 特化路径、含 `arch35` 等新架构子目录的模板族、手写转换指令（VCONV 类）的 kernel 实现。

**算子目录结构约定**（已验证示例 `cann/ops-math` → `math/squared_difference/`）：

```text
{类别}/{op_name}/
├── op_host/
│   ├── *_tiling*.cpp      # dtype 分流与 tilingkey 派发
│   └── config/<soc>/      # *_binary.json（按 dtype / arch 的派发配置）
├── op_kernel/             # kernel 模板：bf16/fp16/fp32 变体 + arch35 等子目录（转换指令与 DAG 检视面）
├── op_api/（或 op_host/op_api/）  # aclnn_*.cpp——dtype 决定的实现选择点
├── op_graph/  tests/  docs/  examples/
└── CMakeLists.txt
```

**aclnn 出口位置提示**：多数算子的 aclnn 出口在 `op_host/op_api/` 或顶层 `op_api/`（`aclnn_*.cpp`），以目录列表与 `docs/aclnn*.md` 确认。

## 4. dtype 特化检视清单（每点：查什么 → 何处 → 命中判据）

对算子的 op_kernel（dtype 模板变体 + DAG 拓扑）/ op_host tiling（dtype 分流）/ op_api（实现选择）全部相关文件逐点核查，**每点先查命中面、再做反证排除**，防护面（已完整的特化、语义必须的转换）也要记录。

### ① dtype 特化分支完整性
- 查什么：把算子所有 **dtype → 实现** 的派发点列全（dtype 分支 / tilingkey / binary.json 分派），逐 dtype 填「落到哪个 kernel 变体 / DAG 拓扑」；重点看 bf16 侧是否有**专属优化实现**，还是复用 fp32/通用实现（特化残缺）。
- 何处：op_kernel 模板实例化清单、op_host tiling 的 dtype 分流、`config/<soc>/*_binary.json`。
- 命中判据：bf16 分支无专属实现 / 落到通用或 fp32 路径，且同算子 fp16 有专属实现（或反之）⇒ 命中（给出派发点与两实现入口的行号对表）。

### ② 硬件/API 能力缺口与软件补救代价
- 查什么：目标硬件是否有该 dtype 的**原生算术指令**、公开 Ascend C API 是否有对应算子（如 BF16 Sub/Mul）；若无，kernel 中的补救实现（手写转换往返）**次数**与参考实现（TBE 自动 lowering）是否一致；转换是否可减少或合并。
- 何处：op_kernel 的算术实现体、转换指令序列（`VCONV` 类）计数点。
- 命中判据：可指认「手写转换次数 > 参考实现次数」且差异源于实现选择而非语义必须 ⇒ 命中（实证 #2535：手写 5 次 VCONV 往返 vs TBE 3 次）；须同时记录「缺口为硬件/API 客观限制」这一前提，避免把能力缺口误判为实现缺陷。

### ③ DAG 冗余软件 Cast 节点
- 查什么：bf16/fp16 路径的 DAG 是否存在**成对的软件 Cast 节点**（`OpCopyIn0Cast` / `OpResultCast` 类），而该类型转换本可由硬件指令（`LoadAlign` / `StoreAlign` 类）在搬入/搬出时直接完成；对照 fp32 或其他已精简路径。
- 何处：op_kernel 的 DAG 定义 / 图节点注册、arch35 等新架构子目录变体（实证 #2993 tanh arch35）。
- 命中判据：DAG 中可指认「结果与省略等价」的 Cast 节点对，且硬件指令可承担同一转换 ⇒ 命中（修复形态见 PR #5250 移除冗余节点）。

### ④ 特化路径的对称性与同族一致性
- 查什么：同仓同族算子（逐元素 / 激活类）的 dtype 特化写法是否一致——某一算子已移除冗余 Cast 而本算子仍保留（或反之），属「同族不同步」；与 FP-C02 #5303 leaky_relu 的 `LeakyReluCastDag` 形态同族比对。
- 何处：同仓同类别算子的 op_kernel 模板与 DAG 定义（同族样板）。
- 命中判据：同族样板已精简而本算子未精简 ⇒ 记录为嫌疑点并对照样板反证。

### ⑤ 语义必须的反证排除（防误报）
- 查什么：手写转换 / Cast 是否**为还原参考实现的中间舍入语义所必需**（#2535 即为此类：手写往返是为对齐 TBE 舍入语义，非可省略冗余）；转换次数是否已为实现该语义的最小值。
- 何处：转换的语义注释、与参考实现（TBE / golden）的舍入对齐说明。
- 命中判据：转换可被证明为语义必须且已达最小次数 ⇒ 反证排除（写出防护面与语义依据）。

### ⑥ 测试拦截面（双 dtype 基线）
- 查什么：tests / 评测脚本是否具备 **bf16/fp16 双 dtype 性能对比基线**；广播 / 多维广播用例是否单独成类（#2535 不达标用例即广播形态）。
- 何处：tests/ut、examples、评测配置。
- 命中判据：无双 dtype 对比项或未覆盖广播形态 ⇒ 记录为拦截缺口（与 FP-C02 合并执行）。

## 5. 检视流程

1. **定界**：换算 op 目录、确认所在仓与 ref/HEAD；确认对比轴为 dtype（非 SOC 代际、非版本）；确认用户是否提供双 dtype 耗时数据与复现条件（SOC/arch、shape、广播形态）。
2. **枚举**：目录列表列出 op_kernel（含 arch 子目录与 DAG 定义）/ op_host（tiling + config）/ op_api 全部相关文件，产出文件清单。
3. **触发词扫描**：按 `bfloat16|bf16`、`half|float16`、`Cast`、`OpCopyIn0Cast|OpResultCast`、`VCONV`、`LoadAlign|StoreAlign`、`CastDag` 定位风险面（本地仓用 grep；API 模式逐文件拉取后检查）。
4. **特化表构建**：以第 4 节 ① 建立「dtype → 实现 → 转换/DAG 节点」对表——后续所有清单点都在此表上比对。
5. **清单逐项核查**：每点记录命中面与防护面证据（文件:行号）；转换逐个确认是否语义必须（第 4 节 ⑤）。
6. **反证排除**：特化完整、转换语义必须且次数最小、DAG 已精简、同族一致 → 明确写出反证理由。
7. **判定**：按第 7 节标准给出 命中 / 观察项 / 反证排除。
8. **GitCode 查重**（仅命中项）：issues API 按接口名 + `bf16|fp16|性能|Cast|VCONV` 检索，逐条比对是否同机理；无同机理才立卡。
9. **业务可达性核查**（仅命中项）：判 B 等级、定业务影响类型、给处置建议；默认保守（无法证明不可达即记 B3），降档须附证据；B 不改 S×O 档位。
10. **出报告**：按第 8 节模板落盘；静态推演结论一律标注「需基线差分实测确认」，并附双 dtype 对比方案。

## 6. 风险定级（S×O）与业务影响评估（B 轴）

- **S**：S2（性能不达标 / 交付受限——bf16 广播等用例明显不达标）；S1（轻度资源浪费——冗余 Cast 节点带来的局部开销）。性能类缺陷不涉 S3/S4（结果仍正确）。
- **O**：O3 = ≥2 条独立实证；O2 = 1 条独立实证；O1 = 仅静态扫描命中或团队笔记（实证 = 确认对应的 issue / PR，或经跨仓、跨分支核验确认的缺陷记录，同权计入）。静态推演命中且无实证默认 **O1**；升档须在报告中给出实证依据。
- **风险 = S×O**：≥6 高；3/4 中；1/2 低。FP-C03 基准：模式卡整体 **S2×O3=6（高）**；纯静态命中 **S2×O1=2（低，暂定，量化劣化待基线差分实测后复评）**。

### B 轴：业务影响评估（与 S×O 正交；报告层新增，不改卡片定级）

S×O 回答"多严重、多常见"，**不回答"真实业务能不能碰到"**。B 轴补这一问，只决定**修复优先级建议**，**不参与 S/O 取值、不改 S×O 档位与卡片元数据**。

**业务可达性（B）**——触发条件在真实负载中的可达程度：

| 等级 | 判据 | 证据要求 |
|---|---|---|
| B3 现实可达 | 主流框架/公开模型默认路径即可命中（如 PTA/torch_npu、vLLM、MindIE 常规调用） | 调用方或公开负载来源 |
| B2 条件可达 | 需特定 attr/dtype/shape 组合，业务中存在但非默认 | 该组合的业务来源 |
| B1 边界/不可达 | 需极端、超规格或非法参数（超出接口合理上限的 shape、退化/非法输入） | "为何不可达"的说明 |

- **默认保守**：无法证明不可达 → 记 **B3**；降为 B1/B2 必须附证据，**不得仅凭"业务应该不会这么用"**。
- 超规格参数是否算 B1 取决于**接口契约**：契约允许但业务不用 → B1；契约不允许（本应报错）→ 属校验缺失（FP-B04/B05 类），另行归属。

**业务影响类型**（命中后对用户可见结果的后果，用业务语言表述）：静默精度损失（模型效果下降 / loss 不收敛 / 偶发 NaN）｜ 任务失败中断（报错 / 崩溃 / 挂死）｜ 性能退化 ｜ 仅可观测性（日志 / 错误码 / 文档，不影响结果）。

**处置建议**（由两轴推导的报告结论，非新档位）：

| S×O \ B | B3 现实可达 | B2 条件可达 | B1 边界/不可达 |
|---|---|---|---|
| 高（≥6） | 尽快修 | 尽快修 | 排期修 |
| 中（3/4） | 尽快修 | 排期修 | 记录（业务难以触达） |
| 低（1/2） | 排期修 | 记录 | 记录 |

## 7. 判定标准与反误报原则

- **性能类特殊纪律（务必贯彻）**：静态检视只能立「嫌疑点 / 优化项」——「特化残缺 / 冗余 Cast 节点」可静态证；但任何「劣化 N 倍 / 慢 X%」的量化结论**必须以基线差分实测为准**（同 shape、同硬件、同版本、bf16 vs fp16 双 dtype 对照），不可用代码审查替代性能基线看护。
- **三种判定**：
  - **命中**（可静态证残缺）：特化表显示某 dtype 无专属实现、或 DAG 中存在可省略的冗余 Cast 节点、或手写转换次数可指认超出语义所需 → 立 Bug 卡；
  - **观察项**：特化残缺存在但降级代价需实测（如 API 缺口下的转换次数差异）→ 记录并附双 dtype 基线方案，按 S2×O1 暂定；
  - **反证排除**：特化完整、转换语义必须且已达最小次数、DAG 已精简 → 明确写出反证理由与防护面证据。
- **硬件/API 能力缺口不等于实现缺陷**：#2535 中手写 5 次 VCONV 往返源于硬件无原生 BF16 算术指令且公开 API 无对应算子——判定须区分「客观能力缺口」与「实现选择不当」，前者作为背景记录，后者才立卡；对缺口类，报告应给出「可优化空间（如合并转换、改用硬件指令完成转换）」而非「实现错误」。
- **Cast / 转换命中 ≠ 冗余**：为还原中间舍入语义的手写转换属语义必须（#2535）；判定前必须过第 4 节 ⑤ 的语义必要性反证。
- **与 C02 的定向**：以「哪一侧路径残缺」定向——fp16 侧残缺（降级/旧路径）归 C02；bf16 侧残缺（API 缺口 / 冗余 Cast DAG）归 C03；两条常合并执行同一份双 dtype 基线。
- **不臆造行号**：每条证据必须是实际读到的 文件:行号；引用实证样板时同样给出路径与行号，issue 时点行号与本仓 HEAD 漂移时注明。

### 判定纪律补充（v3.6）：非对称增减、证据等级与误判记录

**增减不对称**：允许追加候选（有据即可，错了可由用户排除）；**撤销或否决候选必须附 `[文件]:[行号] [代码行]` 负向证据**。无证据的「看起来没问题」一律记为「未核查」，不得计入反证排除，也不得据此下调等级——否决造成的漏报用户不可见、不可恢复。

- **证据等级**（Bug 卡必填）：`静态可证` = 推导链完整且触发输入可静态构造；`需实测确认` = 依赖运行时输入规模、设备行为或环境差异。标 `需实测确认` 的条目**不得以「命中」名义出卡**，按观察项记录并附实测用例。
- **Agent 误判记录**（Bug 卡必填）：本次被推翻的假设、推翻它的证据（`[文件]:[行号] [代码行]` 或实测输出）、判定标准是否随之修订；无推翻写「无」。
- **误判回流**：同类误判在 3 次检视中重复出现，登记至 `cases/misjudgments.jsonl`（字段见 `cases/README.md`），并在本模式判定标准中新增对应防线；守门 C19d 校验台账字段合法。

## 9. 示例速览：aclnnSquaredDifference

- **定位**：`cann/ops-math` → `math/squared_difference/`（op_kernel 含 bf16/fp16 模板变体与转换指令序列；op_host 含 tiling 的 dtype 分流与 config/<soc>/；docs/aclnnSquaredDifference.md）。同族第二样板：`cann/ops-math` tanh（arch35 变体，实证 #2993）。
- **检视面提示**（引导，不预设结论，仍须逐点核查；行号以本地 HEAD 为准）：
  - 清单点 ②：在 bf16 算术实现体内定位转换指令序列（`VCONV` 类）——核查手写往返**次数**与参考实现（TBE 自动 lowering）的差异（实证 #2535：910B/DAV2201 上手写 5 次 VCONV 往返 vs TBE 3 次，BF16 广播用例 TBE 17.77us vs AscendC 37.74us，多维广播 273.33→698.66us）；须同时记录「硬件无原生 BF16 算术指令、公开 API 无 BF16 Sub/Mul」这一客观前提。
  - 清单点 ③：对照实证 #2993 tanh（arch35）——FP16/BF16 路径 DAG 中 `OpCopyIn0Cast` / `OpResultCast` 两个软件 Cast 节点是否可由 `LoadAlign` / `StoreAlign` 硬件指令承担；修复形态见 PR #5250 移除冗余节点；本地代码若已移除，记录为防护面证据。
  - 清单点 ⑤：反证面——若手写转换是为还原参考实现的中间舍入语义（#2535 情形）且次数已最小，写出反证理由；同族现象另见 ops-nn #5303 leaky_relu 冗余 Cast DAG（收录于 FP-C02）。
  - 清单点 ⑥：广播 / 多维广播用例是否单独成类（#2535 不达标用例即广播形态）。
- 任何一点的最终判定以第 4/5/7 节口径为准，禁止凭算子类型直接下结论。

## 10. 能力边界与自检（v3.8）

### 能力边界

- **静态可证**：清单里能在源码内给出「`文件:行号` + 推导链」的部分，按第 7 节判据出卡。
- **需实测确认**：依赖运行时输入规模、设备行为或环境差异的结论，只能记观察项并附实测用例（证据等级见第 7 节）。
- **不覆盖**：本模式以外的机理（边界见第 0 节）与仓外框架侧行为；`TRIAGE.md` 只负责收敛候选，不构成判定依据。
- **找不到 ≠ 没有**：按清单未命中只说明「本轮未发现」，不得表述为「该算子无此缺陷」；抽样核查须在报告写明抽样口径。

python3 scripts/gen_triage.py --check                          # 分诊表与映射一致
