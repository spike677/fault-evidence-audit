## 一、动机：为什么拆

| 维度 | 单文件版（v2.17） | 拆分版（v3.1） |
|------|------------------|----------------|
| 文件体量 | 850 行 / **217157 字节**（约 212 KB） | 库入口 README 约 13 KB + 单卡平均约 3.5 KB |
| LLM 消费 | 每次**读全文**（约 212 KB ≈ 3 万+ token/次） | 第一段只读 README（13 KB）按「适用」声明初筛，第二段按需读命中卡（2~7 KB/张），上下文开销下降约 80% 以上 |
| 定位一条模式 | 850 行大文件内滚动检索 | 直接打开 `patterns/FP-X/FP-XX.md` 一页一卡 |
| 并行维护冲突 | 45 卡挤同一文件，多任务同时增补易冲突 | 卡片粒度隔离，冲突面缩小到单卡文件 |
| 已有质量隐患 | FP-A18 无标题 v1 重复卡在 v2.7~v2.17 均存在（守门 C15 仍报 WARN） | 每卡一文件 + 守门 C15 逐文件探测，此类「孤儿卡」结构性杜绝 |

## 二、业界参照

1. **CWE（本库头部声明的首要对标）**：CWE 采用「View/Category 总览索引 + 每个弱点 ID 一个独立条目页」的组织方式，条目编号唯一稳定、永不复用。本库的「README 总览表 + patterns/ 单卡文件」即对应该结构。
2. **Diátaxis（Reference 型文档）**：参考型文档应「一页一条目、条目结构一致、交叉引用互联」，索引页负责导航而非承载全部内容。
3. **Agent Skills 渐进披露（progressive disclosure）**：元数据/索引先加载、详情按需读取，上下文窗口消耗与条目规模解耦——这正是本库「整体读全文」消费方式的痛点解法。v2.17 的「适用」声明式筛选与渐进披露天然互补：先按声明过滤，再按需展开。

## 三、交付物构成

```text
ascend-op-fault-patterns/
├── README.md                    # 库入口：版本血缘、库标准精简版（含 S4/适用头）、两段式消费方式、总览索引表
├── CHANGELOG.md                 # 变更记录（v1.0~v2.17 迁移 + v3.0/v3.1 登记）
├── REFACTOR_REPORT.md           # 本报告
├── LICENSE                      # CANN Open Software License Agreement Version 2.0
├── fault_patterns_index.json    # 机器可读索引：全字段 + 每条 file 字段
├── check_fault_patterns.py      # 守门脚本 C1~C18（适配拆分结构）
└── patterns/FP-{A..G}/FP-XN.md  # 45 个单模式卡片（八要素 + 适用头，正文逐字平移）
```

`fault_patterns_index.json` 是机器可读消费入口：任何静态检查脚本都可直接按 `signatures`（判别性指纹）与 `keywords`（审查定位提示）字段对本索引做行级扫描，无需迁就索引格式。`check_fault_patterns.py` 用于校验「总览表 ↔ 卡片 ↔ 索引」三者一致，建议在提交前跑一次。

## 四、数据修正说明（两处）

**修正①：FP-A18 遗留孤儿卡合并。** 单文件版 FP-A20 卡之后遗留一块**无标题**的 v1 版 FP-A18 重复卡（v2.0「转标准卡片」时正文被精简替换，但原卡未删除；v2.7 时已发现，v2.17 中仍在，守门 C15 会报 WARN）。处理方式：

- 该块的 2 条检测签名正则、更完整的源码审查映射点与实证细节**合并入 FP-A18 卡片**（与索引 JSON 中 FP-A18 的 signatures 对齐——此前 MD 卡片只有一句泛化描述而 JSON 已含正则，属双源漂移）；
- 重复块本身消除；FP-A20 卡片恢复纯净；
- FP-A18 卡内附备注说明合并来源。

**修正②：总览表 FP-C04 / FP-E02「触发」单元格对齐权威值。** 单文件版总览表中这两行的「触发」列为「关键词」，而二者卡片「适用」行与索引 JSON `applicability.trigger` 均为「无代码触发特征」（守门 C12 只校验卡片↔JSON，不覆盖总览表触发列，故该漂移未被上游发现）。本仓 README 是导航索引，按权威值修正该两格。

## 五、校验结果

拆分完成后执行守门脚本（C1~C18 全部检查项），结果：**0 ERROR**；唯一 WARN 为 C16「66 条 signatures 含中文」——这是从单文件版索引逐字继承的数据特征（属上游既有状态，非拆分引入），故计为 **PASS**。其余全部检查项通过：45 卡集合/顺序/八要素/适用头、正则可编译、applicability 词表合法性与「卡片↔JSON」双份一致、depth 取值、必须触发≤6（实际 4 条）、孤儿卡探测、README 表与 JSON 的风险/状态/负载/触发一致性（含修正②后全对齐）、交叉引用完整性。

> **v3.3 注记（2026-10-02，外部审计整改批次 4）**：上述 C16 WARN 已处置——66 条中文「审查要点」自索引 `signatures` 字段逐字迁入 `keywords` 字段（25 个条目；README「消费方式」与索引 `applicability_vocab` note 均定义 keywords 为「审查定位提示、不产生命中」，语义归位），`signatures` 恢复为纯可扫描代码指纹（138 条 → 72 条，中文残留 0）；守门 C16 由 WARN 升级为 ERROR，此后 `signatures` 含中文直接判错。迁移后守门 **0 ERROR / 0 WARN**。拆分时点「计为 PASS」的判定保留为历史记录，不作改写。
