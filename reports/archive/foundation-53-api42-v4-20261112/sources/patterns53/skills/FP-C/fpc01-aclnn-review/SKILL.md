# FP-C01 aclnn 接口检视（fpc01-aclnn-review）

对用户指定的 aclnn 接口（如 aclnnSwiGlu）做 FP-C01 专项性能源码检视：先定位算子实现，再按三子型清单逐项核查，每个结论给出**文件 + 行号 + 推导链**证据，命中即出 Bug 卡，输出检视报告。**本模式特殊纪律：结果对、只是慢——静态检视只能产出「嫌疑点」，任何「劣化」的量化结论必须以基线差分实测为准，不可用代码审查替代性能基线看护。**

## 0. 与相邻模式的边界

| 相邻模式 | 分工 |
|---|---|
| FP-A07（走错分支致结果错） | **最易混淆项**：A07 是 tiling 条件写错致**走错分支、结果错**；本条是上界写错致**结果对、只是多算**。审查映射点相邻（都是分支/边界表达式）但后果不同，勿合并 |
| FP-C02~C06（dtype/板型/确定性/代际特化型） | C02~C06 均为**同版本内跨维度对比**；本条子型 ③ 是**跨版本同条件对比**——shape / dtype / 芯片 / 编译选项四要素必须一致才成立 |
| FP-G01（挂死/超时） | C01 是「**慢但能完成**」（耗时非整数倍台阶、日志持续推进）；G01 是「**根本没完成**」（日志完全无进展）。host 侧无退出条件循环若异常分支不推进即空转，归 G01 成因①；上界写错多算但收敛，归本条子型 ② |
| FP-F01（构建/工程配置不一致） | 构建期子型（脚本层重复配置）与其交叠：F01 看配置**正确性**，本条只看配置/构建的**耗时浪费** |
| FP-E02（判据/标杆口径设计缺陷） | 精度判据天然发现不了本条——「精度 pass + 耗时对比」双判据必须成对出现 |

**症状反查定位**：同 shape 跨版本耗时比值劣化（5%~15%）且精度全对 → 子型 ③（唯一暴露途径是基线对比）；耗时随 shape 阶跃处出现**非整数倍**异常台阶 → 子型 ②；端到端占比高但无版本/shape 轴异常 → 子型 ①。用户只给「慢」而无接口名时，按此顺序比对。

## 1. FP-C01 模式卡摘要（检视依据，源自本库 `patterns/FP-C/FP-C01.md`，v3.1）

- **编号 / 名称**：FP-C01 算子端到端耗时占比高且单次调用耗时高 ｜ **类别**：性能 ｜ **风险**：高（S2×O3=6）｜ **状态**：活跃
- **适用声明头**（照抄卡片）：仓 All ｜ 侧别 All ｜ 载体 Tiling源码,Kernel源码,构建配置与日志 ｜ 触发 loopTimes|tileNum|foreach|for\( ｜ 默认启用 true
- **skill 核查面**：卡片侧别 All、载体含构建配置与日志——skill 落地为 op_host（tiling + infershape）/ op_kernel / op_api / 工程构建脚本（CMake 等构建配置）四类文件；子型 ③ 需要用户提供对比基线（上一版本 ref / commit 区间），无基线时只执行子型 ①②
- **故障机理**：存在冗余计算、重复搬运、可合并的循环/分支未合并。**三条独立子路径**：① **实现层冗余**——kernel 模板内冗余初始化 / 冗余指令 / 未合并搬运；② **调度层膨胀**——host 侧（tiling / infershape / aclnn / 工程构建脚本）循环上界或派发条件计算错误，致**下发迭代次数、blockDim、tileNum、核间屏障或重复配置次数多于实需**，kernel 被重复调用或空转，而**单次计算逻辑完全正确**；③ **变更引入的版本基线回归**——绝对耗时未超标、结构上也未必冗余，但某次变更把原本合格的表现推坏（新增冗余计算或同步、tiling/分核阈值漂移、dtype 或派发路径变化、模板实例化放大、新增确定性/原子约束），**判据是「与自身上一版本或基线对比出现劣化」**。
- **触发条件**：网络中高频调用路径上的算子；子型 ② 需循环上界处于「小 shape 不显、大 shape 放大」区间且位于端到端热点路径；子型 ③ 需存在可比基线（shape / dtype / 芯片 / 编译选项四要素一致）且劣化由一次变更划界（可用二分 commit 定位）。
- **典型表现**：端到端性能瓶颈；**精度全对、功能全对、无报错、无 coredump，仅耗时变长**（长期漏检的根本原因）；同 shape 跨版本耗时回归；耗时随 shape 阶跃处非整数倍异常台阶；单看新版本绝对值可能仍「合格」，只有基线对比才暴露。
- **实证案例**：子型 ①（均有 issue）：ops-nn #5277 smallkernel 模板 `fix_m` 冗余、#3988 16in32out 场景 mm 劣化、#3151 QBMM pertile `LocalTensor` 初始化劣化、#2231 dynamic_mx_quant 劣化、#1197 DequantSwigluQuant 950 部分劣化、#4960 mm hf32 劣化；ops-transformer #2402 950 DispatchV2 状态问题；ops-math #1228 AICPU RealDiv complex 性能差。子型 ② 暂无 issue 实证（团队笔记锚点：构建脚本「循环变量被摘除后循环体退化为同一批配置重复设置 N 次」；ops-nn `activation/swi_glu/op_host/swi_glu_tiling.cpp:367` `while (true)` 迭代求解循环静态命中待人工确认——空转风险同构锚见 FP-G01）。子型 ③ 为 2026-09 语料对照增补（「相比基线劣化 >5%」主体形态 88 条），暂无 issue 实证。
- **关联**：FP-A07（最易混淆）、FP-C02/C05/C06（特化型）、FP-G01（慢 vs 不完成）、FP-F01（构建配置交叠）、FP-E02（需性能判据补充）。

## 2. 检视输入与算子定位

**输入**：aclnn 接口名（必填，如 `aclnnSwiGlu`）；可选 ref（默认 master）、指定仓（默认自动定位）；**子型 ③ 追加输入**：对比基线 ref 或 commit 区间（缺省时子型 ③ 不执行，并在报告中说明）。

**接口名 → 算子目录换算**：去 `aclnn` 前缀 + 驼峰转下划线小写：
`aclnnSwiGlu → swi_glu`、`aclnnFusedLinearCrossEntropyLossGrad → fused_linear_cross_entropy_loss_grad`、`aclnnGridSampler2DBackward → grid_sampler2d_backward`。

**仓定位顺序**（GitCode `cann` 组织，逐仓用目录列表确认）：`ops-nn`（norm/loss/activation/matmul 类）→ `ops-math`（math/conversion 类）→ `ops-cv`（image/vision 类）→ `ops-transformer`（attention/moe 类）。**类目名不总与直觉一致**（如 fused_linear_cross_entropy_loss_grad 在 `matmul/` 而非 `loss/`、diag_v2 在 `conversion/`），以目录列表为准。FP-C01 高发面：模板化变体多的算子（多 tilingkey / dtype / 架构变体）、带迭代求解的 tiling、高频调用的逐元素与归约算子、大模板规模仓的构建脚本。

**算子目录结构约定**（已验证示例 `cann/ops-nn` → `activation/swi_glu/`）：

```text
{类别}/{op_name}/
├── op_host/           # *_def.cpp（原型）、*_infershape.cpp、*_tiling*.cpp、arch 子目录
│   └── config/<soc>/  # *_binary.json（分核/tilingkey 派发配置——子型②③ 的派发阈值面）
├── op_kernel/         # kernel 模板（impl/单核/bf16 等变体——子型① 的冗余检视面）
├── op_graph/  tests/  docs/  examples/   # 视算子而定
└── CMakeLists.txt     # 构建配置（构建期子型检视面）
```

**aclnn 出口位置提示**：多数算子的 aclnn 出口在 `op_host/op_api/` 或顶层 `op_api/`（`aclnn_*.cpp`）；个别算子目录内无 aclnn_*.cpp（如 `activation/swi_glu`），以 `docs/aclnn*.md` 与目录列表确认——不影响 tiling/kernel 侧检视。

## 4. 三子型检视清单（每点：查什么 → 何处 → 命中判据）

对算子的 op_api / op_host（tiling + infershape）/ op_kernel / 构建脚本全部相关文件逐点核查，**每点先查命中面、再做反证排除**，防护面也要记录（作为反证依据）。

### 子型 ① 实现层冗余（kernel 模板）
- 查什么：循环体内**重复初始化每迭代不变的量**（`LocalTensor` 每轮重 Init——实证 #3151 同族）；冗余指令（重复 Cast / 重复 SyncAll / 模板分支内无效指令）；**未合并搬运**（可一次 `DataCopy` 的拆成多次、同一 GM 数据重复读入）；循环不变量未外提。
- 何处：kernel 主循环体、tilingkey 分发的各模板变体、arch 子目录变体（同一冗余模式常在多个变体重复出现）。
- 命中判据：能写出「该指令/搬运在循环内执行 N 次而其结果与执行 1 次等价」的推导；对照同仓已优化样板反证。

### 子型 ② 调度层膨胀（host 侧上界与派发）
- 查什么（卡片映射点①~⑤）：
  ① host `for` 上界表达式与 `GetShapeSize()` / `CeilDiv(...)` / `blockDim` 三者的**乘积自洽性**（`<=` vs `<`、`+1/-1`、上界用错变量、未做 `min()` 截断）；
  ② tiling 中 `tileNum` / `usedCoreNum` / `loopTimes` 推导是否可能**大于形状所需最小迭代数**；
  ③ 核间循环**双重计数**——分核数已按 shape 缩小后，单核循环仍按全量上界执行；
  ④ `foreach`/`for` 循环体内**未使用循环变量**（循环退化为同一批配置重复设置 N 次）；
  ⑤ 变更 diff 中 host 循环边界与 kernel `loopTimes` 消费点是否**成对更新**（只改一侧必错）。
- 何处：tiling/infershape 的块数与上界计算、aclnn 出口的循环、构建脚本（CMake `foreach` 等）。
- 命中判据：上界推导可给出「实需 X 次 vs 下发 Y>X 次」的静态反例；`while(true)` 类迭代求解循环同时按 FP-G01 成因① 核推进/退出语义（空转归 G01，多算归本条）。

### 子型 ③ 变更引入的版本基线回归（需基线区间）
- 查什么（卡片映射点⑥~⑩，全部针对变更 diff）：
  ⑥ 是否**新增**循环 / 同步 / 类型转换 / 边界判断（尤其本可省略的 Cast、SyncAll、逐元素回退）；
  ⑦ tiling 阈值常量（分核阈值、`2048`/`4096` 类魔数）是否被改动，使原最优点被跨过；
  ⑧ 是否把向量化 / 合并搬运改成分步执行、或用更窄 dtype 承载累加；
  ⑨ 模板实例化数量是否随改动放大（编译产物 size / 编译耗时作旁证）；
  ⑩ 是否新增确定性 / 原子操作约束（与 FP-C05 交叠，须与此前版本对照确认是「新引入」还是「一直如此」）。
- 何处：基线…head 的 diff、tiling 常量、kernel 模板清单变化。
- 命中判据：diff 中可指认的「新增工作」条目 + 基线四要素可比；**劣化幅度只能由基线差分实测给出，静态推导只立「嫌疑点」**。

## 5. 检视流程

1. **定界**：换算 op 目录、确认所在仓与 ref；子型 ③ 确认基线 ref/commit 区间与四要素可比性（shape / dtype / 芯片 / 编译选项），不可比即降级为只做 ①②。
2. **枚举**：目录列表列出 op_api / op_host（含架构子目录、config）/ op_kernel / 构建脚本全部相关文件，产出文件清单。
3. **触发词扫描**：按 `loopTimes|tileNum|foreach|for(`、`while\s*\(\s*true|for\s*\(\s*;\s*;\s*\)`、`CeilDiv|blockDim|usedCoreNum|SyncAll|Cast` 定位风险面（本地仓用 grep；API 模式逐文件拉取后检查）。
4. **三子型逐项核查**：每点记录命中面与防护面证据（文件:行号）；对照实证样板与同仓已优化算子做同族反证。
5. **反证排除**：穷尽反证再下结论——硬件带宽/指令上限（已贴上限的搬运不算冗余）、语义必须（双 buffer 确因流水需要）、编译器优化消除、框架已合并的调用。
6. **判定**：按第 7 节标准给出 命中 / 观察项 / 反证排除。
7. **GitCode 查重**（仅命中项）：issues API 按接口名 + 性能关键词检索，逐条比对是否同机理；无同机理才立卡。
8. **业务可达性核查**（仅命中项）：判 B 等级、定业务影响类型、给处置建议；默认保守（无法证明不可达即记 B3），降档须附证据；B 不改 S×O 档位。
9. **出报告**：按第 8 节模板落盘；静态推演结论一律标注「需基线差分实测确认」，并附探针与基线方案。

## 6. 风险定级（S×O）与业务影响评估（B 轴）

- **S**：S2（性能不达标/交付受限）、S1（轻度资源浪费）；性能类缺陷不涉 S3/S4（结果仍正确）。
- **O**：O3 = ≥2 条独立实证；O2 = 1 条独立实证；O1 = 仅静态扫描命中或团队笔记（实证 = 确认对应的 issue / PR，或经跨仓、跨分支核验确认的缺陷记录，同权计入）。静态推演命中且无实证默认 **O1**；升档须在报告中给出实证依据。
- **风险 = S×O**：≥6 高；3/4 中；1/2 低。FP-C01 基准：模式卡整体 S2×O3=6（高，子型 ① 8 条 issue 实证）；纯静态命中 S2×O1=2（低，嫌疑项待基线验证）。

### B 轴：业务影响评估（与 S×O 正交；报告层新增，不改卡片定级）

S×O 回答"多严重、多常见"，**不回答"真实业务能不能碰到"**。B 轴补这一问，只决定**修复优先级建议**，**不参与 S/O 取值、不改 S×O 档位与卡片元数据**。

**业务可达性（B）**——触发条件在真实负载中的可达程度：

| 等级 | 判据 | 证据要求 |
|---|---|---|
| B3 现实可达 | 主流框架/公开模型默认路径即可命中（如 PTA/torch_npu、vLLM、MindIE 常规调用） | 调用方或公开负载来源 |
| B2 条件可达 | 需特定 attr/dtype/shape 组合，业务中存在但非默认 | 该组合的业务来源 |
| B1 边界/不可达 | 需极端、超规格或非法参数（超出接口合理上限的 shape、退化/非法输入） | "为何不可达"的说明 |

- **默认保守**：无法证明不可达 → 记 **B3**；降为 B1/B2 必须附证据，**不得仅凭"业务应该不会这么用"**。
- 超规格参数是否算 B1 取决于**接口契约**：契约允许但业务不用 → B1；契约不允许（本应报错）→ 属校验缺失（FP-B04/B05 类），另行归属。

**业务影响类型**（命中后对用户可见结果的后果，用业务语言表述）：静默精度损失（模型效果下降 / loss 不收敛 / 偶发 NaN）｜ 任务失败中断（报错 / 崩溃 / 挂死）｜ 性能退化 ｜ 仅可观测性（日志 / 错误码 / 文档，不影响结果）。

**处置建议**（由两轴推导的报告结论，非新档位）：

| S×O \ B | B3 现实可达 | B2 条件可达 | B1 边界/不可达 |
|---|---|---|---|
| 高（≥6） | 尽快修 | 尽快修 | 排期修 |
| 中（3/4） | 尽快修 | 排期修 | 记录（业务难以触达） |
| 低（1/2） | 排期修 | 记录 | 记录 |

## 7. 判定标准与反误报原则

- **签名/触发词命中 ≠ 成立**：`for`/`while` 命中是定位提示，必须过完整推导链 + 可达性分析 + 反证排除三关；`for(i=0;i<n;i++)` 与 `for(i=0;i<n+1;i++)` 语法同为合法，**该缺陷类型静态扫描与 UT 均无法覆盖**——skill 的产出是「嫌疑点 + 待验证方案」，不是最终性能结论。
- **三种判定**：
  - **命中**（可静态证浪费）：机理推导链完整（「实需 X 次 vs 下发 Y>X 次」可推导、循环体不引用循环变量的重复配置等）+ 触发组合可静态证伪可达 + 反证排除失败 → 立 Bug 卡；
  - **观察项**：结构存疑但静态无法确证、或属「劣化幅度需实测」类 → 记录并附基线验证方案，不定级或按 S2×O1 暂定；
  - **反证排除**：硬件上限 / 语义必须 / 编译器消除 / 框架已合并 → 明确写出反证理由。
- **可达性分析要给出可复现反例**：具体 shape / dtype / 分核组合（如「阈值 2048 两侧取 2047/2048/2049」「上界 ±1 探针对」）。

## 11. 已知缺陷案例库：触发条件 / 根因 / 修复范式 / 针对性深挖（v5.1）

> 本节把本型**已确认缺陷**拆到「触发条件 → 根因（具体路径）→ 修复范式（✅ 正确代码）→ 针对性发现步骤 → 最小复现锚」的代码级颗粒度。
> 修复范式为**正确形态示意**；路径引用取自卡片实证，行号以被检仓本地 HEAD 为准，**不得臆造**。

### 案例 1｜kernel 模板内每轮重复初始化 / 冗余指令致单次调用耗时高 —— ops-nn #3151 等（子型①）

- **触发条件**：模板化变体算子（多 tilingkey / dtype / 架构变体）位于高频调用路径上，循环内每轮重复初始化不变量。
- **根因（具体路径）**：kernel 主循环体内**重复初始化每迭代不变的量**（`LocalTensor` 每轮重 Init）→ 同一指令 / 搬运在循环内执行 N 次而其结果与执行 1 次等价 → 单次调用耗时高。同族：`#5277` smallkernel 模板 `fix_m` 冗余、`#3988` 16in32out mm 劣化、`#2231` dynamic_mx_quant 劣化、`#1197` DequantSwigluQuant 950 部分劣化、`#4960` mm hf32 劣化、`#2402` 950 DispatchV2 状态问题、`#1228` AICPU RealDiv complex 性能差。
- **修复范式（✅，示意）**：

```cpp
// ❌ 循环内每轮重 Init 不变的 LocalTensor / 重复搬运
for (int i = 0; i < loop; ++i) {
    LocalTensor<half> buf = inQue.AllocTensor<half>();   // 每轮重复初始化
    ...
}
// ✅ 循环不变量外提 / 合并搬运
LocalTensor<half> buf = inQue.AllocTensor<half>();
for (int i = 0; i < loop; ++i) { ... }   // 与执行 1 次等价的部分只做一次
```

- **针对性发现（可执行）**：① 定位 kernel 主循环体与 `tilingkey` 分发的各模板变体（同一冗余常在多变体重复出现）；② 写出「该指令 / 搬运在循环内执行 N 次而其结果与 1 次等价」的推导；③ 对照同仓已优化样板反证。
- **最小复现锚**：同 shape 对照「循环内 Init 外提」前后的算子级耗时（profiler 占比）。
- **实证**：ops-nn `#5277`、`#3988`、`#3151`、`#2231`、`#1197`、`#4960`；ops-transformer `#2402`；ops-math `#1228`。

### 案例 2｜构建期 `foreach` 循环变量被摘除、循环体退化为重复配置 N 次 —— catlass `83_ascend950_hstu_infer/CMakeLists.txt`（子型②，团队笔记）

- **触发条件**：增量构建或模板规模大的仓（重复配置开销随模板 / 源文件数线性放大）。
- **根因（具体路径）**：新增 `get_filename_component(_SRC_NAME ${_SRC} NAME)` 后**从未使用**，且 `foreach(_SRC ${_HSTU_950_SOURCES})` 循环体内已不再引用 `_SRC` → 外层循环退化为「把同一批 compile definitions / include dirs **重复设置 N 次**（N=源文件数）×2（`_ms` 变体）」→ 未完成重构遗留，循环变量被摘除后循环体失去意义但结构未删。
- **修复范式（✅，示意）**：

```cmake
# ❌ 循环变量被摘除后循环体失去意义，结构未删（重复设置 N 次）
foreach(_SRC ${_HSTU_950_SOURCES})
  target_compile_definitions(...); target_include_directories(...)
endforeach()
# ✅ 移出循环或整体删除
target_compile_definitions(...)
target_include_directories(...)
```

- **针对性发现（可执行）**：① 搜构建脚本 `foreach` / `for` 循环体内是否**未使用循环变量**；② 核 `_SRC_NAME` 类变量的引入点与使用点（引入未用 = 重构遗留信号）；③ 用增量构建耗时 / 配置次数做旁证。
- **最小复现锚**：对照该 `CMakeLists.txt` 的构建配置耗时（或 `--trace` 计数）在删循环前后的差异。
- **实证**：catlass `tests/optest/kernels/83_ascend950_hstu_infer/CMakeLists.txt`（PR 检视日报_20260911 P2），无 issue 实证。

### 案例 3｜host 迭代求解循环空转 / 多算 —— ops-nn `swi_glu_tiling.cpp:367`（子型②，待人工确认）

- **触发条件**：`while (true)` 迭代求解循环（`CalcOptBaseShape`）处于「小 shape 不显、大 shape 放大」区间且算子位于端到端热点路径。
- **根因（具体路径）**：`ops-nn/activation/swi_glu/op_host/swi_glu_tiling.cpp:367` 命中 `F5/无退出条件循环`（`while(true)`）→ 若异常分支不推进则**空转**（归 FP-G01 成因①，锚 `#5032` `AdjustCVTiling` 死循环同构）；C01 视角另看迭代次数是否收敛、有无全区间扫描浪费。
- **修复范式（✅，示意）**：

```cpp
// ❌ 每次迭代都全区间扫描 / 无收敛判据
while (true) { /* 无推进则空转（归 G01）；有推进但多算则只是慢（归本条） */ }
// ✅ 迭代求解须有收敛判据与迭代上限
for (int it = 0; it < MAX_IT && !converged; ++it) { ... }
```

- **针对性发现（可执行）**：① 搜 `while\s*\(\s*true|for\s*\(\s*;\s*;\s*\)`；② 先按 FP-G01 成因① 核推进 / 退出语义（空转归 G01），再按 C01 看迭代次数与收敛性；③ 构造「上界 ±1 两侧」shape 探针对（阈值 2048 取 2047/2048/2049）。
- **最小复现锚**：2047 / 2048 / 2049 三档 shape 的算子级耗时，断言两侧不出现**非整数倍台阶**。
- **实证**：`ops-nn/activation/swi_glu/op_host/swi_glu_tiling.cpp:367` 静态命中待人工确认；同构锚 ops-transformer `#5032`。

### 案例 4｜变更把原本合格的表现推坏（版本基线回归） —— 子型③（88 条语料，无 issue）

- **触发条件**：存在**可比基线**（同一 shape / dtype / 芯片 / 编译选项四要素一致），劣化由**一次变更**划界（可二分 commit 定位）。
- **根因（具体路径）**：某次变更新增冗余计算或同步、tiling / 分核阈值漂移使原最优点被跨过、dtype 或派发路径变化、模板实例化规模放大、新增确定性 / 原子约束 → 绝对耗时未超标、结构上也未必冗余，但**与自身基线对比**出现劣化（常见 5%~15%）；单看新版本绝对值可能仍「合格」，只有基线对比才暴露。
- **修复范式（✅，示意）**：

```text
// ❌ 只看新版本绝对值"合格"即放过；阈值常被改动使原最优点被跨过
// ✅ 每次合入的候选版本与上一基线同 shape 对拍，比值劣化超阈值即阻断合入
//    基线必须记录 shape / dtype / 芯片 / 编译选项 四要素
```

- **针对性发现（可执行）**：① diff 中搜**新增**循环 / 同步 / 类型转换 / 边界判断（可省 `Cast`、`SyncAll`、逐元素回退）；② 核分核阈值常量（`2048`/`4096` 类魔数）是否被改动；③ 核向量化 / 合并搬运是否被改为分步、模板实例化数量是否放大（编译产物 size 旁证）。
- **最小复现锚**：同 shape 跨版本耗时比值（比值 > 1.15 告警），劣化后用**二分 commit** 定位首次劣化点。
- **实证**：子型③ 语料补充（v2.16，2026-09-19）——归类中「性能回归 / 基线劣化」**88 条**，主体为「相比基线性能劣化超过 5%」，暂无 issue 实证。
