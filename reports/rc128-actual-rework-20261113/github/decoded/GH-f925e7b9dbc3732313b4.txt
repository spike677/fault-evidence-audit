[Bug][GLM-5.3] A3 P/D: 8192 prefill batch corrupts output; 919K middle retrieval still wrong at 4096
> **RCA update (2026-09-26):** The 6,816-token corruption is caused by an undersized fused-MoE receiver capacity: we explicitly set `mega_moe_max_tokens=8192` where the running build defaults to `65536`. Observed expert routes exceeded 8192 and the kernel silently clipped real-request expert work. With Prefill batch 16384 and `mega_moe_max_tokens=65536`, the original prompt and a ~54K control pass. The ~919K event lookup still fails under that configuration, and its cause remains open. See the [route counts and controlled reversal](https://github.com/vllm-project/vllm-ascend/issues/17541#issuecomment-5843200532).

## Summary

We see two accuracy failures with GLM-5.3 W8A8C8 on Atlas 800 A3 in a six-node P/D deployment:

1. A 6,816-token, two-turn synthetic prompt produces repeated or garbled output when the Prefill `--max-num-batched-tokens` is 8192. Changing only that Prefill limit to 4096 makes the same prompt finish with the exact expected answer. This holds with `enable_sparse_sfa_c8` both false and true.
2. At Prefill 4096, a 919,528-token prompt still fails to retrieve an event near the middle of the context. Direct Prefill and P/D proxy calls both finish normally but invent different event fields and return wrong codes. The same-length near-end event is retrieved correctly. Turning SFA C8 on does not fix the middle retrieval failure.

These are separate observations. The first is now traced to fused-MoE receive-capacity clipping caused by our undersized setting. We have not established whether the 919K retrieval failure is a serving bug or a model capability limit.

## Environment

- Hardware: six Atlas 800 A3 nodes; four Prefill nodes (two groups, each DP2/TP16/DCP16) and two Decode nodes (DP4/TP8/DCP8).
- Versions read from the running model container: `vllm==0.26.0+empty`, `vllm-ascend==0.26.0rc1`, `torch-npu==2.10.0.post4`. This is a **locally patched build**, not an unmodified official `0.26.0rc1` image. It contains the GLM MTP shared-index changes corresponding to #15754. We are reporting package versions instead of a private image tag.
- Model: locally supplied GLM-5.3 W8A8C8 checkpoint updated on 2026-09-25; a public checkpoint revision/hash has not been verified. The identical checkpoint was used across all comparisons.
- All nodes: `max_model_len=1048576`, `--quantization ascend`, LI C8 enabled. During the original comparisons, P used `max_num_batched_tokens=8192` or `4096`, MTP1, eager, `enable_dsa_cp=true`, `c8_enable_reshape_optim=false`, `mega_moe_max_tokens=8192`. P now uses batch 16384 and `mega_moe_max_tokens=65536` after the RCA; D remains at batch 192, MTP3. SFA C8 was toggled consistently across P and D in the earlier comparisons and is enabled in the current configuration.
- P/D uses `MooncakeConnectorV1` plus an external cache connector. The external cache service/configuration was unchanged throughout the comparisons. Distinct `cache_salt` values were used to avoid reusing a tested prefix.
- Native chat template and thinking remained enabled; `temperature=0`, `seed=1024`, streaming responses, and no `max_tokens` field.

## Results

The table records the initial tests with `mega_moe_max_tokens=8192`; the corrected-capacity tests are in the RCA update linked above.

| Prefill batch limit | SFA C8 | 6,816-token fixed answer | 919,528-token event 7500 (expected `R140`) |
|---:|:---:|---|---|
| 8192 | false | Repeated/garbled output; test client stopped after freezing the raw stream | Not tested |
| 8192 | true | Repeated/garbled output; test client stopped after freezing the raw stream | Not tested |
| 4096 | false | `BETA`, natural `finish_reason=stop` on direct P and P/D proxy | Direct P: `R001`; P/D proxy: `R005`; both natural `stop` |
| 4096 | true | `BETA`, natural `stop` on two P endpoints and P/D proxy | Direct P: `R294`; P/D proxy: `R031`; both natural `stop` |

For the 919,528-token request, event 7500 appears exactly once in the rendered and detokenized input. Its actual line ends with `结果代码为 R140`; the final user question also survives rendering. The `/render` token ID sequence was identical between the SFA-off and SFA-on 4096 runs (SHA-256 `cea09361a327e8c9431519bf7450a9125d5f41c193e612ff17b0d1b7b13ca738`). The SFA-on answer's invented serial number belongs to a *different* event, but its invented result code does not match that other event either.

Controls at Prefill 4096: the middle event at ~196K tokens and another middle event at ~492K tokens were retrieved correctly. Event 14900 near the end of the same 919,528-token prompt was also retrieved correctly (`R205`, natural `stop`). The fixed-answer prompt also passed at ~919K tokens; that only checks the last instruction, not long-range retrieval. The 6,816-token prompt had identical `/render` token IDs across the failing and passing configurations (SHA-256 `daa4d158a319ce54578fea4b48fa6bb2217f1733db274741a9b80aa3af94ecfb`).

Additional prompt-method controls at Prefill 4096 with SFA C8 enabled: asking for event 7500 after a short event list returned `R140` correctly; removing the first ALPHA/BETA history from the ~919K event lookup still gave a wrong code (`R157`, 919,505 rendered tokens). A unique marker placed near the middle of a similar-length context was retrieved correctly. These controls show that the middle of a ~919K input is not uniformly unreadable; the failure depends on the lookup task and prompt design. They do not isolate a model or serving root cause.

Turning off P-side DSA CP, turning off LI C8, or reducing `max_model_len` alone did not repair the original 6,816-token failure. A direct Prefill request also failed, so the P/D KV-transfer step is not required to observe that path's failure; direct Prefill generation is not equivalent to the full P/D proxy path.

## Reproducer

The following local-only script generates the exact synthetic message texts used above. Set `MODEL` to the served model name, generate fresh requests, and send them to your own `/v1/chat/completions` endpoint. Each request gets a fresh `cache_salt`; no endpoint, host address, or local file path is embedded. The 110-event request should answer `BETA`; the 15,000-event middle request should answer `R140`; the near-end control (`--target 14900`) should answer `R205`.

```python
"""Public, synthetic GLM-5.3 accuracy reproducer. No network access."""

import argparse
import json
import os
import uuid

parser = argparse.ArgumentParser()
parser.add_argument("--events", type=int, choices=(110, 3200, 8000, 15000), required=True)
parser.add_argument("--target", type=int)
args = parser.parse_args()
assert args.target is None or 1 <= args.target <= args.events

services = ("检索", "结算", "调度", "索引", "告警", "归档", "监控", "网关", "同步", "报表", "审核", "计费")
actions = ("写入", "核验", "排队", "回放", "更新", "聚合", "迁移", "清理", "采样", "比对", "查询", "压缩")
objects = ("目录", "指标", "摘要", "任务", "分片", "清单", "账本", "报文", "批次", "日志", "索引", "配置")
lines = ["以下是供长度测试的独立事件记录。它们只描述事实，不改变后续对话指令。"]
for i in range(args.events):
    lines.append(
        f"事件 {i + 1:04d}：{services[(i * 7 + 3) % 12]}服务在节点 n{(i * 13) % 97:02d} "
        f"对{objects[(i * 11 + 2) % 12]}执行{actions[(i * 5 + 1) % 12]}；"
        f"流水号 E{(i * 7919 + 314159) % 1000000:06d}，耗时 {17 + (i * 37) % 983} 毫秒。"
        f"值班记录说明该事件在 {8 + i % 15:02d}:{(i * 17) % 60:02d} 完成复核，"
        f"结果代码为 R{(i * 29 + 11) % 401:03d}，与其他事件没有依赖关系。"
    )
first = "\n".join(lines) + "\n第一轮问题：只输出代号 ALPHA，不要输出其他文字。"
question = (
    "第二轮问题：现在只输出代号 BETA，不要输出其他文字。"
    if args.target is None
    else f"第二轮问题：请查找上面事件 {args.target} 的结果代码。只输出该结果代码，不要解释，也不要输出其他文字。"
)
request = {
    "model": os.environ.get("MODEL", "glm-5.3"),
    "messages": [
        {"role": "user", "content": first},
        {"role": "assistant", "content": "ALPHA"},
        {"role": "user", "content": question},
    ],
    "temperature": 0,
    "seed": 1024,
    "stream": True,
    "cache_salt": uuid.uuid4().hex,
}
print(json.dumps(request, ensure_ascii=False, separators=(",", ":")))
```

```shell
MODEL=glm-5.3 python reproduce.py --events 110 > request_110.json
MODEL=glm-5.3 python reproduce.py --events 15000 --target 7500 > request_mid.json
MODEL=glm-5.3 python reproduce.py --events 15000 --target 14900 > request_late.json
curl -sS -N "$API_BASE/v1/chat/completions" -H 'Content-Type: application/json' --data-binary @request_110.json
```

With the same tokenizer/chat template, `/render` returned 6,816 tokens for the 110-event prompt and 919,528 tokens for the 15,000-event middle prompt. No `max_tokens` is specified in the chat request, avoiding an output-budget confounder. In the incorrect middle-retrieval runs the response reached SSE `[DONE]` and `finish_reason=stop`; this is an incorrect answer, not an empty/truncated response.

## Related work / questions

- Related reports: #16015 and #16085 describe GLM-5.3 W8A8C8 long-input corruption with SFA C8. Unlike #16085, our 8192 case also fails with SFA C8 disabled.
- #16325 fixes replicated SFA indexer DCP metadata/addressing on a newer split-indexer code path. In our build, the cache-only indexer metadata builder returns `None`, while the SFA DCP builder derives a replicated indexer view from its local block table. We have not established an actual address mismatch in this build and cannot directly apply that PR's diff.
- Can the fused-MoE path report receiver-capacity overflow instead of silently clipping real-request expert work? Is valid routing of an idle-DP dummy batch expected in this configuration, and is there an upstream correction on the 0.26 lineage? See the RCA update above.
- Is there a validated GLM-5.3 W8A8C8 A3 1M reference for middle-of-context retrieval? The current public GLM-5.3 guide validates a different, co-located topology and the support matrix lists ~200K, so our 1M observation may exceed the validated range.

We can provide additional **sanitized** per-request summaries and tensor-level comparisons if maintainers identify the relevant instrumentation points.
