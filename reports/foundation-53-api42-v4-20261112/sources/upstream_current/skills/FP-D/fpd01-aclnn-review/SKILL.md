# FP-D01 aclnn 接口检视（fpd01-aclnn-review）

对用户指定的 aclnn 接口（如 aclnnFusedLinearCrossEntropyLossGrad）做 FP-D01 专项源码检视：先定位算子实现，再按三映射点清单逐项核查，每个结论给出**文件 + 行号 + 推导链**证据，命中即出 Bug 卡，输出检视报告。

## 0. 与相邻模式的边界

| 相邻模式 | 分工 |
|---|---|
| FP-D02（双路径对比的相对值超限） | **同源**：均指向 workspace 计算与内存复用缺失。D01 关注**绝对值超限**（迁移/图模式下申请量超出实需与容量），D02 关注**相对值**（同一算子两条派发路径/两个版本间占用差异）——「A 卡 OOM 而 B 卡不 OOM」先按 D02 归属 |
| FP-A05（脏数据/数据踩踏） | **同一批「内存问题」的二分**：D01 管内存**容量**（OOM/占用高），A05 管内存**正确性**（脏数据） |
| FP-G01（挂死） | 资源泄漏累积致内存耗尽把正常算子推向挂死/闪退（G01 成因⑤）：泄漏路径与「耗尽→挂死」后果链归 G01，**容量评估口径**问题归本条 |
| FP-B07（越界） | 偏移算式错导致越界访问归 B07；**申请量算多**（写了大数但读写范围仍在界内）归本条 |

**症状反查定位**：OOM / 「显存占用高于 GPU 基线」/ 峰值内存超限 → 本条（先 D01 后 D02：绝对超限看 D01，两路径对比看 D02）；`mssanitizer` / memcheck 报错 → FP-A05 → FP-B07。

## 1. FP-D01 模式卡摘要（检视依据，源自本库 `patterns/FP-D/FP-D01.md`，v3.1）

- **编号 / 名称**：FP-D01 GPU 迁移 NPU 场景显存过度占用 ｜ **类别**：资源/内存 ｜ **风险**：高（S2×O3=6）｜ **状态**：活跃
- **适用声明头**（照抄卡片）：仓 All ｜ 侧别 Tiling ｜ 载体 Tiling源码 ｜ 触发 workspace|GetWorkspaceSize ｜ 默认启用 true
- **skill 核查面**：与卡片侧别（Tiling）一致——以 op_host tiling 的 workspace/内存推导为主核查面；调用侧形态问题（如框架 `zerolike` 类整量复制、图模式宿主申请）只记录观察项并归因调用方，不按算子缺陷立卡
- **故障机理**：workspace 大小计算过大、内存未复用、缓存未设上限；**图模式（aclGraph / 条件算子）下的内存申请路径未纳入容量评估**（v2.13 增补）。
- **触发条件**：GPU 训练/推理脚本直接迁移到 NPU；**aclGraph 等图模式下经条件算子触发的内存申请**（原卡片仅覆盖迁移场景，遗漏图模式申请路径）。
- **典型表现**：网络无法正常训练或推理（OOM）。
- **实证案例**：ops-nn **#408** FusedLinearCrossEntropyLossGrad **省显存分支申请了超出所需的显存大小**——tiling 计算 workspace 时最后两块 buffer 在不同流水下视图一致、不涉及 double buffer，却按双倍申请（期望 shape "4196,7168;64640,7168" 下约 2.5G）；**#4932** embeddingdensegrad 使用 `zerolike` 导致 OOM，在 OOM 包下走 aclnn 通路 aic error；**#4021** max_pool3d_grad_with_argmax aclnn 接口内存检测时 OOM；**#4001** dynamic_mx_quant 跑 OOM 报错。**共性特征：workspace/buffer 申请量按「最坏情况或错误假设」估算，未做复用与生命周期分析，属 tiling 侧可精确修复的问题。**
- **关联**：FP-D02（同源分工）、FP-A05（容量/正确性二分）。

## 2. 检视输入与算子定位

**输入**：aclnn 接口名（必填，如 `aclnnFusedLinearCrossEntropyLossGrad`）；可选 ref（默认 master）、指定仓（默认自动定位）、目标 SoC（影响容量上限与对齐参数）。

**接口名 → 算子目录换算**：去 `aclnn` 前缀 + 驼峰转下划线小写：
`aclnnFusedLinearCrossEntropyLossGrad → fused_linear_cross_entropy_loss_grad`、`aclnnRmsNormGrad → rms_norm_grad`。

**仓定位顺序**（GitCode `cann` 组织，逐仓用目录列表确认）：`ops-nn` → `ops-math` → `ops-cv` → `ops-transformer`。**类目名不总与直觉一致**（如 fused_linear_cross_entropy_loss_grad 在 `matmul/` 而非 `loss/`），以目录列表为准。FP-D01 高发面：带多 buffer workspace 的 tiling、矩阵类/大 shape 算子、迁移自 GPU 实现的算子（含双缓冲与缓存假设）、图模式注册的算子。

**算子目录结构约定**（已验证示例 `cann/ops-nn` → `matmul/fused_linear_cross_entropy_loss_grad/`）：

```text
{类别}/{op_name}/
├── op_host/
│   ├── {op}_def.cpp、{op}_tiling*.cpp/.h   # workspace 推导主检视面
│   ├── op_api/aclnn_{op}.cpp               # GetWorkspaceSize 出口（申请量一致性核对点）
│   └── config/<soc>/{op}_binary.json       # 分核配置（SoC 相关 buffer 上限核对点）
└── op_kernel/  tests/  docs/  examples/    # 视算子而定
```

## 4. 三映射点检视清单（每点：查什么 → 何处 → 命中判据）

以 tiling 侧为主，op_api 的 `GetWorkspaceSize` 出口与 kernel 的实际读写范围作一致性核对。**每点先查命中面、再做反证排除**，防护面也要记录（作为反证依据）。

### ① workspace 申请量推导
- 查什么：申请量公式与**实需**的逐步对照——是否按「最坏情况或错误假设」估算（实证 #408：两块 buffer 流水视图一致、不涉及 double buffer，却按双倍申请）；对齐 padding 的放大倍数；dtype 字节数取值；预留头/安全系数是否重复计入；`GetWorkspaceSize` 返回值与 tiling 内各 buffer 推导之和是否一致；是否有 `min()` 截断到实需上限。
- 何处：`*_tiling*.cpp` 的 workspace/buffer 推导函数、op_api 的 `GetWorkspaceSize`。
- 命中判据：能写出「实需 X 字节 vs 申请 Y≫X 字节」的静态推导（给出 shape 反例组合）；防护面（合理对齐/预留）一并记录。

### ② 内存复用与生命周期
- 查什么：各 buffer 的**生命周期是否重叠**——非重叠生命周期的 buffer 是否共享同一 workspace 段；double buffer 是否真有必要（流水是否实际交替使用两块——实证 #408 即「不需要却申请了」）；临时 buffer 是否可跨 phase 复用；workspace 是否跨调用复用（host 缓存）。
- 何处：tiling 的 buffer 划分、kernel 各 Phase 对 workspace 的写/读时序（可借 FP-A05 ②③ 的 SyncAll 同步链证据——同一份时序既证正确性也证复用可行性）。
- 命中判据：生命周期不重叠的 buffer 列表可静态列出且合并无语义风险；**边界**：复用会**破坏正确性**的场景归 FP-A05 观察项，不按本条立卡。

### ③ 缓存上限与图模式申请路径
- 查什么：host 侧缓存/池是否设上限；**aclGraph 图模式下经条件算子触发的内存申请是否纳入容量评估**（v2.13 增补——图模式申请不走逐调用路径，静态容量评估若只按单调用估算会整体漏掉）；调用形态（如框架 `zerolike` 整量复制）引入的额外显存。
- 何处：tiling 的缓存逻辑、图模式注册与申请路径。
- 命中判据：图模式分支存在无上限/未评估的申请点，按可证性判命中或观察项；纯调用方形态问题记观察项并归因调用方。

## 5. 检视流程

1. **定界**：换算 op 目录、确认所在仓与 ref、目标 SoC；多仓命中时列出全部实现并逐一检视。
2. **枚举**：目录列表列出 tiling / op_api 出口 / config 全部相关文件，产出文件清单。
3. **触发词扫描**：按 `workspace|GetWorkspaceSize|TmpSize|BufferSize|CacheSize` 定位风险面（本地仓用 grep；API 模式逐文件拉取后检查）。
4. **三映射点逐项核查**：每点记录命中面与防护面证据（文件:行号）；与 kernel 实际读写范围做一致性核对；对照实证样板与同族已修复算子做同族反证。
5. **反证排除**：穷尽反证再下结论——对齐必需、预留语义、框架级复用/预分配、双 buffer 确因流水需要、缓存上限在别处约束。
6. **判定**：按第 7 节标准给出 命中 / 观察项 / 反证排除。
7. **GitCode 查重**（仅命中项）：issues API 按接口名 + OOM/workspace 关键词检索，逐条比对是否同机理；无同机理才立卡。
8. **业务可达性核查**（仅命中项）：判 B 等级、定业务影响类型、给处置建议；默认保守（无法证明不可达即记 B3），降档须附证据；B 不改 S×O 档位。
9. **出报告**：按第 8 节模板落盘；运行时结论标注「静态推演，需 NPU 实测确认」，并附峰值显存观测建议。

## 6. 风险定级（S×O）与业务影响评估（B 轴）

- **S**：S2（OOM 致网络无法训练/推理）、S1（占用高但未致 OOM 的资源浪费）。
- **O**：O3 = ≥2 条独立实证；O2 = 1 条独立实证；O1 = 仅静态扫描命中或团队笔记（实证 = 确认对应的 issue / PR，或经跨仓、跨分支核验确认的缺陷记录，同权计入）。静态推演命中且无实证默认 **O1**；升档须在报告中给出实证依据。
- **风险 = S×O**：≥6 高；3/4 中；1/2 低。FP-D01 基准：模式卡整体 S2×O3=6（高，4 条 issue 实证）；纯静态命中 S2×O1=2（低）。

### B 轴：业务影响评估（与 S×O 正交；报告层新增，不改卡片定级）

S×O 回答"多严重、多常见"，**不回答"真实业务能不能碰到"**。B 轴补这一问，只决定**修复优先级建议**，**不参与 S/O 取值、不改 S×O 档位与卡片元数据**。

**业务可达性（B）**——触发条件在真实负载中的可达程度：

| 等级 | 判据 | 证据要求 |
|---|---|---|
| B3 现实可达 | 主流框架/公开模型默认路径即可命中（如 PTA/torch_npu、vLLM、MindIE 常规调用） | 调用方或公开负载来源 |
| B2 条件可达 | 需特定 attr/dtype/shape 组合，业务中存在但非默认 | 该组合的业务来源 |
| B1 边界/不可达 | 需极端、超规格或非法参数（超出接口合理上限的 shape、退化/非法输入） | "为何不可达"的说明 |

- **默认保守**：无法证明不可达 → 记 **B3**；降为 B1/B2 必须附证据，**不得仅凭"业务应该不会这么用"**。
- 超规格参数是否算 B1 取决于**接口契约**：契约允许但业务不用 → B1；契约不允许（本应报错）→ 属校验缺失（FP-B04/B05 类），另行归属。

**业务影响类型**（命中后对用户可见结果的后果，用业务语言表述）：静默精度损失（模型效果下降 / loss 不收敛 / 偶发 NaN）｜ 任务失败中断（报错 / 崩溃 / 挂死）｜ 性能退化 ｜ 仅可观测性（日志 / 错误码 / 文档，不影响结果）。

**处置建议**（由两轴推导的报告结论，非新档位）：

| S×O \ B | B3 现实可达 | B2 条件可达 | B1 边界/不可达 |
|---|---|---|---|
| 高（≥6） | 尽快修 | 尽快修 | 排期修 |
| 中（3/4） | 尽快修 | 排期修 | 记录（业务难以触达） |
| 低（1/2） | 排期修 | 记录 | 记录 |

## 7. 判定标准与反误报原则

- **签名/触发词命中 ≠ 成立**：`workspace` 命中是定位提示，必须过完整推导链 + 可达性分析 + 反证排除三关。
- **「大」不必然浪费**：须证双倍/放大**无语义必要**才立卡——double buffer 若确因流水交替使用则反证排除（实证 #408 的反面教材是「流水视图一致仍按双倍」）。
- **三种判定**：
  - **命中**：申请量推导链完整（实需 vs 申请的逐步对照）+ 触发 shape/SoC 组合可静态证伪可达 + 反证排除失败 → 立 Bug 卡；
  - **观察项**：调用侧形态（zerolike 等）、图模式宿主行为、存量非本次引入 → 记录不定级并归因调用方；
  - **反证排除**：对齐必需 / 预留语义 / 框架级复用 / 双 buffer 确因流水 → 明确写出反证理由。
- **可达性分析要给出可复现反例**：具体 shape / dtype / SoC 组合（如 #408 的期望 shape "4196,7168;64640,7168" 下约 2.5G——形态组合写具体值，不写「大 shape」泛称）。
- **不臆造行号**：每条证据必须是实际读到的 文件:行号；引用样板代码时同样给出路径与行号。
- **静态推演声明**：无 NPU 环境时，所有运行时行为结论必须标注「静态推演，需 NPU 实测确认」，并附实测建议（峰值显存采集、OOM 复现组合）。

### 判定纪律补充（v3.6）：非对称增减、证据等级与误判记录

**增减不对称**：允许追加候选（有据即可，错了可由用户排除）；**撤销或否决候选必须附 `[文件]:[行号] [代码行]` 负向证据**。无证据的「看起来没问题」一律记为「未核查」，不得计入反证排除，也不得据此下调等级——否决造成的漏报用户不可见、不可恢复。

- **证据等级**（Bug 卡必填）：`静态可证` = 推导链完整且触发输入可静态构造；`需实测确认` = 依赖运行时输入规模、设备行为或环境差异。标 `需实测确认` 的条目**不得以「命中」名义出卡**，按观察项记录并附实测用例。
- **Agent 误判记录**（Bug 卡必填）：本次被推翻的假设、推翻它的证据（`[文件]:[行号] [代码行]` 或实测输出）、判定标准是否随之修订；无推翻写「无」。
- **误判回流**：同类误判在 3 次检视中重复出现，登记至 `cases/misjudgments.jsonl`（字段见 `cases/README.md`），并在本模式判定标准中新增对应防线；守门 C19d 校验台账字段合法。

## 11. 子型对照、量化基线与探针矩阵

### 子型对照

| # | 子型 / 检查面 | 检视落点 | 命中判据 |
|---|---|---|---|
| ① | workspace 推导过大 | `GetWorkspaceSize` 计算段 | 按双倍/全量申请，实际视图可复用 |
| ② | 内存未复用 | 中间 tensor 生命周期 | 本可复用却各自申请 |
| ③ | 缓存无上限 | 算子内缓存/池 | 长稳调用内存持续上涨 |
| ④ | 图模式未纳入 | aclGraph/条件算子申请路径 | 图模式峰值高於单算子估算 |

### 量化基线（数字来自卡片实证，引用须注明来源）

- 确认实证包括 ops-nn #408（FusedLinearCrossEntropyLossGrad 省显存分支**按双倍申请**，期望 shape 下约 **2.5 倍**）、#4932、#4021、#4001（GPU 迁移场景）。
- 判据：峰值内存 vs 理论值（输入+输出+必要 workspace）的比值，>1.3 需解释。

### 探针矩阵（最小可执行集）

| 探针 | 构造 | 期望 / 判据 |
|---|---|---|
| workspace 复算 | 按 tiling 参数手工推导 workspace | 申请量 ≤ 理论值 × 1.1 |
| 峰值打点 | `torch.npu.memory_allocated` 前后打点 | 峰值与理论值差距可解释 |
| 视图复用 | 检查最后两块 buffer 是否可同视图 | 无 double buffer 却双倍申请 → 命中 |
| 图模式 | aclGraph/条件算子场景下重复打点 | 图模式峰值不高于直调基线 |

### 证据锚点

- `ops-nn #408` —— workspace 双倍申请（约 2.5 倍）
- `ops-nn #4932` —— 迁移场景显存超基线
- `ops-nn #4021` —— 缓存/复用问题
