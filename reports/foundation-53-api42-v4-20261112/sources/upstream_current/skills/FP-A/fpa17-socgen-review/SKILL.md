# FP-A17 aclnn 接口检视（fpa17-socgen-review）

对用户指定的 aclnn 接口做 FP-A17 专项源码检视：先定位算子实现，再按清单逐项核查，每个结论给出**文件 + 行号 + 推导链**证据，命中即出 Bug 卡，输出检视报告。**本模式特殊纪律：① 缺陷表征是「同用例在一代芯片过、另一代精度异常」——单代基线天然测不出，必须先**枚举代际分支**再逐项对表两侧内容；② 卡片触发为关键词（`GetSocVersion|SOC_VERSION|socVersion`）——该签名在大型仓普遍存在且多数用于合法适配，命中只作定位提示，真正的判据是**代际分支内的精度相关硬编码是否两侧齐全**；③ 本模式卡片**无确认 issue 级实证**（检索命中均为异机理条目）——静态命中一律按 O1 定档，禁止把「存在代际分支」直接表述为「跨代精度不一致」；④ 跨代差异的最终判据是**多代芯片同用例实测**，静态只能立「某代际分支缺某精度项」的推导。**

## 0. 与相邻模式的边界

| 相邻模式 | 分工 |
|---|---|
| FP-A01（硬件指令精度不足，未与竞品对齐） | 卡片关联项：A01 是**指令规格本身**低于竞品（代际无关，同一代内即偏差）；A17 是**代际间规格 / 默认路径不同**致同算子跨代不一致——同代内低于竞品归 A01，代际间差归 A17 |
| FP-C06（A5 性能劣于 A2） | 卡片关联项：同一「跨代（A1 / A2 / A5）」对照轴的**性能面**（C06）vs **精度面**（A17）——同一次跨代核验可同时出两类结论 |
| FP-B02（tiling 未适配多种芯片核数） | B02 是**核数 / 平台常量**适配缺失（性能与功能面）；A17 是**精度规格 / 默认路径**硬编码遗漏——同属代际分支问题，按后果面分流 |
| FP-A19（同算子多 tiling 路径覆盖盲区） | 代际分支（arch22 / arch35）与 tiling 模板分流是两条正交的路径轴：跨代精度不一致时先核 A17 分支内容，再核该分支的 A19 用例覆盖 |
| FP-A07（tiling 条件判断错误走入错误分支） | 代际判断条件本身写错（取反 / 漏判 / 端点错）归 A07；条件正确但分支内容（精度硬编码）遗漏一侧归 A17 |
| FP-F03（文档 / 声明面与实现面不一致） | 代际默认路径差异未在文档标注时属声明面缺口，可连打 F03 |

**症状反查定位**：同一用例在 A2 通过、A5 / A1 精度异常（或反之）→ 首查该算子代际分支（`GetSocVersion` / `SOC_VERSION`）两侧内容；代际分支一侧缺精度相关常量 / 开关 → 硬编码遗漏；`cubeMathType` 降精度模式在代际间口径分歧（ops-nn **#5655**）或 cast 舍入口径 1 ulp 分歧（ops-nn **#5656**）→ 先按 A01 / A03 口径核，确认属代际差异再归 A17；跨代仅性能差 → 归 C06；跨代咨询类条目（ops-nn **#3436**、ops-transformer **#1574**）→ 非缺陷，不立卡。

## 1. FP-A17 模式卡摘要（检视依据，源自本库 `patterns/FP-A/FP-A17.md`，v3.1）

- **编号 / 名称**：FP-A17 A1 与 A2 硬件代际精度差异 ｜ **类别**：精度 ｜ **风险**：中（S3×O1=3）｜ **状态**：活跃 ｜ **来源**：团队笔记
- **适用声明头**（照抄卡片）：仓 All ｜ 侧别 All ｜ 载体 Tiling源码,Kernel源码 ｜ 触发 GetSocVersion|SOC_VERSION|socVersion ｜ 默认启用 true
- **skill 核查面**：侧别 All——skill 落地为 `op_host` 的 tiling / infershape 代际分支（含 `arch22/` `arch35/` 平台子目录与 `config/<soc>/` 配置）、`op_kernel` 的 SOC 宏分支与模板特化、`docs/` 的代际默认路径声明面
- **故障机理**：SOC 代际间指令精度规格 / 默认路径不同，**代际分支含精度相关硬编码遗漏一侧**。
- **触发条件**：跨代芯片（A1 / A2 / A5 等）部署同一算子。
- **典型表现**：跨代芯片精度不一致。
- **源码审查映射点 / 检测签名**：映射点 = SOC 代际分支中的**精度相关硬编码**；卡片未给独立 grep 签名，触发词为 `GetSocVersion|SOC_VERSION|socVersion`（关键词定位提示）。
- **测试拦截建议**：多代芯片同用例精度基线对比。
- **实证案例**：**待补充**——2026-09-16 对 GitCode CANN 组织 12 仓约 1.4 万条 issue 全量关键词检索，命中多为 `cubeMathType` 降精度模式口径分歧（ops-nn #5655）、cast 舍入口径 1 ulp 分歧（ops-nn #5656）、跨代性能咨询（ops-nn #3436、ops-transformer #1574）等**异机理**条目，**无「跨代芯片同算子精度不一致」的确认对应实证**。即本模式暂无确认实证算子，检视结论一律按静态口径定档（详见第 9 节）。
- **关联**：FP-A01、FP-C06。

## 2. 检视输入与算子定位

**输入**：aclnn 接口名（必填）；可选 ref（默认 master）、指定仓（默认自动定位）；可选现象描述（哪一代芯片精度异常 / 是否仅跨代才显——用于症状反查）；可选目标代际清单（A1 / A2 / A5 或 arch22 / arch35，用于分支对表）；可选多代基线资产（若有）。

**接口名 → 算子目录换算**：去 `aclnn` 前缀 + 驼峰转下划线小写：
`aclnnRmsNorm → rms_norm`、`aclnnFlashAttentionScore → flash_attention_score`、`aclnnMatMul → mat_mul`。

**仓定位顺序**（GitCode `cann` 组织，逐仓用目录列表确认）：`ops-nn`（norm / matmul / activation 类）→ `ops-transformer`（attention / moe 大模板——代际模板分叉多）→ `ops-math` → `ops-cv`。**类目名不总与直觉一致**，以目录列表为准。FP-A17 高发面：含 `arch22/` / `arch35/` 平台子目录的算子、`config/<soc>/` 多份 binary.json 的算子、kernel 内按 SOC 宏分叉的实现、带 `cubeMathType` 等降精度开关的算子、`GetSocVersion` 使用点密集的 tiling。

**算子目录结构约定**（已验证示例 `cann/ops-nn` → norm 类算子目录）：

```text
{类别}/{op_name}/
├── op_host/           # *_tiling*.cpp / *_infershape.cpp——代际分支主检视面
│   ├── arch22/ arch35/    # 平台 / 代际子目录
│   └── config/<soc>/      # 多份 *_binary.json（分核与模板配置的代际差异）
├── op_kernel/         # SOC 宏分支与模板特化（arch22/ arch35/ 变体）
├── tests/             # 多代精度基线资产（本型覆盖的关键输入）
└── docs/
```

## 3. 取数方式（Important）

公开网页端点被拦截，**必须走 API**（均需带 `User-Agent`；失败重试 2 次、间隔 5 秒）：

| 用途 | 端点 |
|---|---|
| 目录列表 | `GET https://api.gitcode.com/api/v5/repos/cann/{repo}/contents/{path}?ref={ref}` |
| 单文件内容 | `GET https://api.gitcode.com/api/v5/repos/cann/{repo}/raw/{path}?ref={ref}` |
| Issue 查重 | `GET https://api.gitcode.com/api/v5/repos/cann/{repo}/issues?q={关键词}` |

**已实测不可用（截至 2026-09 实测）**：`https://gitcode.com/{repo}/raw/{sha}/{path}`、`https://raw.gitcode.com/...` → 403 或拦截页；端点策略如有变化可复测。若本地已有算子仓克隆，优先直接读本地文件，行号证据以本地 HEAD 为准并记录 commit。**本模式特有取数限制**：① 代际分支对表需**逐代目录 / 逐份配置**拉取（`config/<soc>/` 各一份），API 模式逐份获取；② 本模式无确认 issue 实证，查重环节多为空结果；③ 跨代精度差异需**多代芯片同用例实测**，静态只能立「某代际分支缺某精度项」的推导，不可直接表述为「跨代精度不一致」。

## 4. 代际分支检视清单（每点：查什么 → 何处 → 命中判据）

对 `op_host`（含 arch 子目录与 config）、`op_kernel`（含 SOC 宏分支）、`docs`、`tests` 逐点核查，**每点先查命中面、再做反证排除**，代际间内容一致的适配也要记录为防护面证据。

### ① 代际分支清单与覆盖面
- 查什么：全部 `GetSocVersion` / `SOC_VERSION` / `socVersion` 使用点——分支覆盖哪些代际（A1 / A2 / A5 或 arch22 / arch35 等）、分支条件写法、是否存在**只列了部分代际**而其余落入默认分支的情况（默认分支兜底是否合理、是否被当作通用路径）。
- 何处：`op_host` tiling / infershape、`op_kernel` 的 SOC 分支、`config/<soc>/` 配置目录清单。
- 命中判据：存在代际分支且某代际落入默认兜底（而非显式分支）⇒ 进入内容对称性核查；无代际分支 ⇒ 反证排除并记录结论。

### ② 代际分支内精度相关硬编码的对称性
- 查什么：各代际分支内的**精度相关硬编码**是否成对齐全——累加器位宽、中间精度提升（fp16→fp32）、降精度开关（`cubeMathType` 类）、舍入模式、精度相关常量 / 阈值定义；一侧有、另一侧缺失即为命中面。
- 何处：代际分支函数体、`config/<soc>/` 各份 binary.json、`op_kernel` 模板特化。
- 命中判据：逐项对表后存在「某代际缺该精度项」⇒ 命中候选（须给出该项对结果的影响推导）；两侧齐全一致 ⇒ 反证排除。

### ③ 默认路径差异与文档标注
- 查什么：各代际的**默认执行路径 / 默认精度模式**是否不同且未在文档标注；代际分支的引入版本（某代际分支何时新增）。
- 何处：tiling 模板注册与 `IsCapable`、`docs/` 的精度与平台说明。
- 命中判据：默认路径不同且无文档说明 ⇒ 命中候选 / 观察项（与 FP-F03 声明面连打）；已在文档标注 ⇒ 反证排除。

### ④ 多代精度基线测试覆盖
- 查什么：卡片拦截建议的「多代芯片同用例精度基线对比」是否具备——是否只有单代基线（跨代差异天然测不出）；代际分支是否各有对应用例。
- 何处：`tests/` 用例与基线资产、CI 的多代配置。
- 命中判据：无多代基线 + 存在代际分支 ⇒ 记观察项（测试建设缺口），不计入缺陷；多代基线齐备 ⇒ 记录为防护面。

## 5. 检视流程

1. **定界**：换算 op 目录、确认所在仓与 ref；按用户现象（哪一代异常 / 仅跨代才显）反查优先清单点；确认目标代际清单与基线资产。
2. **枚举**：目录列表列出 `op_host`（含 arch 子目录与 config 各份）、`op_kernel`（含 SOC 分支）、`tests`、`docs` 全部相关文件，产出文件清单与**代际分支清单**。
3. **触发词扫描**：按 `GetSocVersion|SOC_VERSION|socVersion`、`Ascend910|Ascend950` 类代际标识、`arch22|arch35` 目录与宏、`cubeMathType` 定位风险面（本地仓用 grep；API 模式逐文件拉取后检查）。**签名零命中时清单仍须逐项核查**（无显式分支但存在多份 config 目录同样是命中面）。
4. **逐点核查**：每点记录命中面与防护面证据（文件:行号）；对每个代际分支写出「代际 → 分支位置 → 精度项清单（位宽 / 提升 / 开关 / 舍入 / 常量）→ 与其它代际的差集」四项对表。
5. **反证排除**：无代际分支、各代际精度项齐全一致、默认路径已在文档标注、多代基线齐备 → 明确写出反证理由。
6. **判定**：按第 7 节标准给出 命中 / 观察项 / 反证排除。
7. **GitCode 查重**（仅命中项）：issues API 按接口名 + `精度|A5|A2|跨代|芯片` 检索，逐条比对是否同机理；无同机理才立卡（本模式历史查重命中均为异机理，属预期）。
8. **业务可达性核查**（仅命中项）：判 B 等级、定业务影响类型、给处置建议；默认保守（无法证明不可达即记 B3），降档须附证据；B 不改 S×O 档位。
9. **出报告**：按第 8 节模板落盘；所有跨代结论标注「静态推演，需多代芯片实测确认」，并附多代同用例基线方案。

## 6. 风险定级（S×O）与业务影响评估（B 轴）

- **S**：S3（跨代精度不一致——结果错但可运行）；S2（差异在容差内、仅极端组合触发）；S1（仅测试覆盖缺口、代际行为一致）。
- **O**：O3 = ≥2 条独立实证；O2 = 1 条独立实证；O1 = 仅静态扫描命中或团队笔记（实证 = 确认对应的 issue / PR，或经跨仓、跨分支核验确认的缺陷记录，同权计入）。静态推演命中且无实证默认 **O1**；升档须在报告中给出实证依据。
- **风险 = S×O**：≥6 高；3/4 中；1/2 低。FP-A17 基准：模式卡整体 **S3×O1=3（中）**；纯静态命中一律 S3×O1=3（中，暂定），跨代实测后复评。

### B 轴：业务影响评估（与 S×O 正交；报告层新增，不改卡片定级）

S×O 回答"多严重、多常见"，**不回答"真实业务能不能碰到"**。B 轴补这一问，只决定**修复优先级建议**，**不参与 S/O 取值、不改 S×O 档位与卡片元数据**。

**业务可达性（B）**——触发条件在真实负载中的可达程度：

| 等级 | 判据 | 证据要求 |
|---|---|---|
| B3 现实可达 | 主流框架/公开模型默认路径即可命中（如 PTA/torch_npu、vLLM、MindIE 常规调用） | 调用方或公开负载来源 |
| B2 条件可达 | 需特定 attr/dtype/shape 组合，业务中存在但非默认 | 该组合的业务来源 |
| B1 边界/不可达 | 需极端、超规格或非法参数（超出接口合理上限的 shape、退化/非法输入） | "为何不可达"的说明 |

- **默认保守**：无法证明不可达 → 记 **B3**；降为 B1/B2 必须附证据，**不得仅凭"业务应该不会这么用"**。
- 超规格参数是否算 B1 取决于**接口契约**：契约允许但业务不用 → B1；契约不允许（本应报错）→ 属校验缺失（FP-B04/B05 类），另行归属。

**业务影响类型**（命中后对用户可见结果的后果，用业务语言表述）：静默精度损失（模型效果下降 / loss 不收敛 / 偶发 NaN）｜ 任务失败中断（报错 / 崩溃 / 挂死）｜ 性能退化 ｜ 仅可观测性（日志 / 错误码 / 文档，不影响结果）。

**处置建议**（由两轴推导的报告结论，非新档位）：

| S×O \ B | B3 现实可达 | B2 条件可达 | B1 边界/不可达 |
|---|---|---|---|
| 高（≥6） | 尽快修 | 尽快修 | 排期修 |
| 中（3/4） | 尽快修 | 排期修 | 记录（业务难以触达） |
| 低（1/2） | 排期修 | 记录 | 记录 |

## 7. 判定标准与反误报原则

- **签名 / 触发词命中 ≠ 成立**：`GetSocVersion` 在大型仓普遍存在且多数用于合法适配（核数、UB 大小、模板选择）——必须过「分支清单 + 精度项差集 + 影响推导」三关；命中数大只说明核查工作量大。
- **三种判定**：
  - **命中**（可静态证缺陷路径）：某代际分支缺某精度项且该项对结果有影响的推导链完整 ⇒ 立 Bug 卡；
  - **观察项**：精度项差异存在但影响需跨代实测、或默认路径差异属文档面问题（F03）⇒ 记录并附多代基线方案，按 S3×O1 暂定；
  - **反证排除**：无代际分支、各代际精度项齐全一致、默认路径已文档化 → 写出防护面证据与反证理由。
- **「单代基线全绿」不是反证**：本型识别特征正是「单代测不出跨代差异」——用例覆盖面须按代际分别核。
- **异机理条目不得当实证**：`cubeMathType` 降精度口径分歧（ops-nn #5655）、cast 舍入口径 1 ulp（ops-nn #5656）属 A01 / A03 面；跨代性能咨询（ops-nn #3436、ops-transformer #1574）属 C06 / 咨询面——均不作为本型实证。
- **不臆造行号**：每条证据必须是实际读到的 文件:行号；无实证算子时不写算子名与行号（见第 9 节）。
- **静态推演声明**：无 NPU 环境时，所有运行时行为结论必须标注「静态推演，需多代芯片实测确认」。

### 判定纪律补充（v3.6）：非对称增减、证据等级与误判记录

**增减不对称**：允许追加候选（有据即可，错了可由用户排除）；**撤销或否决候选必须附 `[文件]:[行号] [代码行]` 负向证据**。无证据的「看起来没问题」一律记为「未核查」，不得计入反证排除，也不得据此下调等级——否决造成的漏报用户不可见、不可恢复。

- **证据等级**（Bug 卡必填）：`静态可证` = 推导链完整且触发输入可静态构造；`需实测确认` = 依赖运行时输入规模、设备行为或环境差异。标 `需实测确认` 的条目**不得以「命中」名义出卡**，按观察项记录并附实测用例。
- **Agent 误判记录**（Bug 卡必填）：本次被推翻的假设、推翻它的证据（`[文件]:[行号] [代码行]` 或实测输出）、判定标准是否随之修订；无推翻写「无」。
- **误判回流**：同类误判在 3 次检视中重复出现，登记至 `cases/misjudgments.jsonl`（字段见 `cases/README.md`），并在本模式判定标准中新增对应防线；守门 C19d 校验台账字段合法。

## 9. 示例速览：本模式暂无确认实证算子

卡片「实证案例」为 **待补充**——2026-09-16 全量关键词检索命中条目均为**异机理**：`cubeMathType` 降精度模式口径分歧（ops-nn #5655）、cast 舍入口径 1 ulp 分歧（ops-nn #5656）属精度口径面（FP-A01 / A03），跨代性能咨询（ops-nn #3436、ops-transformer #1574）属性能面（FP-C06）——**无「跨代芯片同算子精度不一致」的确认对应实证**。故本节不给具体算子与行号，改为给**触发词 / 检索起点速览**（**严禁虚构算子名或行号**）：

- **检索起点**（按第 2 节换算 op 目录后，在 `op_host`（含 arch 子目录与 config）+ `op_kernel`（含 SOC 宏分支）+ `docs` 全量 grep）：
  - `GetSocVersion` / `SOC_VERSION` / `socVersion` 的**全部使用点**（分支条件与分支体）；
  - 代际标识常量（`Ascend910` / `Ascend950` 类宏 / 枚举）在精度相关赋值处的出现；
  - `arch22` / `arch35` 目录与宏在 tiling、kernel 模板特化中的分支；
  - `config/<soc>/` 下多份 `*_binary.json` 的逐份对比（分核 / 模板配置的代际差）；
  - `cubeMathType` 等降精度开关在代际分支内的取值（口径分歧时按 FP-A01 / A03 分流）。
- **核查方式**：对每个代际分支写出「代际 → 分支位置 → 精度项清单（位宽 / 提升 / 开关 / 舍入 / 常量）→ 与其它代际的差集」四项对表，差集项进入影响推导。
- **纪律**：不得把「存在代际分支」直接表述为「跨代精度不一致」、不得虚构算子名或行号；命中须附多代同用例基线方案，无实测时档级一律 S3×O1（中，暂定）。
- 任何一点的最终判定以第 4/5/7 节口径为准，禁止凭算子类型直接下结论。

## 10. 能力边界与自检（v3.8）

### 能力边界

- **静态可证**：清单里能在源码内给出「`文件:行号` + 推导链」的部分，按第 7 节判据出卡。
- **需实测确认**：依赖运行时输入规模、设备行为或环境差异的结论，只能记观察项并附实测用例（证据等级见第 7 节）。
- **不覆盖**：本模式以外的机理（边界见第 0 节）与仓外框架侧行为；`TRIAGE.md` 只负责收敛候选，不构成判定依据。
- **找不到 ≠ 没有**：按清单未命中只说明「本轮未发现」，不得表述为「该算子无此缺陷」；抽样核查须在报告写明抽样口径。

### 自检

```bash
python3 scripts/gen_triage.py --check                          # 分诊表与映射一致

```

### 工作量与抽样（v4.0）

- **深度档：宽浅**（索引 `depth` 字段）——只跑签名定位 + 每类抽 3 例；报告必须写「抽样，非全量」，不得表述为全量检视。
- **报告必填**：抽样口径（全量 / 每点前 N 处 / 每类 N 例）+ 停止点记录；未写口径视为未完成。
