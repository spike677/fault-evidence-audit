Qwen-Image-2.1: TP=2 output corrupted with dense chroma speckle (single-GPU clean; SGLang TP=2 shows the identical corruption)
### Summary

Qwen-Image-2.1 serving with `--tensor-parallel-size 2` (PR #7759 branch) produces images corrupted by **dense multicolored (chroma) speckle noise** across smooth regions, while image composition/structure remains correct. Single-GPU serving with the same code and the same local patches produces clean output. The official recipe itself lists "TP=2/4 output parity — pending measurement", and we can confirm: **TP=2 parity does not hold**.

We also reproduced the **identical corruption with SGLang's independent TP implementation** (sgl-project/sglang, diffusion path, `--tp-size 2`), and verified NCCL collective numerics across our mixed-GPU pair are clean — details below. This points to a shared flaw in how this model is sharded under TP (both engines use vLLM-style parallel-layer conventions), rather than a hardware or transport problem.

### Environment

| Item | Value |
|---|---|
| GPUs | 2× RTX 5070 Ti (16GB) + RTX 5070 (12GB), both Blackwell `sm_120` |
| Driver / OS | Windows 11 + WSL2 (Ubuntu 24.04), latest NVIDIA driver |
| vLLM-Omni | PR #7759 branch, commit `3d6a1c4d` |
| vllm / torch | 0.29.0 / 2.13.0+cu130 |
| Model | Qwen/Qwen-Image-2.1 (bf16 weights) |

### Reproduce

```bash
vllm serve /root/models/Qwen-Image-2.1 --omni \
  --served-model-name qwen-image-2.1 \
  --host 0.0.0.0 --port 8091 \
  --tensor-parallel-size 2 \
  --diffusion-offload-config '{"mode":"layer","components":["text_encoder"],"pin_memory":false}' \
  --step-execution --max-num-seqs 1 --enforce-eager
```

```bash
curl http://localhost:8091/v1/images/generations -H "Content-Type: application/json" -d '{
  "model": "qwen-image-2.1",
  "prompt": "a ceramic teapot on a wooden table, soft window light, clean background",
  "size": "1024x1024",
  "num_inference_steps": 40,
  "true_cfg_scale": 1.0,
  "seed": 42
}'
```

Note: on 12–16GB consumer cards we run with a few local patches that keep the text encoder (Qwen3-VL 8B) and its `lm_head`/`embed_tokens` on CPU and pin the VAE to fp16 (the offload path PR #7759 ships assumes larger VRAM). **These patches are exonerated as the corruption source** — single-GPU serving with the exact same patched tree is clean.

### What the corruption looks like

- Dense green/purple/orange single-to-few-pixel speckles over smooth areas (walls, table, gradients); fine structure (edges, objects) preserved.
- Deterministic across seeds and prompts; present at 1024² and larger; present for both t2i and image editing.
- Not subtle — immediately visible; ~4-8% of pixels in flat regions show chroma noise in our pixel-diff quantification vs single-GPU output of the same seed.

### What we ruled out (evidence chain)

1. **VAE decode dtype** — VAE pinned to fp16 in all tests (bf16 decode has its own, different speckle signature); corruption unchanged. Excluded.
2. **Our local patches** — single-GPU run on the same patched tree is clean. Excluded.
3. **Rank order / mixed-GPU placement** — swapped the two different cards between rank 0/1; corruption identical. Excluded.
4. **NCCL transport / mixed GPU models** — wrote a `torch.distributed` test: bf16/fp16/fp32 all-reduce on both cards vs Gloo CPU fp64 reference. Max relative error: fp32 ≈ 4e-8, fp16 ≈ 3e-4 (≈ half-ulp), bf16 ≈ 2.5e-3 (exactly one bf16 ulp) — all normal rounding, no corruption; 50-round 4096² stress accumulation: zero NaN/Inf. Transport is numerically clean. Excluded.
5. **Engine-specific plumbing** — **SGLang** (sgl-project/sglang, main @ `8ab21c8a9`, `--model-type diffusion --tp-size 2`, flash-attn 2.8.3 self-built for sm_120, `--attention-backend fa2`) reproduces the **same speckle corruption at 1024²/30 steps**, while its single-GPU path with the same offload flags is clean. Two independent TP implementations failing with the same visual signature suggests the shared sharding recipe for this architecture is the problem.

### Suspects (for whoever picks this up)

Both engines shard this DiT with the standard vLLM parallel-layer conventions (QKV column-parallel / row-parallel FFN + all-reduce). Things specific to Qwen-Image-2.1 that interact with that recipe and are worth checking first:

- The single-stream joint text+image attention (32 single-stream blocks, structural block-causal masks) — per-rank mask/RoPE boundary handling with 16 heads per rank.
- Per-head QK-norm (`QwenImage21ZeroCenterRMSNorm`, fp32 computed, weight+1 trick) under head sharding.
- AdaLN modulation MLPs — if these are sharded+all-reduced like ordinary FFNs, partial shifts/scales get summed, which would produce exactly this class of mild, structure-preserving corruption.

Happy to attach side-by-side PNGs (TP=2 vs single-GPU, same seed), pixel-diff maps, or the NCCL test script on request.

### Impact

TP=2 is the only way this model fits 2K (2752×1536) workloads on consumer GPUs; with the corruption it is unusable, and single-GPU caps out near ~1536px without DiT layerwise offload. A fix (or even identifying which layer is mis-sharded) would be very welcome.
