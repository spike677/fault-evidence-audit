## 一、库标准（收录与维护规范，12 条）

## 库标准（收录与维护规范，精简版）

1. **实证准入**：每条模式须有真实证据链（issue / PR、精度失败记录或跨仓静态扫描命中），禁止无实证猜想；证据匹配须「确认对应」，检索命中泛化关键词但机理不符者不录入。完整准则见库内维护约定与守门脚本检查项 C1~C50。
2. **唯一稳定编号**：`FP-<类别字母><两位序号>`，类别 A~G 七类，一经分配永不复用、永不重排（对齐 CWE-ID 做法）。
3. **卡片要素**：故障机理 / 触发条件 / 典型表现 / 源码审查映射点 / 测试拦截建议 为必备字段，元数据 / 实证案例 为结构必备字段（以上 7 项与 **适用**（v2.17 起必备声明头）的存在性由守门脚本 C6 逐卡校验）；检测签名为可选节（条件性给出，未给出时由索引 `signatures` / `keywords` 承载）；关联与索引 `related` 集合等值（守门 C18b 双向校验）。**签名两种形态（v6.5）**：字符串（纯正则）或对象 `{re, files?, within?, exclude?}`——对象形态可带上下文约束（限定路径角色 / 限定所在函数 / 排除行），守门 **C37** 校验键白名单与各字段可编译性；缺失型规则可挂 `subtype` 把候选落到子型（该子型须已在本模式 `subtypes` 中定义）。
4. **声明式适用头（v2.17）**：每卡首部 `- **适用**：仓 / 侧别 / 载体 / 触发 / 默认启用`，消费方「先按仓、侧别、载体筛选，再扫签名」；词表见索引 `applicability_vocab`，`必须触发` 上限 6 条（守门 C14）。**`触发` 是正则形态**（`必须触发` / `无代码触发特征` 为哨兵值），须可编译（守门 **C34**，v6.2 新增——此前三条括号未闭合的坏 trigger 带病存活）；能当签名用的 trigger 必须接进索引 `signatures`，否则「触发」写着指纹、扫描器却读不到（v6.2 一次补齐 22 条）。
5. **风险等级（FMEA 简化版，含 S4 档）**：严重度 S4=致命（进程崩溃 / 任务挂死 / 数据静默损坏）、S3=结果错误、S2=功能受限、S1=资源浪费；发生度 **O3=≥2 条独立实证、O2=1 条独立实证、O1=仅静态扫描命中或团队笔记**（实证 = 确认对应的 issue / PR，或经跨仓、跨分支核验确认的缺陷记录，同权计入）；风险 = S×O：高（≥6，含 S4×O2=8、S4×O3=12）、中（3/4）、低（1/2），随证据累积动态复评。**定级纪律（v3.3）**：① 风险档严格按 S×O 乘积执行，卡片元数据、总览表、索引 `risk.level` 三方一致，不设「评级维持中」「降档维持」等脱离公式的例外档——严重度特征（如表达型问题）由 S 取值体现，不重复体现在档位上；② 确需调档的（升/降），应改 S/O 取值本身并在卡片括注理由与复评日期、于 [CHANGELOG.md](../CHANGELOG.md) 登记，守门脚本 C7 对「档位 ≠ 乘积」双向拦截；③ `evidence` 为空且实证案例标「待补充」的条目按当前 S×O 计档，补充实证后按上述 O 判据复评并在 CHANGELOG 登记。
6. **命中判定（v2.17）**：签名命中 ≠ 成立，须过正向与负向两侧证据、置信度 ≥70% 才判成立；**负向证据必须附 `[文件]:[行号] [代码行]`**，不得以「上游已校验」一笔带过。
7. **变更流程**：增补/修改在 [CHANGELOG.md](../CHANGELOG.md) 登记（日期、条目、来源、commit）；新条目必须同时更新总览表与 `fault_patterns_index.json`，并通过守门脚本校验。
8. **判定纪律与误判台账（v3.6）**：候选的增减**不对称**——允许追加候选，**撤销/否决必须附 `[文件]:[行号] [代码行]` 负向证据**（否决造成的漏报不可见、不可恢复；补查只增候选，错了可由用户排除）。Bug 卡必填 **证据等级**（`静态可证` / `需实测确认`，后者不得以「命中」名义出卡）与 **Agent 误判记录**（被推翻的假设 + 推翻证据）。同类误判在 3 次检视中重复出现须登记 [cases/misjudgments.jsonl](../cases/misjudgments.jsonl)（字段见 [cases/README.md](../cases/README.md)），并在对应 skill 第 7 节新增防线；守门 C19c / C19d 校验标准段与台账。
9. **未证实标注（v4.1）**：索引 `evidence` 为空的模式，卡片首部须显式写 `- **实证状态**：未证实（…）`，说明检索结论与来源，并注明「按 O1 计档、引用须标注未证实」；不得以「待补充」代替正式标注（守门 C28）。总览表「实证」列同步写「未证实（检索无对应）」。
10. **子型机读化（v6.3；v6.7 增配对结构判据）**：模式内**确有失效形态枚举**时（卡片/skill 的「子型 ①②③」或「成因 ①—⑥」），索引须给 `subtypes: [{id, name, evidence?, sig?, pair?}]`——**id 形如 `B07-6`（前缀 = 模式编号去掉 `FP-`）、全局唯一**；`name` 为形态名；`evidence` 可选（有独立实证才写，**无独立实证不得编**）；`sig` 为存在型正则数组（「该子型可被机器扫」）；`pair` 为**结构型判据** `{a, b, scope: file, max_diff: 0, strict?, id_re?}`——统计文件内 A/B 两个正则的出现次数，**次数失衡即候选**（`max_diff` 为容忍差；`scope` 目前只支持 `file`）；`strict: true` 时按 `id_re`（捕获组 1 = id）分桶做**顺序判据**：同一 id 的两次 A 之间必须有 B（如 `SetFlag` 同一 event id 连发会覆盖等待语义，**这种错计数是配平的**）。约定：**子型是检索线的拆分，不是新的模式编号**，永不单独定级、不单独占总览表行；`--subtypes` 可列出全部子型（守门 **C35**：结构 + id 唯一 + sig/pair 可编译 + `strict` 须配 `id_re` + 「卡片枚举 ≥3 处而索引无 subtypes」拦截）。**判别型优于定位型**：能用 `pair` 表达的机理（配平/成对/顺序）不要把 `sig` 写成「出现即候选」，`SetFlag`/`WaitFlag` 这类每几十行一次的 token 只会把候选刷成定位清单。
11. **产出审计与豁免（v6.6；v6.8 扩至子型）**：签名只报「命中数」不报分母时，一条**匹配一切**的签名和一条精准签名看起来一样有用。`scripts/sig_yield.py` 对指定语料逐条算（**三源**：模式签名 / 子型存在型指纹 / 子型配对判据）`hits / files_hit / density / coverage`，配对阵据按**失衡文件数**计候选，并在模式级算「用户真正看到的候选量（三者合并去重）」；基线落 `cases/sig_yield-<语料>.json/.md`（生成物，勿手改）。模式级候选 >500 记 `noisy`、>200 记 `watch`；子型判据 >500 记 `noisy`、>200 记 `watch`。**被记 noisy 的必须二选一**：加 `files`/`exclude` 约束或收紧正则把量压下去，或在索引里写 `yield_waiver: "<理由>"` **显式豁免**（定位型 / 必须触发型可豁免，但理由要写清「为什么量大仍然正确」）——子型判据不允许豁免，>500 一律要求收紧或删除。守门 **C38**：基线结构合法、**每条非宽泛签名与每条子型判据都必须在基线中有记录**（改了不重跑审计即报错）、模式 noisy 无豁免即报错、子型 noisy 直接报错。**能力边界**：`pair` 只支持**文件级**——流水同步天然在生产者/消费者两个函数间配对，函数级会把正确答案判成缺陷（ops-math 实测 323 个含同步原语的函数中 49 个"失衡"，绝大多数是 `CopyOut` 置位、`CopyIn` 等待），故 `scope: func` 由 C35 显式拦截。**`near`（窗口邻接）未采纳**：曾尝试用「命中 X 后 N 行内必须有 Y」表达「动作先后」，五组假设实测后否决——三组缺失率 93~100%（假设本身错），另两组抽样 6 例中 5 例假阳（判空在 caller、Wait 在窗口外）；**用行距近似因果不成立**，动作先后改用 `pair.strict` 的 id 状态机表达。
12. **判据能力的边界（v6.10）**：正则判据能看的是「**行内模式**」「**文件内计数配平**」「**同 id 状态机顺序**」「**路径/函数作用域**」四类；**跨语句的数据流判断不了**。有实测依据的一条：`A05-5`（越界 / 尾块覆盖不完整）需要判断「搬运长度是否等于 `min(剩余, 块大小)`」，而 ops-math 里 **224 处尾块搬运中，保护逻辑与搬运同处一条语句的是 0 处**（100% 在别处——`copyParamsTail_` 这类结构体字段、`tailUbSize_` 来自 tiling）→ 正则无法关联「这个变量的值是谁算的」。这类机理只能**人工审**，或在扫描器里引入轻量符号表（未做：成本远高于收益，且会引入"看着能判、其实判不准"的假安全感）。同理，凡需要「值域/表达式等价性」的机理（A12 取整方向、B13 窄化幅度）都不要硬塞进 `signatures`。

## 二、维护约定

## 维护约定

- 新增条目八件套：新建 `patterns/FP-X/FP-XN+1.md` 卡片 → 总览表加行 → `fault_patterns_index.json` 加条（保持每条一行紧凑风格）→ 新建 `skills/FP-X/<新 skill 注册名>/SKILL.md`（目录名须等于 frontmatter `name`，编写规范与登记要求见 [skills/README.md](../skills/README.md)）→ `triage_map.json` 登记到合适入口并重跑 `python3 scripts/gen_triage.py`（C20 要求 53/53 覆盖）→ 重跑 `python3 scripts/gen_evals.py`（C21 要求 53/53 × 3 类用例）→ 重跑 `python3 scripts/score_skills.py`（C27 要求评分卡同步）→ [CHANGELOG.md](../CHANGELOG.md) **首行**登记（该表按日期倒序、最新在前）；完成后跑守门脚本确认 C1~C50 全绿。
- **判据层连带（v6.18.1，v6.17 起新增模式的必做项）**：① 在 `fault_patterns_detect.json` 写本模式 `axes/oracle/signal/lines/min_cases/constructor/judge/kill`（C40 要求 53/53 齐备）；② 若用到新 oracle 类别，**同时**在 `oracle_failures.by_oracle` 登记它会在什么情形下给错结论（D23 拦截「用了却不知道它怎么失效」）；③ 跑 `python3 scripts/gen_detect.py` 合并进索引；④ 若 `depth=深度`，再跑 `python3 scripts/sync_detect_section.py` 生成技能的指针段与 `references/detect-l2-l3.md`（**C42** 双校验）；⑤ 若新模式的 `trigger` 为 `必须触发`，回 `workflows/operator-admission.md` 的 `Stage 1` 表格加行（**C43** 校验，否则准入体检会漏检）。
- **签名接线（v6.2）**：新增/修改模式时，`applicability.trigger` 必须是**可编译正则**（C34 拦截；`必须触发` / `无代码触发特征` 为哨兵值），且凡能作为指纹的 trigger 都要落进索引 `signatures`——「触发写着指纹、扫描器读不到」是 v6.2 前 22 条模式的通病（含 3 条括号未闭合的坏正则）。宽泛 token（`half` / `double` / `Tiling` / `workspace` 等）进 `signatures` 的同时**必须**登记进 `broad_signatures`（C30 校验包含关系，扫描器据此标 `[BROAD]`），避免候选噪声被当成结论。
- **改完库必须跑的生成物（v6.25 新增；漏跑会被 CI 挡下，但知道顺序能少返工）**：
  改**模式卡**后按此序跑——`gen_cases.py` → `gen_triage.py` → `gen_evals.py` → `sync_detect_section.py` → `score_skills.py` → `gen_site.py` → `gen_readme_diagram.py`，最后 `ci_gate.py` 全绿才算完。
  改**索引/判据真源**时先跑 `gen_detect.py` 再跑上序；改**案例库**只需 `gen_cases.py` + `gen_site.py` + `gen_readme_diagram.py`。
  > **为什么单列这条**：`check_fault_patterns.py`（C1–C50）查的是**结构一致性**，**不查生成物是否最新**——那部分在 `ci_gate.py`（24 项）。
  > 只跑前者会得到「全绿」的假象，实测已因此漏过 `site/index.html`、`evals/*.json`、`README` 图三处。
- 编号退役保留编号、状态改「退役」并注明原因；分类归属、风险评级与适用头词表的取值以索引顶层 `applicability_vocab` 为准。
- 误判台账（v3.5）：同类误判在 3 次检视中重复出现时，在 [cases/misjudgments.jsonl](../cases/misjudgments.jsonl) 追加一行（字段与时机见 [cases/README.md](../cases/README.md)），并在对应 skill 第 7 节新增防线；改动后跑守门确认 C19d 通过。
- 欢迎通过 Issue / PR 提交新增模式或修订建议：请附带可复现的证据链（issue / PR 编号、精度失败记录或源码扫描命中），同步更新总览表与 `fault_patterns_index.json`（新增模式建议一并提交对应 `skills/` SKILL.md 与 `triage_map.json` 分诊行），最后跑一遍守门脚本确认 C1~C50 全绿。

## 三、参照的业界标准

- **CWE**（Common Weakness Enumeration）：总览 View + 单条目独立页的两级结构，与唯一稳定编号做法。
- **FMEA / IEC 60812**：S×O 定级与动态复评（见第 5 条）。
- **ODC**（Orthogonal Defect Classification）与 **IEEE 1044**：缺陷分类与证据要求。
- **Diátaxis Reference 型文档**：条目一页、结构一致、交叉引用。
- **Agent Skills 渐进披露**（progressive disclosure）：入口只给筛选所需字段，展开按需读取。
