DeepSeek-MoE（allgather dispatcher + CP=2）跨版本 loss 精度差异 — 问题分析文档
报告日期：2026-09-20
分析对象：MindSpeed + Megatron-LM 在 NPU 上的两套版本组合，脚本
deepseek_moe_4k_gloo.sh
上游/关联文档：
grad_norm_diff_analysis_report.md
（2026-09-18，针对
deepseek_moe_4k_FusedEmaAdamW.sh
、CP=1/EP=2/alltoall 配置，已确认 RoPE 融合为当时的主要种子）
一句话结论：
本次（+CP=2、allgather dispatcher、MoE aux loss 生效）暴露出一个 0.12 与 0.18 在"CP 语义"上不等价的根因——MoE 辅助 loss 的梯度缩放相差
cp
倍；它与第二处实现层差异（RoPE 融合路径）共同解释了 step3 与 step11 的可见 loss 偏差。两者都可由"归一化口径核对 + 算子路径对照"直接推导出来，不依赖试错；残余差异则已证明为算子栈级舍入种子被 MoE 离散路由放大的地板。
0. 结论摘要（TL;DR）
根因一（语义层，主因）：MoE 辅助 loss 在 CP 下的梯度缩放不等价。
0.12：
MoEAuxLossAutoScaler.set_loss_scale(loss_scale / num_microbatches)
0.18：
MoEAuxLossAutoScaler.set_loss_scale(loss_scale * cp_group_size / num_microbatches)
因两侧 DDP 都在
dp_cp
组上做
均值
规约（÷dp·cp），而 aux loss 的
值
是"全局 token 归一"定义、逐 rank 只算部分量（Σ_j A_j = 全局 aux），其梯度必须"对 CP 求和"，
故
S
必须含
×cp
。结论：0.18 的写法使 aux 有效权重 =
--moe-aux-loss-coeff
（与 cp 无关），0.12 的写法使其 =
coeff / cp
（cp=2 时等于 coeff 减半）。
该结论由代数推导得出（§3.3），并由 4 条可证伪预言核验（§3.5），
不是由"改完就对齐"倒推
。
等价性已由实验逐位证实
：
0.18(×cp, coeff=0.01)
与
0.18(无 cp, coeff=0.02)
的 50 步 loss / grad norm 与验证集 loss
完全逐位一致
（§3.5.2）→
×cp
精确等于"把 aux 有效系数乘 cp"。
根因二（实现层）：RoPE 路径不同。
0.12 侧因缺 apex 被 MindSpeed 强制
config.apply_rope_fusion = False
，走手写非融合
t*cos + rotate_half(t)*sin
；0.18 侧
apply_rope_fusion=True
走 TE 融合 RoPE。二者公式等价、算子不同 → 逐层逐 token 舍入不同。由代码路径对照直接推出（§4.1），预言与实测一致（§4.3）。
两处差异的判别特征（可推导、已验证）
：aux 缩放
不进前向
，故只改它时 step1 的
lm loss
与
load_balancing_loss
逐位不变、只有 grad norm 变；RoPE 改的是前向，故它同时改变 step1 的
lm loss
末位与
load_balancing_loss
末位（§3.5 P1/P4、§4.3）。
残余差异是"地板"，不是残留 bug
：任何 1e-6 级相对种子在 MoE 离散路由 + grad 尖峰动力学下都会被放大到中后段 2%~6%。由两个
同版本受控实验
量化（§6）：0.12 基线自身可逐位复现（50 步 loss/grad norm/验证集 loss 全等），而给它加一个纯舍入级开关（
--use-fused-rotary-pos-emb
）后，后半段出现
第 19~50 步连续 32 步单边 +2.4%~+4.8%
、验证集 loss
+2.4%
。
验收判据（重要）
：在非 bit 一致前提下，"每步 loss 相对误差 <2%"
不可达
——上述纯舍入级开关就能让 50 步中
30 步
超 2%。有效判据是：
step1~5 逐位或 ≤1e-6 相对差
、
验证集 loss 落在同配置多次运行的散布内
、曲线趋势一致。
归责
：属
Megatron（mcore）侧
的行为/语义变化，不是 MindSpeed 需要适配的问题（本配置生效的是 Megatron 自己的
schedules.py
；MindSpeed 自带副本只在 ripipe/dualpipev/fb_overlap/multi_parameter 下生效，且其写法与 0.12 一致，无 cp 因子）。建议把
cp_size_for_scaling
做成
显式可配开关
（默认随上游语义），而不是硬编码为 1。

1.2 把"loss 差异"拆成可推理的三层子问题
一个训练步的 loss 由三段决定，逐段核对即可定位，无需先试错：
L1 目标函数的值
：给定同一份权重与数据，前向算出的 loss 值是否一致？（aux 缩放不应影响它；任何前向算子差异会影响它）
L2 反向的梯度
：loss 值若一致，梯度是否一致？→ 取决于
所有对 loss/梯度做缩放的归一化项
是否逐项等价。
L3 参数更新与后续前向
：优化器/DDP 规约/分片是否一致；以及 L1、L2 的差异如何随步数累积。
判别推论（后面反复用到）
：
若差异只出现在 L2（梯度缩放类），则 step1 的
前向 loss 与 aux 值必须逐位不变
，只有 grad norm 变；
若差异出现在 L1（前向算子类），则 step1 的
loss 值本身就会变
（可能只在末位）。
1.3 基线与判据
基准：
core_v0.12.1

本轮元结论
：该判据在"非 bit 一致实现"下不可达（§6.3），需替换（§7.3）。

3. 根因一：MoE 辅助 loss 的 CP 缩放（语义层）
3.0 白话版（先看这段，再看推导）
CP 做了什么
：CP=2 时把一条序列切成两半，前半放 NPU-A、后半放 NPU-B；每个 rank 只看得见自己那半的 token。
主 loss（lm loss）为什么两版一致
：它的定义是"全 batch 所有 token 的平均"。两版用两条不同但等价的路得到同一个数——
0.12：在
loss_func
里把两个 rank 的一加（CP all_reduce），直接得到全 batch 的均值；因为值已经是"全局均值"，而 DDP 后面还会把 CP 维的梯度
取平均
（÷cp），所以要在 schedules 里先
× cp
把这次平均抵消掉。
0.18：不加、也不乘，每个 rank 只留自己那半的
局部均值
，让 DDP 的"÷cp 取平均"正好完成"两半合成全体"。
两条路代数上恒等（§2.1 表 A 的 A2+A3），所以主 loss 与 grad norm 能对上——
主 loss 不是问题所在
。
aux loss（MoE 负载均衡 loss）的问题
：它的定义用
全 batch 的 token 统计
（
f_i
= 全 batch 中分给专家 i 的 token 占比，
P_i
= 全 batch 的平均路由概率），所以它的
值本身是与 cp 无关的一个全局数
；但实现上每个 rank 只能拿自己那半的
probs
去算，于是
每个 rank 只算出这个全局数的一部分
，两份
相加
才等于全 batch 的值。
类比：两个人数一筐苹果，各数一半，各自报"我这半有 5 个"。总数必须
相加
（5+5=10）。如果主管把两份报数
取平均
（10/2=5），结果就少了一半。
而 DDP 对 CP 维的梯度做的正是
取平均
（÷cp）。所以每个 rank 必须先把 aux
乘上 cp
再交给 DDP，平均之后才等价于"相加"。这就是
cp_size_for_scaling
的作用：
侧
aux 交给反向前的系数
DDP 平均后
实际效果
0.18
× cp
变成"对 CP 求和"
aux 力度 = 你设的
--moe-aux-loss-coeff
（与 cp 无关）
0.12
不乘
变成"对 CP 取平均"
aux 力度 = coeff / cp
（cp=2 时 0.02 实际只有 0.01）
两个可自证方向的事实（不看代数也能确认"×cp = 力度 2 倍"，方向没搞反）
：
0.18 原始（带 ×cp）step1 的
grad norm = 68.922
，改成不带 cp 后是
68.277
—— 力度更大 → 梯度范数更大；
带 ×cp 的那次 logged
load_balancing_loss
更低
（step11：2.4725 vs 2.9234）—— aux 推力更大才会把负载压得更均衡。
所以是不是"0.12 有问题"？分两种口径
：
按"aux loss 自己的定义"（全局量、
--moe-aux-loss-coeff
应等于实际权重）：
0.12 是缺陷
——它的 aux 力度被 CP 稀释了 1/cp，且同一个 coeff 在 cp=1 与 cp=2 下含义不同（用户换个 CP 配置就会静默变弱）。0.18 的写法则是一致的。
按"与 0.12.1 数值对齐"这个目标：0.18 的
×cp
是
行为变更
，删掉它（你现在的做法）就是回到 0.12 语义，这是对的。
注意：不带 cp 的 aux 力度 = 你设的 coeff ÷ cp，等于把
0.02
实际变成
0.01
。
另外要留个心眼：0.18 只在 aux 这一处加了 cp，
MTP loss 与
calculate_per_token_loss=True
分支都没有
，说明上游也未必把它当成系统性修正，更像局部补丁（详见 §3.6）。
一句话
：不是"0.12 算错了数"，而是
两版对"CP 下 aux loss 该用多大力度"的口径不同——0.18 用的是 coeff，0.12 用的是 coeff/cp
；你要复现 0.12.1，就得用 0.12 的口径。
3.1 aux loss 的值：两版一致，且是"全局定义 + 逐 rank 部分量"
两侧同一个公式（E=专家数，topk，coeff=
moe_aux_loss_coeff
）：
A_j = E·coeff·Σ_i (S_ij / T_global) · (F_i / (T_global·topk))
F_i
（每个专家的 token 数）=
tokens_per_expert
在
tp_cp 组 all_reduce（SUM）
得到 →
全局量
；
S_ij
= 本 rank 上所有 token 对专家 i 的概率和 →
局部量
；
分母
T_global
=
全局
token 数：
0.12：
num_tokens = probs.shape[0] * num_sub_sequence
（
probs
只有本 rank 的 n 行，故乘 cp）；
0.18：
total_num_tokens = local_num_tokens * reduce_group.size()
；
两者都等于
cp·n
。
因此
Σ_j A_j = 全局 aux
（0.18 的 docstring 专门写出了这个分解：
loss = Σ_j E·Σ_i f_i P_ij
）。
推论：
aux loss 的"值"是与 cp 无关的全局量
（同一 global batch、同一权重下，cp=1 与 cp=2 的 aux 值相同，只是被摊到多个 rank 上算）。
3.2 aux loss 的梯度如何进图
aux 不进入最终 loss 张量，而是挂在每层 router 的输出上（
MoEAuxLossAutoScaler.apply(activation, aux_loss)
），其"上游梯度"由 schedules
每步显式设置
S
，反向时返回
ones_like(aux_loss) * S
：
实际 aux 梯度(每 rank) = S · ∂A_j/∂θ
随后与主 loss 一起经过 A4 的
dp_cp 均值规约
（÷dp÷cp）。
3.3 代数推导：
S
必须含
×cp
以"每 DP 副本的目标 = mean_global_tokens(lm loss) + aux_global"，并取 DP 副本平均为约定：
期望的 aux 梯度贡献 =
(1/N_mb)·(1/dp)·Σ_j ∂A_j/∂θ
实现得到的 =
(1/(dp·cp))·S·Σ_j ∂A_j/∂θ
令二者相等 ⇒
S = cp / N_mb
（再乘 loss_scale）。
侧
S
规约后 aux 梯度
与全局定义的比值
有效权重
0.18
cp/N_mb
(1/(dp·N_mb))·Σ_j ∂A_j
1
= coeff（与 cp 无关）
0.12
1/N_mb
(1/(dp·cp·N_mb))·Σ_j ∂A_j
1/cp
= coeff/cp（被稀释）
即：
cp=2 时，0.12 语义把
--moe-aux-loss-coeff 0.02
实际变成 0.01。
这不是舍入问题，是 2 倍的语义差。
等价关系（可用于验收）
：
0.18语义(×cp) + coeff
≡
0.12语义(无cp) + coeff×cp
。在 cp=2、coeff=0.02 下，"删掉 cp 因子"等价于"把 coeff 减半"。

7. 结论 · 归责 · 建议
7.1 归责
根因一（aux 的 CP 缩放）属 Megatron（mcore）侧
：本配置生效的是
megatron/core/pipeline_parallel/schedules.py
；MindSpeed 自带同名副本只在特定 feature 下替换
forward_step
，且其写法与 0.12 一致（无 cp 因子），即 MindSpeed 侧并未认同该因子。
根因二（RoPE）属两侧"环境+实现栈"差异
（0.12 无 apex/TE → 被强制关闭融合）。
MindSpeed 需要适配吗？
若目标是"新版对齐旧版数值行为"，最合适的位置是
在 Megatron 侧提供可配开关
（改动小、可追溯）；若必须在 MindSpeed 落地，也应走 MindSpeed 的 patch 框架并写明原因与开关，而不是直接改 Megatron 的源文件。
7.2 对
cp_size_for_scaling
的处理建议
不要硬编码
cp_size_for_scaling = 1
。硬编码会让 0.18 在 CP 下的 aux 权重语义与上游不一致，且 cp=1↔cp=2 切换时有效权重静默变化，本次的"对齐经验"无法外推。
建议改为显式开关（如
--moe-aux-loss-cp-scaling
），
默认保持上游 0.18 语义
；需要复现 0.12.1 时切到 1，并在注释里写清：该值等价于"aux 有效权重 × cp"。
同步注意：本次未启用的 MTP loss 与
calculate_per_token_loss=True
分支在 0.18 里没有 cp 因子；若将来启用，需要把同一问题重新评估（否则会出现与 aux 不一致的权重口径）。
7.3 验收判据建议（替换"每步 <2%"）
step1~5
：loss 与 grad norm 逐位一致，或相对差 ≤1e-6（这是"实现保真度"的有效区间）；
验证集 loss
：落在"同配置多次运行"的散布内（当前观测散布：−0.60%~+2.4%）；
曲线趋势
：同区间 loss 的相关系数（如 Pearson）与最终收敛水平一致；
与
grad_norm_diff_analysis_report.md
的判据（val loss 相对差 ≤0.05%、前 10 步 loss ≤1e-3、前 5 步 grad norm ≤0.05%）保持一致口径，注意后者是 CP=1 配置下的结论，在 CP=2 下会放宽。
7.4 若还要继续收敛（性价比判断）
需要把表 B 的 B3/B4/B5 逐一对齐（即让两侧跑
同一份
TE/attention/分片实现），目标是让 step1 达到 bit 一致；只要还剩 1e-6 种子，某个 spike 步仍会分叉（本轮 exp2b 已证明）。
在当前基线与判据下不建议继续投入。

8.4 方法论要点（可复用到其它跨版本精度问题）
先建两张表
：会缩放 loss/梯度的归一化项（表 A）+ 前向算子实现路径（表 B），再找
唯一/少数不等价项
；成对出现的差异通常是自洽设计，孤立出现的差异最可疑。
先给可证伪预言再看数据
：本轮的 P1/P2（前向值逐位不变）与 Q1/Q3（前向值末位改变）能在不跑实验的情况下判出"梯度缩放问题"还是"前向实现问题"。
多步 loss 曲线不能用来判定实现保真度
：必须补一个"同版本 + 单变量舍入级扰动"的受控实验来定界噪声地板；否则会把 realization lottery 误判成 bug（反之亦然）。
一切结论都要标出"实现等价性"与"数值等价性"的层次
：语义不等价（本轮的 aux ×cp）必须改代码；算子栈不等价（TE vs mindspeed.te、attention、分片）只能换实现，且不可能归零。
