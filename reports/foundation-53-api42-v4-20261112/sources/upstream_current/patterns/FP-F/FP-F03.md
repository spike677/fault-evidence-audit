# FP-F03 文档/声明面与实现面不一致

- **适用**：仓 All ｜ 侧别 All ｜ 载体 文档与支持矩阵,IR与图配置 ｜ 触发 README|AddConfig|TensorType::(Real)?NumberType\(\) ｜ 默认启用 true
- **故障机理**：README/产品支持矩阵/确定性声明/参数约束等**声明面**与代码实际（`AddConfig` 注册面、kernel 行为面、公式与 dtype 定义）脱节，误导用户接入与测试判定：① 支持矩阵声明支持某产品而 def 仅注册单一 soc（或反向，开源仓无对应 kernel）；② 确定性描述与代码实际行为不符（声明支持开关实际不支持、声明非确定实际确定）；③ 文档整体复制自兄弟算子，公式/dtype/Op 名/链接全错；④ 脚本 help 文本声称的支持面与代码映射表矛盾；⑤ **Proto / IR 声明面与 OpDef / README 三方不一致**（v6.1 扩面）——Proto 端口的 dtype 集合用 `TensorType::NumberType()` / `RealNumberType()` 兜底，**宽于** OpDef 的 `DataType(dtypeList)` 与 README 支持表（#6892 SegmentSum 声明含 INT8 而实现只支持 7 种；#6790 BNLL；#6793/#6795/#6836 L2Loss/EluGrad/FusedBiasLeakyReluGrad 声明未实现的 DOUBLE），或**反向窄于**实现（#6791 DeformableOffsetsGrad Proto 拒绝已支持的 BF16 输出），或 Proto 注释里的公式/约束与同仓 infershape 不一致（#6870 AvgPool3D `ceil_mode` 公式重复使用 `in_width` 并遗漏 `pad_left`；#6314 文档把约束写成 `N1 > N2` 而实现只需 `N1 % N2 == 0`）；⑥ **可选/必选/属性归属标注与执行端不一致**（v6.13）——Proto 的 `OPTIONAL_INPUT` / `REQUIRED_ATTR` 与 README 参数表、ACLNN 文档、`CheckNotNull`/InferShape 实际要求三者不一致：把必填写成可选（调用方省略后必然失败）、把可选写成必填（合法缺省调用被拒）、把可选输入写成属性（构图侧直接找不到该字段）。**同一契约在 Proto / OpDef / README 三处各写一遍**是该型的结构性诱因。 **⑦ 数值上限「未披露」的口径争议（F03-7，v6.26）**——实现里有硬上限（`dim > 8` 报错、TensorList 长度 >256 拒绝、`headDim > 768` 拒绝、`padding > kernel/2` 拒绝），而文档的**维度列写 `-`、或全篇没有任何数值**。这是本型里**最容易争议、也最容易批量出单**的一类：它没有"文档说 A、实现做 B"的显式矛盾，只有"实现有边界、文档不提"的缺失，所以必须先按下表把"算什么、不算什么"钉死，否则同一份资料会被不同人判出相反结论。
- **触发条件**：兄弟算子复制创建、新平台（如 ascend950）接入后文档未同步、产品矩阵人工维护滞后于注册代码变更。
- **典型表现**：用户按 README 在声明支持的产品上调用报「未适配」；确定性开关不生效与文档矛盾；geir 示例 include/REG_OP 名指向兄弟算子编译失败；误判平台支持范围放弃或误用。
- **源码审查映射点**：README 产品支持表 × `*_def.cpp` 中 `AddConfig` 注册清单比对；确定性描述 × kernel `GetDeterministic()`/`SetAtomicAdd`/同步机制核查；文档公式 × kernel 注释/golden 实现一致性；文档 dtype 清单 × def/binary.json 注册 dtype 一致性；**注册面双形式（v6.27，实测成立）**：`def.cpp` 里注册产品有**两种写法**——字面 `this->AICore().AddConfig("ascend950", cfg)` 与 `opbase::ArchConfigHelper::AddConfigByArch(this->AICore(), Ops::Base::DAV_3510, cfg)`。**只按字面 `AddConfig\("` grep 会把后者判成「未注册」**。实测：`ops-nn` **上游 master** 有 **18 个文件**用 `AddConfigByArch`（含 `matmul/flat_quant/op_host/flat_quant_def.cpp`），而本地检出 `b27fda2` **一处都没有**——所以这条判据还要绑定 commit，否则同一个文件在两个版本上得出相反结论。扫描口径：`grep -rnE "AddConfig\(|AddConfigByArch\(" <op>/op_host/*def*.cpp`，并把 `DAV_3510` 之类的 arch 常量按 `opbase` 头文件的映射表翻译成 soc 名，**不要凭记忆对应**。**Proto 端口集合三方比对**（v6.1）：`op_graph/*_proto.h` 每个 `.INPUT/.OUTPUT` 的 `TensorType(...)` 集合 ↔ `op_host/*_def.cpp` 的 `DataType(dtypeList)` ↔ `README` 参数表 dtype 三处逐项对齐，出现 `TensorType::NumberType()` / `RealNumberType()` 兜底即高危（该集合宽于任何算子的实际支持面，等于用最宽集合兜底）。**可选/必选/归属三方比对**（v6.13）：`op_graph/*_proto.h` 的 `.OPTIONAL_INPUT`/`.INPUT`/`.REQUIRED_ATTR` ↔ README 参数表「必选/可选」列 ↔ `op_api/aclnn_*.cpp` 的 `CheckNotNull` 与 `*_infershape.cpp` 的实际读取方式；三者任一不一致即命中（典型：Proto 标 OPTIONAL 而 `CheckNotNull` 要求非空）。
- **数值披露三分法（F03-7 专用判据，v6.26）**：判「实现有上限、文档没写」之前，先按本表定位文档形态，再决定算不算缺口。**这张表是防口径分裂用的**——同一份资料被两个人判出相反结论，几乎都是因为跳过了"只靠错误码表算不算披露"这一步：

  | 文档形态 | 判定 | 理由 |
  |---|---|---|
  | 维度/参数列写明 `0-8` / `1-8` / `2-8` / 「不大于 8」/「任意维」 | **算披露** | 给了可判定的边界 |
  | 只在错误码表里写「维度范围超过 8」 | **也算披露** | 读者能从错误码项反推上限，不构成信息缺失 |
  | 维度列写 `-`，且全篇无任何数值 | **缺口** | 无法从资料反推边界 |
  | 实现是**降级不拒绝**（reshape 后继续算，如 `aclnnInplaceSelu` / `aclnnSelu`） | **不算缺口** | 没有硬上限，无边界可披露 |
  | **文档比实现严**（Svd 资料 2-8 维而 impl 允许 1 维；`ScaledMaskedSoftmax` 资料 4096 而 regbase 放宽到 8192） | **不算缺口**，属 F03 反向口径 | 实现比文档宽松，用户按文档用不会被拒 |

  三条使用纪律：① **同一族接口横向对齐**——若兄弟接口的资料已写同一上限（如 `aclnnMuls` 写「不大于8」而 `aclnnInplaceMul` 只写 `-`），这条对齐本身就是最强的缺口证据，优先找它；② **报错文案与上限自相矛盾**优先于"没写"（如 `NsaCompressAttention` 上限 768 而报错文案写 512）；③ **上限必须来自实现可指认的常量或分支**，写不出 `[文件]:[行号]` 的一律记「未核实」。
- **证据强度三级（F03-8，v6.27）**：判「文档与实现/声明不一致」时，**必须写清主张属于哪一级**。这不是分类洁癖，而是被一次实战打出来的——2026-11-06 一轮最初把 43 格判成 found，主张形如「`docs/aclnnXxx.md` 说产品 P 不支持，而同算子 `README.md` 说 √」，结果**这一层几乎全部不成立**：

  | 级 | 主张 | 强度 | 能否独立成立 |
  |---|---|---|---|
  | **L1** | 同 opdir 内**两份接口级资料**对同一产品结论相反，且共用同一份 `*_def.cpp` | **最强** | ✅ 可独立提，不依赖 README、不依赖实测 |
  | **L2** | 接口级资料 vs **OpDef 注册面**（`AddConfig` / `AddConfigByArch`），且同 opdir 其余接口都支持 | 中 | ⚠️ 可提，但维护方可答「注册 ≠ 发布宣称」 |
  | **L3** | 接口级资料 vs **README 产品表** | **弱** | ❌ **单独不提**，只能作辅助证据 |

  **为什么 L3 不成立（这是最贵的一课）**：`README.md` 的产品表是**算子级**（整个 Op），`docs/aclnnXxx.md` 的产品表是**接口级**。同一算子下 V1/V2/V4 支持 P 而 V3 不支持 P 是**合法设计**——此时 README 写 √ 完全正确，资料写「V3 不支持」也正确，**两边都没错**。实测例：`norm/layer_norm_v4/docs/aclnnFastLayerNorm.md` 对 Ascend 950PR&950DT 写「不支持」，而同目录 `aclnnLayerNorm&aclnnLayerNormWithImplMode.md` 写「支持」，两者共用同一份 `layer_norm_v4_def.cpp`（`AddConfig("ascend950", regbaseCfg)` 在 `:171`）——这是 **L1**（两份接口级资料相反），**不是**「README 与资料矛盾」。同一批 43 格里最终只有 4 组按 L1 成立，5 组判重复/兄弟，**5 组只剩 L3 → 不提**。

  **落地要求**：`signatures` 里把「资料产品表 vs README」这条**降级为辅助证据**；found 必须由 L1 或 L2 支撑；写 Bug 卡时在「证据」段首行标注 `[L1]` / `[L2]`；L3 证据只能写进「补充说明」，**不得作为 found 的唯一依据**。
- **检测签名**：README 支持表行与 `AddConfig\\(\"([a-z0-9_]+)\"` 的自动差集扫描；文档标题/Op 名与本目录名比对（复制残留检测：`README.md` 首行 Op 名 ≠ 目录名）。 **Proto dtype 兜底扫描**（v6.1）：`TensorType::(Real)?NumberType\(\)` 命中即候选（索引 `signatures` 已收录该指纹），再与同算子 OpDef 的 `DataType(dtypeList)` / README 参数表做差集；差集非空且无豁免理由 ⇒ 命中本型。 **数值上限缺口扫描（F03-7，v6.26）**：`grep` 实现侧上限常量与校验分支（`MAX_DIM|MAX_RANK|MAX_TENSOR_NUM|>\s*8\b|headDim\s*>` 等）取出 `[文件]:[行号]`，再在该接口的 `docs/aclnn*.md` 里检索同一常量/同一数字的**任何出现**（含错误码表）；两边都不出现且文档维度列为 `-` ⇒ 缺口候选。**必须同时跑同族对拍**：把同目录/同前缀兄弟接口的 md 一起扫，兄弟写了我没写即为高置信缺口。 **枚举清单 × 错误码谓词差集扫描（F03-7b，v6.37）**：对同一份 `docs/aclnn*.md` 的**参数说明节**抽「仅支持…取值 a、b、c」类枚举，对**错误码表节**抽同一属性的谓词（`不是…的整数倍` / `大于` / `小于` / `取值范围`），把枚举外的边界值（`0` / 负数 / 最大整除候选）代入谓词，能通过却不在枚举内 ⇒ 缺口候选，再到实现侧确认未拦截。
- **测试拦截建议**：将「README 支持表 vs def 注册」纳入 CI 静态门禁（与 FP-F01 的 binary.json 门禁同源）；算子复制创建类 PR 强制 diff 审查文档改名完整性（标题/公式/dtype/示例/链接五件套）；确定性声明变更须附 kernel 侧代码依据。 **Proto ↔ OpDef ↔ README 三方 dtype 一致性静态门禁**（v6.1）：凡 OpDef 显式列出 `DataType(dtypeList)` 的算子，校验 Proto 每个端口的 `TensorType` 集合与之**逐项一致**，并禁止 Proto 以 `NumberType()` / `RealNumberType()` 兜底（确需兜底须登记豁免理由）；同一门禁顺带覆盖 README 参数表 dtype 列。该族在 KaranocaVe 的 ops-nn 语料中**成批出现**（#6790~#6795 连发、#6836、#6892），完全可由脚本一次扫清，属「投入产出比最高」的一类。 **F03-7 的拦截方式（v6.26）**：把「文档上限 ↔ 实现常量」做成 CI 静态门禁——对每个接口抽实现侧上限常量（含 `MAX_*` 与字面量比较），断言该数字在 md 中出现过**至少一次**（表格或错误码表均可）；不出现则要求新增一行「参数上限」说明。**这条门禁的价值不在判缺陷，而在阻止新接口继续漏写**——2026-11-06 一轮的 21 条文档类 issue 里，**绝大多数是同一族批量漏写**（foreach 七连、Inplace 五连），一次门禁即可止住。

  **两条可复用的判定结论**：① 「成对接口一个写一个不写」是本型性价比最高的证据形态，无需论证上限合理性即可定缺口；② 同一族上限值**可能不同**（foreach 有 128 与 256 两种），不得按族内一例推广到全族。
  **v6.37 补（子型 ⑦ 变体：枚举取值清单与错误码表口径空白，`F03-7b`）**：F03-7 原判据只覆盖「数值上限没披露」，**漏了同族的另一半——取值集合的边界值落在两份资料的夹缝里**。ops-transformer #7234（open，documentation）实证：`aclnnNsaCompressWithCache` 的 `docs/aclnnNsaCompressWithCache.md` 参数说明写「仅支持 compressStride 取值 16、32、48、64」，错误码表 561002 子项只写「compress_block_size、compress_stride 不是 16 的整数倍」——`compressStride=0` **满足 `0 % 16 == 0`、不满足枚举清单**，两份资料谁都没管它；实测两段接口均返回 0（910B2，master 自编包），且 0 直接进入 `set_compressStride()`（`nsa_compress_with_cache_tiling_general.cpp:398`）与 `(value[i] - compressBlockSize) % compressStride`（`:243`）的除零表达式。**判据（与 F03-7 并列，优先级更高）**：① 从文档抽出属性的**枚举清单** `{v1,v2,...}`；② 抽错误码表里该属性的**谓词**（`% 16 == 0`、`> 0`、`<= 64` 等）；③ 取两集合的**差集**——枚举外却能通过谓词的取值（本例 `0`；同族还有负数、超上限但整除的值）即候选；④ 再去实现侧确认该差集**确实未被拦截**（本例 `:123-126` 只有 `%16` 与 `blockSize < stride` 两条），四步齐备才算缺口。**与 F03-7 的分界**：F03-7 是「实现有上限、文档一个数都不写」，本型是「文档写了两个数、但它们互不覆盖」，后者有**文档内部自相矛盾**的硬证据，不必论证实现合理性即可提，故强度高于 F03-7。**易漏点**：只扫「文档 vs 实现」会漏掉它——实现侧看起来「按错误码表写的就是对的」，矛盾藏在同一份文档的两节之间。
