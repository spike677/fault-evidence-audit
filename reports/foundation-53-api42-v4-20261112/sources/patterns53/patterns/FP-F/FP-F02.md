# FP-F02 维测与错误上报缺陷（含跨仓错误码不一致）

- **适用**：仓 All ｜ 侧别 Tiling,Kernel,Host ｜ 载体 Tiling源码,Kernel源码,Host源码 ｜ 触发 OP_LOGE|ACLNN_ERR ｜ 默认启用 true
- **故障机理**：算子/接口的**可观测性产物**缺失或错误，使缺陷无法定位甚至被误导：① 日志与维测信息不打印、打印时机错误（编译/执行结束才输出）、内容缺字段或拼写错误；② dump 类调试产物（`--dump_cce` 的 `kernel_meta`、tiling/日志开关）为空或路径错误；③ **错误码/报错信息不规范**（**v2.13 拆显为两个可独立判定的子面**）：**③-a 跨仓/跨接口不一致**——同一非法输入在不同仓/不同接口返回不同错误码；**③-b 错误码选择错误**——拦截**确实存在**但所选错误码与场景不匹配，典型为 `ACLNN_ERR_PARAM_INVALID`(161002) / `ACLNN_ERR_PARAM_NULLPTR`(161001) / `ACLNN_ERR_INNER_*` 三者混用（如 layout/dtype 不匹配误报为 PARAM_INVALID、空输入误报为 INVALID 而非 NULLPTR）；两子面之外另含缺少上下文（算子名/参数名/实际值）；④ 异常被静默吞掉（日志级别过低、错误分支直接 `return` 未上报）；⑤ **日志级别误用（反向问题）**——**设计内的正常降级/可预期分支被按 error 级别上报**，制造大量误报 error 日志与虚假监控告警，反而**掩盖真实故障**（与 ④ 方向相反：④ 是该报不报，⑤ 是不该报却报，二者共同后果都是真实故障被淹没）。根因多为模板/复制导致的维测宏漏插、错误分支未上报、**降级分支的日志级别未与「是否 fatal」对齐**、跨仓错误码约定未统一。
- **触发条件**：任一异常分支（参数非法、shape/dtype 不支持、内存不足、属性非法）；构建或运行期启用 dump/日志开关；**同源算子在两仓之间的同一非法输入对照**；错误信息巡检（人工阅读）；**规范化工具全量扫描**（如 `cann-log-evaluation` 类工具）；**可预期的降级路径被走通**（如查询类接口返回异常值，而设计上仅回退默认行为并继续执行）。
- **典型表现**：报错信息与真实根因不符 → 排查跑偏；同一输入在 ops-nn 与 ops-math 返回**不同错误码**（如 561002 vs 调用成功）；`--dump_cce` 产物目录为空导致无法复现定位；日志晚于失败点输出，无法定位到具体算子；维测信息缺字段（如 Shape 少一个 `]`）致下游解析失败；**正常降级场景刷出 error 级日志**，使日志中 error 密度失真、依赖 error 级别告警/监控的环境产生**虚假告警**，真实故障被淹没；**日志文案不符合规范且规模化存在**（单模块可达数百处，含拼写错误、语法错误、描述不完整），人工评审无法覆盖。
- **源码审查映射点**：每个错误分支是否上报且携带上下文（`OP_LOGE_FOR_INVALID_*` 系列 vs 裸 `OP_LOGE`）；错误码与错误类别是否匹配（`ACLNN_ERR_PARAM_INVALID`(161002) / `ACLNN_ERR_PARAM_NULLPTR`(161001) / `ACLNN_ERR_INNER_*` 不可混用）；`return ge::GRAPH_FAILED;` / `return ACLNN_ERR_*;` 之前是否已有日志；维测宏（`OP_LOGD`、`DUMP_*`、`--dump_cce`、tiling dump 开关）是否插入且级别正确；**同源算子在四仓的返回码是否一致**；是否存在「校验到了但静默返回 SUCCESS」；**每个 `OP_LOGE` 所在分支是否真的 fatal**（可预期降级应按 `OP_LOGW`/`OP_LOGI` 上报，否则制造误报）；**日志文案是否符合《CANN 日志规范》**（语法完整性、拼写正确、错误描述含上下文、含度量单位）；是否存在**含义相反的拼写**（如 `Excepted` 与 expected 反义）导致语义完全反转。
- **检测签名**：`OP_CHECK_[A-Z_]+` 覆盖率统计（错误分支数 vs 上报数）；`OP_LOGE(_FOR_[A-Z_]+)?\(`；`return\s+(ge::GRAPH_FAILED|ACLNN_ERR_[A-Z_]+)\s*;` 前一行是否有日志；`DUMP_(SCENES|TENSOR)|dump_cce|TILING_?DUMP`；`ACLNN_ERR_(PARAM|INNER)_[A-Z_]+` 与场景匹配性；**`OP_LOGE` 与 `return (false|SUCCESS|GRAPH_SUCCESS)` 同现于同一分支**（降级分支误用 error 级别的高危形态）；**`INT32_MAX|UINT32_MAX` 等异常返回值与 `OP_LOGE` 同现**（异常返回值常被当 fatal 误报）；日志文案规范扫描工具输出（`cann-log-evaluation` 类）。
- **测试拦截建议**：负向用例断言「返回码 + 错误信息关键字段」而不仅 `rc != 0`；对跨仓同源算子做**同一非法输入的返回码对照矩阵**（把不一致本身当缺陷提）；CI 增加「配置了 dump/日志开关但产物为空」的产物检查；错误码文档化并纳入审查（避免同因不同码）；错误信息做拼写/字段完整性巡检。**增补**：① 引入**日志规范自动化评测工具**（如 `cann-log-evaluation`）做**全量模块扫描并纳入 CI 门禁**，把「文案规范」从人工评审转为机器拦截（这是能把数百处问题一次暴露的唯一可行手段）；② 用例侧对**可预期降级路径**增加断言——断言「**该场景不应出现 error 级别日志**」，把误报本身当缺陷；③ 跑正常业务用例时**统计 error 日志条数基线**，异常增幅即告警（过滤误报噪音）。
- **实证案例**：ops-nn **#143** `HardSwish` 在 ops-nn 库 aclnn 调用报 **561002**，而在 ops-math 库 aclnn 调用**成功**（跨仓错误码/行为不一致，最易误导定位）；**#1151** 编译指定 `--dump_cce` 后 `kernel_meta` 文件夹为空；**#1103** kernel 编译日志只在实际编译结束后才打印（失败时看不到过程信息）；**#1004** DLQBMM 异常拦截维测信息 Shape 少一个 `]`；**#2224** GroupNormGrad 日志打印文本拼写错误；**#1283** tbmm warning 报错信息待修复。语料统计（2026-09-14，四仓缺陷类）：「维测/dump/日志缺失或错误」110 条 + 「报错信息/错误码不规范或不一致」90 条。**canndev 仓增补实证（2026-09-16）**：**#1660**（closed）gemm tiling 中 `GetCloseKShiftFlag()` 经 `context->GetDeterministicLevel()` 判断是否关闭 K-shift，当该接口返回异常值 `INT32_MAX` 时实现**打印 error 级别日志**（`OP_LOGE(nodeName, "GetDeterministicLevel() failed.")`）——而该场景表示「无法获取确定性级别」，函数**按设计回退 `false` 并继续执行，属可预期降级，不应按 error 上报**；issue 明列三条后果：① 日志被大量误报 error 干扰真实故障排查；② 依赖 error 级别告警/监控的环境产生**虚假告警**；③ 与函数实际行为（正常 `return false`，非 fatal）不一致（MatMul/BatchMatMul 等算子 tiling 路径，属**子型 ⑤ 日志级别误用**的教科书案例，同时是 **FP-A20** 的实证）；**#1837**（open）用 CANN 日志规范评测工具（`cann-log-evaluation`）对 `ops/built-in/aicpu` 运行时日志做**全量扫描**，发现 **721 处**不符合《CANN 日志规范》——语法错误 525、拼写错误 109、错误描述不完整 86、缺少度量单位 1；典型拼写 `succcess`/`ouput`/`memeset_s`/`shoule`/**`Excepted`（与 expected 含义相反）**/`dismatch`/`invlaid`/`argumengt`/`verfication`/`Poissonon`/`NonZeroe`/`Copyview`/`Ranperm`，语法问题如 `not support`→`is not supported`、`must greater than`→`must be greater than`、`need be same`——**单模块 721 处的规模化实证，且附带了可行的工具化拦截方案**。
- **测试集失败语料补充（v2.13，2026-09-19，具体 issue 编号待核）**：ErrMsg/错误码整改是**规模化**问题——QSFA/SFA/LI/QLI/FA 算子族在 layout 错误时拦截所用**错误码不对**（**子型 ③-b**）、FIA dtype 格式需统一大小写、MlaProlog shape 约束描述有误。结合已入库的 canndev **#1837**（单模块 721 处日志不规范）与 **#1660**（日志级别误用），本型的体量已超出「逐条人工评审」的可承受范围 ⇒ **子型 ③-b 必须做成静态检查项而非文档约定**。
- **子型 ③-b 的错误码选择矩阵（v2.13 新增，供源码审查直接对照）**：
| 实际异常类型 | 应报错误码 | 常见误用 |
|---|---|---|
| 指针为 `nullptr` | `ACLNN_ERR_PARAM_NULLPTR`(161001) | 误报 `PARAM_INVALID` |
| dtype / layout / format 不匹配 | `ACLNN_ERR_PARAM_INVALID`(161002) | 与 161001 互换 |
| shape / 属性取值非法（维数、维度值、属性长度） | `ACLNN_ERR_PARAM_INVALID`(161002) | 误报 `INNER_*`（把用户侧错误报成内部错误） |
| 平台 / SoC 不支持该能力 | `ACLNN_ERR_PARAM_INVALID`(161002) 或按支持面约定 | 误报 `INNER_*` |
| CANN 内部状态、资源异常（非用户输入所致） | `ACLNN_ERR_INNER_*` | 误报 `PARAM_INVALID`（把内部缺陷推给用户） |
