# FP-C04 aclnn 接口检视（fpc04-board-variant-perf-review）

对用户指定的 aclnn 接口做 FP-C04 专项性能源码检视：先定位算子实现，再按清单逐项核查，每个结论给出**文件 + 行号 + 推导链**证据，命中即出 Bug 卡，输出检视报告。**本模式特殊纪律：① 结果对、只是同芯片不同板型间有性能差异——静态检视只能产出「嫌疑点」，任何「劣化 N 倍」的量化结论必须以基线差分实测为准；② 卡片触发为「无代码触发特征」——不依赖签名命中，检视主线是「频率/带宽相关 tiling 假设点枚举」，签名扫描仅作辅助；③ 判据是「同 SOC、同版本、仅板型不同」，缺板型对比轴即不成立；④ 本模式暂无确认实证算子，不得虚构算子、文件或行号。**

## 0. 与相邻模式的边界

| 相邻模式 | 分工 |
|---|---|
| FP-C06（A5 性能劣于 A2） | **对比轴不同**：C06 是**跨 SOC 代际**（A5 vs A2/A3）；C04 是**同芯片不同板型**（A2 B2 vs A2 B3）。同一份「性能劣于」现象先确认轴——实证案例中 ops-transformer #3226 的跨 SOC 劣化属 FP-C06，**不属本条** |
| FP-C01（端到端耗时占比高） | 版本/分支轴归 C01 子型③（实证案例中 ops-nn #5038 的「tiling 分支劣化」属异机理，不归本条）；C04 判据须「同 SOC、同版本、仅板型不同」 |
| 评测环境/口径类（FP-F01 构建工程配置、FP-E02 判据标杆口径） | 实证案例中 cann-bench #63 的「评测平台别名错配」是**评测配置/口径缺陷**，不是算子 tiling 假设问题——命中别名/型号映射可疑即排除本条，转评测配置类 |
| FP-C05（确定性场景性能劣化） | 板型差异可能只在确定性开关开启时显现；记录开关状态，勿把「开关轴差异」误记为「板型轴差异」 |
| FP-B02 / FP-A17（代际/型号分支遗漏的功能面与精度面） | 同一处板型/型号分支写错：功能面归 B02、精度面归 A17；C04 只管**性能面**（结果仍正确） |

**症状反查定位**：同 SOC、同版本、同 shape、仅**板型（B2/B3 等）**不同出现性能差异 → C04；跨 SOC 代际（A5 vs A2）→ C06；同板型跨版本 → C01 子型③；差异只出现在某一评测平台上且伴随型号别名/映射可疑 → 评测配置/口径类（F01/E02），先排除再归本条。

## 1. FP-C04 模式卡摘要（检视依据，源自本库 `patterns/FP-C/FP-C04.md`，v3.1）

- **编号 / 名称**：FP-C04 A2 B2 机器性能劣于 A2 B3 ｜ **类别**：性能 ｜ **风险**：低（S2×O1=2）｜ **状态**：活跃
- **适用声明头**（照抄卡片）：仓 All ｜ 侧别 Tiling ｜ 载体 Tiling源码 ｜ 触发 无代码触发特征 ｜ 默认启用 true
- **skill 核查面**：侧别 Tiling——skill 落地为 op_host 的 tiling 源码（分核 / tile 大小 / 流水与并行度推导）与 `config/<soc>/` 的分核配置；延伸至 tiling 读取平台信息的入口（板型/频率/带宽参数获取点）。**因触发为「无代码触发特征」，检视以「假设点枚举」为主线，不做签名依赖**
- **故障机理**：**频率/带宽相关 tiling 假设不适用于部分板型**——tiling 在推导分核数、tile 大小、流水深度、带宽 bound / 算力 bound 判定阈值时使用了**隐含单一板型的频率/带宽假设**（如按某一板型的频率或带宽推算最优分核），跨板型部署时假设失效，致性能劣化（结果仍正确）。
- **触发条件**：跨板型部署（B2/B3）；同芯片、同版本、同 shape 下仅板型不同。
- **典型表现**：**同芯片不同板型性能差异**；精度全对、功能全对、无报错，仅耗时变长；单看某一板型绝对值可能仍「合格」，只有多板型对比才暴露。
- **源码审查映射点**：频率/带宽相关 tiling 假设。
- **检测签名**（本模式触发为「无代码触发特征」，下列仅为**辅助定位提示**，不构成触发条件）：tiling 源码中的频率 / 带宽 / 核数相关常量与魔数（`2048` / `4096` 类阈值、频率倍率、带宽系数）；tiling 内对平台信息的读取点（`GetSocVersion` / 平台信息结构体）；`config/<soc>/` 下是否仅有单板型配置。
- **审查关键词**（命中只表示值得人工审）：频率 / 带宽 / `bandwidth` / `freq` / `coreNum` / `blockDim` / `usedCoreNum` 相关常量；tiling 中**不随板型变化的**推导常量；bound 判定阈值（带宽 bound vs 算力 bound 的分界魔数）。
- **测试拦截建议**：多板型性能基线对比（同 SOC、同版本、同 shape，仅板型不同）；把板型作为评测维度固定记录。
- **实证案例**：**待补充**（2026-09-16 gitcode CANN 组织 12 仓约 1.4 万条 issue 全量关键词检索，命中均为**异机理**条目：跨 SOC 劣化（ops-transformer #3226，属 FP-C06）、tiling 分支劣化（ops-nn #5038，属 FP-C01 类版本/分支轴）、评测平台别名错配（cann-bench #63，属评测配置类）——**无「同芯片 B2/B3 板型性能差异」的确认对应实证**）。故本 skill 不提供示例算子，第 9 节改为「板型/频率-带宽 tiling 假设速览」。
- **关联**：FP-C06（跨 SOC 代际，对比轴不同）、FP-C01（版本/分支轴）、评测环境/口径类（F01/E02）。

## 2. 检视输入与算子定位

**输入**：aclnn 接口名（必填）；可选 ref（默认 master）、指定仓（默认自动定位）；**必填可比性要素**：SOC 型号 + 对比的两个板型（如 A2 B2 vs A2 B3）+ shape + 版本（缺任一要素则结论降级为嫌疑点）；可选现象描述（多板型耗时对比数据）。

**接口名 → 算子目录换算**：去 `aclnn` 前缀 + 驼峰转下划线小写：
`aclnnSwiGlu → swi_glu`、`aclnnIndexAdd → index_add`、`aclnnAdaptiveMaxPool3d → adaptive_max_pool3d`。

**仓定位顺序**（GitCode `cann` 组织，逐仓用目录列表确认）：`ops-nn`（norm/loss/activation/matmul 类）→ `ops-math`（math/conversion 类）→ `ops-cv`（image/vision 类）→ `ops-transformer`（attention/moe 类）。**类目名不总与直觉一致**，以目录列表为准。FP-C04 高发面：分核 / tile 大小推导中带频率、带宽、核数假设的 tiling；`config/<soc>/` 下只有单一板型配置的算子；bound 判定（带宽 bound / 算力 bound）阈值硬编码的 tiling。

**算子目录结构约定**（通用形态，以目录列表为准）：

```text
{类别}/{op_name}/
├── op_host/
│   ├── *_tiling*.cpp      # 分核/tile/流水/bound 判定——频率与带宽假设的主检视面
│   ├── *_infershape.cpp
│   └── config/<soc>/      # *_binary.json——是否按板型分化配置
├── op_kernel/             # 受 tiling 假设影响的 kernel 模板
├── op_api/（或 op_host/op_api/）
├── op_graph/  tests/  docs/  examples/
└── CMakeLists.txt
```

**aclnn 出口位置提示**：多数算子的 aclnn 出口在 `op_host/op_api/` 或顶层 `op_api/`（`aclnn_*.cpp`），以目录列表与 `docs/aclnn*.md` 确认。

| 单文件内容 | `GET https://api.gitcode.com/api/v5/repos/cann/{repo}/raw/{path}?ref={ref}` |

**已实测不可用（截至 2026-09 实测）**：`https://gitcode.com/{repo}/raw/{sha}/{path}`、`https://raw.gitcode.com/...` → 403 或拦截页；端点策略如有变化可复测。**若本地已有算子仓克隆，优先直接读本地文件，行号证据以本地 HEAD 为准并记录 commit**（tiling 常量在 commit 间漂移较大）。**本模式特有取数限制：性能结论需基线差分实测**——静态检视产出「频率/带宽假设点」的嫌疑清单与对比方案，任何「B2 慢于 B3 N 倍 / 慢 X%」的量化结论必须由「同 SOC、同版本、同 shape、仅板型不同」的多板型基线差分给出，不可用代码审查替代实测。**板型频率/带宽规格与实测数据须来自公开资料或用户提供，不得凭推测填写。**

## 4. 板型 tiling 假设检视清单（每点：查什么 → 何处 → 命中判据）

对算子的 op_host tiling（含 config）全部相关文件逐点核查，**每点先查命中面、再做反证排除**，防护面（已按板型分化的推导、已读取平台信息）也要记录。

### ① 频率/带宽假设点枚举
- 查什么：tiling 中所有**与频率、带宽、核数相关的常量与推导**——核数 / `blockDim` / `usedCoreNum` 的取值是否来自固定常量而非平台信息；tile 大小 / 流水深度是否按单一板型的频率或带宽推算；是否存在「假设某频率倍率 / 某带宽系数」的隐式常量。
- 何处：op_host `*_tiling*.cpp` 的分核与 tile 推导段、常量定义段。
- 命中判据：能列出「假设点 → 假设值 → 是否随板型变化」清单，且存在**不随板型变化**的假设值 ⇒ 命中（给出假设点行号；本模式无实证样板可对照，判据为静态推导）。

### ② bound 判定阈值与板型适配
- 查什么：tiling 中的**带宽 bound / 算力 bound 判定阈值**（分界魔数）是否隐含单一板型的带宽/算力比；跨板型时该阈值是否仍成立。
- 何处：tiling 中的 bound 判定分支与阈值常量。
- 命中判据：可指认「阈值由单一板型带宽/算力比推出」且无板型适配 ⇒ 命中。

### ③ 平台信息读取与板型分流
- 查什么：tiling 是否读取板型 / 平台信息（`GetSocVersion` / 平台信息结构体 / 频率与带宽查询接口）并按板型分流；是否存在「读了 SOC 但未区分板型」的缺口（同 SOC 不同板型走同一分支）。
- 何处：tiling 的平台信息获取点与后续分支。
- 命中判据：存在板型可分化的假设点但代码未分流 ⇒ 命中；已分流则记录为防护面证据。

### ④ config 分核配置的板型覆盖度
- 查什么：`config/<soc>/` 下是否只有单一板型配置、或板型维度未体现在配置项中；分核配置是否需按板型分别维护而实际缺失。
- 何处：`config/<soc>/*_binary.json` 目录结构与配置项。
- 命中判据：配置仅覆盖单一板型而算子需跨板型部署 ⇒ 记录为嫌疑点（配置面）。

### ⑤ 反证排除（防误报）
- 查什么：假设点是否**已被平台信息动态修正**（读取频率/带宽后按实际值推导）；假设是否在两种板型上取值一致（此时板型差异不成立）；现象是否实际由**评测平台别名/型号映射错配**造成（实证案例中 cann-bench #63 的异机理条目）。
- 何处：假设点附近的动态修正代码、评测配置与型号映射。
- 命中判据：假设已被动态修正 / 两板型取值一致 / 存在别名错配证据 ⇒ 反证排除（写明理由）。

### ⑥ 测试拦截面（多板型基线）
- 查什么：tests / 评测脚本是否把**板型作为评测维度**固定记录；是否具备多板型性能基线对比。
- 何处：tests、examples、评测配置。
- 命中判据：无板型维度可静态确认 ⇒ 记录为拦截缺口。

## 5. 检视流程

1. **定界**：换算 op 目录、确认所在仓与 ref/HEAD；**确认对比轴为「同 SOC、仅板型不同」**（若为跨 SOC 则转 FP-C06，若为跨版本则转 FP-C01）；核对可比性要素（SOC、两板型、shape、版本）是否齐备。
2. **枚举**：目录列表列出 op_host（tiling + infershape + config）全部相关文件，产出文件清单。
3. **触发词扫描（辅助）**：本模式触发为「无代码触发特征」，签名扫描仅为辅助——按 `bandwidth|freq|coreNum|blockDim|usedCoreNum`、tiling 阈值魔数（`2048|4096` 类）定位候选假设点；**主线是第 4 节 ① 的假设点全量枚举，签名零命中时清单仍须逐项核查完毕**。
4. **假设表构建**：以第 4 节 ① 建立「假设点 → 假设值 → 是否随板型变化 → 是否动态修正」对表——后续所有清单点都在此表上比对。
5. **清单逐项核查**：每点记录命中面与防护面证据（文件:行号）。
6. **反证排除**：假设已被平台信息动态修正、两板型取值一致、存在评测别名错配 → 明确写出反证理由。
7. **判定**：按第 7 节标准给出 命中 / 观察项 / 反证排除。
8. **GitCode 查重**（仅命中项）：issues API 按接口名 + `板型|B2|B3|频率|带宽|性能` 检索，逐条比对是否同机理；无同机理才立卡。
9. **业务可达性核查**（仅命中项）：判 B 等级、定业务影响类型、给处置建议；默认保守（无法证明不可达即记 B3），降档须附证据；B 不改 S×O 档位。
10. **出报告**：按第 8 节模板落盘；静态推演结论一律标注「需基线差分实测确认」，并附多板型对比方案。

## 6. 风险定级（S×O）与业务影响评估（B 轴）

- **S**：S2（性能不达标 / 交付受限——跨板型部署时性能劣化）；S1（轻度资源浪费）。性能类缺陷不涉 S3/S4（结果仍正确）。
- **O**：O3 = ≥2 条独立实证；O2 = 1 条独立实证；O1 = 仅静态扫描命中或团队笔记（实证 = 确认对应的 issue / PR，或经跨仓、跨分支核验确认的缺陷记录，同权计入）。静态推演命中且无实证默认 **O1**；升档须在报告中给出实证依据。
- **风险 = S×O**：≥6 高；3/4 中；1/2 低。FP-C04 基准：模式卡整体 **S2×O1=2（低）**；纯静态命中同样 **S2×O1=2（低，暂定，量化劣化待基线差分实测后复评）**。

### B 轴：业务影响评估（与 S×O 正交；报告层新增，不改卡片定级）

S×O 回答"多严重、多常见"，**不回答"真实业务能不能碰到"**。B 轴补这一问，只决定**修复优先级建议**，**不参与 S/O 取值、不改 S×O 档位与卡片元数据**。

**业务可达性（B）**——触发条件在真实负载中的可达程度：

| 等级 | 判据 | 证据要求 |
|---|---|---|
| B3 现实可达 | 主流框架/公开模型默认路径即可命中（如 PTA/torch_npu、vLLM、MindIE 常规调用） | 调用方或公开负载来源 |
| B2 条件可达 | 需特定 attr/dtype/shape 组合，业务中存在但非默认 | 该组合的业务来源 |
| B1 边界/不可达 | 需极端、超规格或非法参数（超出接口合理上限的 shape、退化/非法输入） | "为何不可达"的说明 |

- **默认保守**：无法证明不可达 → 记 **B3**；降为 B1/B2 必须附证据，**不得仅凭"业务应该不会这么用"**。
- 超规格参数是否算 B1 取决于**接口契约**：契约允许但业务不用 → B1；契约不允许（本应报错）→ 属校验缺失（FP-B04/B05 类），另行归属。

**业务影响类型**（命中后对用户可见结果的后果，用业务语言表述）：静默精度损失（模型效果下降 / loss 不收敛 / 偶发 NaN）｜ 任务失败中断（报错 / 崩溃 / 挂死）｜ 性能退化 ｜ 仅可观测性（日志 / 错误码 / 文档，不影响结果）。

**处置建议**（由两轴推导的报告结论，非新档位）：

| S×O \ B | B3 现实可达 | B2 条件可达 | B1 边界/不可达 |
|---|---|---|---|
| 高（≥6） | 尽快修 | 尽快修 | 排期修 |
| 中（3/4） | 尽快修 | 排期修 | 记录（业务难以触达） |
| 低（1/2） | 排期修 | 记录 | 记录 |

## 7. 判定标准与反误报原则

- **性能类特殊纪律（务必贯彻）**：静态检视只能立「嫌疑点 / 优化项」——「频率/带宽假设未随板型分化」可静态证；但任何「劣化 N 倍 / 慢 X%」的量化结论**必须以基线差分实测为准**（同 SOC、同版本、同 shape、仅板型不同），不可用代码审查替代性能基线看护。
- **无代码触发特征 ⇒ 不依赖签名**：本模式不以触发词命中作为成立前提；签名扫描零命中时，第 4 节假设点清单仍须逐项核查完毕。
- **三种判定**：
  - **命中**（可静态证假设失效）：可指认「tiling 使用不随板型变化的频率/带宽/核数假设，且该假设未被平台信息动态修正」→ 立 Bug 卡；
  - **观察项**：假设点存在但板型差异需实测（无实测数据即只能为观察项）→ 记录并附多板型基线方案，按 S2×O1 暂定；
  - **反证排除**：假设已动态修正、两板型取值一致、或差异实为评测别名错配 → 明确写出反证理由与防护面证据。
- **对比轴必须先确认**：跨 SOC 代际 → C06；跨版本 → C01；仅评测平台差异 → 评测配置/口径类（F01/E02）。轴错则整份结论作废。
- **本模式暂无确认实证**：报告中不得引用虚构算子、文件或行号，也不得把异机理条目（#3226 / #5038 / cann-bench #63）当作本模式实证；引用它们时必须显式标注「异机理参照」。
- **不臆造行号**：每条证据必须是实际读到的 文件:行号；引用异机理参照条目时给出 issue 编号与其归属模式。

### 判定纪律补充（v3.6）：非对称增减、证据等级与误判记录

**增减不对称**：允许追加候选（有据即可，错了可由用户排除）；**撤销或否决候选必须附 `[文件]:[行号] [代码行]` 负向证据**。无证据的「看起来没问题」一律记为「未核查」，不得计入反证排除，也不得据此下调等级——否决造成的漏报用户不可见、不可恢复。

- **证据等级**（Bug 卡必填）：`静态可证` = 推导链完整且触发输入可静态构造；`需实测确认` = 依赖运行时输入规模、设备行为或环境差异。标 `需实测确认` 的条目**不得以「命中」名义出卡**，按观察项记录并附实测用例。
- **Agent 误判记录**（Bug 卡必填）：本次被推翻的假设、推翻它的证据（`[文件]:[行号] [代码行]` 或实测输出）、判定标准是否随之修订；无推翻写「无」。
- **误判回流**：同类误判在 3 次检视中重复出现，登记至 `cases/misjudgments.jsonl`（字段见 `cases/README.md`），并在本模式判定标准中新增对应防线；守门 C19d 校验台账字段合法。

## 9. 板型/频率-带宽 tiling 假设速览（本模式暂无确认实证算子）

- **假设点速览**（引导，不预设结论，仍须逐点核查；行号以本地 HEAD 为准）：
  - 定位面：op_host 的 `*_tiling*.cpp`——分核数 / `blockDim` / `usedCoreNum` 推导段、tile 大小与流水深度推导段、bound 判定阈值段、平台信息获取点。
  - 假设点 ①：核数与分核推导是否来自**固定常量**而非平台信息（跨板型时核数/频率比可能变化）。
  - 假设点 ②：tile 大小 / 流水深度是否按**单一板型的频率或带宽**推算，且未随板型修正。
  - 假设点 ③：带宽 bound / 算力 bound 的**判定阈值魔数**是否隐含单一板型的带宽/算力比。
  - 假设点 ④：`config/<soc>/` 下是否只有**单一板型配置**、板型维度未体现。

## 10. 能力边界与自检（v3.8）

### 能力边界

- **静态可证**：清单里能在源码内给出「`文件:行号` + 推导链」的部分，按第 7 节判据出卡。
- **需实测确认**：依赖运行时输入规模、设备行为或环境差异的结论，只能记观察项并附实测用例（证据等级见第 7 节）。

- **找不到 ≠ 没有**：按清单未命中只说明「本轮未发现」，不得表述为「该算子无此缺陷」；抽样核查须在报告写明抽样口径。
