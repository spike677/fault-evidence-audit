# FP-B02 aclnn 接口检视（fpb02-corenum-review）

对用户指定的 aclnn 接口（如 aclnnRmsNorm）做 FP-B02 专项源码检视：先定位算子实现，再按清单逐项核查，每个结论给出**文件 + 行号 + 推导链**证据，命中即出 Bug 卡，输出检视报告。**本模式特殊纪律：① 判定面是「跨型号一致性」——单型号能跑不是安全证据，必须逐 SOC 型号（310P 系列 / 910B / 950 / regbase / kirin 等）核对核数与切分假设；② 核数相关缺陷分两种方向——「核数假设写死致某型号报错/踩内存」（正向缺失）与「型号分支未随支持面收敛而残留」（#2122 反向残留），两者都立卡；③ 多核调度模式（`SetScheduleMode`）与核数强相关，`SyncAll` 误用等跨核同步写法要并入核数面核查；④ 静态检视只能立「核数假设未参数化 / 型号分支缺失」，某型号是否真报错须实机验证，不可直接断言。**

## 0. 与相邻模式的边界

| 相邻模式 | 分工 |
|---|---|
| FP-A07（tiling 分支边界，精度/功能面） | **同源相邻**：A07 是 tiling 分支边界/阈值算错，本条是**核数档位**未适配——同一段 tiling 的两类缺陷，报告可双向关联；核数算错致分核不整除的边界问题归本条 |
| FP-A17（同因在精度侧的呈现） | **同因不同面**：型号/核数适配缺失在精度侧表现为结果偏差（如某型号踩内存致数值错）→ 后果面归 A17，成因面（核数假设/型号分支）归本条 |
| FP-C04（性能面） | 核数用不满 / blockDim 设小致性能不达标归 C04；**核数假设错误致报错或踩内存**归本条 |
| FP-B09（动态 shape 标签未参与校验） | 同属「编译期前置适配考虑不全」：本条是**核数档位**未适配，B09 是**维数未知**未适配——排查时先确认是型号/核数差异还是动态标签 |
| FP-B01（过拦） | 若某型号被 checker 以「不支持该 SOC」直接拒掉，属型号支持面声明问题：白名单过严归 B01，tiling 核数假设写死归本条 |

**症状反查定位**：同一算子在某型号正常、另一型号（尤其 310P1 与 310P3 之间）报错 → 首查核数/`blockDim` 计算与型号分支；310P 上整网执行报错、单算子 UT 通过 → 型号分支遗漏；310P 上踩内存 / 精度异常 → 核数假设致越界写（同步看 A17）；编译期「找不到类 / 算子缺失」→ 型号支持面与编包配置；tiling 中出现**已停止支持的型号分支**（如 310P 残留）→ 反向问题（分支未清理）；`SyncAll` / 多核调度模式相关报错 → 调度模式与核数不匹配。

## 1. FP-B02 模式卡摘要（检视依据，源自本库 `patterns/FP-B/FP-B02.md`，v3.1）

- **编号 / 名称**：FP-B02 tiling 未适配多种芯片核数 ｜ **类别**：功能/兼容 ｜ **风险**：高（S2×O3=6）｜ **状态**：活跃
- **适用声明头**（照抄卡片）：仓 All ｜ 侧别 Tiling ｜ 载体 Tiling源码 ｜ 触发 GetCoreNum|GetBlockNum|coreNum ｜ 默认启用 true
- **skill 核查面**：与卡片载体一致——主检视面为 op_host 的 tiling（`*_tiling*.cpp` / `*_tiling.h` 与 `arch*/` 子目录）中核数/AIC/AIV 取值、`SetBlockDim`、SOC 型号分支、多核调度模式；延伸至 `config/<soc>/*_binary.json`（各型号支持面与模板声明）与 `*_def.cpp`（型号约束）；kernel 侧仅在跨核同步写法（`SyncAll` 等）与核数强相关时纳入
- **故障机理**：核数 / AIC / AIV 计算**硬编码**或 SOC 型号分支**遗漏**，按单核数假设切分任务——某型号核数与该假设不符时，分核不整除、`blockDim` 越界或任务切分错误，表现为报错或踩内存。
- **触发条件**：跨芯片型号部署（如 310P3 8 核正常、310P1 10 核报错）；同一算子族在不同 SOC 核数档位不同；新增 SOC 型号未补分支；已停支持型号的分支未清理。
- **典型表现**：部分芯片可执行、部分报错；某型号整网执行报错而单算子 UT 通过；某型号踩内存 / 精度异常；编译期找不到类或算子缺失；型号分支残留导致行为不一致。
- **源码审查映射点**：核数/AIC/AIV 计算硬编码、SOC 型号分支遗漏、核数假设未参数化。
- **检测签名**：`GetCoreNum|GetCoreNumAiv|GetCoreNumAic|GetBlockNum|coreNum|blockDim|SetBlockDim`（核数取值与使用点）；SOC 型号枚举比较（`SocVersion::ASCEND310P|ASCEND910B|IsRegbaseSocVersion`）与型号分支清单；`SetScheduleMode|SyncAll`（调度模式与跨核同步，与核数强相关）；`config/<soc>/` 目录与 tiling 内型号分支集合做**差集**（声明支持的型号 ∉ 分支处理集合，或反之残留）。
- **测试拦截建议**：**全型号芯片 CI 矩阵执行（禁止单型号抽检代替）**；同一算子在每个声明支持的 SOC 上跑通功能用例；310P 系列内 P1/P3 分别建例；新增型号合入时补齐矩阵。
- **实证案例**：ops-nn **#3047** RmsNorm 在 **310P1** 上整网执行报错（9.1.0 B030，模型推理必现）；**#253** ge_glu_v2 在 **310P3+arm** 编译/运行不通；**#406** avgPool3d 在 310P 上误用 `SyncAll`，需改 `SetScheduleMode(batchmode)`（多核调度模式与核数强相关）；**#700** DynamicQuant 在 310P 上踩内存；ops-math **#1565** 310P 上自定义 aicpu 的 `add_aicpu` 算子以 aclnn 方式调用报错；ops-transformer **#1627 / #1815** 310P 侧算子缺失与编包找不到类；ops-transformer **#2122** tiling 代码中**残留已不支持的芯片型号 310P 分支**（反向问题：型号分支未随支持面收敛而清理）。**共性特征：310P 系列（P1/P3 核数与形态差异）是核数/型号适配遗漏的高发区。**
- **关联**：FP-A07、FP-A17（A17 是同因在精度侧的呈现）、FP-C04。

## 2. 检视输入与算子定位

**输入**：aclnn 接口名（必填，如 `aclnnRmsNorm`）；可选 ref（默认 master）、指定仓（默认自动定位）；可选型号信息（报错型号，如 310P1 / 310P3 / 910B / 950——决定优先核对哪条型号分支）；可选现象描述（报错原文 / 踩内存 / 编译失败——用于症状反查）。

**接口名 → 算子目录换算**：去 `aclnn` 前缀 + 驼峰转下划线小写：
`aclnnRmsNorm → rms_norm`、`aclnnGeGluV2 → ge_glu_v2`、`aclnnAvgPool3d → avg_pool3d`。**目录名以目录列表为准**。

**仓定位顺序**（GitCode `cann` 组织，逐仓用目录列表确认）：`ops-nn`（norm/loss/activation/pool 类）→ `ops-math`（math/conversion 类）→ `ops-cv`（image/vision 类）→ `ops-transformer`（attention/moe 类）。**类目名不总与直觉一致**，以目录列表为准。FP-B02 高发面：带 SOC 型号分支的 tiling（`curSocVersion` 比较、`IsRegbaseSocVersion` 分流）、多平台各写一套的 tiling（arch22 / arch35）、核数与 `blockDim` 计算点、含跨核同步的 kernel、有 310P 历史分支的存量算子。

**算子目录结构约定**（已验证示例 `cann/ops-nn` → `norm/rms_norm/`）：

```text
{类别}/{op_name}/
├── op_host/                  # *_tiling.cpp / *_tiling.h / *_tiling_arch35.cpp——核数与型号分支主检视面
│   └── config/<soc>/         # *_binary.json（各 SOC 支持面与模板声明：型号支持面的权威来源）
├── op_api/（或 op_host/op_api/）  # aclnn_*.cpp（入口：型号相关拒绝点）
├── op_kernel/                # kernel（含 arch35 / regbase / 多模板变体）——跨核同步与核数强相关时纳入
├── op_graph/ framework/      # proto / onnx 插件 / fusion pass（视算子而定）
├── docs/ examples/ tests/ CMakeLists.txt
```

## 4. 核数与型号适配检视清单（每点：查什么 → 何处 → 命中判据）

对算子的 op_host tiling / config / op_api / kernel 逐点核查，**每点先查命中面、再做反证排除**，已有的型号分支与核数取值逻辑也要记录（防护面证据）。

### ① 核数 / AIC / AIV 取值是否参数化
- 查什么：核数来源——是运行时取自平台（`GetCoreNumAiv` / `GetCoreNumAic` / `GetBlockNum` / `totalCoreNum`），还是**硬编码常量**；核数参与切分（`CeilDiv` / `blockFactor`）时是否随型号变化；是否存在「按单核数假设」写死的任务切分。
- 何处：op_host tiling 的核数取值与 `SetBlockDim`、切分计算；compileInfo 的 `totalCoreNum` 赋值点。
- 命中判据：存在核数硬编码常量，或核数取值路径在某型号分支下被绕过（用固定值替代平台值）且该值与该型号实际核数不符 ⇒ 命中（给出「核数取值处 → 使用处」链）。

### ② SOC 型号分支完整性与支持面对齐
- 查什么：tiling 内的型号分支集合（`curSocVersion == ASCEND310P` / `ASCEND910B` / `IsRegbaseSocVersion` 等）是否覆盖 `config/<soc>/` 与 `*_def.cpp` 声明的**全部支持型号**——漏分支的型号会落到默认（多为单核假设）路径。
- 何处：tiling 的型号分叉点、`config/<soc>/` 目录集合、`*_def.cpp` 型号约束。
- 命中判据：`声明支持型号集合 ∖ 型号分支处理集合 ≠ ∅`（差集非空，且差集型号会走默认路径）⇒ 命中（实证样板 #3047 RmsNorm 310P1、#1627/#1815 310P 侧算子缺失）。

### ③ 型号分支残留（反向）
- 查什么：是否残留**已停止支持**的型号分支（如 310P）——分支未随支持面收敛而清理，导致行为与支持面不一致（#2122）。
- 何处：tiling 的型号比较分支、config 中已删除但代码仍引用的 SOC 分支。
- 命中判据：存在型号分支其 SOC 已不在声明支持面内且仍参与执行路径 ⇒ 命中（反向残留）。

### ④ 多核调度模式与跨核同步（核数强相关）
- 查什么：多核调度模式设置（`SetScheduleMode`）与核数是否匹配；`SyncAll` 类跨核同步写法是否适用于该型号/调度模式（实证 #406 avgPool3d 在 310P 误用 `SyncAll`，应改 `SetScheduleMode(batchmode)`）；核数变化时同步语义是否仍成立。
- 何处：op_host tiling 的调度模式设置、op_kernel 的跨核同步点。
- 命中判据：存在「调度模式与核数不匹配」或「同步写法在该型号不适用」的静态路径 ⇒ 命中（后果需实机验证）。

### ⑤ 分核不整除 / blockDim 边界
- 查什么：核数变化后分核是否整除（`numRow % useCoreNum`、`latsBlockFactor` 尾核计算）；`blockDim` 是否可能超过该型号实际核数；尾核处理是否随核数变化而正确。
- 何处：tiling 的分核与尾块计算、`SetBlockDim` 调用点。
- 命中判据：给出「某型号核数 → 分核不整除 / blockDim 越界」的静态反例推导 ⇒ 命中（或立观察项，视能否静态确证）。

### ⑥ 编译/编包与算子缺失面
- 查什么：该型号下算子是否参与编包（CMake 型号过滤、`config/<soc>/` 是否存在）；是否存在「编包找不到类」（#1627/#1815）——属型号支持面与构建配置不一致。
- 何处：`CMakeLists.txt`、`config/<soc>/`、算子注册文件。
- 命中判据：声明支持但该型号 config/注册缺失 ⇒ 命中（构建面）；否则记观察项。

## 5. 检视流程

1. **定界**：换算 op 目录、确认所在仓与 ref；按用户型号信息锁定优先核对分支；列出 `config/<soc>/` 作为声明支持型号集合。
2. **枚举**：目录列表列出 op_host tiling（含 `arch*/` 子目录）/ config / op_api / op_kernel / CMake 全部相关文件，产出文件清单。
3. **触发词扫描**：按 `GetCoreNum|GetBlockNum|coreNum|blockDim|SetBlockDim`、SOC 型号枚举比较、`SetScheduleMode|SyncAll` 定位风险面（本地仓用 grep；API 模式逐文件拉取后检查）。
4. **清单逐项核查**：按第 4 节 ①~⑥ 逐点记录命中面与防护面证据（文件:行号）；对 ②③ 做**型号集合双向差集对表**。
5. **反证排除**：核数全部取自平台、型号分支覆盖全部声明支持型号且无残留、调度模式与核数匹配、分核整除、编包配置齐全 → 明确写出反证理由（防护面证据）。
6. **判定**：按第 7 节标准给出 命中 / 观察项 / 反证排除。
7. **GitCode 查重**（仅命中项）：issues API 按接口名 + 型号（`310P|310P1|310P3|核数|coreNum|SyncAll`）检索，逐条比对是否同机理；无同机理才立卡。
8. **业务可达性核查**（仅命中项）：判 B 等级、定业务影响类型、给处置建议；默认保守（无法证明不可达即记 B3），降档须附证据；B 不改 S×O 档位。
9. **出报告**：按第 8 节模板落盘；静态结论一律附**全型号 CI 矩阵**方案（逐 SOC 功能用例、310P1/P3 分别建例、新增型号补矩阵）。

## 6. 风险定级（S×O）与业务影响评估（B 轴）

- **S**：S2（某型号功能不可用 / 报错——部分芯片可执行、部分报错）；S3（核数假设致踩内存 / 精度异常——后果面，与 FP-A17 交叠时按主导机理归属并双向关联）；S1（仅编译期算子缺失/分支残留等构建与一致性面）。
- **O**：O3 = ≥2 条独立实证；O2 = 1 条独立实证；O1 = 仅静态扫描命中或团队笔记（实证 = 确认对应的 issue / PR，或经跨仓、跨分支核验确认的缺陷记录，同权计入）。静态推演命中且无实证默认 **O1**；升档须在报告中给出实证依据。
- **风险 = S×O**：≥6 高；3/4 中；1/2 低。FP-B02 基准：模式卡整体 S2×O3=6（高）；纯静态命中 S2×O1=2（低，暂定，实机型号矩阵验证后复评）。

### B 轴：业务影响评估（与 S×O 正交；报告层新增，不改卡片定级）

S×O 回答"多严重、多常见"，**不回答"真实业务能不能碰到"**。B 轴补这一问，只决定**修复优先级建议**，**不参与 S/O 取值、不改 S×O 档位与卡片元数据**。

**业务可达性（B）**——触发条件在真实负载中的可达程度：

| 等级 | 判据 | 证据要求 |
|---|---|---|
| B3 现实可达 | 主流框架/公开模型默认路径即可命中（如 PTA/torch_npu、vLLM、MindIE 常规调用） | 调用方或公开负载来源 |
| B2 条件可达 | 需特定 attr/dtype/shape 组合，业务中存在但非默认 | 该组合的业务来源 |
| B1 边界/不可达 | 需极端、超规格或非法参数（超出接口合理上限的 shape、退化/非法输入） | "为何不可达"的说明 |

- **默认保守**：无法证明不可达 → 记 **B3**；降为 B1/B2 必须附证据，**不得仅凭"业务应该不会这么用"**。
- 超规格参数是否算 B1 取决于**接口契约**：契约允许但业务不用 → B1；契约不允许（本应报错）→ 属校验缺失（FP-B04/B05 类），另行归属。

**业务影响类型**（命中后对用户可见结果的后果，用业务语言表述）：静默精度损失（模型效果下降 / loss 不收敛 / 偶发 NaN）｜ 任务失败中断（报错 / 崩溃 / 挂死）｜ 性能退化 ｜ 仅可观测性（日志 / 错误码 / 文档，不影响结果）。

**处置建议**（由两轴推导的报告结论，非新档位）：

| S×O \ B | B3 现实可达 | B2 条件可达 | B1 边界/不可达 |
|---|---|---|---|
| 高（≥6） | 尽快修 | 尽快修 | 排期修 |
| 中（3/4） | 尽快修 | 排期修 | 记录（业务难以触达） |
| 低（1/2） | 排期修 | 记录 | 记录 |

## 7. 判定标准与反误报原则

- **核数相关签名命中 ≠ 成立**：`GetCoreNum` / `SetBlockDim` 是每个 tiling 都会出现的常规调用，命中只作定位提示；须证明「核数取值在某型号下与该型号实际核数不符且进入切分计算」才立卡。
- **三种判定**：
  - **命中**（可静态证缺陷路径）：「核数硬编码 + 型号核数差异」「声明支持型号 ∉ 分支集合」「型号分支残留」「调度模式与核数不匹配」的完整推导链 → 立 Bug 卡；
  - **观察项**：踩内存 / 精度后果依赖实机形态、分核不整除需具体核数才能确证 → 记录并附型号矩阵方案；
  - **反证排除**：核数全部参数化、型号分支覆盖声明支持面且无残留、调度模式匹配、分核整除 → 写出防护面证据。
- **单型号通过不是反证**：禁止以「910B 上跑通」排除本型——本型缺陷的定义就是**跨型号不一致**，须逐型号核对。
- **后果面与成因面分开**：踩内存 / 精度异常的**后果**可归 FP-A17，但核数假设/型号分支的**成因**归本条，报告双向关联，不重复计缺陷。
- **不臆造行号**：每条证据必须是实际读到的 文件:行号；引用实证样板时同样给出路径与行号，issue 时点行号与本仓 HEAD 漂移时注明。

### 判定纪律补充（v3.6）：非对称增减、证据等级与误判记录

**增减不对称**：允许追加候选（有据即可，错了可由用户排除）；**撤销或否决候选必须附 `[文件]:[行号] [代码行]` 负向证据**。无证据的「看起来没问题」一律记为「未核查」，不得计入反证排除，也不得据此下调等级——否决造成的漏报用户不可见、不可恢复。

- **证据等级**（Bug 卡必填）：`静态可证` = 推导链完整且触发输入可静态构造；`需实测确认` = 依赖运行时输入规模、设备行为或环境差异。标 `需实测确认` 的条目**不得以「命中」名义出卡**，按观察项记录并附实测用例。
- **Agent 误判记录**（Bug 卡必填）：本次被推翻的假设、推翻它的证据（`[文件]:[行号] [代码行]` 或实测输出）、判定标准是否随之修订；无推翻写「无」。
- **误判回流**：同类误判在 3 次检视中重复出现，登记至 `cases/misjudgments.jsonl`（字段见 `cases/README.md`），并在本模式判定标准中新增对应防线；守门 C19d 校验台账字段合法。

## 9. 示例速览：aclnnRmsNorm

- **定位**：`cann/ops-nn` → `norm/rms_norm/`。关键文件：`op_host/rms_norm_tiling.cpp` / `rms_norm_tiling.h` / `rms_norm_tiling_arch35.cpp`、`op_host/rms_norm_def.cpp`、`op_host/config/<soc>/rms_norm_binary.json`（含 `ascend310p` / `ascend910b` / `ascend910_93` / `ascend950` / `ascend350` / `kirin9030` / `kirinx90` 等 SOC 目录）、`op_kernel/rms_norm.cpp` 等。
- **检视面提示**（引导，不预设结论，仍须逐点核查；行号以本地 HEAD 为准）：
  - 清单点①：`rms_norm_tiling.cpp` 中核数取值路径——`curSocVersion = ascendc_platform.GetSocVersion()` 与 `numCore = ascendc_platform.GetCoreNumAiv()`（平台值），以及 compileInfo 分支的 `ptrCompileInfo->totalCoreNum` / `curSocVersion`；核查 `numCore` 是否在任何型号分支下被固定值替代、`useCoreNum = CeilDiv(numRow, blockFactor)` 与 `SetBlockDim(useCoreNum)` 是否随型号核数正确变化；
  - 清单点②：型号分叉点集合（`IsRegbaseSocVersion(context)`、`curSocVersion == ASCEND910`、`ASCEND910B`、`ASCEND310P` 等）是否覆盖 `config/<soc>/` 中全部 SOC 目录——实证 #3047 即 RmsNorm 在 **310P1** 上整网执行报错（9.1.0 B030，模型推理必现），核对 310P 分支的核数假设；
  - 清单点③：是否存在已停止支持型号的残留分支（对照 ops-transformer #2122 的残留形态）；
  - 清单点④：跨核同步/调度模式写法（`SyncAll` / `SetScheduleMode`）与 310P 核数是否匹配（对照 #406 avgPool3d 的 `SetScheduleMode(batchmode)` 修复形态）；
  - 清单点⑤：310P 分支内 `useCoreNum` / `latsBlockFactor` 尾核计算在核数变化下是否整除；
  - 同族对照实证：ops-nn #253 ge_glu_v2（310P3+arm）、#700 DynamicQuant（310P 踩内存）；ops-math #1565 add_aicpu（310P aicpu 调用报错）；ops-transformer #1627/#1815（310P 算子缺失/编包找不到类）。
- 任何一点的最终判定以第 4/5/7 节口径为准，禁止凭算子类型直接下结论。

## 10. 能力边界与自检（v3.8）

### 能力边界

- **静态可证**：清单里能在源码内给出「`文件:行号` + 推导链」的部分，按第 7 节判据出卡。
- **需实测确认**：依赖运行时输入规模、设备行为或环境差异的结论，只能记观察项并附实测用例（证据等级见第 7 节）。
- **不覆盖**：本模式以外的机理（边界见第 0 节）与仓外框架侧行为；`TRIAGE.md` 只负责收敛候选，不构成判定依据。
- **找不到 ≠ 没有**：按清单未命中只说明「本轮未发现」，不得表述为「该算子无此缺陷」；抽样核查须在报告写明抽样口径。

### 自检

```bash
python3 scripts/gen_triage.py --check                          # 分诊表与映射一致

python3 check_fault_patterns.py                                # 全库守门
```

### 工作量与抽样（v4.0）

- **深度档：标准**（索引 `depth` 字段）——每映射点取前 20 处命中；同一映射点连续 20 处反证排除即停止该点并记录。报告须写「抽样口径：每点前 20 处」。
- **报告必填**：抽样口径（全量 / 每点前 N 处 / 每类 N 例）+ 停止点记录；未写口径视为未完成。
