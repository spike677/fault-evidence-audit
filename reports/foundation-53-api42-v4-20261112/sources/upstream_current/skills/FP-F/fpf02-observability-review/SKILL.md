# FP-F02 维测与错误上报检视（fpf02-observability-review）

对用户指定的算子 / aclnn 接口做 FP-F02 专项维测与错误上报检视：先定位日志、错误码、dump 与维测宏的代码点，再按五子型清单逐项核查，每个结论给出**文件 + 行号 + 推导链**证据，命中即出 Bug 卡，输出检视报告。**本模式特殊纪律：① 检视对象是**可观测性产物**，不是算子计算正确性——「报错信息与真实根因不符导致排查跑偏」「正常降级刷 error 淹没真实故障」都是缺陷；② 子型④（该报不报）与子型⑤（不该报却报）构成完整对称面，须双向核查；③ 本型体量已超出逐条人工评审（单模块可达 721 处），错误码选择与日志规范**必须做成静态检查项而非文档约定**；④ 返回码/日志实际取值需运行时或工具扫描确认，静态只能立「上报缺失/级别错配/错误码错配」的代码路径。**

## 0. 与相邻模式的边界

| 相邻模式 | 分工 |
|---|---|
| FP-B04（空指针校验缺失） | 空指针校验缺失常与「未上报」伴生——B04 管**校验是否缺失**（崩溃面），F02 管**校验到了是否上报、错误码是否正确**（可观测面）；实证 #143 类「同输入不同返回」归本条 |
| FP-B05（校验覆盖度参差） | 同源，均为范差不齐——B05 管校验骨架覆盖率，F02 管上报质量与错误码一致性 |
| FP-B01（校验过严误拦截） | 误拦截时错误信息质量决定排查成本——B01 管拦截行为，F02 管拦截后的错误码/文案 |
| FP-B08（属性读取失败后静默降级） | 静默降级 `return false` 且以 `OP_LOGE` 上报，与本型子型⑤ 同属「降级路径日志级别与 fatal 语义不对齐」 |
| FP-E01（golden/UT 期望值失配） | 测试只断言 `rc != 0` 不校验错误信息会导致此类漏检——E01 管期望值，F02 管错误码/文案 |
| FP-A20（确定性等级描述不足） | 「信息未暴露给使用者」的可观测性问题——#1660 同时是 A20 实证（确定性接口异常返回值的语义未与调用方对齐） |

**症状反查定位**：报错信息与真实根因不符 → 子型③（错误码选择）；同一非法输入在 ops-nn 与 ops-math 返回**不同错误码**（如 561002 vs 调用成功）→ 子型③-a（跨仓不一致）；`--dump_cce` 产物目录为空 → 子型②；日志晚于失败点输出 → 子型①（时机错误）；维测信息缺字段（Shape 少一个 `]`）→ 子型①；**正常降级场景刷出 error 级日志**、虚假告警 → 子型⑤；日志文案规模化不规范（拼写/语法）→ 子型① + 横切面（规范扫描）。

## 1. FP-F02 模式卡摘要（检视依据，源自本库 `patterns/FP-F/FP-F02.md`，v3.1）

- **编号 / 名称**：FP-F02 维测与错误上报缺陷（含跨仓错误码不一致） ｜ **类别**：工程/交付 ｜ **风险**：中（S1×O3=3）｜ **状态**：活跃
- **适用声明头**（照抄卡片）：仓 All ｜ 侧别 Tiling,Kernel,Host ｜ 载体 Tiling源码,Kernel源码,Host源码 ｜ 触发 OP_LOGE|ACLNN_ERR ｜ 默认启用 true
- **skill 核查面**：载体为 Tiling/Kernel/Host 源码——skill 落地为 op_host（tiling / infershape）与 op_kernel 的错误分支、op_api 的 `ACLNN_ERR_*` 返回点、维测宏（`OP_LOGD` / `OP_LOGE` / `OP_LOGW`、`DUMP_*`、`--dump_cce`、tiling dump 开关）；跨仓同源算子的返回码对照矩阵为子型③-a 的核心核查面
- **故障机理**：算子/接口的**可观测性产物**缺失或错误，使缺陷无法定位甚至被误导。五种独立成因：① 日志与维测信息不打印、打印时机错误（编译/执行结束才输出）、内容缺字段或拼写错误；② dump 类调试产物（`--dump_cce` 的 `kernel_meta`、tiling/日志开关）为空或路径错误；③ **错误码/报错信息不规范**（拆为两个可独立判定的子面）：**③-a 跨仓/跨接口不一致**（同一非法输入在不同仓/接口返回不同错误码）；**③-b 错误码选择错误**（拦截确实存在但所选错误码与场景不匹配，典型为 `ACLNN_ERR_PARAM_INVALID`(161002) / `ACLNN_ERR_PARAM_NULLPTR`(161001) / `ACLNN_ERR_INNER_*` 混用），两子面之外另含缺少上下文（算子名/参数名/实际值）；④ 异常被静默吞掉（日志级别过低、错误分支直接 `return` 未上报）；⑤ **日志级别误用（反向问题）**——设计内的正常降级/可预期分支被按 error 级别上报，制造大量误报 error 与虚假监控告警，反而**掩盖真实故障**（④ 该报不报，⑤ 不该报却报，二者共同后果都是真实故障被淹没）。根因多为模板/复制导致的维测宏漏插、错误分支未上报、**降级分支的日志级别未与「是否 fatal」对齐**、跨仓错误码约定未统一。
- **触发条件**：任一异常分支（参数非法、shape/dtype 不支持、内存不足、属性非法）；构建或运行期启用 dump/日志开关；**同源算子在两仓之间的同一非法输入对照**；错误信息巡检；**规范化工具全量扫描**（如 `cann-log-evaluation` 类）；**可预期的降级路径被走通**（如查询类接口返回异常值，设计上仅回退默认行为并继续执行）。
- **典型表现**：报错信息与真实根因不符 → 排查跑偏；同一输入在 ops-nn 与 ops-math 返回**不同错误码**（如 561002 vs 调用成功）；`--dump_cce` 产物目录为空；日志晚于失败点输出；维测信息缺字段（如 Shape 少一个 `]`）致下游解析失败；**正常降级场景刷出 error 级日志**使 error 密度失真、依赖 error 告警/监控的环境产生**虚假告警**；**日志文案不符合规范且规模化存在**（单模块可达数百处，含拼写/语法错误）。
- **源码审查映射点**：每个错误分支是否上报且携带上下文（`OP_LOGE_FOR_INVALID_*` 系列 vs 裸 `OP_LOGE`）；错误码与错误类别是否匹配（161002 / 161001 / `INNER_*` 不可混用）；`return ge::GRAPH_FAILED;` / `return ACLNN_ERR_*;` 之前是否已有日志；维测宏（`OP_LOGD`、`DUMP_*`、`--dump_cce`、tiling dump 开关）是否插入且级别正确；**同源算子在四仓的返回码是否一致**；是否存在「校验到了但静默返回 SUCCESS」；**每个 `OP_LOGE` 所在分支是否真的 fatal**（可预期降级应按 `OP_LOGW`/`OP_LOGI` 上报）；**日志文案是否符合《CANN 日志规范》**（语法完整、拼写正确、含上下文与度量单位）；是否存在**含义相反的拼写**（如 `Excepted` 与 expected 反义）。
- **检测签名**：`OP_CHECK_[A-Z_]+` 覆盖率统计（错误分支数 vs 上报数）；`OP_LOGE(_FOR_[A-Z_]+)?\(`；`return\s+(ge::GRAPH_FAILED|ACLNN_ERR_[A-Z_]+)\s*;` 前一行是否有日志；`DUMP_(SCENES|TENSOR)|dump_cce|TILING_?DUMP`；`ACLNN_ERR_(PARAM|INNER)_[A-Z_]+` 与场景匹配性；**`OP_LOGE` 与 `return (false|SUCCESS|GRAPH_SUCCESS)` 同现于同一分支**（降级分支误用 error 级别的高危形态）；**`INT32_MAX|UINT32_MAX` 等异常返回值与 `OP_LOGE` 同现**（异常返回值常被当 fatal 误报）。
- **错误码选择矩阵（子型 ③-b 对照表）**：

| 实际异常类型 | 应报错误码 | 常见误用 |
|---|---|---|
| 指针为 `nullptr` | `ACLNN_ERR_PARAM_NULLPTR`(161001) | 误报 `PARAM_INVALID` |
| dtype / layout / format 不匹配 | `ACLNN_ERR_PARAM_INVALID`(161002) | 与 161001 互换 |
| shape / 属性取值非法（维数、维度值、属性长度） | `ACLNN_ERR_PARAM_INVALID`(161002) | 误报 `INNER_*`（把用户侧错误报成内部错误） |
| 平台 / SoC 不支持该能力 | `ACLNN_ERR_PARAM_INVALID`(161002) 或按支持面约定 | 误报 `INNER_*` |
| CANN 内部状态、资源异常（非用户输入所致） | `ACLNN_ERR_INNER_*` | 误报 `PARAM_INVALID`（把内部缺陷推给用户） |

- **测试拦截建议**：负向用例断言「返回码 + 错误信息关键字段」而不仅 `rc != 0`；对跨仓同源算子做**同一非法输入的返回码对照矩阵**（把不一致本身当缺陷提）；CI 增加「配置了 dump/日志开关但产物为空」的产物检查；错误码文档化并纳入审查；**引入日志规范自动化评测工具（如 `cann-log-evaluation`）做全量模块扫描并纳入 CI 门禁**；用例侧对可预期降级路径断言「**该场景不应出现 error 级别日志**」；跑正常业务用例时统计 error 日志条数基线，异常增幅即告警。
- **实证案例**：ops-nn **#143** `HardSwish` 在 ops-nn 库 aclnn 调用报 **561002**，而在 ops-math 库 aclnn 调用**成功**（跨仓错误码/行为不一致，最易误导定位）；**#1151** 编译指定 `--dump_cce` 后 `kernel_meta` 文件夹为空；**#1103** kernel 编译日志只在实际编译结束后才打印（失败时看不到过程信息）；**#1004** DLQBMM 异常拦截维测信息 Shape 少一个 `]`；**#2224** GroupNormGrad 日志打印文本拼写错误；**#1283** tbmm warning 报错信息待修复。语料统计（2026-09-14，四仓缺陷类）：「维测/dump/日志缺失或错误」110 条 + 「报错信息/错误码不规范或不一致」90 条。canndev 增补：**#1660**（closed）gemm tiling 中 `GetCloseKShiftFlag()` 经 `context->GetDeterministicLevel()` 判断是否关闭 K-shift，当该接口返回异常值 `INT32_MAX` 时实现**打印 error 级别日志**（`OP_LOGE(nodeName, "GetDeterministicLevel() failed.")`）——而该场景表示「无法获取确定性级别」，函数**按设计回退 `false` 并继续执行，属可预期降级，不应按 error 上报**（子型⑤ 教科书案例，同时是 FP-A20 实证）；**#1837**（open）用 CANN 日志规范评测工具（`cann-log-evaluation`）对 `ops/built-in/aicpu` 运行时日志做**全量扫描**，发现 **721 处**不符合《CANN 日志规范》——语法错误 525、拼写错误 109、错误描述不完整 86、缺少度量单位 1；典型拼写 `succcess`/`ouput`/`memeset_s`/`shoule`/**`Excepted`（与 expected 含义相反）**/`dismatch`/`invlaid`/`argumengt`/`verfication`/`Poissonon`/`NonZeroe`/`Copyview`/`Ranperm`，语法问题如 `not support`→`is not supported`、`must greater than`→`must be greater than`、`need be same`。
- **关联**：FP-B04、FP-B05、FP-B01、FP-E01、FP-A20（#1660 同时是 A20 实证）、FP-B08（静默降级 + error 上报，与子型⑤ 同属级别错配）。

## 2. 检视输入与检视对象定位

**输入**：算子名 / aclnn 接口名（必填，如 `aclnnHardSwish` / `HardSwish`）；可选 ref（默认 master）、指定仓（默认自动定位）；可选**现象描述**（实测错误码、日志缺失点、dump 产物为空、error 日志刷屏）；可选**跨仓同源算子对照目标**（子型③-a 需要：同源算子在两仓的返回码对照）；可选**规范化工具输出**（如 `cann-log-evaluation` 扫描结果——子型① 横切面的证据来源）。

**接口名 → 算子目录换算**：去 `aclnn` 前缀 + 驼峰转下划线小写：
`aclnnHardSwish → hard_swish`、`aclnnGroupNormGrad → group_norm_grad`、`aclnnDLQBMM → dlqbmm`。

**仓定位顺序**（GitCode `cann` 组织，逐仓用目录列表确认）：`ops-nn`（activation/norm/loss/matmul 类）→ `ops-math`（math/conversion 类）→ `ops-cv`（image/vision 类）→ `ops-transformer`（attention/moe 类）；跨仓错误码对照另需定位**同源算子**所在仓；日志规范实证来源含 `canndev`。**类目名不总与直觉一致**，以目录列表为准。FP-F02 高发面：模板/复制生成的错误分支（维测宏漏插）、跨仓同源算子（错误码约定未统一）、降级/查询类分支（级别误用）、dump 开关插入点、含 `INT32_MAX` 等异常返回值的判定分支。

**维测与上报面结构约定**（示例 `cann/ops-nn` → `activation/hard_swish/`）：

```text
{类别}/{op_name}/
├── op_host/{op}_tiling*.cpp、{op}_infershape.cpp   # 错误分支上报、tiling dump 开关、错误码取值点
├── op_kernel/                                      # kernel 内日志宏与 dump 相关（OP_LOGD/OP_LOGE）
├── op_api/aclnn_{op}.cpp（或 op_host/op_api/）     # ACLNN_ERR_* 返回点（子型③④ 主检视面）
├── tests/                                          # 负向用例：是否断言返回码 + 错误信息字段
└── docs/                                           # 错误码/文案的文档依据（旁证）
```

## 4. 五子型检视清单（每点：查什么 → 何处 → 命中判据）

对 op_host / op_kernel / op_api 的全部错误分支与维测点逐点核查，**每点先查命中面、再做反证排除**；上报正确的分支也要记录（作为反证依据）。

### 子型① 日志与维测信息缺失 / 时机错误 / 内容缺字段
- 查什么：错误分支是否上报且携带上下文（算子名/参数名/实际值）；日志**打印时机**是否晚于失败点（实证 #1103：kernel 编译日志只在实际编译结束后才打印，失败时看不到过程信息）；维测信息字段是否完整（实证 #1004：Shape 少一个 `]` 致下游解析失败）；文案是否规范（拼写/语法——实证 #2224 GroupNormGrad 拼写错误；#1837 单模块 721 处，含含义相反的 `Excepted`）。
- 何处：`{op}_tiling*.cpp` / `{op}_infershape.cpp` / kernel 的 `OP_LOGE(_FOR_*)?\(`、`return ge::GRAPH_FAILED` / `return ACLNN_ERR_*` 之前的日志点。
- 命中判据：错误分支无日志、日志点在失败点之后、字段缺失、文案违反《CANN 日志规范》⇒ 命中；批量文案问题按横切面全量扫描。

### 子型② dump 类调试产物缺失 / 路径错误
- 查什么：`--dump_cce` 的 `kernel_meta` 是否为空或路径错误（实证 #1151）；tiling dump / 日志开关是否插入且路径正确。
- 何处：`DUMP_(SCENES|TENSOR)|dump_cce|TILING_?DUMP` 签名命中处、构建/运行配置。
- 命中判据：开关已配置而产物目录为空/路径不存在（须产物实测确认）⇒ 命中或观察项。

### 子型③ 错误码 / 报错信息不规范
#### ③-a 跨仓/跨接口不一致
- 查什么：**同源算子在两仓的同一非法输入**是否返回不同错误码或行为（实证 #143：HardSwish 在 ops-nn 库 aclnn 报 561002、在 ops-math 库 aclnn **成功**）——不一致本身即缺陷。
- 何处：同源算子在各仓 op_api 的 `ACLNN_ERR_*` 返回点（跨仓对照矩阵）。
- 命中判据：同一输入在两仓的返回码/行为差集非空 ⇒ 命中。

#### ③-b 错误码选择错误
- 查什么：每个拦截分支所选错误码与**异常类型**是否匹配（对照第 1 节错误码选择矩阵）——`161001`（NULLPTR）/`161002`（PARAM_INVALID）/`INNER_*` 混用；实证：layout/dtype 不匹配误报 `PARAM_INVALID`（应为 161002 或按约定）、空输入误报 `INVALID` 而非 `NULLPTR`；QSFA/SFA/LI/QLI/FA 算子族 layout 错误时错误码不对。
- 何处：`CheckParams` 与各校验函数的 `ACLNN_ERR_*` 取值点、`OP_LOGE_FOR_INVALID_*` 系列选择。
- 命中判据：错误码与场景类型不匹配（逐分支对表）⇒ 命中。**「有报错」≠「错误码正确」**。

### 子型④ 异常被静默吞掉（该报不报）
- 查什么：错误分支是否直接 `return`（`return false` / `GRAPH_FAILED` / `SUCCESS`）而未上报；是否存在「校验到了但静默返回 SUCCESS」；日志级别是否过低致故障无痕。
- 何处：全部错误分支的返回语句与其前一行日志；`OP_CHECK_[A-Z_]+` 覆盖率（错误分支数 vs 上报数）。
- 命中判据：错误分支无上报即返回 ⇒ 命中。

### 子型⑤ 日志级别误用（不该报却报）
- 查什么：每个 `OP_LOGE` 所在分支**是否真的 fatal**——可预期降级/查询类分支应按 `OP_LOGW`/`OP_LOGI`；**`OP_LOGE` 与 `return (false|SUCCESS|GRAPH_SUCCESS)` 同现于同一分支**是降级误用 error 的高危形态；**`INT32_MAX|UINT32_MAX` 等异常返回值与 `OP_LOGE` 同现**（异常返回值常被当 fatal 误报——实证 canndev #1660：`GetCloseKShiftFlag()` 遇 `GetDeterministicLevel()` 返回 `INT32_MAX` 打印 `OP_LOGE(... "GetDeterministicLevel() failed.")`，而函数按设计 `return false` 继续执行）。
- 何处：`OP_LOGE` 所在分支的返回值与控制流；降级分支的日志宏选择。
- 命中判据：`OP_LOGE` 分支实际非 fatal（`return false`/`SUCCESS`/继续执行）⇒ 命中；后果为虚假告警、error 密度失真、真实故障被淹没。

### 横切面：日志规范全量扫描与 error 基线
- 查什么：引入日志规范自动化评测工具（`cann-log-evaluation` 类）做全量扫描（实证 #1837：721 处）；跑正常业务用例时统计 error 日志条数基线，异常增幅即告警；可预期降级路径断言「该场景不应出现 error 级别日志」。
- 何处：CI 门禁配置、用例断言、日志统计脚本。
- 命中判据：门禁/基线缺失（本型体量已超人工评审承受范围）⇒ 记录为流程缺陷观察项。

### 防护面与反证（记录用）
- 查什么：已有 `OP_LOGE_FOR_INVALID_*` 携带上下文、错误码与场景匹配、dump 产物正常、降级分支用 `OP_LOGW`、文案合规——逐条记录（文件:行号）。

## 5. 检视流程

1. **定界**：换算算子/接口目录，确认所在仓与 ref；按用户现象（实测错误码 / 日志缺失 / dump 空 / error 刷屏）反查优先子型；确认跨仓同源对照目标与规范化工具输出是否提供。
2. **枚举**：目录列表列出 op_host（tiling/infershape）/ op_kernel / op_api / tests / docs 中全部错误分支、`OP_LOGE`、`ACLNN_ERR_*`、dump 宏，产出文件与上报点清单。
3. **触发词扫描**：按 `OP_LOGE(_FOR_[A-Z_]+)?\(`、`ACLNN_ERR_(PARAM|INNER)_[A-Z_]+`、`return\s+(ge::GRAPH_FAILED|ACLNN_ERR_[A-Z_]+|false|SUCCESS)\s*;`、`DUMP_(SCENES|TENSOR)|dump_cce|TILING_?DUMP`、`INT32_MAX|UINT32_MAX` 定位风险面（本地仓用 grep；API 模式逐文件拉取后检查）。
4. **五子型逐项核查**：每点记录命中面与防护面证据（文件:行号）；错误码逐分支对表（矩阵）；`OP_LOGE` 分支逐个确认是否 fatal；跨仓同源算子做返回码对照矩阵。
5. **反证排除**：上报携带上下文且时机正确、错误码与场景匹配、dump 产物正常、降级分支用 WARN/INFO、文案合规、跨仓返回码一致 → 明确写出反证理由（防护面证据）。
6. **判定**：按第 7 节标准给出 命中 / 观察项 / 反证排除。
7. **GitCode 查重**（仅命中项）：issues API 按接口名 + `错误码|error|日志|dump|561002|561103|warning` 检索，逐条比对是否同机理；无同机理才立卡。
8. **业务可达性核查**（仅命中项）：判 B 等级、定业务影响类型、给处置建议；默认保守（无法证明不可达即记 B3），降档须附证据；B 不改 S×O 档位。
9. **出报告**：按第 8 节模板落盘；静态结论一律附探针/扫描方案（跨仓返回码对照矩阵、dump 产物检查、`cann-log-evaluation` 全量扫描、error 日志基线）。

## 6. 风险定级（S×O）与业务影响评估（B 轴）

- **S**：S1（维测/错误码缺陷——排查成本上升、虚假告警、错误码误导，通常不改变计算结果）；S2 仅当错误码不一致致调用方按错误分支处理、或跨仓行为差异改变功能结果时升级（须依据）。
- **O**：O3 = ≥2 条独立实证；O2 = 1 条独立实证；O1 = 仅静态扫描命中或团队笔记（实证 = 确认对应的 issue / PR，或经跨仓、跨分支核验确认的缺陷记录，同权计入）。静态推演命中且无实证默认 **O1**；升档须在报告中给出实证依据。
- **风险 = S×O**：≥6 高；3/4 中；1/2 低。FP-F02 基准：模式卡整体 S1×O3=3（中）；纯静态命中 S1×O1=1（低）。

### B 轴：业务影响评估（与 S×O 正交；报告层新增，不改卡片定级）

S×O 回答"多严重、多常见"，**不回答"真实业务能不能碰到"**。B 轴补这一问，只决定**修复优先级建议**，**不参与 S/O 取值、不改 S×O 档位与卡片元数据**。

**业务可达性（B）**——触发条件在真实负载中的可达程度：

| 等级 | 判据 | 证据要求 |
|---|---|---|
| B3 现实可达 | 主流框架/公开模型默认路径即可命中（如 PTA/torch_npu、vLLM、MindIE 常规调用） | 调用方或公开负载来源 |
| B2 条件可达 | 需特定 attr/dtype/shape 组合，业务中存在但非默认 | 该组合的业务来源 |
| B1 边界/不可达 | 需极端、超规格或非法参数（超出接口合理上限的 shape、退化/非法输入） | "为何不可达"的说明 |

- **默认保守**：无法证明不可达 → 记 **B3**；降为 B1/B2 必须附证据，**不得仅凭"业务应该不会这么用"**。
- 超规格参数是否算 B1 取决于**接口契约**：契约允许但业务不用 → B1；契约不允许（本应报错）→ 属校验缺失（FP-B04/B05 类），另行归属。

**业务影响类型**（命中后对用户可见结果的后果，用业务语言表述）：静默精度损失（模型效果下降 / loss 不收敛 / 偶发 NaN）｜ 任务失败中断（报错 / 崩溃 / 挂死）｜ 性能退化 ｜ 仅可观测性（日志 / 错误码 / 文档，不影响结果）。

**处置建议**（由两轴推导的报告结论，非新档位）：

| S×O \ B | B3 现实可达 | B2 条件可达 | B1 边界/不可达 |
|---|---|---|---|
| 高（≥6） | 尽快修 | 尽快修 | 排期修 |
| 中（3/4） | 尽快修 | 排期修 | 记录（业务难以触达） |
| 低（1/2） | 排期修 | 记录 | 记录 |

## 7. 判定标准与反误报原则

- **签名 / 触发词命中 ≠ 成立**：`OP_LOGE` 命中量大且多数正常——命中只是定位提示，必须过「分支是否 fatal / 错误码与场景是否匹配 / 是否携带上下文」三关；`INT32_MAX` 与 `OP_LOGE` 同现须人工确认该返回值是否真异常。
- **三种判定**：
  - **命中**（可静态证缺陷路径）：「错误分支无上报」「日志晚于失败点」「错误码与场景不匹配」「跨仓返回码不一致」「降级分支用 OP_LOGE」任一推导链完整 + 触发输入可静态指认 → 立 Bug 卡；
  - **观察项**：dump 产物是否为空、实测返回码取值、文案规模化问题需工具扫描 → 记录并附方案，按 S1×O1 暂定；
  - **反证排除**：上报携带上下文且时机正确、错误码与场景匹配、降级分支用 WARN/INFO、跨仓一致 → 明确写出反证理由。
- **「有报错」≠「错误码正确」**：非匹配错误码（如 layout 错误报 PARAM_INVALID、空输入报 INVALID）仍是本型命中（子型③-b）。
- **子型④与⑤须双向核查**：只查「该报不报」会漏掉「不该报却报」；只查 error 缺失会漏掉 error 泛滥——两者共同后果都是真实故障被淹没。
- **错误码对照矩阵必须实读**：跨仓返回码两边都要实际读到（返回点 + 错误码常量），引用具体文件与行号；实测返回码留待探针确认。
- **不臆造行号与文案**：每条证据必须是实际读到的 文件:行号 / 文案；引用实证样板时同样给出路径与行号，issue 时点行号与本仓 HEAD 漂移时注明。
- **静态推演声明**：无运行环境时，所有实测返回码/日志输出结论标注「静态推演，需运行时探针/工具扫描确认」。

### 判定纪律补充（v3.6）：非对称增减、证据等级与误判记录

**增减不对称**：允许追加候选（有据即可，错了可由用户排除）；**撤销或否决候选必须附 `[文件]:[行号] [代码行]` 负向证据**。无证据的「看起来没问题」一律记为「未核查」，不得计入反证排除，也不得据此下调等级——否决造成的漏报用户不可见、不可恢复。

- **证据等级**（Bug 卡必填）：`静态可证` = 推导链完整且触发输入可静态构造；`需实测确认` = 依赖运行时输入规模、设备行为或环境差异。标 `需实测确认` 的条目**不得以「命中」名义出卡**，按观察项记录并附实测用例。
- **Agent 误判记录**（Bug 卡必填）：本次被推翻的假设、推翻它的证据（`[文件]:[行号] [代码行]` 或实测输出）、判定标准是否随之修订；无推翻写「无」。
- **误判回流**：同类误判在 3 次检视中重复出现，登记至 `cases/misjudgments.jsonl`（字段见 `cases/README.md`），并在本模式判定标准中新增对应防线；守门 C19d 校验台账字段合法。

## 10. 能力边界与自检（v3.8）

### 能力边界

- **静态可证**：清单里能在源码内给出「`文件:行号` + 推导链」的部分，按第 7 节判据出卡。
- **需实测确认**：依赖运行时输入规模、设备行为或环境差异的结论，只能记观察项并附实测用例（证据等级见第 7 节）。
- **不覆盖**：本模式以外的机理（边界见第 0 节）与仓外框架侧行为；`TRIAGE.md` 只负责收敛候选，不构成判定依据。
- **找不到 ≠ 没有**：按清单未命中只说明「本轮未发现」，不得表述为「该算子无此缺陷」；抽样核查须在报告写明抽样口径。


- **报告必填**：抽样口径（全量 / 每点前 N 处 / 每类 N 例）+ 停止点记录；未写口径视为未完成。
