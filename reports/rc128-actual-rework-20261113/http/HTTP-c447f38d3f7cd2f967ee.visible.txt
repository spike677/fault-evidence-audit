问题描述
frequency_regulator
当前手工调用 ACLNN 接口并管理 ACL Tensor、workspace、executor 和 HugeMem 资源，与 MindIE-SD 其他
PyTorch plugin 的统一调用方式不一致。
当前实现还包含流同步以及 D2H/H2D 状态拷贝，会将调频调用串行化，并增加异步执行时的资源生命周期风险。
当前实现
主要存在以下问题：
手工调用
aclnnFrequencyRegulatorGetWorkspaceSize
和
aclnnFrequencyRegulator
。
使用
aclrtMalloc
和
aclrtFree
管理 workspace。
手工创建和销毁 ACL Tensor。
算子下发后调用
aclrtSynchronizeStream
。
通过 D2H 和 H2D 拷贝转换返回状态。
未复用其他 plugin 使用的
EXEC_NPU_CMD
公共框架。
预期行为
使用
EXEC_NPU_CMD
调用
aclnnFrequencyRegulator
。
由公共 plugin 框架管理 workspace、executor 和 ACL Tensor 生命周期。
不在算子内部执行流同步。
不进行额外的 D2H/H2D 状态拷贝。
保持返回值为 NPU 上的
int64
Tensor。
支持连续异步调用，最后统一同步时不发生异常。
建议方案
创建 INT32 存储 Tensor，并通过
TensorWrapper
将 ACL 数据类型声明为
ACL_UINT32
。
使用
EXEC_NPU_CMD
下发调频算子。
在当前流上将状态 Tensor 转换为
int64
。
删除手工 ACL API 查找、workspace 分配、资源释放及同步逻辑。
