### 🐛 Describe the bug

### Background

This issue was found while validating **GLM-5.2 DSpark speculative decoding on Ascend A5 (950DT)**. The affected setup uses the SFA/DSpark path on current `main`, including PD serving and compiled `FULL_DECODE_ONLY` execution. The three problems below were isolated from the same A5 GLM DSpark accuracy investigation, although each is an independent runtime-correctness issue.



GLM-5.2 SFA/DSpark serving on current `main` can produce incorrect output or enter an invalid execution path because several decisions that vary by runtime batch are derived from initialization/profile state or are traced outside an opaque compiled boundary.

The investigation found three independently reproducible correctness problems.

#### 1. SFA PROLOG_V3 can incorrectly fall back to NATIVE

A KV consumer may select `PreprocessType.PROLOG_V3`, prepare its fused weights, and dispose the native projection weights during initialization. In `AscendSFAImpl.forward`, an attention state other than `DecodeOnly` or `SpecDecoding` nevertheless changes the local `fused_type` back to `NATIVE`.

This is reachable for multi-token verification/chunked-prefill and prefix-cache-hit states. The NATIVE branch subsequently calls `fused_qkv_a_proj`, even though the weights required by that branch have already been released.

Expected behavior: once a KV consumer has selected PROLOG_V3 and disposed native weights, supported runtime attention states must stay on PROLOG_V3. The legacy attention-state and token-count fallback should apply only to MLAPO.

#### 2. Compiled MoE can freeze the wrong final-reduction decision

`MoERunner.forward()` evaluates `_maybe_reduce_final_output` outside the existing fused MoE custom-op boundary. The result depends on the live MoE communication method:

- `ALLGATHER` without sequence parallelism requires the outer TP all-reduce.
- `MC2` and `ALLTOALL` already reduce the routed output.

A graph traced/profiled with one method can be replayed when another method is selected for the runtime batch. The Python guard is not retraced, so the graph may double-reduce the output or omit a required reduction, causing severe accuracy loss.

Expected behavior: the communication-dependent reduction decision must remain runtime-visible instead of being frozen by the first trace.

Related alternative fixes are being discussed in #16455, #16459, and #16476.

#### 3. DSpark profiling can truncate the full speculative query batch

The number of draft queries is:

```text
max_batch_size * (num_speculative_tokens + (not sample_from_anchor))
```

This can exceed `max_num_batched_tokens`, but `AscendDSparkProposer.input_ids` is inherited with only `max_num_batched_tokens` entries. During `dummy_run(..., is_profile=True)`, slicing this buffer silently produces fewer IDs than positions/the expected query count.

In addition, DSpark is documented as eager-only, but draft model construction only inherited the eager context in configurations that happened to enable sequence parallelism. Target compilation settings can therefore leak into draft construction.

Expected behavior:

- Size the DSpark ID buffer for the complete speculative query batch, independently of the target scheduler token budget.
- Construct the draft model with compilation disabled while preserving and restoring the target model's compilation configuration.

### Reproduction coverage

The failures are covered by focused tests using:

- SFA states `DecodeOnly`, `ChunkedPrefill`, and `PrefillCacheHit`, with PROLOG_V3 native projection access made fatal after simulated weight disposal.
- A single `make_fx` MoE graph replayed while switching the live communication method across `ALLGATHER`, `MC2`, and `ALLTOALL`.
- DSpark profile shapes with `max_num_batched_tokens` 256/1024, 64 requests, 7 speculative tokens, and both anchor-sampling layouts.

### Reference implementation

Draft PR #16482 is provided **for reference only**. It records the implementation used to validate the identified root causes and regression tests; it is not presented as the final merge proposal.

In particular, its MoE portion overlaps with #16455, #16459, and #16476, so maintainers may choose one of those approaches instead. The SFA and DSpark changes can also be reviewed or split independently.

The reference draft keeps PROLOG_V3 on its prepared path, puts the complete MoE runner call behind an opaque runtime boundary, grows the DSpark profile ID buffer, and explicitly constructs the draft model under the eager context.
