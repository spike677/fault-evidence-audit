[Bug][GLM-5.2-W4A8C8][co-located] Stochastic async MTP enters a parser-before periodic raw-token loop
## Why this is a separate report

This is an independent **two-node co-located** reproduction, not P/D disaggregation. It is related to #14463 and #14656, but adds two isolation results that those issue bodies do not contain:

1. the failure reproduces through the vLLM OpenAI-compatible endpoint directly, bypassing the agent harness, LiteLLM, and the API gateway;
2. `return_token_ids=true` proves that the periodic loop already exists in the engine's raw output token IDs before GLM tool parsing.

The symptom eventually becomes repeated or unterminated `tool_calls[].function.arguments`, but the parser is downstream of the first observed corruption in this case.

## Impact

In a production-style agent request, approximately 0.9%-1.0% of default-sampling requests entered a long-running periodic token loop. They continued returning HTTP 200 SSE chunks until a 300-second client protection timeout, with no terminal `finish_reason`, usage chunk, or `[DONE]`. If the incomplete tool call is persisted and sent back in a later turn, downstream JSON parsing reports `Unterminated string` and returns HTTP 400.

## Reproduction statistics

All runs used the same request shape and called the serving endpoint directly:

| Arm | Result |
|---|---:|
| default model sampling, concurrency 4 | 991/1000 completed; 9/1000 timed out at 300 s |
| independent default-sampling repeat, concurrency 4 | 297/300 completed; 3/300 timed out at 300 s |
| `temperature=0`, concurrency 4 | 300/300 completed; 0/300 observed timeouts |

The zero failures in 300 greedy requests are evidence that stochastic sampling is a trigger/risk factor; they are not claimed as proof of a complete fix.

The request did **not** set `tool_choice`, `strict`, or `temperature`. It therefore used auto tool choice and the model's default generation configuration (`temperature=1.0`, `top_p=0.95`).

Non-sensitive request shape:

```text
OpenAI Chat Completions
stream=true
about 50,190 prompt tokens after template application
36 messages
85 function tool schemas
max_completion_tokens=128,000 (an upper bound, not a fixed requested output length)
stream_options.include_usage=true
return_token_ids=true for the evidence run
concurrency=4
per-request protection timeout=300 seconds
```

## Parser-before raw-token evidence

All three failures in the 300-request evidence run had low-diversity periodic repetition in raw `output.token_ids` before parser processing. The three token-stream hashes and best periods were different, so this is not one SSE response duplicated by the client or proxy.

| Request | Raw engine token evidence | Token-stream SHA-256 |
|---|---|---|
| 44 | best period 13 over the last 8192 tokens; 74.61% agreement | `a5f86d630332741d00746281a50594bd4d07f4496f63f08cd5201c45419a096b` |
| 82 | exact period 768 over a 6144-token tail; 5376/5376 comparable tokens match | `e1df762935c36e64f1383e0bfba62c9f86683e3d27a45d0b8c3a69bd3fee754d` |
| 142 | exact period 8 over the last 8192 tokens; 8184/8184 comparable tokens match | `eb9cd9c12bffa1ebe41dba9c4294bf1c9749082c67494a045314cb9d5cd13b5b` |

After those raw-token loops begin, the parser converts the repeated GLM tool markup into repeated/unclosed arguments. For request 82, the parsed argument tail also repeats exactly (period 1248 characters) and ends with `Unterminated string`. Request 142 independently produces a different repeated argument period and the same incomplete-JSON class.

## Fix/version audit already performed

- vLLM #45915 and #46351 are present in the tested image. They improve GLM streaming parsing, but the parser-before token loop still reproduces.
- vLLM-Ascend #13865 is present byte-for-byte in both serving images. The issue still reproduces, so the async accepted-token snapshot fix is insufficient by itself.
- vLLM #47512 / issue #47504 cover `tool_choice=required`; this request uses auto tool choice and does not set `tool_choice`.
- vLLM #52805 covers speculative grammar advancement after structural-tag termination. This request has neither `strict` nor required/named tool choice, so it does not build that constrained structural-tag path.
- vLLM-Ascend #13766 fixes an always-accepting rejection sampler in ModelRunner V2 on v0.26+. The tested v0.23 path is ModelRunner V1 and uses generated uniform probabilities, not the hardcoded `u=0.0` code fixed there.
- vLLM-Ascend #14536 is specific to P/D decode nodes with `enable_sparse_sfa_c8`; this reproduction is co-located and uses `enable_sparse_li_c8` without `enable_sparse_sfa_c8`.
- vLLM-Ascend #14451 may be relevant to GLM-5.2 MTP shared-index handling on the v0.26rc line, but it is still a draft with no end-to-end validation for this failure mode.
- As of 2026-08-20, the latest published vLLM-Ascend release is v0.23.0. Main/v0.26rc contains additional candidate fixes, but no released or merged change claims to fix this parser-before periodic raw-token loop.
