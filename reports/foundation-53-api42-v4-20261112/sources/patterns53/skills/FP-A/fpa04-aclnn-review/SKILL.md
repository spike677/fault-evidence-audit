# FP-A04 aclnn 接口检视（fpa04-aclnn-review）

对用户指定的 aclnn 接口（如 aclnnChunkGatedDeltaRule）做 FP-A04 专项源码检视：先定位算子实现，再按五形态清单逐项核查，每个结论给出**文件 + 行号 + 推导链**证据，命中即出 Bug 卡，输出检视报告。**本模式特殊纪律：① 缺陷的表征恰恰是「什么都没发生」——不崩溃、不报错，错误以数值偏差形式静默流出，UT 数值断言可能全绿而线上 loss 不收敛；② `OP_LOGE` 不是「已处理」的证据——错误状态是否真正传出（错误码 / 状态位）才是判据；③ 卡片触发为关键词（`OP_LOGE|GRAPH_SUCCESS|return false`）——签名命中只是定位提示，静默形态须逐分支核控制流；④ 「静默出错」的最终判据是运行时输出值——静态立「错误路径可达且错误状态无法传出」，NaN / 超大值等数值后果需实测。**

## 0. 与相邻模式的边界

| 相邻模式 | 分工 |
|---|---|
| FP-A05（脏数据/数据踩踏） | **最易混淆项**：同为脏数据 / 未初始化数据被当作有效输入读入——A04 侧重「**不报错**」（错误分支吞掉错误状态），A05 侧重「**数据源本身脏**」（workspace 未清零、未初始化先读）。A04 命中的分支链下游若读脏数据，两卡连打 |
| FP-B03（迁移丢失防御） | 成因面：迁移丢失的防御逻辑被吞后，功能问题静默化——B03 管丢失过程，A04 管吞错形态 |
| FP-E01（golden 失配） | golden / UT 与错误实现共错时，静默缺陷不被测试暴露——核 A04 时同步核测试资产是否会把「静默错误」当期望值 |
| FP-B04 / FP-B06（拦截缺失） | 同为「该拦没拦」家族：B04 多为「响」面（SIGSEGV），B06 是空输入语义面（误拦/放过）；**未崩溃的**拦截缺失 / 吞错才落 A04——先核 B04/B06 再归 A04 |
| FP-G01（挂死） | 「不返回」vs「返回了但值错」——G01 是任务永不完成，A04 是带着错值正常返回 |
| FP-F02（日志误用） | F02 子型④「该报不报」是上报面的静默；A04 是**执行流**的静默——日志规范问题不改变执行结果 |

**症状反查定位**：无报错但输出 NaN / 超大值 / 全 0 → 首查错误分支的控制流；日志里有 `OP_LOGE` 但执行继续 → 截留点就在该分支；网络 loss 不收敛且无任何告警 → tiling 降级 / 部分失败未中断；同一输入两次结果不一致 → 并发 A06 一并核。

## 1. FP-A04 模式卡摘要（检视依据，源自本库 `patterns/FP-A/FP-A04.md`，v3.1）

- **编号 / 名称**：FP-A04 功能问题演变为精度静默故障 ｜ **类别**：精度 ｜ **风险**：高（S3×O3=9）｜ **状态**：活跃
- **适用声明头**（照抄卡片）：仓 All ｜ 侧别 All ｜ 载体 Tiling源码,Kernel源码 ｜ 触发 OP_LOGE|GRAPH_SUCCESS|return false ｜ 默认启用 true
- **skill 核查面**：侧别 All——skill 落地为 `op_host` 的 tiling / infershape 错误分支（形态①②③⑤）、`op_kernel` 的部分写入与全量读（形态④）、`op_api` 两段式的错误码语义（截留点）
- **故障机理**：错误分支吞掉返回值或输出部分结果而不报错，错误以数值偏差形式静默流出。**共性特征：错误分支不是返回错误码而是「静默早退 + 继续执行」。**
- **触发条件**：异常分支、tiling 不匹配时的降级路径、部分失败未中断。
- **典型表现**：静默出错数值、无报错。
- **源码审查映射点**：错误分支是否静默吞掉返回部分结果而非报错。
- **测试拦截建议**：错误注入用例（非法输入必须报错而非出数）；输出 NaN/inf 哨兵检查。
- **实证案例**：ops-math #3044 / #2867 / #5590（9.2.0-beta.2）reduction Group 模板 `rGroupCnt > rOuter` 产生空分组，对应核早退不写 workspace 行，Phase2 却以 `rGroupCnt` 全行 Reduce 把未写入的**脏 GM 数据**当 partial sum 读入，**不报错地**输出 NaN/超大值（data_compare、reduce_std_v2_update、bn_training_reduce、euclidean_norm、act_ulq_clamp_max_grad、act_ulq_clamp_min_grad 多算子同源；master 已由 cann/ops-math!5068 修复，issue 用于跟踪分支同步）；ops-transformer #3799 `chunk_gated_delta_rule_tiling.cpp:83-86` `GetPlatformInfo()` 空实现恒返回 `GRAPH_SUCCESS`，`InitCompileInfo()`（L64-81）出错仅 `OP_LOGE` 后 `return`，**错误状态无法传出**，后续 `SetBlockDim(0)` 进入未定义行为（关联 PR 8802）。**共性特征：错误分支不是返回错误码而是「静默早退 + 继续执行」，错误以数值偏差形式流出。**
- **关联**：FP-B03、FP-E01、FP-A05（同为脏数据/未初始化数据被当作有效输入读入，A04 侧重「不报错」，A05 侧重「数据源本身脏」）。

## 2. 检视输入与算子定位

**输入**：aclnn 接口名（必填，如 `aclnnChunkGatedDeltaRule`）；可选 ref（默认 master）、指定仓（默认自动定位）；可选现象描述（NaN / 超大值 / loss 不收敛 / 「有 OP_LOGE 但没报错」——用于症状反查）。

**接口名 → 算子目录换算**：去 `aclnn` 前缀 + 驼峰转下划线小写：
`aclnnChunkGatedDeltaRule → chunk_gated_delta_rule`、`aclnnReduceStdV2Update → reduce_std_v2_update`。

**仓定位顺序**（GitCode `cann` 组织，逐仓用目录列表确认）：`ops-nn` → `ops-math`（归约 / reduction 类高发——Group 模板族）→ `ops-transformer`（attention / mamba 类多阶段算子）→ `ops-cv`。**类目名不总与直觉一致**（如 reduce_std_v2_update 在 `math/`），以目录列表为准。FP-A04 高发面：多阶段 kernel（Stage1/Stage2 分文件、workspace 行传递）、带降级路径的 tiling、void 返回的初始化函数、带 `GetPlatformInfo` 类取数函数的 tiling 类。

**算子目录结构约定**（已验证示例 `cann/ops-transformer` → `attention/chunk_gated_delta_rule/`）：

```text
{类别}/{op_name}/
├── op_host/                  # *_tiling.cpp / *_infershape.cpp——错误分支控制流：形态①②③⑤ 主检视面
│   └── op_api/（或顶层 op_api/）  # aclnn_*.cpp——两段式错误码语义与截留点
├── op_kernel/                # 多阶段 kernel（arch22/ arch35/ 分文件）——部分写入/全量读：形态④
└── tests/ docs/
```

## 4. 静默错误五形态检视清单（每点：查什么 → 何处 → 命中判据）

对 `op_host` tiling / infershape、`op_kernel`、`op_api` 全部相关文件逐点核查，**每点先查命中面、再做反证排除**；同文件内的正确错误处理形态（`OP_CHECK_IF` + `return GRAPH_FAILED` 类）要记录为反证参照。

### 形态 ① void 初始化函数失败静默早退
- 查什么：返回类型为 `void` 的初始化 / 资源获取函数（`InitCompileInfo` 类命名）——失败分支 `OP_LOGE` 后**裸 `return`**，既无返回值也无成员状态位标记失败，调用链无从感知。
- 何处：`op_host` tiling 类的 `Init*` / `Get*Info` 成员函数。
- 命中判据：失败分支早退后，类内**无**任何可被后续流程检查的失败标记，且后续流程（SetBlockDim / 写 tiling data）仍会执行 ⇒ 命中（推导链：失败输入 → 早退 → 后续以默认值执行）。

### 形态 ② 恒返回成功的空 / 占位实现
- 查什么：`ge::graphStatus` 返回函数**无条件** `return ge::GRAPH_SUCCESS`（空实现 / 占位实现）——它所承诺的检查（如平台信息获取）实际不存在，失败不可能被发现。
- 何处：tiling 类的 `GetPlatformInfo` 类函数；对比函数名承诺的职责与函数体实际内容。
- 命中判据：函数体为空 / 恒真返回，且其结果被后续流程**当作「已检查」**依赖 ⇒ 命中。

### 形态 ③ 日志后无错误码 / 部分失败未中断
- 查什么：`OP_LOGE` 命中分支是否携带有效控制流——`return`（无值）/ 继续执行 / 只置局部标志但不传出，均属「打了日志 ≠ 处理了错误」；部分失败的循环体（某组 / 某块失败）是否中断整个执行。
- 何处：全部 `OP_LOGE` / `OP_LOGW` 命中分支；多分组 / 多 tile 循环内的失败处理。
- 命中判据：日志分支后执行流继续且无错误状态传出 ⇒ 命中。

### 形态 ④ kernel 部分写入 + 后续全量读
- 查什么：多阶段 kernel（Stage1 写 workspace 行、Stage2 读）——**条件早退的核不写自己那一份**，而读取端按**全部行数**（`rGroupCnt` 类全量计数）Reduce，把未写入的脏 GM 数据当 partial sum 读入，不报错地混入结果。
- 何处：`op_kernel` 分 stage 实现（arch22/ arch35/ 内 stage 文件）；写端的条件跳过 / 早退条件与读端的循环上界是否**同源**。
- 命中判据：写端跳过条件与读端行数计数不一致（`rGroupCnt > rOuter` 空分组类）⇒ 命中（实证样板 ops-math Group 模板族，master 已由 !5068 修复——检视时若已含修复记录为防护面，历史形态参照该实证）。
- 判读注意：空分组产生脏读属 A04（吞错）与 A05（数据源脏）连打点——按「读端未初始化数据」核 A05、按「写读计数不一致不报错」核 A04。

### 形态 ⑤ 降级路径不报错继续
- 查什么：tiling 不匹配 / 能力检查失败时的降级分支——降级后是否置可观测状态；降级输出与正常路径的差异是否有文档说明。
- 何处：`IsCapable` 返回 false 后的兜底路径、`GRAPH_PARAM_INVALID` 类回退分支。
- 命中判据：降级后无任何状态位 / 日志可区分，输出静默偏离正常路径 ⇒ 命中。

### 横切面：错误注入测试资产
- 查什么：测试资产是否有**错误注入用例**（非法输入必须报错而非出数）与输出 NaN/inf 哨兵检查（卡片拦截建议）——纯数值断言的用例集天然漏检静默型。
- 何处：`tests/` 用例清单（ut / st / pytest）。
- 命中判据：无错误注入类用例 + 存在静态命中的静默路径 ⇒ 记观察项（测试建设缺口）。

## 5. 检视流程

1. **定界**：换算 op 目录、确认所在仓与 ref；按用户现象（NaN / loss 不收敛 / 有日志无报错）反查优先形态。
2. **枚举**：目录列表列出 op_host（tiling + infershape）/ op_kernel（含 arch 子目录与 stage 分文件）/ op_api / tests 全部相关文件，产出文件清单。
3. **触发词扫描**：按 `OP_LOGE|OP_LOGW`、`return\s+ge::GRAPH_SUCCESS`、`void\s+\w+::(Init|Get)` 定位错误分支与初始化函数（本地仓用 grep；API 模式逐文件拉取后检查）。签名零命中时五形态清单仍须逐项核查——静默缺陷的定义就是「没有显式错误信号」。
4. **控制流逐分支核查**：对每个错误分支写出「入口状态 → 分支动作 → 退出后状态 → 后续流程感知」四行推导；正确形态（`OP_CHECK_IF` + `GRAPH_FAILED`）记录为反证参照。
5. **反证排除**：函数有返回值且携带失败 / 失败有状态位且被检查 / 降级可观测 → 明确写出反证理由。
6. **判定**：按第 7 节标准给出 命中 / 观察项 / 反证排除。
7. **GitCode 查重**（仅命中项）：issues API 按接口名 + `NaN|静默|精度|不收敛|error.*吞` 检索，逐条比对是否同机理；无同机理才立卡。
8. **业务可达性核查**（仅命中项）：判 B 等级、定业务影响类型、给处置建议；默认保守（无法证明不可达即记 B3），降档须附证据；B 不改 S×O 档位。
9. **出报告**：按第 8 节模板落盘；静态结论一律附错误注入 / 哨兵检查方案。

## 6. 风险定级（S×O）与业务影响评估（B 轴）

- **S**：S3（静默数值错误——精度损坏且无告警，线上以 loss 不收敛 / 结果偏差暴露，排查成本最高）；S2（降级未标注——行为偏离但可预期范围）。
- **O**：O3 = ≥2 条独立实证；O2 = 1 条独立实证；O1 = 仅静态扫描命中或团队笔记（实证 = 确认对应的 issue / PR，或经跨仓、跨分支核验确认的缺陷记录，同权计入）。静态推演命中且无实证默认 **O1**；升档须在报告中给出实证依据。
- **风险 = S×O**：≥6 高；3/4 中；1/2 低。FP-A04 基准：模式卡整体 S3×O3=9（高）；纯静态命中 S3×O1=3（中，暂定，实测后复评）。

### B 轴：业务影响评估（与 S×O 正交；报告层新增，不改卡片定级）

S×O 回答"多严重、多常见"，**不回答"真实业务能不能碰到"**。B 轴补这一问，只决定**修复优先级建议**，**不参与 S/O 取值、不改 S×O 档位与卡片元数据**。

**业务可达性（B）**——触发条件在真实负载中的可达程度：

| 等级 | 判据 | 证据要求 |
|---|---|---|
| B3 现实可达 | 主流框架/公开模型默认路径即可命中（如 PTA/torch_npu、vLLM、MindIE 常规调用） | 调用方或公开负载来源 |
| B2 条件可达 | 需特定 attr/dtype/shape 组合，业务中存在但非默认 | 该组合的业务来源 |
| B1 边界/不可达 | 需极端、超规格或非法参数（超出接口合理上限的 shape、退化/非法输入） | "为何不可达"的说明 |

- **默认保守**：无法证明不可达 → 记 **B3**；降为 B1/B2 必须附证据，**不得仅凭"业务应该不会这么用"**。
- 超规格参数是否算 B1 取决于**接口契约**：契约允许但业务不用 → B1；契约不允许（本应报错）→ 属校验缺失（FP-B04/B05 类），另行归属。

**业务影响类型**（命中后对用户可见结果的后果，用业务语言表述）：静默精度损失（模型效果下降 / loss 不收敛 / 偶发 NaN）｜ 任务失败中断（报错 / 崩溃 / 挂死）｜ 性能退化 ｜ 仅可观测性（日志 / 错误码 / 文档，不影响结果）。

**处置建议**（由两轴推导的报告结论，非新档位）：

| S×O \ B | B3 现实可达 | B2 条件可达 | B1 边界/不可达 |
|---|---|---|---|
| 高（≥6） | 尽快修 | 尽快修 | 排期修 |
| 中（3/4） | 尽快修 | 排期修 | 记录（业务难以触达） |
| 低（1/2） | 排期修 | 记录 | 记录 |

## 7. 判定标准与反误报原则

- **`OP_LOGE` 命中 ≠ 静默缺陷**：必须核对**命中后控制流**——有返回值携带失败、或有状态位被后续检查，即为反证；「日志 + 无状态传出 + 继续执行」三要素齐才命中。
- **三种判定**：
  - **命中**（可静态证缺陷路径）：五形态任一推导链完整（失败输入 → 早退/恒真/无中断 → 后续以默认或脏值执行 → 输出无告警）→ 立 Bug 卡；
  - **观察项**：数值后果（NaN/超大值）依赖运行时形态 → 记录并附错误注入方案，按 S3×O1 暂定；
  - **反证排除**：错误状态可传出且被检查 / 写读计数同源 / 降级可观测 → 写出反证理由（防护面证据）。
- **「测试全绿」不是反证**：静默型的定义就是数值断言等不到错误——UT/green 恰是本型漏检特征；测试资产核查只用于评估**拦截建设缺口**，不用于排除缺陷。
- **与 A05 连打**：读端把未初始化数据当有效输入时，先定 A05（数据源脏）还是 A04（写读不一致不报错）——以**第一个错误动作**为准：源头未清零归 A05，计数不一致归 A04；两者同时成立时连打两卡并交叉引用。
- **不臆造行号**：每条证据必须是实际读到的 文件:行号；引用实证样板时注明 issue 时点行号与本仓 HEAD 漂移。

### 判定纪律补充（v3.6）：非对称增减、证据等级与误判记录

**增减不对称**：允许追加候选（有据即可，错了可由用户排除）；**撤销或否决候选必须附 `[文件]:[行号] [代码行]` 负向证据**。无证据的「看起来没问题」一律记为「未核查」，不得计入反证排除，也不得据此下调等级——否决造成的漏报用户不可见、不可恢复。

- **证据等级**（Bug 卡必填）：`静态可证` = 推导链完整且触发输入可静态构造；`需实测确认` = 依赖运行时输入规模、设备行为或环境差异。标 `需实测确认` 的条目**不得以「命中」名义出卡**，按观察项记录并附实测用例。
- **Agent 误判记录**（Bug 卡必填）：本次被推翻的假设、推翻它的证据（`[文件]:[行号] [代码行]` 或实测输出）、判定标准是否随之修订；无推翻写「无」。
- **误判回流**：同类误判在 3 次检视中重复出现，登记至 `cases/misjudgments.jsonl`（字段见 `cases/README.md`），并在本模式判定标准中新增对应防线；守门 C19d 校验台账字段合法。

## 10. 能力边界与自检（v3.8）

### 能力边界

- **静态可证**：清单里能在源码内给出「`文件:行号` + 推导链」的部分，按第 7 节判据出卡。
- **需实测确认**：依赖运行时输入规模、设备行为或环境差异的结论，只能记观察项并附实测用例（证据等级见第 7 节）。
- **不覆盖**：本模式以外的机理（边界见第 0 节）与仓外框架侧行为；`TRIAGE.md` 只负责收敛候选，不构成判定依据。
- **找不到 ≠ 没有**：按清单未命中只说明「本轮未发现」，不得表述为「该算子无此缺陷」；抽样核查须在报告写明抽样口径。
