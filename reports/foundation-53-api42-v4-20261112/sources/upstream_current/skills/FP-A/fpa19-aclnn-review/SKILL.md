# FP-A19 aclnn 接口检视（fpa19-aclnn-review）

对用户指定的 aclnn 接口（如 aclnnRmsNormGrad）做 FP-A19 专项 tiling 覆盖审计：先定位算子实现，枚举全部 tiling 模板与分流阈值，再映射测试用例的 shape 分布，产出覆盖缺口清单与补齐建议；若盲区路径存在确定性 / 归约方式差异，升级为 Bug 卡。**本模式特殊纪律：① 检视对象不是「代码错」而是「**测不到**」——多模板分流本身正确也可能存在覆盖盲区，代码全对也可能立卡（覆盖缺口）；② 产出以「**模板清单 → 阈值区间 → 用例映射**」三表为核心，数值缺陷仅当路径差异（非确定归约等）被证实时才立 Bug 卡；③ 阈值表达式依赖平台常量（`vlFp32`、`aivCoreNum`、`UB_SIZE`），区间必须**按平台分别计算**——跨平台阈值不同是设计使然、不是缺陷，但盲区评估不按平台分算就会漏判；④ 卡片触发为关键词（`REGISTER_TILING_TEMPLATE|IsCapable`）——单模板算子（零命中）直接反证排除、记录结论，不强行立卡。**

## 0. 与相邻模式的边界

| 相邻模式 | 分工 |
|---|---|
| FP-A06（非确定性） | 新路径的非确定性正是 A06 的一个具体来源——A19 立缺口卡、A06 立非确定卡，同一发现可连打 |
| FP-A07（条件判断错误） | **最易混淆项**：阈值边界**写错** = A07（代码错）；阈值写对但**没测到** = A19（覆盖缺口）。核 A19 时同步验算 A07——盲区路径里的边界错误更难发现 |
| FP-A08（切块粒度致归约分组不同） | A08 是粒度参数正确但归约分组后果；A19 的路径差异维度之一（归约方式不同）与 A08 同源，以「多模板分流」为前提归 A19 |
| FP-B02（阈值依赖芯片核数跨平台不一致） | B02 管**参数来源**（平台常量致同 shape 跨平台行为差）；A19 管**覆盖**（测试 shape 分布没盖住区间）——同 shape 跨平台走不同路径时先核 B02 再核 A19 |
| FP-E01（golden 失配） | 同属「测不到」家族：E01 是期望值**错了**，A19 是路径**没被执行**——补用例前先修 E01，否则补的用例与错误期望共错 |
| FP-B06 子型③（平台分支不对称） | arch22 / regbase 双路径是 A19 的两路径特例——空输入语义上的覆盖与修复单侧 gate，与 A19 的平台维重叠 |

**症状反查定位**：测试全绿但线上特定 shape 精度异常 / 结果不确定 → 首查该 shape 命中的模板路径是否在用例矩阵内；同 shape 在 A 平台与 B 平台结果不同 → 平台常量参与阈值（B02 + A19 连打）；版本升级新增 `*_big_m_tiling.cpp` / `*_tail_tiling.cpp` 类文件后线上出问题 → 新路径 0 覆盖；两次运行结果不一致 → 盲区路径非确定（A06 连打）。

## 1. FP-A19 模式卡摘要（检视依据，源自本库 `patterns/FP-A/FP-A19.md`，v3.1）

- **编号 / 名称**：FP-A19 同算子多 tiling 路径覆盖盲区（新增路径未纳入测试矩阵）｜ **类别**：精度 ｜ **风险**：高（S3×O2=6）｜ **状态**：活跃
- **适用声明头**（照抄卡片）：仓 All ｜ 侧别 Tiling,Kernel ｜ 载体 Tiling源码,Kernel源码 ｜ 触发 REGISTER_TILING_TEMPLATE|IsCapable ｜ 默认启用 true
- **skill 核查面**：侧别 Tiling,Kernel——skill 落地为 `op_host` 的模板注册与 `IsCapable` 阈值（映射点①②③）、`op_kernel` 各路径的归约方式差异（映射点④）、`tests/` 用例 shape 分布（覆盖映射的输入）、`*_tiling.h` 的 tilingKey 注册面（跨平台同 key 核对）
- **故障机理**：算子在同一平台上注册**多条 tiling 模板**（按 `REGISTER_TILING_TEMPLATE` 的优先级数字决定尝试顺序），各模板由其 `IsCapable()` 的 shape 阈值分流。新版本引入新模板时，**两条路径可能一条确定、一条非确定**，或归约实现不同（核内二叉树折叠 vs 跨核两段归约）。若测试用例的 shape 全部落在旧路径一侧，新路径**永远不被执行**，缺陷长期潜伏。
- **触发条件**：算子存在按 shape 阈值分流的多 tiling 模板；版本升级新增 / 修改了其中一条模板；测试 shape 分布集中在单一侧；分流阈值依赖平台参数（`vlFp32`、`aivCoreNum`、`UB_SIZE`）故**跨平台阈值不同**。
- **典型表现**：新路径在线上被特定 shape 触发后精度异常 / 结果不确定，而测试全绿；同一 shape 在 A 平台走路径 1、B 平台走路径 2 而表现不同，跨代际对比困难。
- **源码审查映射点**：① `REGISTER_TILING_TEMPLATE(op, Cls, PRIORITY)` 的**优先级数字**（越小越先尝试）；② 各模板 `IsCapable()` 的**全部阈值表达式**及其中引用的平台常量；③ 模板内 `DoOpTiling()` 里**二次能力检查**（不通过会返回 `GRAPH_PARAM_INVALID` 回退，形成隐式第三态）；④ 各路径 kernel 侧的归约方式差异（是否有 `SyncAll()` / 跨核 `ReduceSum` / 原子加）。
- **检测签名**：`git grep -n "REGISTER_TILING_TEMPLATE"` 定位多模板算子；对比 `IsCapable()` 中的 `return false` 分支收集阈值；跨分支 `diff` 新增的 `*_big_m_tiling.cpp` / `*_tail_tiling.cpp` 类文件。
- **测试拦截建议**：**按阈值两侧构造对照用例**（阈值 ±1、恰好命中、恰好不命中），而非随机 shape；建立「模板 → 触发 shape 区间 → 覆盖用例」映射表并纳入 CI；版本升级后**对比新旧分支的模板清单**，新增模板必须补齐用例；同 shape 跨平台验证是否命中同一 `tilingKey`。
- **实证案例**：ops-nn `norm/rms_norm_grad` 跨分支核验（2026-09-13）——`RmsNormGradBigMTiling`（优先级 100）在 **9.1.0 才引入**，8.5.0 无此文件；其 `IsCapable()` 要求 `rows_ >= 64×aivCoreNum/2`（950 上即 **M ≥ 2048**）且 `rows_ >= 2×cols_`。该路径的 dgamma 采用 `SyncAll()` + 0 核跨核 `ReduceSum<RA>`（非确定），而常规 `RmsNormGradRegbaseTiling`（优先级 200）按列切分、核间无交叉归约（数值确定）。**若测试 shape 的 M 全部 < 2048，则 big_m 路径 0 覆盖**。另：`9.1.0 → 9.2.0` 该文件 diff 全为格式化改动，阈值自引入起未变——说明**阈值稳定但版本引入点明确**，覆盖缺口不会随版本自然消失。
- **关联**：FP-A06（新路径的非确定性正是 A06 的一个具体来源）、FP-A07（阈值边界写错 = A07）、FP-A08（切块粒度致归约分组不同）、FP-B02（阈值依赖芯片核数、跨平台不一致）。

## 2. 检视输入与算子定位

**输入**：aclnn 接口名（必填，如 `aclnnRmsNormGrad`）；可选 ref（默认 master）与历史版本 ref（版本轴核对用，如引入点比对）；可选指定仓（默认自动定位）；可选平台信息（`aivCoreNum` / `vlFp32` 取值——阈值区间按平台实算的关键输入）；可选测试用例来源（`tests/` 目录或用户提供的用例清单）。

**接口名 → 算子目录换算**：去 `aclnn` 前缀 + 驼峰转下划线小写：
`aclnnRmsNormGrad → norm/rms_norm_grad`、`aclnnMoeInitRoutingV4 → moe/moe_init_routing_v4`。

**仓定位顺序**（GitCode `cann` 组织，逐仓用目录列表确认）：`ops-nn`（norm/matmul/index 类——多模板高发）→ `ops-transformer`（attention/moe 类大模板）→ `ops-math` → `ops-cv`。FP-A19 高发面：同目录下多个 `*_tiling*.cpp` 文件（`*_big_m_tiling.cpp` / `*_tail_tiling.cpp` / `*_empty_tiling.cpp` 类命名）、带 `IsCapable` 阈值分流的算子、近期版本新增过 tiling 文件的算子。

**算子目录结构约定**（已验证示例 `cann/ops-nn` → `norm/rms_norm_grad/`）：

```text
{类别}/{op_name}/
├── op_host/                  # 全部 *_tiling*.cpp（多模板）+ *_tiling.h（tilingKey 注册面）
│   └── （arch22/ arch35/）   # 部分算子按平台分目录
├── op_kernel/                # 各路径归约方式差异——arch35/ 内按模板分文件（*_dgamma*.h 类）
└── tests/                    # 用例 shape 分布——覆盖映射的核心输入
```

| 单文件内容 | `GET https://api.gitcode.com/api/v5/repos/cann/{repo}/raw/{path}?ref={ref}` |
| Issue 查重 | `GET https://api.gitcode.com/api/v5/repos/cann/{repo}/issues?q={关键词}` |

**已实测不可用（截至 2026-09 实测）**：`https://gitcode.com/{repo}/raw/{sha}/{path}`、`https://raw.gitcode.com/...` → 403 或拦截页；端点策略如有变化可复测。若本地已有算子仓克隆，优先直接读本地文件，行号证据以本地 HEAD 为准并记录 commit。**本模式特有取数限制**：① 版本轴核对需**多个 ref**（引入点比对：旧版本目录列表 + 新版本文件 diff）——API 模式逐 ref 拉取，本地克隆用 `git diff <old>..<new>`；② 阈值区间含平台常量（`aivCoreNum` / `vlFp32`），区间计算须以目标平台的实测常量代入，跨平台各算一套；③ 覆盖缺口的数值后果（精度异常 / 非确定）需按区间构造 shape 实测——静态审计只立「0 覆盖」缺口，不立「必然出错」。

## 4. 多路径覆盖审计清单（每点：查什么 → 何处 → 命中判据）

对 `op_host` 全部 tiling 文件、`*_tiling.h`、`op_kernel` 各路径、`tests/` 逐点核查，**每点先查命中面、再做反证排除**；单模板算子（`REGISTER_TILING_TEMPLATE` 唯一或零命中）在清单① 后即可整体反证排除并记录。

### ① 模板清单与优先级（映射点①）
- 查什么：`REGISTER_TILING_TEMPLATE(op, Cls, PRIORITY)` 全部注册行——每条模板类名、优先级数字（**越小越先尝试**）；优先级与尝试顺序的语义核对。
- 何处：`op_host` 全部 `*_tiling*.cpp` 文件尾部的注册行。
- 命中判据：注册行 ≥2 条 ⇒ 进入多模板审计；仅 1 条或零命中 ⇒ 反证排除（记录「单模板，无分流盲区面」结论）。

### ② 阈值表达式全量提取（映射点②）
- 查什么：每条模板 `IsCapable()` 的**全部** `return false` / `return true` 分支——逐条阈值表达式、其中引用的平台常量（`vlFp32` / `aivCoreNum` / `UB_SIZE`）；多条件表达式（`||` / `&&`）逐项拆解。
- 何处：各模板 tiling 文件的 `IsCapable` 函数体。
- 命中判据：为每条模板产出「shape 约束区间」（按平台常量实算），区间之间无缝隙、无意外重叠 ⇒ 合格；存在 shape 空间中**无模板可接**（尝试链全部 false）的缝隙 → 隐式第三态风险，记观察项。

### ③ 二次能力检查与隐式第三态（映射点③）
- 查什么：模板内 `DoOpTiling()` 的二次能力检查——不通过返回 `GRAPH_PARAM_INVALID` **回退**的分支：回退后落点（下一条模板？直接失败？）；回退路径的用例覆盖。
- 何处：各模板 `DoOpTiling` 及能力复查函数。
- 命中判据：回退形成设计外的第三态（既非路径 A 也非路径 B）且无对应用例 ⇒ 记观察项。

### ④ 各路径归约方式差异（映射点④）
- 查什么：每条模板对应 kernel 的**归约实现**——`SyncAll()` / 跨核 `ReduceSum<RA>` / 原子加（非确定）vs 核内二叉树折叠 / 无跨核交互（确定）；同一输出在不同路径下的确定性标注是否一致。
- 何处：`op_kernel` 按模板分文件的头文件（`arch35/*_dgamma*.h` 类）；跨核同步原语与归约调用点。
- 命中判据：两条路径对**同一输出**的确定性不同（一条确定一条非确定）⇒ 高价值发现（A06 连打点）——盲区一旦被触发即不可复现类风险。

### ⑤ 测试 shape 分布映射（覆盖核心）
- 查什么：`tests/` 全部用例（ut / st / pytest 的输入生成脚本）的 shape 清单 → 逐条代入各模板区间 → 产出「模板 → 触发 shape 区间 → 覆盖用例」三表；区间内**用例数 0** 的模板即覆盖缺口。
- 何处：`tests/assets/*.py`（输入生成）、ut/st 用例清单、用户提供的用例集。
- 命中判据：任一模板（或模板在某平台常量下的区间）用例数 = 0 ⇒ 立覆盖缺口卡（这不是代码缺陷，是测试矩阵缺陷）。

### ⑥ 版本轴核对
- 查什么：新增 / 修改模板的**引入版本**（旧 ref 目录无此文件、新 ref 有）；引入以来阈值表达式的 diff（变更即盲区扩大信号）；引入版本与测试矩阵更新是否同步（实证：阈值自引入未变而覆盖缺口持续存在）。
- 何处：多 ref 的目录列表 / `git diff <old>..<new> -- '*_tiling*.cpp'`。
- 命中判据：版本升级引入新模板而用例矩阵未同步补齐 ⇒ 命中（实证样板即此形态）。

### ⑦ tilingKey 注册面与跨平台一致性
- 查什么：`*_tiling.h` 的 `REGISTER_TILING_DATA_CLASS` 注册行——每条模板的 key 编号族；同 shape 跨平台是否命中**同一 tilingKey**（卡片拦截建议的核对面）；key 注册与模板类是否一一对应（key 有注册而无模板承接 → 死 key）。
- 何处：`op_host/*_tiling.h`。
- 命中判据：key 族与模板清单不对应，或跨平台同 shape 命中不同 key（超出平台常量导致的合理差异）⇒ 记观察项 / 命中。

## 5. 检视流程

1. **定界**：换算 op 目录、确认所在仓与 ref；确认目标平台常量来源（用户给定或按 950 类典型值计算并注明）；收集测试用例来源。
2. **枚举**：目录列表列出全部 `*_tiling*.cpp` / `*_tiling.h` / `op_kernel` 各路径 / `tests`，产出文件清单。
3. **触发词扫描**：按 `REGISTER_TILING_TEMPLATE`、`IsCapable`、`SyncAll|ReduceSum|atomic`、`REGISTER_TILING_DATA_CLASS` 定位注册行、阈值、归约差异（本地仓用 grep；API 模式逐文件拉取后检查）。零命中 → 单路径结论、整体反证排除。
4. **三表构建**：模板清单表（类名 / 优先级 / 文件）→ 阈值区间表（表达式 / 平台常量代入值 / 实算区间）→ 用例映射表（用例 shape / 命中模板 / 命中区间）。
5. **清单逐项核查**：按第 4 节 ①~⑦ 逐点记录证据（文件:行号）；④ 的确定性差异与 ⑤ 的 0 覆盖合并为高价值发现。
6. **版本轴核对**（多模板时必做）：引入版本 diff、阈值稳定性、用例矩阵同步性。
7. **判定**：按第 7 节标准给出 覆盖缺口 / 命中（路径差异缺陷）/ 反证排除。
8. **GitCode 查重**（仅命中项）：issues API 按接口名 + `精度|不确定|两次.*不一致|tiling` 检索，逐条比对是否同机理；无同机理才立卡。
9. **业务可达性核查**（仅命中项）：判 B 等级、定业务影响类型、给处置建议；默认保守（无法证明不可达即记 B3），降档须附证据；B 不改 S×O 档位。
10. **出报告**：按第 8 节模板落盘；三表为报告主体，补齐建议按「阈值 ±1 / 恰好命中 / 恰好不命中」生成对照用例清单。

## 6. 风险定级（S×O）与业务影响评估（B 轴）

- **S**：S3（盲区路径被线上 shape 触发后精度异常 / 结果不确定）；S2（仅确定性未标注——比对策略选错风险）。
- **O**：O3 = ≥2 条独立实证；O2 = 1 条独立实证；O1 = 仅静态扫描命中或团队笔记（实证 = 确认对应的 issue / PR，或经跨仓、跨分支核验确认的缺陷记录，同权计入）。静态推演命中且无实证默认 **O1**；升档须在报告中给出实证依据。覆盖缺口本身为**测试建设项**（不按缺陷定级）；缺口路径存在确定性差异时按 S3×O1=3（中，暂定）立卡，实测精度异常后复评。
- **风险 = S×O**：≥6 高；3/4 中；1/2 低。FP-A19 基准：模式卡整体 S3×O2=6（高）。

### B 轴：业务影响评估（与 S×O 正交；报告层新增，不改卡片定级）

S×O 回答"多严重、多常见"，**不回答"真实业务能不能碰到"**。B 轴补这一问，只决定**修复优先级建议**，**不参与 S/O 取值、不改 S×O 档位与卡片元数据**。

**业务可达性（B）**——触发条件在真实负载中的可达程度：

| 等级 | 判据 | 证据要求 |
|---|---|---|
| B3 现实可达 | 主流框架/公开模型默认路径即可命中（如 PTA/torch_npu、vLLM、MindIE 常规调用） | 调用方或公开负载来源 |
| B2 条件可达 | 需特定 attr/dtype/shape 组合，业务中存在但非默认 | 该组合的业务来源 |
| B1 边界/不可达 | 需极端、超规格或非法参数（超出接口合理上限的 shape、退化/非法输入） | "为何不可达"的说明 |

- **默认保守**：无法证明不可达 → 记 **B3**；降为 B1/B2 必须附证据，**不得仅凭"业务应该不会这么用"**。
- 超规格参数是否算 B1 取决于**接口契约**：契约允许但业务不用 → B1；契约不允许（本应报错）→ 属校验缺失（FP-B04/B05 类），另行归属。

**业务影响类型**（命中后对用户可见结果的后果，用业务语言表述）：静默精度损失（模型效果下降 / loss 不收敛 / 偶发 NaN）｜ 任务失败中断（报错 / 崩溃 / 挂死）｜ 性能退化 ｜ 仅可观测性（日志 / 错误码 / 文档，不影响结果）。

**处置建议**（由两轴推导的报告结论，非新档位）：

| S×O \ B | B3 现实可达 | B2 条件可达 | B1 边界/不可达 |
|---|---|---|---|
| 高（≥6） | 尽快修 | 尽快修 | 排期修 |
| 中（3/4） | 尽快修 | 排期修 | 记录（业务难以触达） |
| 低（1/2） | 排期修 | 记录 | 记录 |

## 7. 判定标准与反误报原则

- **三种判定**：
  - **覆盖缺口**（测试矩阵缺陷）：三表证明某模板区间用例数 = 0 ⇒ 立缺口卡（含平台分算结果）；**这不是代码 Bug**，产出为补齐建议而非修复方案；
  - **命中**（路径差异缺陷）：盲区路径与主路径对同一输出的**确定性 / 归约方式不同**（映射点④ 证实的），且确定性标注未区分 ⇒ 立 Bug 卡（A06 连打）；
  - **反证排除**：单模板；或多模板但三表全覆盖；或跨平台差异完全由平台常量解释且各平台分别全覆盖 → 写出反证理由。
- **「测试全绿」不是反证**——恰是本型的识别特征（盲区路径根本没被执行）；同理「线上没出问题」也不是，缺口是**潜伏态**。
- **跨平台阈值不同不是缺陷**：`aivCoreNum` 参与阈值是设计使然——判定时按平台**分别**计算区间、分别判覆盖；只在其导致「某平台整条路径 0 覆盖」时立缺口卡。
- **不把「新增模板」当缺陷**：新增模板本身是正常演进，命中条件是「新增后未同步补用例」；版本轴核对给出引入点即可，不评价设计本身。
- **不臆造行号**：每条证据必须是实际读到的 文件:行号；引用实证样板时同样给出路径与行号。

### 判定纪律补充（v3.6）：非对称增减、证据等级与误判记录

**增减不对称**：允许追加候选（有据即可，错了可由用户排除）；**撤销或否决候选必须附 `[文件]:[行号] [代码行]` 负向证据**。无证据的「看起来没问题」一律记为「未核查」，不得计入反证排除，也不得据此下调等级——否决造成的漏报用户不可见、不可恢复。

- **证据等级**（Bug 卡必填）：`静态可证` = 推导链完整且触发输入可静态构造；`需实测确认` = 依赖运行时输入规模、设备行为或环境差异。标 `需实测确认` 的条目**不得以「命中」名义出卡**，按观察项记录并附实测用例。
- **Agent 误判记录**（Bug 卡必填）：本次被推翻的假设、推翻它的证据（`[文件]:[行号] [代码行]` 或实测输出）、判定标准是否随之修订；无推翻写「无」。
- **误判回流**：同类误判在 3 次检视中重复出现，登记至 `cases/misjudgments.jsonl`（字段见 `cases/README.md`），并在本模式判定标准中新增对应防线；守门 C19d 校验台账字段合法。

## 11. 已知缺陷案例库：触发条件 / 根因 / 修复范式 / 针对性深挖（v5.1）

> 本节把本型**已确认缺陷**拆到「触发条件 → 根因（具体路径）→ 修复范式（✅ 正确代码）→ 针对性发现步骤 → 最小复现锚」的代码级颗粒度。
> 修复范式为**正确形态示意**；路径引用取自卡片实证，行号以被检仓本地 HEAD 为准，**不得臆造**。

### 案例 1｜新增 big_m 模板阈值高、测试 shape 全落旧路径侧致 0 覆盖 —— rms_norm_grad 跨分支核验（2026-09-13）

- **触发条件**：需同时 `rows_ >= 64×aivCoreNum/2`（950 上即 M ≥ 2048）且 `rows_ >= 2×cols_` 才入 big_m 路径；而用例矩阵 M 全部 < 2048。
- **根因（具体路径）**：`RmsNormGradBigMTiling`（优先级 100）**9.1.0 才引入**（8.5.0 无此文件）→ `IsCapable()` 阈值只有大 M 可入 → 测试 shape 分布未随引入同步补齐 → big_m 路径**永远不被执行**、缺陷潜伏；9.1.0→9.2.0 该文件 diff 全为格式化、阈值自引入未变 → 缺口不随版本自然消失。
- **修复范式（✅，示意）**：

```cpp
// ❌ 旧用例矩阵：M 全部 < 2048 → big_m 路径 0 覆盖
{/* M=1024, N=512 */}, {/* M=1024, N=1024 */}
// ✅ 按阈值两侧补对照用例（恰好命中 / 恰好不命中）
{/* M=2047 */}, {/* M=2048 */}, {/* M=2049 */}
{/* rows_ == 2*cols_ */}, {/* rows_ == 2*cols_ - 1 */}
```

- **针对性发现（可执行）**：① `git grep -n "REGISTER_TILING_TEMPLATE"` 列出全部模板与优先级（数字越小越先尝试）；② 提取各 `IsCapable()` 的 `return false` 阈值表达式、代入平台常量实算区间；③ 对照 `tests/` 用例 shape 分布，任一模板区间用例数 = 0 即缺口。
- **最小复现锚**：M=2047 与 M=2048 各跑一次，确认命中模板由 `RmsNormGradRegbaseTiling` 切到 `RmsNormGradBigMTiling`（tilingKey 7000 族 → 9000 族）。
- **实证**：跨分支核验 2026-09-13（无 issue）；`rms_norm_grad_regbase_big_m_tiling.cpp:253` 注册优先级 100、`:34` `MFACTOR_DEFAULT = 64`、`:37-50` `IsCapable()`；对照 `rms_norm_grad_regbase_tiling.cpp:416` 优先级 200 兜底、`:246` `IsCapable(){ return true; }`。

### 案例 2｜模板二次能力检查回退形成隐式第三态 —— 映射点③

- **触发条件**：shape 已通过 `IsCapable()` 阈值进入模板，但模板内 `DoOpTiling()` 的**二次能力检查**不通过。
- **根因（具体路径）**：外层 `IsCapable()` 放行 → `DoOpTiling()` 二次检查返回 `GRAPH_PARAM_INVALID` **回退** → 落点既非路径 A 也非路径 B（隐式第三态）→ 该落点无用例覆盖。
- **修复范式（✅，示意）**：二次检查不通过时显式 `return GRAPH_PARAM_INVALID`（回退语义明确），并把该 shape 条件前移到 `IsCapable()` 拦截，使回退分支不可达。
- **针对性发现（可执行）**：① 逐模板搜索 `DoOpTiling` 内 `GRAPH_PARAM_INVALID` 返回点；② 判定回退落点（下一条模板 / 直接失败）；③ 检查该落点是否有用例覆盖。
- **最小复现锚**：构造「`IsCapable()` 通过但 `DoOpTiling` 二次检查失败」的 shape，观察回退后实际执行的模板 / 失败码。
- **实证**：映射点③（模式卡「源码审查映射点」），无 issue 实证。

### 案例 3｜盲区路径与主路径归约方式不同、确定性标注未区分 —— 映射点④（连打 FP-A06）

- **触发条件**：同一输出（`dgamma`）在 big_m 路径与 regbase 路径下走不同归约实现。
- **根因（具体路径）**：big_m `dgamma` 用 `SyncAll()` + 0 核跨核 `ReduceSum<RA>`（**非确定**）→ 常规 `dgamma` 核间无交叉归约、核内折叠（**数值确定**）→ 两条路径对同一输出确定性不同而文档 / 测试未按路径区分 → 盲区一旦被触发即不可复现类风险。
- **修复范式（✅，示意）**：

```cpp
// ❌ 对同一输出在两条路径下都做 bitwise 比对
// ✅ 按路径分级：big_m 容差并标注触发 shape 区间；regbase bitwise 看护
torch.equal(dgamma, golden)                 // regbase：数值确定 → bitwise
torch.allclose(dgamma, golden, tol)         // big_m：非确定 → 容差 + 标注 M ≥ 阈值区间
```

- **针对性发现（可执行）**：① `git grep -n "SyncAll\|ReduceSum\|atomic"` 定位各路径归约调用点；② 对照同一输出在两条路径下的原语（核内 vs 跨核）；③ 核对该输出的确定性标注是否按路径区分。
- **最小复现锚**：同输入在 M<2048 与 M≥2048 各跑两次，比对 big_m 路径两次结果是否 bit 不等。
- **实证**：跨分支核验 2026-09-13；`op_kernel/arch35/rms_norm_grad_regbase_dgamma_big_m.h:103` `SyncAll()`、`:106-108` 非零核早退、`:199` `ReduceSum<float,...,RA,true>`；对照 `rms_norm_grad_regbase_dgamma.h:138` `VFBinaryReduceSumWithoutTail`。

### 案例 4｜阈值含平台常量、同 shape 跨平台走不同路径 —— 触发条件（连打 FP-B02）

- **触发条件**：`IsCapable()` 阈值引用 `vlFp32` / `aivCoreNum` / `UB_SIZE`，故同一 shape 在 A 平台走路径 1、B 平台走路径 2。
- **根因（具体路径）**：`rows_ >= 64×aivCoreNum/2` 与 `cols_ > vlFp32×aivCoreNum/2` 含平台常量 → 阈值**按平台不同** → 同 shape 跨平台命中模板不同（tilingKey 7000 族 vs 9000 族）→ 覆盖评估不按平台分算即漏判。
- **修复范式（✅，示意）**：覆盖评估**按平台分别**算区间、分别判覆盖；同 shape 跨平台校验是否命中同一 tilingKey（平台常量导致的合理差异除外）。
- **针对性发现（可执行）**：① 提取阈值中全部平台常量并取目标平台实值；② 各平台各算一套区间；③ 仅当「某平台整条路径 0 覆盖」时立缺口卡（阈值本身跨平台不同不是缺陷）。
