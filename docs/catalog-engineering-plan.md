# 从手工整理到模式库草案工具

## 2026-11-06 优化方案：连续执行、独立上下文与真实页面采集

本节记录 0.1.11 实施方案，基线为 0.1.10 / `3c136fe1dc3ed5a62e9522cea52060eba7bab1b0`。现已接入连续驱动、冻结目标范围、独立任务上下文、页面观察、语义搜索轨迹及资源去重；实际验收与剩余现场事项以 VALIDATION.md 和 integration/OPENCODE_HANDOFF.md 为准。以下优先于旧方案，不表示现场 OpenChamber 已接通。继续仅支持结构化 XLSX，沿用原账本、分段摘要、文件合同和最终单份 XLSX，不新增网站/模型客户端。

### 已核实的问题与需要纠正的解释

1. 代码没有“每 10 条申请继续”的限制。`xlsx-workflow drive` 已可自动领取任务、调用配置的外部 Agent 命令、提交结果和导出；但它不是已经配置完成的现场 OpenCode 子会话/Edge 执行器。不能把通用 argv 适配器当成现场已经联通，也不能把依赖 Agent 的判断说成必须由用户逐条操作。
2. 当前驱动串行执行，任意一次 Agent/提交错误会中断整轮。纯内存复现中，两项任务的第一项模拟超时，第二项未执行。默认命令超时 300 秒，CLI 未按任务类型配置超时。这是需要修复的执行问题。
3. 正常库映射不要求人工 ACCEPT，也不要求先有事件组。代码允许满足同事件、直接根因支持且无冲突的独立 case 自动映射；事件组合并另需明确确认。资料事实整理、同事件判断、模式候选、正式入库分开处理。
4. 当前工作流默认读取整个 run，没有冻结目标 case 子集。只在报告中过滤目标记录，会使任务、预算与待办继续混入其他来源。附件中的现场数量尚未在本机核实。
5. 真正空正文不能声明 COMPLETE；但纯内存核查确认，仅标题或简短目录仍能通过 body=COMPLETE 的机械检查，并可能被视为可用 Wiki。现有登录页识别不能代替页面采集质量检查。尚未取得现场七页的浏览器观察，不能判定它们均由搜索不匹配造成。
6. 约 16K 字符的摘要分组、整请求预算、缺组不汇总已经存在；子 Agent 只能隔离会话历史，不能解决单个请求本身超限。比较可能仍携带大量摘要和被引段落，后续请求仍可能 INPUT_TOO_LARGE。
7. 同 URL 抓取、同快照摘要、work_id 去重已有基础，但 URL 的 query/fragment 当前保留，PR 本体与讨论锚点等可能重复采集。相同链接不能自动证明相同客户事件；共享页面的不同子问题不能误去重。
8. 摘要变化后旧 compare 失效是正确门禁，不能重绑旧答案哈希。附件所述直接写 store 的七条结果需现场只读核查，不能据此视为通过了原提交合同。另需测试并收紧当前快照更新时将同 run 全部 catalog 标旧的失效粒度。

本轮只读核查实际执行 65 项针对性回归：工作流 11 项、输入预算 15 项、证据计划 39 项，均通过；另做失败隔离与标题/目录页的纯内存行为复现。此前 429 项完整回归是上一轮结果，不冒充本次现场 232 条核验。未改现场 state。

### 目标执行方式

```text
一次指定目标 XLSX/目标 case 集合 + 冻结原始模式库 + 本轮预算
  → 程序冻结范围、查已有资源/摘要/工作结果
  → 持续领取依赖就绪任务
      → Edge 采集队列：原 Wiki / Wiki 检查 / 其他原链 / 必要搜索
      → 独立语义 worker：摘要组 → work_id 事实对照 → 当前库比较/草案
  → 主协调器验证响应并写入现有账本
  → 自动继续，直到目标均有处理结论或明确阻塞且没有可执行工作
  → 单份 故障整理及模式库建议.xlsx
```

授权整批处理后，每 10 条只是内部进度刻度，不是用户确认点。主会话只持有任务 ID、状态、进度和产物位置，不累计全部正文或所有子 Agent 答案。登录、真实归属争议及需要用户选择的分组才交接用户；一般未知字段、正常来源关系和库比较不例行请示。

### 按功能拆分实施

| 功能 | 程序负责 | Agent / 现场负责 | 最小修改位置 |
| --- | --- | --- | --- |
| 目标范围 | 冻结 selected_case_ids、输入 hash、库 identity；贯穿计划、任务、校验、统计、导出 | 恢复选择依据，不自行扩大整批 | xlsx_workflow / pipeline / evidence_plan / 报告 |
| 持续执行协调器 | 依赖就绪派发、独立尝试、有限重试、错误隔离、续跑和唯一提交 | 每项工作执行到底，返回合法响应 | xlsx_workflow / agent_adapter / CLI |
| OpenCode 执行适配 | 传 request/response 路径、kind、执行者与预算；核对真实服务/项目和工具能力 | 使用现场 OpenCode 独立子会话；模型服务仍由 OpenCode 管理 | integration 项目模板及现场适配入口 |
| Edge 页面采集 | 按站点管理登录等待与任务恢复，保存页面观察 | 在用户现有 Edge 会话读页面；用户手动完成登录 | 采集合同、wiki_checks、现场适配 |
| 语义搜索规划 | 保存实际字段依据、搜索尝试、范围和停止条件 | 提取事实、生成查询变体、读候选并判断相关性 | 搜索任务合同 / prompts / wiki_checks |
| 上下文控制 | 复用分组，检查最终请求，保留覆盖范围；只下发当前必要材料 | 一个任务/摘要组独立上下文，检查引用和反证 | pipeline / bridge / prompts / input_budget |
| 硬证据与工作去重 | 平台资源键、快照、work_id、输入和策略贯穿执行；只失效受影响依赖 | 区分同资源、同子问题和同事件 | store / evidence_plan / 调度及统计 |

先实现一个主协调器，SQLite 由它单点写入。子 Agent 只读本任务及资料文件，写自己的响应文件；不让多个浏览器子 Agent 争抢 Edge，不引入分布式队列或第二套状态库。

### 独立子 Agent 与连续推进

- 一个必要工作使用一个独立上下文，采用小型 worker 池，建议先从 2 个语义 worker 开始，配置允许扩至 4 个。不是同时创建 232 个长期会话。
- 抓取按唯一资源派发；摘要按 snapshot_id + summary_group 派发；比较按 work_id 派发；模式比较按 case 或已确认且技术输入相同的事件组派发。同份 Wiki 不因引用行多而重复摘要。
- Edge 交互队列默认并发 1；已经采集的正文可由语义 worker 并行处理。子 Agent 的浏览器权限必须实测，不能假定继承。
- 保留同一资料所有摘要组齐备才生成完整摘要。该资料完成即可启动对应比较，不等待全部目标摘要完成；草案也改为当前 case 就绪后生成，移除无关任务的全批屏障。
- 一项超时、无效 JSON、引文错误或网络失败，只影响该项及其下游；其余就绪工作继续。重试次数和各类超时可配置，保留旧尝试；确定阻塞不无限重试。
- 主协调器管理唯一执行身份及恢复。中断后复用有效结果，不重复派发；过期请求领取新版本，重新核验后提交，不改旧响应身份、不直接写 store。
- 终态区分全部已处理、部分明确阻塞、等待登录和无进展等原因。无新任务不等于根因或覆盖全部已确认；受阻项保留在最终 XLSX。

### Wiki 空页与 Edge 登录

采集 Agent 首先记录实际 requested_url、final_url、页面标题、可见正文区域、采集时间及工具观察。页面诊断作为现有证据/尝试的元数据，至少区分正文、目录/索引、仅标题、登录/权限页、未完成渲染、提取失败、不相关候选及原记录不足；不凭字符数机械判断。

| 实际观察 | 后续动作 |
| --- | --- |
| 需要登录 | 站点级暂停相关采集，集中向用户交接一次 Edge 登录；登录后验证正文可读并恢复受影响任务。其他站点及纯文本任务继续 |
| DOM/正文仍未加载 | 有限等待、滚动或刷新后复读；仍无正文记实际采集阻塞，不能记搜索无匹配 |
| 可见正文存在但提取为空 | 修复读取区域或读取方式，保留观察；不能伪造正文摘要 |
| 目录/索引 | 定向打开与原故障相关的子页，保留父页导航来源；子页仍需独立采集、摘要及关联核验 |
| 仅标题 | 保存标题及缺口，不能把正文组件或 Wiki 补证标完整；尝试对应正文入口/适用子页 |
| 实际正文与目标不相关 | 保留候选及否定依据，按剩余搜索预算换查询；不改原故障根因 |
| 原记录截断或只有 URL | Agent 先恢复原单元格附近内容/已有引用，恢复不了再报告输入缺口 |

已有有效 Wiki 不再补搜。已有 Wiki 为登录页/目录/空壳时先修复读取或导航，不当成“已经补证”，也不直接当作“没有任何证据”。Edge 必须使用现场既有连接，用户自行输入账号、密码及验证码；程序不记录凭据。相同站点恢复后一次解除相关任务等待，真正不同权限/登录域分别处理。

### 搜索由 Agent 提取和扩展，程序约束范围与停止

不在 Python 里拼一套固定关键词代替 Agent 搜索。Agent 先从原始描述、算子列、进展和既有资料提取：模型及别名、完整算子标识、症状、触发条件、框架/配置、版本/时间，以及“原述可能根因”。每项带原文件/Sheet/单元格连续引文；缺项保持未知，历史归因只作假设。

Agent 根据实际结果逐步调整查询：先保留具体症状与完整标识；无结果时使用有依据的别名、实现术语或拆分组合；必要时放宽版本/模型条件，转向具体触发/修复机制。完整算子名和参数单位保持区别，不能把 rope/npu_mrope、TP64/对齐64 混为一项。可能根因不能成为强制检索过滤器，否则会排除推翻旧归因的资料。

建议默认最多 3 轮查询扩展，可在整批策略中配置；这是单故障的搜索预算，不是每几条向用户请示。记录每轮实际 query、范围、命中/无命中、候选和调整理由。没有真正执行搜索不得写 NO_MATCH；无结果只代表该范围及查询，不表示全站不存在。

先 Wiki；无原 Wiki 时必须完成有范围的检查。Wiki 已有适用证据后停止新增搜索，其余原始链接仍整理。Wiki 检查无匹配后按既有 GitHub/GitCode/Gitee/CodeHub/DTS 能力和目标线索继续；一份足够证据满足本轮策略就停，不为补满证据类型或未知字段扩搜。未知根因不自动转成不同事件。

### 摘要与单请求超限

复用原约 16K 正文分组及原文片段，不重写分段系统。增加组覆盖清单、失败组重试、同快照摘要冻结/复用；新鲜子会话只读一个组，不读整批聊天历史。并行组调度只需暴露独立待办，不强制增加新的聚合状态。

先测量每类最终请求中重复正文、重复资料卡、历史结果及完整 schema 的贡献。收紧任务视图中的冗余表示，只保留本任务实际需要的字段，维持原始事实、完整引文和哈希绑定；原始记录与全部资料留在账本。比较使用现有 issue_scope 和有覆盖说明的适用选段，必须保留相关支持与冲突；不能宣称核验未传入的全文。摘要只是索引，判断仍回到原文引用。

库比较保留冻结库的完整唯一 ID 及机制定义，不能删条目或只传近邻命中。预算测量包括指令和最终序列化数据，并匹配现场实际执行容量。不得自动抬高预算掩盖问题。精简后仍超限就明确阻塞；复杂多层长文/库聚合算法暂不列入本次实现。

### 优先硬证据去重，保留语义边界

| 对象 | 去重依据 | 不做的推断 |
| --- | --- | --- |
| 页面资源 | 平台 + 仓库/域 + Issue/PR/Wiki/DTS 身份；未知 URL 沿用原规范化规则 | 不盲删 query；不同 ref/head/版本不能当作同份内容 |
| 采集 | 资源键 + 采集范围/版本；原 URL、讨论锚点和每个来源关系均保留 | 同链接不能自动合并故障；评论锚点仍限制适用子问题 |
| 摘要 | 当前快照 + 摘要策略 + 分组覆盖 | 旧快照和新正文不混用；跨子问题事实不合成同一根因 |
| 判断工作 | 现有 work_id + 输入 + 策略 | 不退化为 case/snapshot 配对；不同子问题单独处理 |
| 故障记录 | 硬证据重复优先列为可追溯候选；已明确确认关系复用现有组 | 共享 Wiki/PR 或相似描述不能自行登记用户确认事件组 |

平台资源键优先解决 GitHub PR 本体、评论锚点和可识别跟踪参数造成的重复；原始 URL、版本/ref 与适用范围不丢失。补测试“更新 A 的资料仅失效 A 的真实依赖，B 的有效映射查询/导出不受影响”，再收紧旧的全 run catalog 失效行为。重复结果按当前唯一 judgment_id、case_id、snapshot_id 和 work_id 各自统计，理由条目不当故障数。

### 开发顺序、续跑与验收

1. **先修可靠执行与范围。** 固定目标集合和原始库；补失败隔离、可配置超时/重试、任务唯一派发及子会话入口，完成单任务和断点续跑验收。范围必须影响全链路；无法安全附加到旧混合 run 时才新建有明确父运行关系的目标 run。
2. **再修采集与搜索。** Edge 能力/登录预检、页面质量诊断、目录导航、Agent 事实提取及有限查询扩展；更新项目 Skill/命令/接入说明，消除旧入口或输出要求造成的歧义。规则变化继续参与现有失效指纹。
3. **最后收紧上下文和重复工作。** 暴露摘要组独立工作、按资源/case 就绪推进、去掉请求冗余、资源身份归一化、收紧依赖失效，报告同步使用目标范围和任务必要性。

Codex 先开发并使用合成数据验证调度、异常、范围及数据合同，再做真实公开资料实机；现场 Edge 登录和内网正文需要 OpenChamber 验收。不能以 SDK/命令存在证明现场服务已接通。

| 必须验证 | 预期 |
| --- | --- |
| 232 个目标记录在更大的历史 run 中 | 计划、模型、校验、统计、导出只针对冻结目标；输入行全量对账 |
| 完整批次连续推进 | 内部可分页/限并发，但没有每 10 条确认边界 |
| 一条任务超时/无效引文 | 阻塞其依赖，其余独立任务继续；重试有限且留档 |
| 浏览器登录过期 | 同站点一次登录交接，恢复相应任务，不重复问所有 case |
| 标题页/目录页/未渲染页面 | 不能冒充 COMPLETE 正文；定向补读或明确采集缺口 |
| 模型/算子别名与错误旧归因 | 查询有原字段依据、逐轮理由；可放宽假设，不能强搜旧结论 |
| 60K 以上资料、关键结论在末尾 | 所有分组和末尾保留；缺组无完整摘要；后续单请求超限明确阻塞 |
| 同 PR 不同 URL 锚点、多个 case | 采集/摘要共享；每条来源与适用子问题保留，不自动合并事件 |
| 摘要更新、旧 compare/草案并存 | 只重新执行受影响工作；旧请求拒收，旧响应及人工历史保留 |
| 更新 A，查询/导出 B | B 的有效库映射仍有效，不靠再次运行临时恢复 |
| 中断后重启执行器 | 复用已通过结果，未完成工作恢复，无重复任务和自动 ACCEPT |
| 全量最终交付 | 仅一个 XLSX；目标数、当前判断、阻塞数按不同单位清楚对账 |

现场先备份原 state、保留生产运行身份和请求响应。修复后重启的是执行器/会话，清空聊天历史与重建状态不是同一件事。优先原 state 原 run 续跑；若本轮原始库与旧冻结库不同等确实不兼容，再建立关联后续运行，不覆盖旧库。附件中的直接 store 写入项在恢复正式判断前先只读核验来源、依赖和门禁状态。

本机方案仅留在本文件，不新增多套需求说明。实现继续使用下文固定的 `<state>/audit.sqlite3`、snapshots、`work/runs/<run_id>/tasks/.../request.json` 与 `attempt-<n>/response.json`；最终仍只有 `output/故障整理及模式库建议.xlsx`。

## 文档整理的最新约束：Wiki 前置检查与固定文件

以下是下一阶段文档流水线的实施要求，不表示 0.1.9 已具备程序门禁或精简输出开关；本节优先于下文一般性的“一份证据停止搜索”。不新增单独的需求说明文档。

### Wiki 第一优先级

- 文档已给出 Wiki：优先读取这些 Wiki，保留文档来源关系；默认不搜索额外 Wiki。其他原始引用仍整理，技术支持和关联是否正确在最终核对时检查。
- 文档没有 Wiki：即使已有 GitHub、GitCode、Gitee、CodeHub、DTS 或 PR，也必须先执行有范围的 Wiki 补证检查。已有其他证据不能跳过这一步。
- 找到对应 Wiki：保留搜索来源、正文、适用子问题和引文，停止继续补 Wiki，不为补齐所有资料类型扩搜。
- 查无匹配：保存实际查询词、范围、执行时间与 `NO_MATCH`，继续整理其他证据；不能声称全站不存在，也不能无限搜索。
- 登录或访问失败：记录 `BLOCKED` 及原因，Wiki 检查不得标完成；其他可处理资料继续推进。
- 已有 Wiki 最终发现错挂、内容冲突或无法定位：保留原链和异常，进入定向补读/补证；“存在 URL”不能覆盖这些问题。

必须执行 Wiki 检查，不等于必须找到 Wiki。现有 `required_sources=["WIKI"]` 要求存在可用 Wiki，不能单独替代“查过但未找到”的检查结果。结果应记入现有状态台账，不建立第二套 Wiki 台账。

该规则用于从文档整理故障。按项目及时间范围收集故障时，仍须完成指定范围的分页和收集验收，不能找到一个 Wiki 就结束整批。

### 固定存放位置与最少文件

项目根目录现场默认示例为 `D:\project\fault-evidence-audit`，开发副本不改变现场路径。新建运行默认复用 `<项目根目录>/.faultaudit/`；已有现场 state 一律按原路径使用，不为目录统一而搬迁。

| 内容 | 固定名称与位置 | 约定 |
| --- | --- | --- |
| 原始 XLSX、Word、PPT | 用户提供的原路径 | 只读，记录 hash 和来源位置，不生成多个副本 |
| 状态、故障、Wiki 检查、摘要、比较、异常及历史 | `<state>/audit.sqlite3` | 复用现有台账，不逐类另导出 JSON/说明文档；草案文件接口接入统一任务时保留其依赖 |
| 证据正文及可选原始内容 | `<state>/snapshots/<snapshot_id>/text.txt`、`raw.bin` | 沿用现有命名；相同快照不重复保存，raw.bin 只在实际取得原始内容时存在 |
| Agent 请求 | `<项目根目录>/work/runs/<run_id>/tasks/<task_id>/request.json` | 按任务 ID 保存完整合同和输入，不另出“任务说明.md” |
| Agent 响应 | `<项目根目录>/work/runs/<run_id>/tasks/<task_id>/attempt-<n>/response.json` | 按实际尝试保留，不覆盖旧响应；不同任务类型仍用各自合法合同和验收入口 |
| 最终交付 | `<项目根目录>/work/runs/<run_id>/output/故障整理及模式库建议.xlsx` | 一个工作簿容纳故障、引用与 Wiki 检查、归类/新增建议、异常和统计 |

不默认生成 HTML、Markdown 总结、逐案例说明、重复 TSV、重复 JSON 报告或多版 XLSX。程序校验信息留在台账/任务结果和最终工作簿；XLSX 适配器必需的临时 JSON 或预览作为内部临时文件，不作为交付物。保留必要原文和请求/响应历史，不通过清理历史来减少文档。

## 目标与现状

把本次“读资料、对照原故障、比较原库、抽象模式、保留缺口、合并导出”的工作做成可复核流程。先实现小型模式草案层，复用取证链路，不重新建设网站客户端、模型客户端或自动事件合并系统。

当前已有来源台账、证据计划、快照与独立摘要、`work_id` 事实对照、原库映射、模型文件桥接、输入预算、策略失效及报告导出。`investigation-plan` 能生成只读调查输入和带引文的六列资料摘要卡片；它不会自动执行采集、判断或正式入库。

本次 XLSX 是手工审查交付物。它能作为实现时的对照样本，不能据此宣称自动整理链路已完成。

## 数据流

```text
原表 / 旧表 + 冻结原库
  → evidence_plan：全部已有引用优先整理、控制新增搜索
  → 外部 Agent 采集：正文 / 讨论 / 必要 issue 与修复 Diff
  → 独立资料摘要：快照、子问题、事实、精确引文
  → work_id 事实对照：原记录与资料逐项比较，执行有限自检
  → investigation_plan + 当前有效库映射
  → CatalogProposal：覆盖比较、抽象模式、具体根因、未知项
  → 程序校验：15 列、来源、版本、枚举与选定新增集合
  → 只读合并预览：旧库原值 + 明确选定的新增草案
  → JSON / 差异清单 / XLSX
```

已有原始、旧表及确认关联的引用全部保留并安排必要整理。同 URL 在同批只采集一次，同快照共享独立摘要；不同子问题范围分别处理，`work_id` 贯穿任务和结果。

默认一份适用证据即可停止新增搜索。停止搜索不取消其他原始引用的整理，也不等于全部技术字段已证实。登录失败、部分采集或来源冲突分别记录，不转换成“没有证据”后自动扩搜。未知修复版本、缺失字段不触发补齐所有资料类型的搜索。

## 最小新增数据结构

建议新增独立 `CatalogProposal`，不把 15 列草案塞入现有 `CatalogItem` 或故障判断中。首版可让 Agent 按 JSON 合同提交草案，程序验收，不必先增加模型任务种类。

| 内容 | 最小字段或约束 |
| --- | --- |
| 身份与版本 | `proposal_id`、修订号、基线库 identity/hash、规则版本及输入指纹 |
| 处理建议 | `ADD / REFINE / APPEND_CASE / NO_CHANGE`、可选目标模式 ID、覆盖理由 |
| 产品内容 | 完整 15 列；抽象模式名和具体根因分开 |
| 适用范围 | 原 case IDs、work IDs、子问题范围、实现归属 `implementation_owner` |
| 字段依据 | 对每个事实字段记录原单元格或 snapshot/fact IDs、精确引文、支持程度 |
| 证据属性 | 区分原文事实、代码推断、作者验证、当地复现及未知；提案不改变原判断 |
| 建议与缺口 | 检查/处理/注入建议、未执行状态、未知项、冲突及修订来源 |

结构化 JSON 与证据记录作为后续工具的真源，XLSX 是展示与交付物。若支持人工修改 XLSX，应通过显式校验导入形成新修订；不得静默覆盖事实或继承人工 `ACCEPT`。该回导能力可放在后续阶段，不阻塞首版。

客户事件身份、通用技术模式和库覆盖是不同判断。公开 PR 可以支持一种实现机制，但客户事件关联、具体版本和产品归属仍须分别保留依据。其他事件资料不能确认原故障根因；未确认客户关联也不能把公开代码变更写成该客户已经验证的修复。

## 程序、Agent 与人工的分工

| 执行者 | 职责 |
| --- | --- |
| 程序 | 检查引文存在、来源链、哈希与当前有效性、固定分类、必需字段、选定集合、唯一 ID、无损合并和导出；已有任务与失效机制继续复用。 |
| Agent | 读正文和必要 Diff，对照数值含义、术语、场景、机制和修复；比较原库，提出抽象模式与合并建议，并检查反证、子问题串用和推断越界。 |
| 人工 | 处理无法消解的冲突、范围和分组争议；明确决定正式库是否采用草案。正常来源整理不增加逐条确认，系统处理不冒充人工 ACCEPT。 |

程序能验证引文和结构，不能单靠关键词或枚举证明根因成立。相同数字必须含义和条件相同；字节、元素数、TP 与块尺寸不得互换，算子名称相似也不证明同事件。

## 复用接口与最小实现步骤

现有 `investigation_plan(store, run_id)` 提供当前资料卡片、事实与根因候选；`import_catalog(..., scope, expected_count)` 提供冻结原库与数量约束；`export_report → workbook_data → scripts/export_xlsx.mjs` 提供表格导出基础。先复用这些接口，不建设第二份采集或判断台账。

1. **草案合同与纯校验。** 在 `contracts.py` 定义 `CatalogProposal`，在独立小模块实现字段和来源校验。三级只允许“计算算子、通信算子、图引擎”；四级只允许“算子计算、算子接口、数据切分、图融合优化”。建议字段明确未验证，缺失事实保持未知。用合成数据测试；本次手工 XLSX 作为本机对照资料，不把客户原文复制成自动化测试夹具。
2. **只读合并预览与导出。** 建议增加 `catalog-draft validate`、`catalog-draft export` 两个命令（尚未实现）。输入冻结原库和草案 JSON，输出校验、差异及新工作簿。核对基线哈希、唯一 ID 与明确选定的提案集合；重复执行不重复追加。语义合并由 Agent 提建议，程序不能按名称相似自动覆盖旧条目。首版不回写原库或现场 state。
3. **接入 Agent 文件任务。** 沿用 OpenCode/Codex 的请求和提交协议，让 OpenChamber/OpenCode 或 Codex 执行摘要、对照及草案填写。新模块、规则和模板必须进入策略指纹或任务输入哈希；证据、基线、Prompt、预算或规则变化使旧草案失效，历史响应和人工记录保留。正式采用时形成明确的新库版本，不原地改变本轮冻结库。

若最终模型请求超过现有预算，明确 `BLOCKED / INPUT_TOO_LARGE`；不删减原文、事实或库条目后声称完整成功。本机试行已出现摘要成功而比较请求超限的情况，首版允许保持阻塞，不以新增复杂聚合算法作为前置条件。
