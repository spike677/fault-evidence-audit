### 🐛 Describe the bug

The service crashed twice with an identical signature — once after ~16h of uptime and once after
~1.7h after restart — so the failure is uptime-independent and deterministic.

Python-side error (identical in both crashes, in MoE token dispatch preprocess):

```text
File "vllm_ascend/ops/fused_moe/token_dispatcher.py", line 623, in _preprocess
    global_input_tokens_local_experts_indices = torch.repeat_interleave(
RuntimeError: operator():../torch_npu/csrc/aten/common/LocalScalarDenseNpu.cpp:23 NPU function error:
c10_npu::acl::AclrtSynchronizeStreamWithTimeout(copy_stream), error code is 507035
[ERROR] ERR00100 PTA call acl api failed
[Error]: The vector core execution is abnormal.
```

Device-side error:

```text
The error from device(chipId:x, dieId:y), serial number is 1, there is an exception of fftsplus
aivector error, vec error info: 0x470000020d, subErrType:4, errorStr: The VEC instruction parameter is invalid.
An error occurred in the kernel task, retCode=0x31, [vector core exception]
rtStreamSynchronizeWithTimeout execution failed, reason=vector core exception
```

Key observations:

1. All 16 devices failed in the same second with bit-identical vec error info (0x470000020d).
   npu-smi reports Health OK for every device before and after, and the failing task serial number
   is 1/2 on every device. This looks like a deterministic kernel/tiling bug, not a hardware fault.
2. The device exception dump identifies the failing kernel: the dump directory next to each
   exception_info.* file contains only TopKV2_<hash>_high_performance_*_host.o — i.e. the crashing
   kernel is the custom high-performance TopKV2 from the vendor opp package (MoE routing top-k),
   not repeat_interleave itself; repeat_interleave is only where the stream synchronize surfaced
   the error. The dumps also contain full tiling data (64B) and input tensors.
3. The trigger pattern is reproducible: right before both crashes, a burst of 4 concurrent requests
   with ~32K-token prompts arrived (identical traffic replayed both times: Avg prompt throughput
   3276.7 tokens/s, then Running: 2 reqs, Waiting: 2 reqs), and the crash happened during the first
   mixed chunked-prefill + decode forward passes (max_num_batched_tokens=8192).
4. The crash occurred while the acl-graph wrapper executed the step via its eager fallback
   (acl_graph.py fx_run_eagerly), since the mixed-batch shape is not covered by decode-only graphs.
   Additionally, at startup every worker recorded
   "EE1016: Synchronous memory copy failed ... capture mode GLOBAL(0) ... supported only in
   RELAXED mode" during graph capture — pointing at the same op family (synchronous scalar copy
   inside repeat_interleave) being incompatible with GLOBAL capture.

Current workaround / status:

- Temporarily ran with --enforce-eager and reduced limits (--max-model-len 8192 --max-num-seqs 1):
  service was up, no 507035/EE1016 during that run. However, the original crash happened on the
  eager fallback path, so enforce-eager alone may not fully avoid it.
- Next step we plan to try: drop the custom_transformer vendor opp package from the env so TopK
  falls back to the native implementation, and re-run the trigger traffic.
- npu-smi health is OK; we have per-device exception_info dumps (incl. tiling data) and plog
  available if needed.

Questions:

1. Is this a known issue with the custom high-performance TopKV2 kernel under mixed
   chunked-prefill batches?
2. Is there a supported way to force native TopK for this model (instead of removing the whole
   vendor opp package), e.g. an op-priority config?
3. Any fixed version you can point us to?
