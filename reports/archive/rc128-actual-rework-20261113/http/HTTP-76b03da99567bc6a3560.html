描述

修复 Ascend 950 上 QuantLightningIndexer 的 FP8 E4M3 TopK 结果随 query 长度变化的问题。完整 prefill 和 chunked prefill 对同一 query 使用相同的 Q、K、权重、反量化系数和因果范围时，仍可能选出不同的索引。

arch35 的单行路径分别累加偶数和奇数 head 后再相加，双行路径按 head 顺序逐项累加。FP32 舍入差异会影响 BF16 排序分数，进而改变 TopK 边界。本改动让 FP8 双行任务中的每一行复用单行规约顺序。

测试

  • Ascend 950DT、CANN 9.2.1、torch_npu 2.10.0.post7。基于同一上游提交 4197a29c 分别构建原版和补丁版算子。
  • 新增独立合成回归，使用 TND/PA_BSND、因果模式和 TopK=2048。比较 Q 长度为 2、64、314、5688 时倒数第二行的 TopK。原版在 5688 时选择索引 2048，补丁版四种长度均选中预期索引 2047。
  • GLM-5.3 W4A4C8 MXFP4，单机 TP8，同时开启 HiSparse、MTP=3 和前缀缓存。三轮真实 8 并发共 72 组冷/热对照，一轮真实 4 并发含两条约 128K 输入共 12 组对照。生成 token ID 和返回的 logprob 全部一致。
  • 算子延迟变化尚未单独评估。

变更摘要

本 PR 修复 Ascend 950 上 QuantLightningIndexer 的 FP8 E4M3 场景中 TopK 结果随 query 长度变化的问题。原因是 arch35 单行向量任务与双行向量任务对 head 维度采用不同的 FP32 累加顺序（前者分别累加偶/奇 head 再相加，后者按 head 顺序逐项累加），舍入差异会改变 BF16 排序分数，从而影响 TopK 边界选择。改动通过模板参数让 FP8 双行任务对每一行复用单行规约顺序，并新增回归测试验证不同 query 长度下 TopK 一致。

主要改动

  • 新增规约顺序模板参数: 在 quant_lightning_indexer_vector1.h 的 BatchMulWeightAndReduceSum 模板中新增非类型参数 consistentRowReduction，用于在编译期选择双行累加策略。
  • FP8 双行路径改为逐行顺序归约: 原 batch == 2 的合并实现 MulWeightAndReduceSum2 被限定在 consistentRowReduction 为假的分支；当该参数为真时，对两行分别调用 MulWeightAndReduceSum（第二行通过 outStride/qkStride/weightStride/kScaleStride/qScaleStride 偏移），与单行路径保持相同 head 累加顺序；单行路径前置为独立的 batch == 1 分支。
  • 按 query 数据类型启用该策略: 在 quant_lightning_indexer_service_vector_arch35.h 的 ProcessVec1 中以 std::is_same_v<typename QLIT::queryType, fp8_e4m3fn_t> 计算 constexpr 布尔 consistentRowReduction，仅对 FP8 E4M3 query 传入新模板参数，其他数据类型保持原有合并归约行为。
  • 新增跨 query 长度一致性回归测试: 新增 test_quant_lightning_indexer_fp8_consistency.py，构造两个争夺最后一个 TopK 槽位的候选 key，在 TND/PA_BSND、因果模式（sparse_mode=3）、sparse_count=2048 下比较 query 长度为 2、64、314、5688 时倒数第二行的 TopK 结果，断言选中索引集合均为 range(2048)。
