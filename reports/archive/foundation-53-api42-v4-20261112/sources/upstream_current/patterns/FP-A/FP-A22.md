# FP-A22 kernel dtype 分派/模板映射错配（特定 dtype 静默走错分支）

> [← 库索引](../../README.md) ｜ [变更记录](../../CHANGELOG.md) ｜ 类别：精度 ｜ 风险：高（S3×O3=9） ｜ 状态：活跃

- **元数据**：类别 精度 ｜ 风险 高（S3×O3=9）｜ 状态 活跃 ｜ 来源 ops-math #3747/#3748（2026-10-21，aclnnTril 的 dtype 全组合实测，同算子两条独立实证）；v2.18 增补子型④（现网修复复盘 26-01，2026-11-05）
- **适用**：仓 All ｜ 侧别 Kernel,Tiling ｜ 载体 Kernel源码,Tiling源码 ｜ 触发 必须触发 ｜ 默认启用 true
- **子型**：① **映射表条目错配**；② **类型特化路径缺失**；③ **分派后输出覆盖不全**；④ **输出 dtype 被误当计算 dtype**（v2.18 增补——dtype 本身没派错，但**取错了 dtype 的位宽**去算容量/尺寸）。
- **故障机理**：kernel 按 dtype 把计算派发到不同的**执行模板 / TilingKey / 类型特化分支**，而 `dtype ↔ 模板` 的**映射表条目缺失或错配**时，某个 dtype 会静默落到**默认分支、错误模板或部分覆盖的循环上界**，函数照常返回 `ACLNN_SUCCESS`，但输出只被写入了部分元素，或掩码/边界按错误的类型语义计算。它不是「数值近似差一点」（FP-A01/A02/A03），也不是「路径没被测到」（FP-A19）——**派发表本身是错的，任何输入只要落到该 dtype 就必现**。五个子型：① **映射表条目错配**（同宽度的兄弟 dtype 表现不同，可排除单一宽度搬运解释）；② **类型特化路径缺失**（bool / 无符号类型走默认或错误模板，掩码边界按有符号/位宽语义计算）；③ **分派后输出覆盖不全**（部分元素未写却返回成功，未写区域保留调用方预填值）；④ **输出 dtype 被误当计算 dtype**（用 `GetSizeByDataType(outDataType)` 推容量/临时 buffer 尺寸，而该算子实际在更宽类型上计算——如 BF16/INT8 输出、FP32 中间计算。**位宽差 2~4 倍，容量估算系统性偏小或偏大**，表现为 tiling 分块数错、单次处理量错、workspace 不足；与 ①的区别是「dtype 都对，但用错了**哪个** dtype」）。 ⑤ **出参 dtype 未纳入白名单/一致性校验（v6.33）**：`out` 只做了 `CheckNotNull`，没有 `OP_CHECK_DTYPE_NOT_SUPPORT(out, ...)`，也没有 `self/out dtype` 一致性检查；非法 out dtype 被放行后由 kernel 按错误位宽写，表现为部分输出未写或结果错。
- **触发条件**：kernel 用 `dtype` / `sizeof(T)` / `TILING_KEY` / 函数指针表做模板派发，且映射表是**手写枚举**而非 `if constexpr` 全覆盖；同一算子支持 ≥5 种 dtype（尤其同时含 `int32/uint32`、`int64/uint64`、`bool`、`uint8`）；输出 shape 非 1 元素且按行/块写入。**单 dtype 用例无法暴露**——必须跑 dtype 全组合矩阵，并与同宽度兄弟 dtype 对照。
- **典型表现**：① **特定 dtype 返回 0 但输出部分未写**——`out` 预填魔数后回读，未写区域原样保留（#3747：`uint32`/`int64` 后 `ceil(n/2)` 个元素一个字节都没写）；② **掩码/布尔结果边界错位**——全量写出但保留/置零边界算错，误差随规模放大（#3748：3×3 错 4/9、4×4 错 12/16、8×8 错 42/64）；③ **同宽度兄弟 dtype 对照分裂**——`int32` 对而 `uint32` 错、`uint64` 对而 `int64` 错，这一条是排除「按字节宽度搬运」解释的关键判据。**关键识别特征：缺陷只随 dtype 变化，与 shape、数值范围、调用顺序无关。**
- **源码审查映射点**：① 找到 dtype → 模板/TilingKey 的**映射表**（`switch (dtype)`、`if (dtype == ...)` 链、`std::unordered_map`、函数指针数组），逐项核对枚举值是否**每个受支持 dtype 都有条目**且指向正确模板；② 每个模板的**输出循环上界**是否取自该 dtype 自身的元素数/字节数，而非由其他 dtype 推导（漏写一半常见于「按 8 字节元素数算 4 字节 dtype」或反过来的复用）；③ `bool` 的存储宽度与掩码语义——按位还是按字节、`true` 的表示、边界 `i + diagonal >= j` 的比较是否在正确类型域；④ 是否存在 `default:` 静默兜底（兜底到某模板而不报错 = 高危）；⑤ **同接口其他 dtype 与同族算子**（前向/反向、`tril`/`triu`）是否复制了同一张表。**子型④（v2.18）额外查**：所有 `GetSizeByDataType(...)` / `GetTypeSize(...)` 的实参——是 `outDataType`/`outputDtype`（输出存储）还是 `calcDataType`（实际计算）？该尺寸喂给谁（临时 buffer 容量 / 每核元素数 / 单次处理量 / 循环次数）？**只要该尺寸用于计算容量而非输出分配，就必须用计算 dtype**；查是否已有 `calcDtype` 映射表（BF16/INT32→FP32、INT8/UINT8/INT16→FP16 这类），以及该映射是否覆盖算子支持的全部输出 dtype。
- **检测签名**：子型④ 可机器定位：`GetSizeByDataType\s*\(\s*(outDataType|outputDtype|outDtype)\s*\)`（配置内比对，同一文件若存在 `calcDataType` 却未用于该处即高危）。其余子型**暂无机器签名**（新增签名须重跑 `scripts/sig_yield.py` 重建产出基线，避免与既有 ops-math 语料基线不可比）。人工核查命令：
  ```bash
  git grep -nE "switch\s*\(\s*(dtype|dataType|DT_)" -- <op>/op_kernel/
  git grep -nE "TILING_KEY|tilingKey|GetTypeSize|sizeof\(" -- <op>/op_kernel/
  git grep -nE "default\s*:" -- <op>/op_kernel/
  ```
  ```bash
  # 子型④：输出 dtype 被拿去算容量
  git grep -nE "GetSizeByDataType\s*\(\s*(outDataType|outputDtype)" -- <op>/op_host/
  git grep -nE "calcDataType|calcDtype|computeDtype" -- <op>/op_host/
  ```
  先列出受支持 dtype 全集（`def.cpp` 的 `DataType(dtypeList)` / `binary.json`），再与映射表条目做**差集**——差集非空且落到 `default` 即候选。
- **审查关键词**：`dtype 分派|type dispatch|dtype.*template`；`模板映射表|dispatch table`；`GetTypeSize|sizeof`；`default:`；`bool|uint32|uint64|int64`；`输出覆盖率|canary 预填`。
- **测试拦截建议**：① **dtype × shape 全组合矩阵**——对每个受支持 dtype 至少跑「1 元素 / 非整除行宽 / 带 diagonal 边界」三档，断言返回码 + 输出全量正确；② **输出 buffer 预填魔数**（如 `0x7FC07FC0` 重复），跑后统计残留比例，任何非零残留即失败——这是发现「部分未写」最快的判据，禁止只断言返回码；③ **同宽度兄弟 dtype 成对对照**（`int32` vs `uint32`、`int64` vs `uint64`、`bool` vs `uint8`），两者结果必须各自正确，不能互相替代；④ CI 里把「映射表条目集合 == `def.cpp` 支持的 dtype 集合」做成静态差集门禁。**子型④ 额外测**：对每个「输出 dtype ≠ 计算 dtype」的组合（BF16、INT8、UINT8、INT16、INT32）分别跑单次 + **连续多次**调用，断言返回码、输出数值与 tiling 分块数一致；把「输出元素数跨 tiling 分块边界」的 shape 纳入矩阵（位宽算错时该边界最先暴露）；用 tiling UT 直接断言 `CalcMaxOutNum`/每核元素数的返回值，比端到端更快定位。
- **实证案例**：`cann/ops-math` **#3747**（`aclnnTril`，2026-10-21）——`self` 为 `uint32` 或 `int64` 时两段接口均返回 0，但 4×4 输出后 8/16 个元素一个字节都没写（预填值 `0x7FC07FC0` 原样保留），已写部分掩码也错；未写元素数恒为 `ceil(n/2)`（3×3 4/9、4×8 16/32）。同为 4 字节的 `int32` 与同为 8 字节的 `uint64` 全部正确，issue 据此排除「按字节宽度搬运」的单一解释，指向 `dtype → 执行模板` 映射表条目错配。`cann/ops-math` **#3748**（同算子，2026-10-21）——`bool` 下全量写出但掩码边界错位（3×3 错 4/9、4×4 错 12/16、8×8 错 42/64），与其它 dtype 走同一条按字节宽度分派路径却只错在掩码，属类型特化语义错误。两条同日、同算子、不同 dtype，构成 O3。**子型④ 实证（v2.18 增补，现网修复复盘 26-01）**：`cann/ops-math` `aclnnLinSpace`（issue #1004）——tiling 的 `CalcMaxOutNum` 用 `ge::GetSizeByDataType(outDataType)` 取宽度做容量推导，而 LinSpace 对 BF16/INT32 实际在 **FP32** 上计算、对 INT8/UINT8/INT16 在 **FP16** 上计算；位宽差 2~4 倍 → 尺寸估算错 → 连续调用报错。修复引入 `calcDataType` 映射后取宽度。修复后形态锚：`math/lin_space/op_host/lin_space_tiling.cpp:122-132`（@ops-math HEAD `9a37afe`，2026-11-05 本地核验）。**注意**：该修复只改了这一处尺寸推导，未清理任何跨调用状态——原单标题写「连续调用」，但 diff 里没有状态复位，故本案**不能**按 FP-A21 跨调用残留定根因。 **2026-11 批次（v6.33 反哺）**：本簇 23 条；代表 ops-math#3881（BitwiseXorTensor out dtype 未校验）、ops-nn#7556（AscendAntiQuant 空张量+INT4 非连续放行）、ops-nn#7679（Hardshrink lambd dtype 未校验）。 **v6.55 增补（输出 dtype 未校验，2026-11-08）**：本轮把该子型扩到「**输出张量 dtype**」并给出三条已知实证——ops-nn#8386（`aclnnUnique` 的 `valueOut` 传 COMPLEX64 被放行，内核按 `self` 的 4 字节元素写回）、ops-math#3921（open，`aclnnArgMax` 的 `out` 传 BOOL/UINT8/FLOAT 均两段 0/0；A2 实测 `out=UINT8` 时索引 299/288 被截成 43/32，源码 `math/arg_max_v2/op_api/aclnn_argmax.cpp:64` 的 `CheckDtypeValid(self)` 只校验 self，`:211/:218/:223` 却用 `out->GetDataType()` 决定写回类型；资料 `docs/aclnnArgMax.md:111` 限定 INT32/INT64、`:172` 的 161002 覆盖 out）、ops-math#4618（`aclnnMaxDim` 的 `indices` dtype）。**判据**：`CheckDtypeValid(...)` 的实参表是否覆盖全部输出；只要 kernel 侧出现 `out->GetDataType()` 参与写回/Cast，而 aclnn 未校验该输出，即候选。**负控**：同族 `aclnn_argmin.cpp:65-70` 已正确校验 out；ops-cv 43 处 `CheckDtypeValid` 中唯一漏检的 `aclnnNonMaxSuppression` 在代码里硬拦 DAV_2002、资料明示 A2 不支持 ⇒ ops-cv 本子型 0 个。
- **参考实现前置（v6.30）**：判 aclnn 层必须用 `golden.py` 的 `__golden__["aclnn"]` 入口；只有 `kernel` 入口时**不得**用于 aclnn 层判定（层间 dtype/校验/布局差异会被误判成算子缺陷）；连 `aclnn` 入口都没有时记「判据不成立」而非「未覆盖」。实测 `ops-nn` 全仓 362 个 `golden.py` 仅 **80 个（22.1%）**含 `aclnn` 键——见 [EVIDENCE_DISCIPLINE.md](../../EVIDENCE_DISCIPLINE.md) D12/D13。
