1. 概述

1.1 简介

本提案为 torch_npu 的 ProcessGroupHCCL 补齐 HcclCommConfig.hcclDeterministic 的透传：配置入口沿用既有 ProcessGroupHCCL.Options.hccl_config 字典，新增 key hccl_deterministic（uint32：0=关闭 / 1=开启 / 2=严格），在创建通信域的单一漏斗 createHcclCommConfigWithOptions() 中映射到 config.hcclDeterministic 并做类型/值域校验。Python 侧零新增 API，C++ 核心改动约 10 行。未配置 key 时保持既有哨兵 0xffffffff 不变，由 HCCL 按"环境变量 → 默认值"链解析，默认行为与现状逐位一致。

1.2 动机

使用场景：RL训练需要通信域粒度的 Batch 一致性（确定性）配置——同一作业中，默认全域开确定性保证可复现，性能敏感子域（专家/TP）关闭确定性换取吞吐。

现状与痛点：浮点归约不满足结合律，all_reduce / reduce_scatter 等归约类算子的结果依赖归约顺序，确定性通信通过固定归约顺序保证同输入同输出。HCCL 当前仅有 HCCL_DETERMINISTIC 环境变量做进程级全局开关（token：true→1 / strict→2 / false→0），同一进程内所有通信域只能同开同关。CANN ≥ 8.2.RC1 的 HcclCommConfig 已提供 hcclDeterministic 字段（建域时按通信域下发，HCCL 文档明确优先级：通信域配置 > 环境变量 > 默认值），但 torch_npu 未透传，用户无法按通信域配置。

必要性与影响：torch_npu 已通过 hccl_config 支持 hccl_buffer_size、group_name、qos_* 等键按通信域下发，createHcclCommConfigWithOptions() 是所有建链路径的单一漏斗，相邻键均已同构透传，缺的只有这一个键；不补齐则通信域粒度确定性在 torch_npu 生态完全不可达。

1.3 目标

  • hccl_config["hccl_deterministic"]（uint32 0/1/2）在建域时透传至 HcclCommConfig.hcclDeterministic；
  • 类型校验（int）与值域校验（≤2），报错文案明确；
  • 未配置 key 时行为与现状完全一致（哨兵路径），零兼容性影响；
  • 多通信域独立配置互不干扰（含 8 卡不相交子域场景）。

非目标（不在本期）：P2P 通信域（send/recv，无归约语义）；行为级确定性验证（位级比对，另行立项）；A3/A5 平台支持（有 HCCL 侧问题单待处理）。

2. 用例分析

2.1 用例 1：多通信域混合确定性配置

关键路径：训练脚本为默认全域与子域分别构造 pg_options，init_process_group() / new_group() 时传入；首个集合通信触发懒创建，配置随 HcclCommConfig 下发到对应通信域。
现状：所有通信域只能跟随 HCCL_DETERMINISTIC 同开同关。
本提案后：默认域确定性=1、专家/TP 子域确定性=0，互不干扰（8 卡三域用例已验证）。

2.2 用例 2：op_option 覆盖环境变量

关键路径：部署脚本已设 HCCL_DETERMINISTIC=true（全局兜底），个别通信域需要不同档位时通过 hccl_config["hccl_deterministic"] 显式覆盖。
现状：无覆盖手段。
本提案后：op_option 压制环境变量（真值冲突场景已验证：op=0 vs env=true、op=2 vs env=true）。

2.3 用例 3：未配置时的既有行为保持

关键路径：存量训练脚本完全不出现该 key。
现状：getHcclCommConfig() 填充哨兵 0xffffffff，HCCL 按 env → 默认值解析。
本提案后：行为逐位一致（空 hccl_config 在透传函数入口提前返回；非空但无该 key 不触碰该字段）。

2.4 DFX 要求

  • 兼容性：未配置 key 行为与现状一致；不改变既有 hccl_config 键的处理；对外零 API 变更；
  • 可靠性：类型/值域校验前置，非法值在建链时立即报错，不进入 HCCL；
  • 可维护性：实现与相邻键同构，无新抽象；
  • 可测试性：UT + plog 双证据矩阵全覆盖（见第 4 章）。

2.5 使用限制 / 约束

  • 依赖 HCCL：HcclCommConfig.hcclDeterministic 需 CANN ≥ 8.2.RC1；
  • 平台：暂时仅 A2（A3/A5 有 HCCL 侧问题单）；
  • P2P 通信域（send/recv）不透传；
  • op_option 值域为 uint32 0/1/2；环境变量仅接受 token（true/false/strict），数字值会被 HCCL 拒绝初始化。

3. 方案设计

3.1 总体方案

核心思路：沿用 hccl_config 既有键值透传机制，在单一漏斗处新增一个与相邻键完全同构的处理块。

关键设计点：

  • 单一漏斗：collective() / collectiveCoarsced() / getHcclCommName() 三个外部预建入口 + createHCCLComm() 四条建链路径全部经过同一函数，一处透传全覆盖；
  • 哨兵语义：未配置时不干预 getHcclCommConfig() 的基线填充，优先级链完整交给 HCCL 收口；
  • comm 身份 =（PG 实例， devicesKey），天然保证多域隔离。

3.2 技术选型

方案 描述 优劣 结论
沿用 hccl_config 键值透传（选定） 新增一个与 hccl_buffer_size 等同构的 key 优势：与既有机制零割裂、Python 零新增 API、pybind def_readwrite 已就绪、改动约 10 行 采用
独立 Python API（如 set_deterministic(pg, ...)） 显式 setter 劣势：需新增绑定层与状态管理，与 hccl_config 体系割裂 放弃
仅环境变量 + 子进程拆分 无代码改动 劣势：进程级全局，无法通信域粒度（正是本需求要解决的） 放弃

3.3 功能与性能设计

功能实现（位于 hccl_buffer_size 与 group_name 块之间，与相邻键同构）：

if (options_->hccl_config.find("hccl_deterministic") != options_->hccl_config.end()) {
    if (std::holds_alternative<uint32_t>(options_->hccl_config["hccl_deterministic"])) {
        config.hcclDeterministic = std::get<uint32_t>(options_->hccl_config["hccl_deterministic"]);
        TORCH_CHECK(config.hcclDeterministic <= 2, "Value of hccl_deterministic should be 0, 1 or 2.",
            DIST_ERROR(ErrCode::VALUE));
        TORCH_NPU_HCCL_LOGI("Create hccl comm config, group id is %s, hcclDeterministic is %u.",
            options_->group_id.c_str(), config.hcclDeterministic);
    } else {
        TORCH_CHECK(false, "Value type of hccl_deterministic should be int.", DIST_ERROR(ErrCode::TYPE));
    }
}
  • 数据模型：无新增字段，仅消费 HcclCommConfig 既有字段；
  • 影响范围：仅 ProcessGroupHCCL.cpp 单文件；空 hccl_config 在函数入口提前返回，不触及任何既有键；
  • 日志设计：INFO 日志位于块内、校验之后——非法值不打印、未配 key 不打印，避免未配置场景打印哨兵 4294967295 造成误读；
  • 性能：仅在通信域创建时执行一次键查找与赋值，集合通信热路径零开销。

3.4 安全隐私与DFX设计

  • 正确性/可靠性：类型与值域 TORCH_CHECK；错误码 DIST_ERROR(ErrCode::VALUE/TYPE) 对齐既有键；日志先校验后打印，不产生误导性输出；
  • 兼容性：对外零 API 变更；未配置 key 的行为与现状逐位一致；不改变任何既有 hccl_config 键的处理；
  • 可维护性：与相邻键同构的实现模式，无新抽象；
  • 可测试性：单元测试（6 用例）+ plog 双证据矩阵（9 case，自动判定 PASS/FAIL，支持 2/8 卡）全覆盖；
  • 安全隐私：不涉及敏感数据；plog 证据含机器网卡 IP（HCCL 拓扑日志），验证材料置于私仓、勿转公开。

3.5 编程与调用设计

本提案不引入新的公开 API，用户侧通过既有 pg_options 使用：

import torch.distributed as dist
from torch_npu._C._distributed_c10d import ProcessGroupHCCL

# 通信域 A：确定性=1（Batch 一致性）
opts_a = ProcessGroupHCCL.Options()
opts_a.hccl_config = {"hccl_deterministic": 1}
dist.init_process_group(backend="hccl", pg_options=opts_a, ...)

# 同进程通信域 B：确定性=0（保吞吐），与 A 互不干扰
opts_b = ProcessGroupHCCL.Options()
opts_b.hccl_config = {"hccl_deterministic": 0}
pg_b = dist.new_group(backend="hccl", ranks=[0, 1], pg_options=opts_b)

优先级语义（用户可观察）：op_option > 环境变量 HCCL_DETERMINISTIC > HCCL 默认值 0；两接口值域不同（op_option 为 uint32 0/1/2，env 仅 token true/false/strict），需在文档中明确。

3.5.1 编程模型基本设计

开发环境：torch_npu（含本特性）+ CANN ≥ 8.2.RC1 + Ascend A2 系列；编译工具链与既有 ProcessGroupHCCL 一致，无新增依赖。
开发约束：P2P 通信域不透传；A3/A5 暂不支持（HCCL 侧问题单）；值域仅 uint32 0/1/2。
