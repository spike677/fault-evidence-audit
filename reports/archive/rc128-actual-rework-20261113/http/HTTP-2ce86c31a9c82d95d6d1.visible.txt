背景
PR #15358 合入后，
engram_fetch_train
返回
fetched_sf
时仍把真实 CPU
sf_table
作为 CustomOp 输入。该张量只用于推导输出 shape/dtype，kernel 实际读取的是 NPU 上的
sf_table_addr
。Dynamo/FakeTensor 会检查同一 CustomOp 的全部 tensor 输入，因此训练图模式打开 FP8 时会报 CPU/NPU 混设备。
修改
训练 schema 将
Tensor sf_table
替换为
ScalarType sf_dtype
和
int sf_packs
。
Python 直接传
torch.dtype
，C++ 直接接收
at::ScalarType
，删除
6
/
44
这类 PyTorch 枚举数值映射。
sf_table_addr
继续作为 kernel 使用的映射主机表地址输入。
ElasticBuffer.engram_write()
缓存 SF dtype/packs，
_wait_train
不再保留 CPU
sf
张量。
Meta/C++ 双路径校验
sf_packs >= 0
与 SF dtype 白名单，并在输出分配前完成校验。
新增公开 schema 测试，覆盖 supported dtype 输出分配、非法 dtype、负 packs，同时走 FakeTensor/Meta 与真实 NPU dispatch。

变更摘要
本 PR 用于修复
engram_fetch_train
在训练图模式（Dynamo/FakeTensor）下配合 FP8 时的设备不一致问题：原先训练 schema 仍将位于 CPU 的真实
sf_table
张量作为图输入，仅用于推导
fetched_sf
的形状与 dtype，导致算子的张量输入同时包含 NPU 与 CPU 设备而被拒绝。本次改动将
sf_table
张量入参替换为标量 SF 元数据
sf_dtype
与
sf_packs
，保留
sf_table_addr
作为 kernel 使用的映射主机表地址输入，并在
ElasticBuffer
写入阶段缓存 SF dtype/pack 元数据，从而在
code
侧与 Python Meta 实现中直接依据标量元数据在 NPU 上分配
fetched_sf
。
主要改动
EngramFetchTrain
接口签名调整
：
elastic_buffer.cpp
中
EngramFetchTrain
的形参由
const at::Tensor& sfTable
改为
int64_t sfDtypeEnum, int64_t sfPacks
，
sfTableAddr
继续作为训练 kernel 的映射主机表地址输入。
新增 SF 参数校验与输出分配
：在 C++ 实现中通过
TORCH_CHECK
限制
sf_packs >= 0
且
sf_dtype
仅支持
at::kFloat
或
at::kFloat8_e8m0fnu
，并使用
indices.device()
与标量 dtype/packs 构造
fetchedSf
。
Python 侧 schema 与 Meta 实现同步
：
elastic_buffer.py
中
engram_fetch_train
的算子签名改为
int sf_dtype, int sf_packs
，Meta 分支改用
_ENGRAM_INT_TO_SF_DTYPE
映射解码 dtype 后按
sf_packs
生成
meta
设备形状。
新增 SF dtype 枚举映射
：引入
_ENGRAM_SF_DTYPE_TO_INT
/
_ENGRAM_INT_TO_SF_DTYPE
（
torch.float32
对应 6、
torch.float8_e8m0fnu
对应 44），用于 Python 与 C++ 之间的标量 dtype 传递。
ElasticBuffer
缓存并改用标量元数据
：在
engram_write
中记录
_engram_sf_dtype_enum
与
_engram_sf_packs
（初始化时默认 float32 与 0），训练前向调用改为传入这两个标量，并用
has_sf
标记替代在
_wait_train
闭包中保留 CPU
sf
张量。
