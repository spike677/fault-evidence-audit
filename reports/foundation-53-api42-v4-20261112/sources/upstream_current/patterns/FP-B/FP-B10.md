- **故障机理**：集合通信算子（AllReduce / AllGather / AllToAllV / ReduceScatter / Scatter / Broadcast / Send / Recv）的故障集中在**计算算子不具备的四个维度**上：① **通信域与 rank 拓扑结构假设错误**——模板把多级 rank 结构（如二维 Mesh 的 `subCommRanks_`）收缩后仍按下标取多级元素，越界读污染拓扑变量，下游取模可致整数除零；② **图模式 shape / 维度契约未落实**——infershape 在 count 为非常量（编译期不可知）时把输入形状**原样赋给输出并返回成功**，日志声称已标记未知维而代码从未 `SetDim(0, ge::UNKNOWN_DIM)`，属「声明了动态语义却没写进 IR」；③ **通信域匹配与配置校验缺失**——调优插件用 `get<uint32_t>()` 直接取配置，不拒窄化与负数回绕，超大 rank 数被截断成真实 rank 数从而**错误命中通信域**并改写算法 cost；④ **同族算法实现不对称**——功能等价的 executor 之间精度类型选用不一致（Broadcast 用 `float()`、AllReduce 用 `double()`+`std::floor`），前者在数据量 >2^24 时丢精度致切片不均；⑤ **跨模式 / 跨版本算法路径差异**——同一算子在 AICPU 与 AICore、单级与多级拓扑、不同 toolkit 版本下的实现与约束各不相同（含 CCLBuffer 配置阈值与「新包在旧 toolkit 下返回不支持」）。
- **触发条件**：多级或复杂拓扑（Mesh 1D/2D、UBX、超大 rank 数、奇数 rank 数）；`send_counts`/`recv_count` 为非常量（图编译期不可知）；配置值超 `uint32_t` 或为负；数据量跨越 2^24 的 Broadcast / 切分类算子；**AICPU 模式 + CCLBuffer 配置 >2GB**；CANN 版本与 toolkit 版本错配；跨版本复用 tiling/kernel。
- **典型表现**：通信结果错位、部分输出列恒为 0；图编译期 shape 推导与实际不符（日志与代码不一致）；初始化连接超时、个别 rank 掉线；越界读污染通信域变量；大数据量切片不均致精度不达标；配置解析**静默错配**（schema 不报错、算法 cost 被改写）；新功能在老 toolkit 下返回「不支持」。
- **源码审查映射点**：多级 rank 结构（`subCommRanks_`、`commRanks_`、`templateRankSize_`、mesh 维度）的规模与下标是否成对校验；`*InferShape*` 中未知维是否**真的**调用了 `SetDim(i, ge::UNKNOWN_DIM)`（**只打日志不算**）；配置读取是否用 `get<T>()` 直接窄化（应前置 `is_number_unsigned` 或范围校验）；同族 executor 之间的精度类型与取整方式是否对称；AICPU 与 AICore 两条算法路径的约束是否**分别**声明与校验；`HCCL_CONNECT_TIMEOUT` / `HCCL_EXEC_TIMEOUT` / `HCCL_RETRY_CNT` / `HCCL_DFS_CONFIG` 的默认值与文档是否一致；跨版本复用（v4 复用 v3 的 tiling/kernel）时上游新增的 tilingkey 是否已同步适配。
- **检测签名（判别性指纹，命中即候选缺陷点位）**：`float\s*\(\s*\w*[Ss]lice[Cc]ount`（u64 → float 丢精度，hccl 实测命中 **1 处**）；`get\s*<\s*(u?int(32|64)_t|size_t)\s*>\s*\(\s*\)`（配置读取直接窄化，**须人工确认同函数内无范围校验**，hccl 实测命中 13 处）。
- **审查关键词（`keywords` 字段；命中只表示该处值得按上文映射点人工审，不是缺陷候选）**：`subCommRanks_|commRanks_|templateRankSize_`（拓扑变量——⚠️ hccl 实测命中 **1952 次**，出现在拓扑模板基础设施的每一处使用点，**不可作判别性指纹**）；`HCCL_(CONNECT|EXEC)_TIMEOUT|HCCL_RETRY_CNT|HCCL_DFS_CONFIG`（超时 / 重试配置项名，实测 15 处）；`SetDim\s*\(\s*\w+\s*,\s*ge::UNKNOWN_DIM`（**对照组锚点**：命中 = 已正确置未知维的实现，真正的缺陷是「声明支持动态 count 却**没有**它」，属跨行差集、单行正则表达不了）。
- **测试拦截建议**：① **多级拓扑矩阵**——同一集合算子在最简拓扑（单机 2 卡）与最复杂拓扑（多级 Mesh/UBX、非 2 的幂 rank 数、奇数 rank）下对拍；② **count 非常量用例**——`send_counts`/`recv_count` 作为**图输入**（编译期不可知）而非常量，断言 shape 推导结果并**在 IR 上校验**置未知维行为（不只看日志）；③ **配置边界**——rank 数类配置给到 `2^32±k` 与负值，断言明确报错而非静默错配；④ 数据量跨 **2^24** 的 Broadcast / 切分类算子必须建例；⑤ **AICPU 与 AICore 双路径对拍**（含 CCLBuffer 跨 2GB）；⑥ **通信算子精度用例需单独建库**——现有精度矩阵几乎只覆盖计算算子，HCCL 侧等同空白。
- **实证案例**：cann/hccl **#744**（open）AllToAllV Mesh1D 模板把 `subCommRanks_` 收缩为单层后又按下标 `[1]` 取值，**越界读污染 `templateRankSize_`**，后续取模可能整数除零（基线 `27d0ea5a`，文件 `src/ops/all_to_all_v/algorithm/template/`）；**#749**（open）`HcomReduceScatterVInferShapeV2` 在 `recv_count`/`send_counts` 为非常量时将输入形状**原样赋给输出形状并返回成功**，日志声称 "shape first dim is unknown" 但代码从未调用 `outputShape->SetDim(0, ge::UNKNOWN_DIM)`（文件 `src/ops/reduce_scatter_v/op_graph`）；**#738**（open）`examples/07_tuner_plugin/plugin.cpp::ParseMatchField` 用 `get<uint32_t/size_t/uint64_t>()` 不拒窄化，`min_ranks`/`max_ranks` 均设 `4294967304`（2^32+8）时被转换为 **8**，schema 未报错，插件**错误命中 8-rank 通信域**并将原算法 cost 从 2 改为 0；**#275**（closed）`src/ops/broadcast/executor/ins_v2_broadcast_parallel_executor.cc` 用 `float()` 转换 `u64 sliceCount`，数据量超过 **2^24（16M）** 时丢精度致数据切片不均匀，而**功能等价的 AllReduce executor 正确使用了 `double()` 与 `std::floor`**（修复即改为 `double()`+`std::floor` 与 AllReduce 对齐）；**#609**（closed）ReduceScatter 的 concurrent 算法在 **AICPU 模式 + CCLBuffer 配置大于 2GB** 时存在精度问题（950 UBX 机型，4p 数据量 >1M 场景）；**#141**（closed）`BatchSendRecvOutPlace` 动态申请堆内存后**异常分支未释放**，长期高频调用致设备内存持续上涨，最终内存耗尽报错、**任务卡死/闪退**；**#106**（closed）HCCL 前向兼容特性——新版本包在老版本 toolkit 下运行时，新功能**可返回错误（不支持等）**。**语料统计（2026-09-19 全量抓取）**：cann/hccl 仓共 **714 条** issue，其中功能/异常/失败类 **302 条**、集合通信算子关键词命中 **235 条**、超时/挂死类 **16 条**、精度类 **3 条**——**证明「集合通信是独立且高发的故障域」这一判断**。
