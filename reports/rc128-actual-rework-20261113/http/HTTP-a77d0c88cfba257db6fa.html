Describe the current behavior / 问题描述 (Mandatory / 必填)

examples/07_tuner_plugin/plugin.cpp::ParseMatchField 直接使用 nlohmann/json 的 get<uint32_t/size_t/uint64_t>()。这些数值转换不保证拒绝窄化或负数回绕。实测将 min_ranks、max_ranks 均设为 4294967304（2^32+8）时，两者被转换为 8，schema 未报错，插件错误命中实际 8-rank 通信域并将原算法 cost 从 2 改为 0。

这是用户配置输入导致错误干预算法选择的功能问题，不要求真实部署 2^32 个 rank。配置若不可由目标类型表示，应沿用现有 schema 失败策略，保留原 cost。13 个无符号整数字段具有同一转换根因，一并修复；本次不改上一轮的 Python 性能测量数据，也不改变浮点 cost 的语义。

Environment / 环境信息 (Mandatory / 必填)

Linux x86_64；g++，C++14，-Wall -Wextra -Werror；nlohmann/json 3.11.3。本地采用同一 HCOMM 基线的公开 hccl_types.h 和仓内 securec 测试声明，沿用示例已有的 securec/host 回调 stub；没有安装或运行 NPU。头文件仅用作本地验证依赖，没有新增跨仓编译期依赖。

cann/hccl master 基线：31054b7189b830e613b1f8d7097fa026d74cbf00。

Steps to reproduce the issue / 重现步骤 (Mandatory / 必填)

  1. 在 examples/07_tuner_plugin/hccl_tuner_config.json 的一个合法 allreduce 规则中，将 min_ranks 和 max_ranks 同时设置为 4294967304；保留其余必要字段，令字节范围包含 8192，类型为 fp16。
  2. 使用示例已有 host 回调测试环境初始化插件：通信域 nRanks=8，调用数据 nBytes=8192、dataType=fp16，匹配算法初始 cost=2。
  3. 调用 hcclTunerPlugin_v1.init，再调用 getCollInfo。新增 TestOverflowConfigDoesNotIntervene 完整执行此路径。
  4. 也可在包含 plugin.cpp 的现有测试环境直接验证转换：
nlohmann::json match = {{"min_ranks", 4294967304ULL}, {"max_ranks", 4294967304ULL}};
Rule rule = {};
SchemaState schema = {};
ParseMatchField(match, &rule, &schema);
printf("errors=%d min=%u max=%u\n", schema.errors, rule.match.minRanks, rule.match.maxRanks);

配置好文档要求的头文件与 nlohmann/json 后，执行 make -C examples/07_tuner_plugin/test run。

Describe the expected behavior / 预期结果 (Mandatory / 必填)

配置 schema 报错，init 仍按已有策略优雅返回；getCollInfo 不命中该配置，不修改算法 cost。修复后 156/156 项断言通过。

Special notes for this issue / 备注 (Optional / 选填)

修复方案：在进行整数转换前统一检查 JSON 整数类型、非负性和目标 C++ 类型上界，覆盖 rank、字节数、所有拓扑维度及 buffer_size，共 13 个字段。非法值计入 SchemaError，现有 configValid 逻辑使插件不介入；零值、上界及正常配置保持兼容。

检索最新 API 返回的 690 条 Issue 和 3228 条 PR 的标题、正文；相关命中 !2821 是性能采集功能引入，不涉及本 C++ 整数匹配值校验。已排除其他团队报告的 INI 校验、依赖版本比较等问题。本次与本团队 #736 的 Python NaN/Inf 测量过滤位置、输入和影响不同。未发现同根因已有报告；不声称逐一检视全部历史 diff。
