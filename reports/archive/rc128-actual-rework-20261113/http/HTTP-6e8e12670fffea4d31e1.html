现象

aclnnSparseLightningIndexerKLLossGrad（Ascend950PR / CANN 9.3.0）在 softmaxOut 为非连续 Tensor 时两段接口均返回 0，但 kernel 按连续布局写入。

资料中 softmaxOut 的非连续列标 x（不支持）。实现既没拒绝，也没正确处理。

组 出参 两段返回码 按 stride 读回 物理 storage 与连续基线相同
基线（全连续） softmaxOut 0/0 哨兵 0/8192 —
缺陷组（末维 stride=2） softmaxOut 0/0 哨兵 4096/8192，超差 4096/8192，worst=777000 @4096 8192/8192（100%）

基线轮哨兵残留为 0，非连续轮变成 4096，且物理 storage 与基线完全相同 —— 三个判据同向，无歧义。

本单与 #7490 的关系：#7490 记录的是 Atlas A2（910B3 / CANN 9.2.0） 上的同一现象。
本单是 Ascend950PR（950PR / CANN 9.3.0） 的独立复现，按平台分开跟踪。
注意 A5 上基线更干净（哨兵 0，而 A2 是 2048，因 A2 有 maskMode=3 合法不写区），
因此 A5 的判据更强，修复与验收需按平台分别确认。

期望

softmaxOut 非连续时，实现二选一，不得停在中途：

  1. 在 host 侧拒绝，GetWorkspaceSize 返回 161002；或
  2. 支持 stride 回写（ViewCopy 到 out）并把资料标记改为 √。

该判断只需读 aclTensor 的 GetViewStrides() / GetStorageShape() 元数据，不涉及 device 数据读取。

环境

  • 芯片：Ascend950PR × 8（Ascend950PR_9579），使用 NPU 1
  • CANN：9.3.0（V100R001C25B114）
  • 驱动：25.7.rc1（V100R001C10SPC102B224）
  • 被测仓：cann/ops-transformer master 4197a29c0（2026-11-12 22:12）
  • 该接口无 op_host/op_api/，属自动生成 aclnn 接口

复现步骤

  1. 起特权容器：docker run --privileged --name nc --shm-size=64g -v /home:/home -e ASCEND_RT_VISIBLE_DEVICES=1 <cann-9.3.0-image> sleep infinity
  2. docker exec -it nc bash，source <cann>/set_env.sh
  3. 编译：g++ -std=c++17 -O2 repro.cpp -o repro -I$ASCEND_HOME_PATH/include -L$ASCEND_HOME_PATH/lib64 -lascendcl -lopapi -lnnopbase
  4. 运行 ./repro：基线轮哨兵 0/8192；非连续轮哨兵 4096/8192，两段返回码仍为 0/0
  5. 观察 [物理] storage 前 8192 个中与基线相同 8192 (100%)：stride 未参与寻址

复现脚本

// layoutQ/layoutK 为 char[4] 字符串 "TND"；maskMode=3
// softmaxOut shape {8,1024} FLOAT32，末维 stride=2 → storage 需 16383
char layoutQ[4] = "TND", layoutK[4] = "TND";
int64_t shape[2] = {8, 1024};
int64_t stC[2]   = {1024, 1};        // 基线：连续
int64_t stNC[2]  = {2048, 2};        // 非连续：末维 stride=2
aclTensor* sm = aclCreateTensor(shape, 2, ACL_FLOAT, /*基线 stC / 非连续 stNC*/, 0,
                                ACL_FORMAT_ND, shape, 2, devSm);
aclnnSparseLightningIndexerKLLossGradGetWorkspaceSize(q, k, ..., layoutQ, layoutK, 3,
                                                      sm, &ws, &exec);
aclnnSparseLightningIndexerKLLossGrad(wsPtr, ws, exec, stream);   // 两段均返回 0

实测输出（Ascend950PR / CANN 9.3.0）：

[基线   K=1] ret=0/0
[softmaxOut非连 K=2] ret=0/0
  [FAIL] softmaxOut(按stride) 超差 4096/8192 worst=777000 @4096
        [物理] storage 前 8192 个中与基线相同 8192 (100%)
        => 物理与基线相同但读回不一致：按连续布局写，stride 未参与寻址

影响

softmaxOut 作为中间结果常被下游直接当连续张量使用（例如喂给 SparseLightningIndexer 的反向链路）。非连续时算子静默返回，下游读到 4096 个未初始化的 -777000（float 解释为极大负值或 NaN 源头），损失梯度全部污染，且无错误码可捕获。

建议

该接口无 op_host/op_api/，出参经 NnopbaseAddOutput 传给 kernel。建议参照仓库内 foreach 已修复的写法补齐回写（foreach/foreach_utils/op_host/foreach_contiguous_helper.h:54，ForeachViewCopyToOutputTensorList）：host 侧算到连续 buffer，结束后 ViewCopy 回写 out。若短期不做，至少应在 host 侧对非连续出参返回 161002。

从反馈结果看，Ascend950PR / CANN 9.3.0 上非连续的 softmaxOut 可能未按 stride 回写：两段接口均返回 0，但按 stride 读回时有 4096 个元素仍为哨兵值。具体调用链和原因仍需确认。

在此期间，建议使用连续的 softmaxOut；如下游需要非连续布局，可在算子完成后再拷贝到目标视图。

针对非连续出参，可以考虑在接口侧检查并拒绝，或先写入连续缓冲区，再按目标 stride 回写；返回码和回写方案的适用性仍需核实。该问题会按 Ascend950PR 平台继续分析，与 #7490 的 A2 场景分别确认。
