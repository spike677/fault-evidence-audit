# FP-C01 算子端到端耗时占比高且单次调用耗时高

- **故障机理**：存在冗余计算、重复搬运、可合并的循环/分支未合并。**两条独立子路径（2026-09-16 增补子型 ②）**：① **实现层冗余**——kernel 模板内冗余初始化/冗余指令/未合并搬运；② **调度层膨胀**——host 侧（tiling / infershape / aclnn / 工程构建脚本）循环上界或派发条件计算错误，致**下发迭代次数、blockDim、tileNum、核间屏障或重复配置次数多于实需**，kernel 被重复调用或空转，而**单次计算逻辑完全正确**（与 FP-A07 的区别：A07 走错分支致结果错，本条结果对、只是白干）。**③ 变更引入的版本基线回归（v2.16 增补）**——绝对耗时未超标、结构上也未必是"冗余"，但**某次变更把原本合格的表现推坏**：新增冗余计算或同步、tiling/分核阈值漂移使原最优点被跨过、dtype 或派发路径变化、模板实例化规模放大、新增确定性/原子约束。**判据是「与自身上一版本或基线对比出现劣化」，而非与其它维度（dtype / 板型 / 代际）对比**——这是与子型 ①②（结构性冗余）及 C02~C06（维度对比型）的本质区别，后者的绝对值可能一直"合格"，只有基线对比才暴露。
- **触发条件**：网络中高频调用路径上的算子；**子型 ②** 额外需同时满足：该循环上界处于「小 shape 不显、大 shape 放大」的区间（如 `n` 与 `n±1` 在小 n 下耗时差不可测），且该算子位于端到端热点路径（劣化被放大才可观测）；构建期子型需为增量构建或模板规模大的仓（重复配置开销随模板/源文件数线性放大）。**子型 ③** 额外需满足：存在**可比基线**（同一 shape / dtype / 芯片 / 编译选项四要素一致），且劣化由**一次变更**划界（可用二分 commit 定位首次劣化点）。
- **典型表现**：端到端性能瓶颈。**子型 ②**：**精度全对、功能全对、无报错、无 coredump，仅耗时变长**——这正是其长期漏检的根本原因；表现为同 shape 跨版本耗时回归（新版本反而慢）、或耗时随 shape 阶跃处出现「非整数倍」异常台阶（如 `n` 翻倍但耗时不翻倍，说明多出的迭代命中了空转/重复路径）。**子型 ③**：同一 shape 跨版本耗时比值劣化（常见阈值 5%~15%），而**精度 / 功能 / 报错全部正常**；劣化随 shape 放大或呈阶跃；**单看新版本的绝对值可能仍落在"合格"区间**，只有与基线对比才暴露——这与子型 ② 的"非整数倍台阶"可区分（后者台阶出现在 shape 轴，前者出现在版本轴）。
- **源码审查映射点**：冗余计算、重复搬运、可合并的循环/分支。**子型 ② 增补映射点**：① host 侧 `for` 上界表达式与 `GetShapeSize()` / `CeilDiv(...)` / `blockDim` 三者的**乘积自洽性**（审查 `<=` vs `<`、`+1` 与 `-1`、上界是否用错变量或未做 `min()` 截断）；② tiling 中 `tileNum`、`usedCoreNum`、`loopTimes` 的推导是否可能大于「形状所需最小迭代数」；③ 核间循环（核数 × 单核循环）的**双重计数**——分核数已按 shape 缩小后，单核循环仍按全量上界执行；④ `foreach`/`for` 循环体内是否**未使用**循环变量（循环退化为「同一批配置重复设置 N 次」，见实证 ③）；⑤ 变更 diff 中 host 侧循环边界与 kernel 侧 `loopTimes` 消费点是否**成对更新**（只改一侧必错）。**子型 ③ 增补映射点**：⑥ 变更 diff 中是否**新增**了循环 / 同步 / 类型转换 / 边界判断（尤其本可省略的 `Cast`、`SyncAll`、逐元素回退）；⑦ tiling 阈值常量（如分核阈值、`2048`/`4096` 类魔数）是否被改动，使原最优点被跨过；⑧ 是否把向量化 / 合并搬运改成分步执行或用更窄的 dtype 承载累加；⑨ 模板实例化数量是否随改动放大（可用编译产物 size / 编译耗时做旁证）；⑩ 是否新增确定性或原子操作约束（与 FP-C05 交叠，需与此前版本对照确认是"新引入"还是"一直如此"）。
- **测试拦截建议**（v2.16 起「跨版本耗时比值看护」上升为本卡通用项）：① **同 shape 跨版本 / 跨分支耗时比值看护（比值 >1.15 告警）—— 对子型 ①②③ 一律适用**：本卡各类缺陷都可能只表现为版本间回归、而不表现为绝对值超标（这是子型 ③ 的**唯一**暴露途径）；profiler 基线看护（算子级耗时占比阈值告警）保留为兜底。**子型 ② 增补拦截**：② 对 host 侧循环边界改动，构造「**上界 ±1 两侧**」的 shape 探针对（如阈值 2048 取 2047/2048/2049），断言两侧耗时不出现阶跃；③ 回归用例必须包含「精度 pass + 耗时对比」双判据——只跑精度永远拦不住本条；④ 该缺陷类型**静态扫描与 UT 均无法覆盖**（`for(i=0;i<n;i++)` 与 `for(i=0;i<n+1;i++)` 语法同为合法），只能靠性能基线差分，**不可依赖代码审查兜底**。**子型 ③ 增补拦截**：⑤ **变更级性能看护**——每次合入的候选版本与上一基线做同 shape 对拍，比值劣化超阈值即**阻断合入**（把回归拦在合入点，而非等端到端回归才发现）；⑥ 对已知热点算子维护「版本 × 耗时」趋势表，劣化后先用**二分 commit** 定位首次劣化点（比回归发生后再查的成本低一个数量级）；⑦ 基线必须记录 **shape / dtype / 芯片 / 编译选项**四要素，缺一项即不可比（否则会把环境差异误判成性能回归）。
- **实证案例**：ops-nn #5277 smallkernel 模板 `fix_m` 冗余导致性能问题；#3988 16in32out 场景 mm 接口性能劣化严重；#3151 QBMM pertile `LocalTensor` 初始化导致的性能劣化；#2231 dynamic_mx_quant 原场景性能劣化；#1197 DequantSwigluQuant 在 950 上部分 case 性能劣化；#4960 mm 的 hf32 场景性能劣化；ops-transformer #2402 950 DispatchV2 算子发状态性能问题；ops-math #1228 AICPU 实现的 RealDiv 在 complex 数据类型下性能差。**共性特征：多为模板化实现中的冗余初始化/冗余指令/未合并搬运，属「实现层可优化」而非硬件上限**（均属子型 ① 实现层）。**子型 ②（调度层膨胀）实证锚点（无 issue 实证，降档为团队笔记）**：① **工程构建期**——catlass `tests/optest/kernels/83_ascend950_hstu_infer/CMakeLists.txt`（PR 检视日报_20260911 P2）：新增 `get_filename_component(_SRC_NAME ${_SRC} NAME)` 后**从未使用**，且 `foreach(_SRC ${_HSTU_950_SOURCES})` 循环体内已不再引用 `_SRC`，外层循环退化为「把同一批 compile definitions / include dirs **重复设置 N 次**（N=源文件数）×2（`_ms` 变体）」——属未完成重构遗留，循环变量被摘除后循环体失去意义但结构未删；② **静态扫描命中（同族，待人工确认）**——`ops-nn/activation/swi_glu/op_host/swi_glu_tiling.cpp:367` 命中 `F5/无退出条件循环`（`for(;;)`/`while(true)` 在 tiling 产品代码内，若异常分支不推进则空转，锚 #5032 `AdjustCVTiling` 死循环同构；见 `内部同类问题追溯记录（2026-09-07）` 第 60 条）；③ **人工核验未成立（反向证据，保留以警）**——catlass `rdma_device_backend_xscale.hpp` 的 `target_wqe_id = (target_idx - 1) & mask` 曾被怀疑 off-by-one，经交叉验证掩码位宽（v1/v2 为 16/20 位，右移 3 位后 13/17 位）与调用点语义自洽，**已排除**（内部 PR 检视记录（2026-09-11）的审查摘要），提示此类审查需先核对位宽与语义再定论。**子型 ② 当前 O1（无 issue 实证）；待出现真实「host 循环上界写错致耗时劣化」issue 时按 0.2 复评升 O2。整卡档位按 v3.3 定级纪律由整卡实证全集决定（2026-10-02 复评：子型① 8 条独立 issue 实证 → O3，整卡中→高），子型级 O 判断不变。****子型 ③ 语料补充（v2.16，2026-09-19，具体 issue 编号待核）**：一批归类中「性能回归 / 基线劣化」**88 条**，主体为「相比基线性能劣化超过 5%」「性能劣化度超预期」「性能不达标（含对比 A100 / 上一版本）」——其中「**相对自身基线**回归」是主体形态，而本卡此前只把它当作子型 ② 的一种表现、**未作为独立子型承载**。子型 ③ 自身暂无 issue 实证（O1），**维持子型级 O1 判断；整卡档位由整卡 S×O 决定，见元数据**。
