已合并至 #4721：TopKV2 索引边界及缓冲复用同步问题，统一在该 Issue 跟踪。关闭本分项不代表缺陷已修复或 PR 已合入。

一、问题描述 （必填）

位置：math/top_k_v2/op_kernel/arch35/radix_sort_top_k_single_core.h，InitQueuesAndTmpBuf / CalTileTopK2CopyOut。

输出索引队列容量按 min(tileNum,k_) 分配，旧 INT32/INT64 Adds 的 count 却是 tileNum。这与实际分配容量及 TopK 有效输出数不一致。本单记录已确认的源码长度失配，不声称已动态复现单核 memcheck 告警。

二、环境信息 （可选）

  • 硬件：Ascend950；2026-11-12 的索引长度对照环境为 Ascend950DT_9574。
  • CANN：9.3.0；TTK：3.0.0；工具：mssanitizer（编译选项 sanitizer,ccec_g）。
  • 受影响源码：ops-math master 基线 21eb43732 中对应 arch35 路径；修复提交为 PR !7358 的 562b64e560d993695b68fd9391359ea792941e54 / d76e037fa460438cb05f824e64638c7fa08027f8。

三、重现步骤 （可选）

  1. 使用 Ascend950、CANN 9.3.0、TTK 3.0.0 和配套 mssanitizer。将受影响 TopKV2 编译安装到隔离 custom OPP，并设置 ASCEND_CUSTOM_OPP_PATH 指向该 vendor 目录；加载 CANN 环境，确保 TTK 能选择 Ascend950 的 arch35 kernel。不要直接使用已经包含本修复的代码来复现旧问题。
  2. 将下面内容保存为 cases.csv。输入生成和 golden 使用 ops-math 的 math/top_k_v2/tests/assets/golden.py；_unique 名称会生成排序轴上递增的唯一值输入，其余按 CSV 范围和 seed 生成。
testcase_name,op_name,input_shapes,input_dtypes,input_formats,output_shapes,output_dtypes,output_formats,attributes,input_data_ranges
top_k_v2_single_core_f16,top_k_v2,"((64, 20000), (1,))","('float16', 'int32')","('ND', 'ND')","((64, 17), (64, 17))","('float16', 'int32')","('ND', 'ND')","{'sorted': False, 'dim': -1, 'largest': True, 'indices_dtype': 3}","((-100, 100), (17, 17))"
top_k_v2_single_core_f16_i64,top_k_v2,"((64, 20000), (1,))","('float16', 'int32')","('ND', 'ND')","((64, 17), (64, 17))","('float16', 'int64')","('ND', 'ND')","{'sorted': False, 'dim': -1, 'largest': True, 'indices_dtype': 9}","((-100, 100), (17, 17))"
  1. 设置 OPS_MATH 为源码根目录，在已安装 TTK 的 Python 环境运行：
mssanitizer --tool=memcheck --full-backtrace=yes --log-file=sanitizer.log -- \
  python3 -m ttk kernel -i cases.csv \
  --plugin "$OPS_MATH/math/top_k_v2/tests/assets/golden.py" \
  --compile-opts op_debug_config=sanitizer,ccec_g \
  --device-whitelist=0 --pc=1 -c -d=false --run=1 \
  --warmup=false --task-prof=false --seed=42 --single-log -o result.csv
  1. 同时检查 sanitizer.log 与精度结果。不能仅用进程退出码或 TTK 精度 PASS 判定内存安全。工具版本、UB 布局及编译结果变化时，告警地址/PC 可能不同。

实际结果与证据边界：

  • 本场景实测 key=3002、mode=1、2 个 tile，tileNum=10000，k=17。
  • INT32 索引队列 32B 对齐后仅 96B，旧 Adds count=10000 对应 40000B；INT64 队列对齐后 160B，旧请求 80000B。这是源码容量与 tiling 推导，不是 memcheck 报告的非法字节数。
  • 2026-11-12 两种原始 API 旧 count 用例均精度 PASS、memcheck 未报警；临时显式匹配 Adds 模板及 scalar 类型的辅助诊断仍未报警。因此不能将漏报原因确定为 API 重载选择，也不能据此向 SDK 归因。
  • 修复后的 4 个单核用例（含 INT32/INT64、尾 tile、FP32）在先前独立验证中精度、边界、memcheck 均通过；之后同输入原始 API 配对重跑因 Runtime 初始化 OOM 未完成。

四、预期结果 （可选）

缓存本 tile 实际选出数量 validIndexCount，让 TopK、Cast、Adds、CopyOut 与输出偏移累加使用一致的数量。Adds 的有效访问范围不得超过分配容量；无需等待精度失败才修正长度契约。
